# 작업지시 02. 예약 애그리게이트와 상태 머신

- 작성일: 2026-08-24
- 작성: Cowork 세션 (문서·설계 담당)
- 대상: Claude Code (구현 담당)
- 범위: P1 4주차
- 관련: 계획서 5.4 / 8.3 / 12.2 / 13.1, ADR 0002, ADR 0005, CLAUDE.md 중복예약 방어 절

이 문서는 무엇을 만들지와 어떤 제약을 지킬지를 적는다. 어떻게 짤지는 적지 않는다.
5절의 결정은 착수 전에 받았다. 다시 열지 말 것.

## 1. 지금 상태

P1 3주차까지 `main` 에 병합돼 있다. 테스트 44건 통과.

**재고 계층은 이미 다 있다.** 새로 만들지 말고 이것을 쓴다.

```java
InventoryService.reserve(unitId, period, units)       // BOOK
InventoryService.hold(unitId, period, units)          // HOLD
InventoryService.promoteHold(unitId, period, units)   // PROMOTE
InventoryService.releaseHold(unitId, period, units)   // RELEASE_HOLD
InventoryService.release(unitId, period, units)       // RELEASE
InventoryService.forceBook(unitId, period, units)     // FORCE_BOOK
InventoryService.availableFor(unitId, period)
```

`Reservation`, `ReservationStatus`, `StayPeriod`, `IllegalReservationTransition`,
`ReservationRepository`(`findByChannelCodeAndChannelBookingId`, `findByConfirmationCode`,
`findOverlapping`)도 이미 있다. 4주차는 이 위에 생애주기와 HTTP 표면을 얹는 일이지
재고 계층을 다시 만드는 일이 아니다.

`reservation`, `reservation_night`, `guest`, `payment` 테이블과 인덱스도 V1 에 있다.
`idx_res_hold` 는 `hold_expires_at` 부분 인덱스이며 만료 처리가 이걸 쓴다.

## 2. 이번에 만드는 것

### A. 상태 머신

계획서 5.4 의 전이도와 재고 영향표가 명세다. 전이는 엔티티의 의미 있는 메서드로
표현한다. setter 를 두지 않는다.

| 전이 | 재고 연산 | held | booked |
|---|---|---|---|
| 신규 HOLD | `hold` | +1 | 0 |
| HOLD → CONFIRMED | `promoteHold` | −1 | +1 |
| HOLD → EXPIRED | `releaseHold` | −1 | 0 |
| 수기 예약 즉시 확정 | `reserve` | 0 | +1 |
| CONFIRMED → CANCELLED | `release` | 0 | −1 |
| CONFIRMED → CHECKED_IN | 없음 | 0 | 0 |
| CHECKED_IN → CHECKED_OUT | 없음 | 0 | 0 |
| CONFIRMED → NO_SHOW | 없음 | 0 | 0 |

`NO_SHOW` 는 재고를 되돌리지 않는다(5절 3번). 방은 비었지만 요금은 받으므로
`booked` 를 유지한다. 리포트의 매출 집계와도 이 편이 맞는다.

허용되지 않는 전이는 `IllegalReservationTransition` 을 던진다. 이미 있는 예외다.

**취소는 멱등하다.** 이미 CANCELLED 인 예약을 다시 취소하면 아무 일도 하지 않고
성공으로 답한다. 재고를 두 번 반납하면 원장이 틀어진다.

**CHECKED_OUT 은 종착점이다.** 여기서는 취소도 상태 변경도 되지 않는다.

### B. 상태 전이와 재고는 한 트랜잭션이다

이번 작업에서 가장 중요한 규칙이다.

예약 상태가 바뀌었는데 원장이 안 바뀌면, 또는 그 반대면, 캘린더가 거짓말을 한다.
초과 판매나 팔 수 있는 방을 못 파는 상태가 되고, 둘 다 조용히 일어난다.
**두 쓰기는 함께 성공하거나 함께 실패해야 한다.**

**ADR 0005 의 `REQUIRES_NEW` 를 여기에 가져오지 말 것.** 저기는 성격이 반대다.
재사용 탐지는 "실패로 끝나면서 기록은 남겨야" 하므로 기록을 별도 트랜잭션에 담았다.
여기는 "함께 성공하거나 함께 실패해야" 하므로 같은 트랜잭션이어야 한다.
판별 기준은 이것이다 — 바깥이 롤백될 때 이 쓰기가 남아야 하는가, 사라져야 하는가.

다만 **락은 트랜잭션 바깥에서 먼저 잡는다.** CLAUDE.md 의 규칙이고
`InventoryService`(락)와 `InventoryLedgerWriter`(트랜잭션)가 이미 그렇게 나뉘어 있다.
순서를 뒤집으면 트랜잭션이 열린 채 락을 기다려 커넥션 풀이 마른다.

날짜 오름차순 락 규칙도 그대로다. `StayPeriod.nightDates()` 가 정렬을 보장한다.

### C. 수기 예약

전화 예약 등을 직접 등록한다. 계획서 8.3 항목이다.

- `channel_code` 는 `DIRECT`, `channel_booking_id` 는 비운다.
  `uq_channel_booking` 이 있지만 PostgreSQL 은 NULL 을 서로 다르게 보므로
  직접예약이 여러 건이어도 충돌하지 않는다
- 재고가 모자라면 **거절한다.** OTA 수신과 다르다. CLAUDE.md 가 거절하지 말라고 한 것은
  이미 외부에서 성사된 예약이고, 수기 등록은 아직 성사되지 않았으므로 막는 것이 맞다
- `confirmation_code` 는 `SS-XXXXXX` 형식이다. 뒤 6자는 `0 O 1 I L` 을 뺀 31글자
  집합에서 뽑은 난수다. 전화로 불러 줄 값이라 헷갈리는 글자를 미리 뺀다.
  `uq_confirmation` 이 걸려 있으니 충돌하면 다시 뽑는다. 재시도 횟수에 상한을 둔다

### D. 게스트 정보와 암호화

`guest` 를 함께 만든다. 이름은 평문, 연락처와 이메일은 암호문과 검색용 해시를
따로 저장한다. 계획서 15.2 가 약속한 것이고, 미루면 나중에 평문 행을 옮겨야 한다.

- **암호화는 AES-256-GCM.** `phone_enc`, `email_enc` 는 `TEXT` 다.
  GCM 은 같은 키로 같은 IV 를 두 번 쓰면 안전성이 무너지므로 **암호화할 때마다 새 IV 를
  만들고 암호문과 함께 보관한다.** IV 와 태그를 붙여 한 문자열로 인코딩하는 편이 단순하다
- **키는 환경 변수로 받는다.** `JWT_SECRET` 과 같은 방식이다. 없거나 길이가 모자라면
  기동을 막는다. local 프로파일만 개발용 고정값을 둔다
- **검색용 해시에 맨 SHA-256 을 쓰지 말 것.** 휴대폰 번호는 사실상 1억 가지뿐이라
  해시를 전부 미리 계산해 되돌릴 수 있다. 비밀번호가 아니라서 솔트를 붙이면 조회가
  안 되므로, **키를 섞는 HMAC-SHA256 을 쓴다.** 키를 모르면 대조표를 만들 수 없다.
  결과를 소문자 16진수로 쓰면 64자라 `VARCHAR(64)` 에 맞는다
- 화면 표시는 이번 범위가 아니다. 마스킹과 조회 기록은 P5 에서 본다

### E. HOLD 만료

`hold_expires_at` 이 지난 HOLD 를 EXPIRED 로 바꾸고 `releaseHold` 로 재고를 되돌린다.
수명은 15분이다(계획서 5.4).

`@Scheduled` 로 주기 실행한다. 리프레시 토큰 정리 배치와 같은 방식이며
`@EnableScheduling` 은 이미 켜져 있다. 인스턴스가 하나뿐이라 ShedLock 은 아직 걸지 않는다.

**만료도 락을 거친다.** 배치가 원장을 직접 고치면 방어 계층을 우회하게 된다.
반드시 `InventoryService` 를 통한다.

한 번에 처리할 건수에 상한을 둔다. 밀린 HOLD 가 많을 때 한 트랜잭션이 길어지면
락을 오래 쥔다.

테스트는 스케줄러가 아니라 메서드를 직접 부른다.

### F. 예약 REST API

```
GET    /api/reservations                  목록. 필터: 채널, 상태, 기간, 검색어
GET    /api/reservations/{id}             상세
POST   /api/reservations                  수기 등록
PATCH  /api/reservations/{id}             날짜·인원 변경
POST   /api/reservations/{id}/cancel      취소
POST   /api/reservations/{id}/check-in
POST   /api/reservations/{id}/check-out
```

**날짜 변경이 이 API 에서 가장 어렵다.** 옛 기간의 재고를 되돌리고 새 기간을 잡아야
하는데, 새 기간이 모자라면 전부 없던 일이 되어야 한다. 중간 상태가 남으면 안 된다.
두 기간의 합집합을 날짜 오름차순으로 잠그고 한 트랜잭션에서 처리한다.

**조직 스코핑은 3주차에 만든 `OwnedResources` 를 쓴다.** 새로 만들지 않는다.
`reservation` 에는 `org_id` 가 없고 `property_id` 로 거슬러 올라간다. 소유가 아닌
자원은 3주차와 같게 404 로 답한다.

`reservation_night` 는 예약을 만들 때 함께 쓰고 날짜가 바뀌면 다시 쓴다.
박별 요금은 총액을 박 수로 나눈 값이며, 나누어떨어지지 않는 나머지는 첫 박에 붙인다.
**박별 요금의 합이 `total_amount` 와 정확히 같아야 한다.** 반올림으로 어긋나면
리포트 집계가 예약 총액과 달라지고, 그건 나중에 원인을 찾기 어려운 종류의 차이다.
P2 에서 `rate_calendar` 가 채워지면 실제 박별 요금으로 바꾼다.

### G. 테스트

완료 조건은 6절에 있다.

## 3. 이번에 만들지 않는 것

- **`BookingIngestService`.** 계획서 13.2 에 있지만 채널 수신이라 P3 다.
  다만 애그리게이트를 그때 뜯어고치지 않아도 되게 `channel_code`, `channel_booking_id`,
  `revision` 을 지금부터 채운다. `fromChannel` 과 `applyRevision` 은 P3 에서 만든다
- **환불 계산과 결제사 호출.** `rate_plan.cancel_policy` 가 있지만 payment 모듈은 P5 다.
  취소는 상태 변경과 재고 반납까지만 한다
- **체크아웃 시 청소 태스크 생성.** ops 모듈은 P5 다. 전이만 만든다
- **Outbox 발행과 감사 로그.** 6주차다. 이벤트를 등록할 자리만 비워 둔다
- **CSV 내보내기.** 계획서 8.3 에 있지만 P5 리포트와 함께 하는 편이 낫다
- **역할별 인가(`@PreAuthorize`).** 3~5단계로 미뤄져 있다. 인증 여부와 조직 스코핑까지만

## 4. 지켜야 할 제약

- **암호화 키는 `.env.example` 에 항목과 생성법을 적는다.** `JWT_SECRET` 이 그렇게 되어 있다
- **모듈 경계.** `booking` 이 `property` 를 쓸 때는 `property.UnitCatalog` 인터페이스만
  쓴다. `property.domain.Unit` 을 직접 참조하면 `ModularityTest` 가 깨진다.
  인증 정보는 `shared.security.AuthenticatedUser` 로만 읽는다
- **원장을 직접 쓰지 않는다.** 재고 변경은 전부 `InventoryService` 를 통한다.
  `InventoryLedgerWriter` 를 컨트롤러나 새 서비스에서 직접 부르면 락을 건너뛴다
- **오류 표현.** `shared/error` 의 `DomainException`, `ApiError`, `GlobalExceptionHandler`
- **엔티티에 setter 를 두지 않는다.** `confirm()`, `cancel(reason)`, `checkIn()`,
  `checkOut()`, `expire()` 처럼 전이 이름으로 표현한다
- **`ddl-auto: validate`.** 컬럼을 더하면 V1 과 JDBC 타입 코드까지 맞아야 한다
- **`net_amount` 는 생성 컬럼이다.** 엔티티에서 쓰려면 `@Generated` 로 읽기 전용이어야
  하고, 값을 넣으려 하면 기동이나 저장이 막힌다
- **테스트 포트.** 앱은 15433/`.localdb-test`, API 테스트는 15434/`.localdb-api`
- **주석은 "왜".** 테스트 이름은 한국어 서술형

## 5. 착수 전에 받은 결정

| 항목 | 결정 |
|---|---|
| 1. 게스트 연락처 | 지금 암호화한다. AES-256-GCM 과 HMAC 검색 해시. ADR 0007 로 기록 |
| 2. `confirmation_code` | `SS-XXXXXX`. 헷갈리는 글자를 뺀 31글자에서 6자 난수 |
| 3. `NO_SHOW` 재고 | 되돌리지 않는다. `booked` 유지 |
| 4. `reservation_night.price` | 총액을 박 수로 나누고 나머지는 첫 박에 붙인다 |

1번을 지금 하는 이유는 나중에 하면 평문 행을 옮기는 마이그레이션이 따라오기 때문이다.
계획서 15.2 가 이미 약속한 것이라 범위를 늘리는 결정도 아니다.

4번은 P2 에서 `rate_calendar` 가 채워지면 실제 박별 요금으로 바뀐다. 지금 중요한 것은
합계가 `total_amount` 와 맞는 것이지 박별 값의 정확도가 아니다.

## 6. 완료 조건

1. HOLD → CONFIRMED → CHECKED_IN → CHECKED_OUT 전 과정이 도는 통합 테스트,
   각 단계에서 `inventory_ledger` 의 `held`/`booked` 가 5.4 표와 일치하는지 확인
2. HOLD 를 만료시키면 EXPIRED 가 되고 재고가 정확히 되돌아오는 테스트
3. 허용되지 않는 전이(체크아웃된 예약 취소 등)가 `IllegalReservationTransition` 을 던지는 테스트
4. 같은 예약을 두 번 취소해도 재고가 한 번만 반납되는 테스트
5. 날짜 변경에서 새 기간의 재고가 모자라면 **옛 기간도 그대로 남아 있는지** 확인하는 테스트.
   중간 상태가 남지 않아야 한다
6. 다른 조직의 예약 식별자로 조회·변경했을 때 데이터가 나오지 않는 테스트
7. 게스트 연락처를 넣었다 꺼내면 원래 값이 나오고, 같은 값을 두 번 암호화하면
   암호문은 다르지만 검색 해시는 같은지 확인하는 테스트. 암호문이 같게 나오면
   IV 를 재사용하고 있다는 뜻이다
8. 박별 요금의 합이 `total_amount` 와 정확히 같은지 확인하는 테스트.
   나누어떨어지지 않는 금액으로도 한 번 확인한다
9. `ModularityTest` 와 `InventoryConcurrencyTest` 가 계속 통과

5번을 빠뜨리지 않는다. 부분 실패가 남기는 유령 재고는 조용히 생기고, 캘린더를 보기
전에는 드러나지 않는다.

## 7. 브랜치와 기록

- 새 브랜치를 판다. `feat/booking-lifecycle` 정도가 맞다
- 게스트 연락처 암호화는 ADR 0007 로 남긴다. 키 관리와 검색 해시에 HMAC 을 쓴 이유가
  들어가야 한다. ADR 0004 의 `JWT_SECRET`, ADR 0005 의 BCrypt 기각과 같은 계열의 결정이다
- 끝나면 CLAUDE.md "현재 상태" 절을 갱신한다
- 이 문서에 없는 판단이 필요해지면 임의로 정하지 말고 물어본다
