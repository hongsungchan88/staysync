# 확인 03. P3 완료 조건 1·2

- 확인일: 2026-09-05
- 범위: P3 12주차, 작업지시 09 의 6절 1번·2번
- 대상: 계획서 12.2 의 P3 완료 조건 첫째·둘째

> 첫째, Mock 채널에서 발생한 예약이 15초 이내에 캘린더에 반영되고 다른 채널의
> 재고가 자동으로 차감된다.
> 둘째, 5% 에러율을 주입한 상태에서 ARI 100건을 전송해도 재시도 후 최종 정합성이 유지된다.

셋째(에어비앤비 iCal)는 13주차다.

**이 둘은 자동화 테스트로 판정했다.** 9주차·10주차의 브라우저 확인과 다르다 — 재는 것이
사람이 볼 수 있는 화면이 아니라 주기 실행의 합과 재시도의 결과라서, 사람이 눈으로
반복 확인할 수 있는 종류가 아니다. 대신 **11주차 시뮬레이터를 별도 프로세스로 실제로
띄워** 진짜 HTTP 왕복 위에서 쟀다.

---

## 조건

| 항목 | 값 |
|---|---|
| 시뮬레이터 | `mock-ota-simulator`, 별도 JVM 프로세스, OS 가 준 빈 포트 |
| 백엔드 | `@SpringBootTest`, 내장 PostgreSQL |
| 테스트 | `ChannelRoundTripTest`(조건 1), `AriConsistencyTest`(조건 2) |

시뮬레이터를 같은 JVM 에 띄우지 않았다. `classpath:/application.yml` 이 둘이 되어 어느
쪽이 읽힐지가 클래스패스 순서에 달리고, 백엔드의 JPA·Flyway·Security 자동 설정이
시뮬레이터 컨텍스트에도 걸린다(자동 설정은 컴포넌트 스캔이 아니라 클래스패스가 정한다).
무엇보다 **재려는 것이 실제 HTTP 왕복과 타임아웃**이라 같은 JVM 안의 호출로는 대신할
수 없다.

## 조건 1 — 15초 안에 반영되고 다른 채널로 나간다

**주기 실행을 운영 기본값 그대로 켜고 쟀다.** 다른 테스트는 스케줄러를 멈추고
`pollAll()`·`flushAll()`·`drainOnce()` 를 직접 부르지만, 여기서 재려는 것이 바로 그
주기들의 합이다. 직접 부르면 15초를 지키는지가 아니라 코드가 도는지만 확인하게 된다.

시뮬레이터 하나에 Mock 연결 둘(`MOCK_A` → `room-a`, `MOCK_B` → `room-b`)을 붙이고
같은 판매 단위(2실)에 매핑했다. `room-a` 에 예약을 하나 만들었다.

| 구간 | 측정 |
|---|---|
| 캘린더 반영 | **1,474ms** |
| 다른 채널로 재고 전파 | **8,676ms** |
| 상한 | 15,000ms |

확인한 것.

- 캘린더의 잔여 수량이 2 → 1 로 바뀌었다
- 시뮬레이터가 받은 ARI 에 `room-b` 가 있고 `availability: 1` 이다
- **`room-a` 는 없다.** 자기가 판 예약을 자기에게 되보내지 않는다(계획서 6.5 수신 경로 5번)
- 예약은 한 건이고 `channel_code` 가 `MOCK_A` 다. 폴링이 여러 번 돌아도 늘지 않는다

### 여유가 6.3초다 — 13주차 설계의 입력

경로가 넷을 지난다. 폴링 5초 + Outbox 릴레이 1초 + 병합 버퍼 6초 + 워커 1초라 **최악의
경우 13초**이고, 이번 측정의 8.7초는 각 주기에 운 좋게 걸린 값이다.

**13주차가 이 여유 안에서 설계해야 한다.**

- iCal 폴링 주기를 15분으로 잡아도(계획서의 `ical.poll-interval-minutes`) 이 조건은
  Mock 에만 걸리므로 무관하다. 다만 **iCal 예약이 캘린더에 뜨는 지연은 조건 1의 상한과
  전혀 다른 크기**라는 것을 13주차 지시서가 분명히 해야 한다
- 병합 버퍼 6초가 이 경로에서 가장 큰 몫이다. 재동기화 배치가 버퍼를 우회하면 그 6초를
  아끼지만, 그러면 Channex 한도를 지키는 장치를 우회하는 것이 된다. 우회하지 않는 쪽이 맞다
- 폴링 주기를 5초보다 늘리면 여유가 그만큼 줄어든다. 채널이 늘면 한 바퀴가 길어지므로
  13주차에 iCal 이 붙을 때 다시 재야 한다

## 조건 2 — 5% 에러율에서 ARI 100건

시뮬레이터에 `error-rate=0.05`, `seed=20260905` 을 주입했다. **시드를 고정한 것이
요점이다** — 재현되지 않는 주입은 실패가 결함 때문인지 운 때문인지 구분되지 않아
아무것도 보증하지 못한다.

날짜마다 다른 요금 100건을 만들어 작업 100건으로 보냈다.

- `DEAD` **0건**. 8회를 연달아 실패할 확률이 `0.05^8 ≈ 4×10⁻¹¹` 이다
- `SUCCESS` 100건
- **시뮬레이터가 가진 날짜별 최종 요금이 우리 값과 정확히 일치한다**

우리 로그가 성공이라고 해서 채널이 받았다는 뜻은 아니다. 그 간극이 이 조건이 겨냥하는
지점이라, 판정은 시뮬레이터가 실제로 받은 전문을 읽어서 했다.

### 여기서 결함이 하나 드러났다

처음 돌렸을 때 **100건이 전부 `DEAD`** 가 됐다. 시뮬레이터의 API 키와 연결의 자격
증명이 달라 모든 요청이 401 을 받았고, 어댑터가 그걸 영구 오류로 옮겨 즉시 포기했다.

정확히 **11주차에 자격 증명 검사를 넣은 이유**가 드러난 자리다. 검사가 없었다면 어댑터가
키를 빠뜨려도 100건이 전부 성공했을 것이고, 드러나는 것은 실제 OTA 로 바꾸는 순간이었다.

분류도 함께 검증됐다. 401 을 일시 오류로 뒀다면 100건이 각각 여덟 번씩 두드리고 나서야
죽었을 것이다.

## 12주차에 잡힌 다른 결함 둘

테스트가 잡았고, 둘 다 **정상 경로에서 증상이 없는** 종류다.

### `MOCK` 이 `PULL_BOOKING` 을 선언하지 않고 있었다

10주차에 `AdapterType.MOCK` 의 기능을 적을 때 웹훅만 넣고 예약 목록 조회를 빠뜨렸다.
시뮬레이터는 11주차부터 `GET /api/bookings` 를 내놓고 있었는데 선언이 그보다 좁았다.

`ChannelBookingPoller` 가 `PULL_BOOKING` 으로 거르므로 **폴링이 돌면서 이 채널만 조용히
건너뛴다.** 예약이 하나도 들어오지 않고 로그에도 아무것도 남지 않는다. 조건 1의 테스트가
15초를 기다리다 실패해서 잡혔다.

선언이 실제보다 좁으면 그 채널이 사라진다. 넓으면 없는 기능을 부르다 오류가 난다.
드러나는 방식이 반대이고, **좁은 쪽이 더 위험하다.**

### 재고 부족 예외가 트랜잭션을 rollback-only 로 찍고 있었다

`InventoryLedgerWriter.apply` 가 `@Transactional` 이라, `InsufficientInventoryException`
이 그 경계를 넘는 순간 스프링이 지금 트랜잭션을 rollback-only 로 표시한다. 예외를 잡아
`forceBook` 으로 넘어가도 커밋 시점에 `UnexpectedRollbackException` 이 나고 **예약도
충돌 기록도 전부 사라진다.**

"OTA 에서 이미 성사된 예약은 거절하지 않는다"는 결정이 조용히 뒤집히는 자리였다.
계획서 13.2 의 스케치가 `try { reserve } catch { forceBook }` 모양이라 그대로 따르면
걸린다.

**먼저 보고 나서 고르는 방식으로 바꿨다.** 판매 단위 락을 이미 쥐고 있으므로 보는 것과
잡는 것 사이에 재고가 바뀌지 않는다. 예외를 만들지 않으니 rollback-only 도 없다.

## 정리

**계획서 12.2 의 P3 완료 조건 셋 중 둘이 통과했다.** 셋째(에어비앤비 iCal 수신·발행)는
13주차다.

## 남는 것

- **`RUNNING` 인 채로 앱이 죽으면 그 연결이 막힌다.** 순서 보장 조건이 `RUNNING` 도
  앞선 작업으로 세기 때문이다. 인스턴스가 하나이고 재기동이 드물어 두었다. 되살리는
  배치가 필요해지면 13주차 재동기화와 같은 자리에 넣는다(ADR 0012 결과 절)
- **병합 버퍼가 메모리에 있다.** 앱이 죽으면 flush 되지 않은 6초치가 사라진다. 그 자리를
  메우는 것이 13주차의 정기 재동기화(계획서 6.6)다
- **웹훅 수신 엔드포인트가 없다.** 시뮬레이터의 웹훅 발신은 11주차에 만들어 뒀고
  13주차에 `verifySignature()` 와 함께 쓴다
- 충돌 해소 절차 넷과 관리 화면은 13주차다(계획서 7.4). 12주차는 기록까지다
