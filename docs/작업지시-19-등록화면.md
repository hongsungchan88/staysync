## 1. 왜 필요한가

**지금 StaySync 는 혼자 시작할 수 없다.** 회원가입도, 숙소·판매 단위 등록도 API 만 있고 화면이 없다
(확인-08 3절 4번). 배포 환경의 데이터는 전부 사람이 API 로 넣었다.

- **판매를 시도하려면 호스트가 혼자 가입하고 자기 숙소를 넣을 수 있어야 한다**(교수 방향, 09-17)
- **Channex 상용 인증의 화면 공유 검토가 "실제 사용자 조작"을 본다**(조사-04 3절). 데이터를 API 로 넣는
  시스템은 그 자리에서 약하다
- 2차 테스트(업체 수강생 실사용)는 계정을 나눠 주는 일이다. 지금은 계정마다 사람이 손으로 만들어야 한다

## 2. 이번에 만드는 것

### A. 회원가입 화면

- `/signup`. 이메일, 비밀번호, 이름, 조직 이름 넷을 받는다 — `AuthService.signup` 이 이미 그 넷을 받고,
  조직 하나와 OWNER 한 명을 함께 만든다. **서버 쪽은 새로 만들 것이 없다**
- 로그인 화면에 "가입" 링크, 가입 화면에 "로그인" 링크
- 가입에 성공하면 로그인과 같은 상태가 된다(토큰 한 쌍이 그대로 온다). 바로 캘린더로 보낸다
- **이미 쓰는 이메일**은 서버가 409 와 메시지를 준다. 그 메시지를 그대로 보여 준다
- 비밀번호 규칙은 **서버가 이미 적용하는 것만** 보여 준다. 화면에서 새 규칙을 만들지 않는다 —
  화면과 서버가 갈리면 서버가 이기고, 사용자는 이유를 모른 채 막힌다
- **가입 직후 화면이 비어 있다.** 숙소가 없으면 캘린더에 무엇을 보여 줄지 B 의 빈 상태로 잇는다

### B. 숙소·판매 단위 등록·편집 화면

새 화면 하나. 이름은 `/settings` 든 `/properties` 든 지금 화면 이름들과 어울리는 쪽으로 고른다.

- **숙소** — 목록, 추가, 이름·주소·체크인/체크아웃 시각 편집. `PropertyService.createProperty`·
  `updateProperty` 가 이미 있다. 체크인·체크아웃은 **함께** 바꾼다(서비스가 그렇게 받는다)
- **판매 단위** — 숙소 아래 목록, 추가(이름·종류·수량·기본 요금), 이름·수량 편집.
  `PropertyService.registerUnit`·`updateUnit` 이 이미 있다. 등록하면 기본 요금제가 함께 생긴다
  (`UnitRegistrationService`) — **요금제는 화면에 드러내지 않는다.** 채널이 요구해서 데이터로만 두는 것이다
- **요금 화면은 만들지 않는다.** 날짜별 요금·최소 숙박은 캘린더의 기간 선택 편집이 이미 한다(5절 2번)
- **빈 상태** — 숙소가 없으면 "숙소를 먼저 등록하세요"와 이 화면으로 가는 길. 캘린더·리포트·채널 화면이
  숙소 0 개에서 오류 없이 이 안내로 떨어지는지 본다(확인-08 1차가 잡은 그 자리다)
- 채널 연결·매핑 화면은 그대로 둔다. 이 화면에서 링크만 건다

### C. 판매 단위 수량 변경이 재고에 반영되지 않는다 — 작업지시-18 9.4.1

`PropertyService.updateUnit` 이 `unit.changeCapacity` 만 하고 **이미 만들어진 원장 행은 옛 수량으로 남는다**
(`InventoryLedger.changeTotalUnits` 는 호출자가 없다). 화면에서 수량을 고칠 수 있게 되는 순간 이 결함이
사용자 손에 닿는다.

- **수량을 바꾸면 그 판매 단위의 원장 행이 따라간다.** 초과분(`overbooked_units`)도 함께 다시 계산한다 —
  V10 의 등식 CHECK 가 있어 그러지 않으면 저장이 실패한다(작업지시-18 9.4.2)
- **줄이는 쪽은 이미 팔린 날을 넘지 못한다.** 어느 날짜가 막는지 사람이 알 수 있게 응답에 담는다.
  줄이기를 강행해 그 날을 초과 상태로 만들지 않는다 — 초과는 채널이 밀어 넣을 때만 받는 것이고(`forceBook`),
  호스트가 스스로 만드는 자리가 아니다
- 지난 날짜를 어떻게 다룰지는 훑은 뒤 정하고 8절에 적는다. 과거 행까지 바꾸면 리포트의 과거가 움직인다

### D. 역할

- **가입은 지금도 OWNER 만 만든다.** 이번 범위에서 역할을 늘리거나 역할별 인가를 새로 넣지 않는다(5절 3번)
- 다만 **`Role` 에 어떤 값이 있고 어디서 읽히는지 훑어 8절에 적는다.** 다음 단계(심사자 읽기 전용 계정,
  조직 안에 사람 초대)가 무엇을 건드릴지 그 표가 정한다

## 3. 이번에 만들지 않는 것

- **역할별 인가(`@PreAuthorize`)와 사용자 초대** — 5절 3번
- 요금제 화면, 요금 규칙(주말·성수기) 화면 — 캘린더 편집으로 충분하다
- 비밀번호 재설정, 이메일 인증, 소셜 로그인 — 판매 단계에서 다시 본다
- 숙소·판매 단위 삭제 — 예약·원장·채널 매핑이 딸린 삭제는 이번 범위가 아니다. **비활성 표시도 만들지 않는다**
- 조직 이름 변경, 결제 수단, 요금제(구독) — 판매 단계
- 체크인·체크아웃을 키보드로 여는 길 — 예약 패널에 이미 있다

## 4. 지켜야 할 제약

- **서버 쪽은 이미 있는 것을 쓴다.** 새 엔드포인트가 필요해 보이면 먼저 기존 API 로 되는지 보고, 그래도
  필요하면 8절에 이유를 적는다. C 만은 서버를 고치는 일이다
- **조직 스코핑은 `OwnedResources` 를 거친다.** 화면이 보내는 식별자를 그대로 믿지 않는다. 요청 본문의
  조직 식별자는 받지 않는다(`PropertyService` 주석)
- **C 는 원장 쓰기다.** 판매 단위 락 안에서, 트랜잭션 경계는 기존 쓰기 경로와 같은 모양으로.
  예외로 흐름을 제어하지 않는다 — 줄이기가 막히는 경우는 먼저 조회해 분기한다
- **화면이 없어 못 보던 것이 드러난다.** 숙소 0 개, 판매 단위 0 개, 요금 0 일인 상태에서 기존 화면 다섯
  (캘린더·채널·충돌·청소·리포트)이 오류 없이 떨어지는지 본다
- **테스트는 실제 진입점으로.** 가입·등록은 HTTP 로, C 는 수량 변경 API 를 부르고 원장 행을 확인한다.
  프론트 테스트는 서버가 실제로 보내는 응답 모양 그대로 픽스처를 만든다(17주차 `ReportTest` 의 교훈)
- 그대로 가는 것 — 자기 호출 금지, `JdbcTemplate` 없음, `ChannelRoundTripTest` 병렬 금지, 주석·문서 한국어
- **마이그레이션이 필요해지면 멈추고 묻는다.** 이번 범위는 스키마 변경 없이 닫힐 것으로 본다

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. 가입의 범위 | **이메일·비밀번호·이름·조직 이름 넷.** 서버가 이미 받는 그대로다. 이메일 인증·재설정은 판매 단계 |
| 2. 요금 화면 | **만들지 않는다.** 날짜별 요금·최소 숙박은 캘린더의 기간 선택 편집이 한다. 기본 요금은 판매 단위 등록에서 한 번 받는다 |
| 3. 역할별 인가 | **이번에 넣지 않는다.** 가입이 OWNER 하나만 만들고 다른 역할을 발급하는 경로가 없어, 지금 넣으면 아무것도 막지 않는 코드가 된다. **읽기 전용 심사자 계정이나 조직 안 초대를 만들 때 함께 짓는다**(Cowork 판단, 30차 — 사용자에게 보고함) |
| 4. 수량 줄이기 | **이미 팔린 날 아래로는 못 줄인다.** 막는 날짜를 응답에 담아 사람이 알게 한다 |

### 3번의 근거

지금 `@PreAuthorize` 를 붙여도 모든 계정이 OWNER 라 거절되는 요청이 없다. 인가는 **막을 대상이 생긴 뒤**
막아야 한다. 그 전에 붙이면 검증되지 않은 규칙이 코드에만 남고, 실제로 역할이 갈리는 날 다시 설계해야 한다.
지금 필요한 것은 D — 역할이 어디서 읽히는지 아는 것이다.

## 6. 완료 조건

1. **가입 → 로그인 상태 → 캘린더까지 이어지는 테스트**(HTTP). 같은 이메일로 다시 가입하면 409 와 그 메시지
2. **가입 직후(숙소 0 개) 기존 화면 다섯이 오류 없이 빈 상태를 보이는 테스트** — 최소한 캘린더와 리포트
3. **숙소 등록·편집 테스트**(HTTP). 다른 조직의 숙소는 못 고친다
4. **판매 단위 등록 테스트** — 기본 요금제가 함께 생긴다
5. **수량을 늘리면 그 판매 단위의 원장 행이 따라가고 초과분이 다시 계산되는 테스트**
6. **이미 팔린 날 아래로 줄이면 거절되고, 막는 날짜가 응답에 담기는 테스트**
7. **줄이기가 성공하는 경우 원장이 따라가고 가용 수량이 맞는 테스트**
8. 지난 날짜를 어떻게 다뤘는지와 그 이유를 8절에 적는다
9. `Role` 값과 읽히는 자리 목록을 8절에 적는다(D)
10. 프론트 테스트 — 가입 화면 1건, 등록 화면 1건(서버 응답 모양 그대로)
11. `./gradlew build`, `npm run build`, `npm run test`, `ModularityTest` 통과. 건수를 적는다(지금 325·37·107)
12. **배포하고 브라우저로 본다.** 배포 환경에서 **새 조직으로 가입해 숙소 하나·판매 단위 하나를 넣고 캘린더에
    뜨는 것까지** 본다. 업체 데이터(조직 `1차 심사`)는 건드리지 않는다. **그 시험 조직은 지우지 말고
    8절에 조직 이름과 계정을 적는다**(비밀번호는 적지 않는다) — 심사 때 "혼자 시작하는 흐름"을 보여 줄 자리다

**1·2·5·6 을 빠뜨리지 않는다.** 1·2는 호스트가 처음 보는 화면, 5·6은 재고 엔진에 닿는 자리다.

### 8.1 착수 전 조사 (09-20)

**기존 API 로 되는가.**

| 화면이 필요한 것 | 기존 API | 판단 |
|---|---|---|
| A 가입 | `POST /api/auth/signup {email, password, displayName, orgName}` → 토큰 + 리프레시 쿠키. 중복 이메일 409 `EMAIL_ALREADY_USED`("이미 사용 중인 이메일입니다. email=…"). 비밀번호 규칙은 길이 10~100 뿐(`@Size`) | **그대로 쓴다.** 서버 변경 없음 |
| B 숙소 목록·추가·편집 | `GET/POST /api/properties`, `PATCH /api/properties/{id} {name, address, checkInTime, checkOutTime}` — 시각 둘은 둘 다 있을 때만 바뀐다 | 그대로 |
| B 판매 단위 목록·추가·이름 편집 | `GET/POST /api/properties/{id}/units`, `PATCH /api/units/{id} {name, totalUnits}` | 이름은 그대로. **수량은 아래 C** |
| B 요금제 | `GET /api/units/{id}/rate-plans` | 화면에 안 드러낸다(5절 2번). 안 부른다 |
| C 수량 변경 | `PATCH /api/units/{id} {totalUnits}` → `PropertyService.updateUnit` → `unit.changeCapacity` 만. 원장 행은 안 따라간다 | **새 엔드포인트가 필요하다.** 이유는 아래 |

**C 에 새 엔드포인트가 필요한 이유.** 원장 쓰기는 booking 의 일이고(락 → 트랜잭션, `InventoryService` 모양),
지금 수량 변경은 property 에 있다. property → booking 호출은 의존 방향(booking → property)의 역이라
`ModularityTest` 가 막고, 역방향 포트는 CLAUDE.md 가 금지한다. 그래서 **수량 변경을 booking 이 든다** —
`PATCH /api/units/{id}/capacity {totalUnits}`. booking 이 판매 단위 락을 잡고, 한 트랜잭션 안에서 원장 행을
바꾸고 property 의 `changeUnitCapacity` 를 불러 `unit.total_units` 를 맞춘다(booking → property, 허용 방향).
**기존 `PATCH /api/units/{id}` 에서 `totalUnits` 를 뺀다** — 두 길이 있으면 옛 길이 원장을 다시 어긋나게 한다.

**`Role` — 값과 읽히는 자리(D).**

| 자리 | 하는 일 |
|---|---|
| `shared.security.Role` | `OWNER`·`MANAGER`·`HOUSEKEEPER`. shared 에 둔 이유: 인가 판단이 모든 모듈의 웹 계층에서 일어날 것이라서 |
| `user_account.role` (V1) | `chk_user_role CHECK (role IN ('OWNER','MANAGER','HOUSEKEEPER'))`. 열거형과 값을 맞춰야 한다 |
| `AuthService.signup` | **쓰는 자리 하나.** 언제나 `Role.OWNER`. 다른 값을 발급하는 경로는 없다 |
| `UserAccount.role` → `toAuthenticatedUser()` | 로그인 때 `AuthenticatedUser(userId, orgId, role)` 로 |
| `JwtTokenService` | 액세스 토큰 클레임 `role` 에 이름을 넣고, 검증 때 `Role.valueOf` 로 되읽는다 |
| `SecurityConfig` | `GrantedAuthority("ROLE_" + name)` 로 올린다 — **`hasRole`·`@PreAuthorize` 를 쓰는 곳은 0** |
| `AuthenticatedUser.isOwner()` | 있지만 **호출자 0** |
| `AuthDtos.MeResponse` → `GET /api/auth/me` | 화면에 내려간다. 프론트 `meResponseSchema` 가 enum 으로 받지만 **읽는 화면은 없다** |

결론 — 역할은 발급(OWNER 고정)·저장·토큰 왕복·`/me` 노출까지만 있고 **판정에 쓰이는 곳이 없다.** 5절 3번대로
이번에 안 넣는다. 다음 단계(심사자 읽기 전용, 조직 안 초대)가 건드릴 자리는 넷 — 발급 경로(초대 API),
`SecurityConfig`/컨트롤러의 `hasRole`, 프론트가 `/me` 의 role 로 쓰기 버튼을 감추는 것, `chk_user_role`(값을 더할 때만).

**지난 날짜(C).** 원장 행은 **오늘(Asia/Seoul) 이후만** 바꾸고 막힘 판정도 그 범위다. 지난 행은 그날 팔 수
있었던 수량의 기록이라 건드리지 않는다 — 캘린더의 지난 칸 `avail` 은 그대로, ARI·위젯은 과거를 안 본다.
**리포트의 판매 가능 객실박(분모)은 원장이 아니라 `unit.total_units` 를 읽으므로**(작업지시-18 9.4.1) 수량을
바꾸면 과거 기간의 점유율도 새 수량으로 다시 계산된다. 수량 이력이 없어 이번 범위에서는 어쩔 수 없다 —
적어 둔다.
