### 이번 주가 P3 완료 조건 둘을 판정한다

> 첫째, Mock 채널에서 발생한 예약이 15초 이내에 캘린더에 반영되고 다른 채널의

> 둘째, 5% 에러율을 주입한 상태에서 ARI 100건을 전송해도 재시도 후 최종 정합성이 유지된다.

없는 것을 조건에 넣으면 검증할 수 없다.

## 2. 이번에 만드는 것

송신과 수신 두 갈래다. 계획서 6.5 가 양쪽 흐름을 그려 뒀고 그것이 명세다.

### A. MockOtaAdapter

레지스트리의 첫 등록자다. 시뮬레이터를 두드린다.

- `capabilities()` 는 `AdapterType` 이 선언한 값을 그대로 돌려준다(10주차 결정)
- **자격 증명을 실제로 보낸다.** 시뮬레이터가 `/api/**` 전체에서 키를 검사하므로,
  빠뜨리면 401 로 드러난다. 11주차에 그걸 위해 넣은 검사다
- 시뮬레이터의 오류를 우리 예외로 옮긴다. 계획서 13.3 이 세 갈래로 나눴다 —
  `RateLimitedException`(429), `TransientChannelException`(5xx),
  `PermanentChannelException`(4xx 중 재시도해도 소용없는 것).
  **이 구분이 C 의 재시도 정책 전체를 좌우한다**

### B. ARI 병합 버퍼

계획서 6.5 의 `AriCoalescingBuffer` 다. CLAUDE.md 가 근거를 적어 뒀다 —
Channex 제한이 숙소당 분당 20회이고, 변경을 **6초 윈도로 모아** 연속된 같은 값을
날짜 구간으로 압축해 보낸다.

- 같은 연결·같은 판매 단위의 변경이 윈도 안에 여럿 오면 하나로 합친다
- **나중 값이 이긴다.** 6초 안에 25만원 → 23만원으로 바꾸면 23만원 하나만 나간다
- 연속된 날짜에 같은 값이면 구간으로 압축한다
- flush 하면 `sync_job` 한 건이 된다. 멱등성 키는 6.5 대로
  `hash(connId, dateRange, values)` 다

Mock 은 분당 제한이 없지만 **버퍼를 우회하지 않는다.** 채널마다 다른 경로를 만들면
검증한 것과 실제로 도는 것이 갈라진다.

### C. sync_job 과 SyncJobWorker

계획서 13.3 이 명세다.

- `claimBatch` 는 `FOR UPDATE SKIP LOCKED` 로 집는다(5절 2번)
- **같은 연결의 작업은 순서대로 처리한다.** 요금 갱신이 뒤집히면 채널 쪽 값이 틀린다.
  5~6주차 Outbox 의 순서 보장과 같은 문제이고 같은 방식으로 푼다
- 재시도 정책은 13.3 그대로다

| 결과 | 처리 |
|---|---|
| 성공 | `SUCCESS`, `last_sync_at` 갱신 |
| 429 | 60초 뒤 재시도 |
| 5xx | 지수 백오프, 상한 30분 |
| 8회 초과 | `DEAD`, 경고 로그 |
| 영구 오류 | 즉시 `DEAD` |

**`DEAD` 인 작업의 행을 지우지 않는다.** 5~6주차 Outbox 재시도 상한과 같은 이유다 —
`last_error` 가 남아 있어야 사람이 원인을 보고 다시 넣을 수 있다.

### D. 채널 예약 수신

계획서 13.2 의 `BookingIngestService` 가 명세다. 판단 순서가 정해져 있다.

1. **멱등성** — `(channel_code, channel_booking_id)` 로 찾는다.
   없으면 신규, `revision` 같으면 무시, 크면 수정, 취소면 해제
2. **재고** — `InventoryService` 를 통한다. 락은 날짜 오름차순
3. **부족하면 거절하지 않는다.** CLAUDE.md 가 못박은 그대로다. 예약을 받아들이고
   `overbooking_conflict` 에 기록해 사람이 처리하게 한다
4. **이벤트와 감사** — 도메인 변경과 한 트랜잭션이다

**3번이 이 주의 핵심이다.** OTA 에서 이미 성사된 예약을 재고 없음으로 거절하면
게스트와 플랫폼 양쪽에서 문제가 된다. 시뮬레이터의 "재고보다 많은 예약" 시나리오가
이걸 위해 있다.

수신은 폴링으로 한다(5절 1번). 주기는 완료 조건의 15초를 지킬 수 있게 정한다.

### E. Outbox 소비자 — 요금 변경 전파

계획서 6.5 송신 경로의 윗단이다. 9주차의 일괄 편집이 이미 `outbox_event` 를 남기고
있고, 이번에 그것을 받아 버퍼로 넘긴다.

- 매핑된 활성 연결을 찾는다
- **`capabilities()` 로 `PUSH_RATE` 미지원 채널을 제외한다.** 계획서 6.1 이 말하는
  설계의 요점이 실제로 동작하는 첫 자리다. iCal 은 13주차에 여기서 걸러진다
- `AriCoalescingBuffer` 에 넣는다

### F. 충돌 기록

`overbooking_conflict` 엔티티와 저장. **기록까지만이다.**

계획서 7.4 의 해소 절차 네 가지와 관리 화면은 13주차다. 지금은 D 의 3번이 행을
남기고, 그 행을 조회할 수 있으면 된다.

**캘린더 응답의 `conflict` 가 이번 주부터 실제 값을 갖는다.** 7주차에 항상 `false`
로 두고 "P3 에서 채운다"고 주석을 남긴 자리다. 프론트엔드는 이미 이 값을 보고
셀을 표시하도록 짜여 있으므로 화면은 손대지 않아도 된다.

## 4. 지켜야 할 제약

- **재고 변경은 전부 `InventoryService` 를 통한다.** 락은 날짜 오름차순.
  `StayPeriod.nightDates()` 의 정렬을 우회하지 않는다
- **모듈 경계.** `channel` 이 `booking.domain` 을 보지 않는다. 예약 생성과 재고 조작은
  booking 이 공개한 인터페이스로 한다. 방향은 channel → booking 이다.
  **`ModularityTest` 가 이번 주에 가장 많이 울릴 곳이다**
- **한 트랜잭션.** 예약 저장, 재고 변경, `outbox_event`, `audit_log` 가 함께 성공하거나
  함께 실패한다. 판별 기준은 같다 — 바깥이 롤백될 때 이 쓰기가 남아야 하는가
- **`sync_job` 의 상태 변경은 워커 밖에서 하지 않는다.** 클레임과 완료가 한곳에 있어야
  `SKIP LOCKED` 가 의미를 갖는다
- **자격 증명을 로그와 이벤트에 남기지 않는다.** 10주차에 그은 선이 그대로다
- **`ddl-auto: validate`, V1 수정 금지.** 컬럼이 모자라면 V3 를 더한다
- **시뮬레이터를 고치지 않는다.** 어댑터가 시뮬레이터에 맞춘다. 반대로 하면 검증
  대상이 우리 흉내가 된다. 시뮬레이터가 명세와 어긋나면 그건 별건으로 보고한다
- 주석과 문서는 한국어, 식별자는 영어, 테스트 이름은 한국어 서술형

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. 수신 방식 | 폴링. 웹훅 수신 엔드포인트는 13주차 |
| 2. 동시성 | `SKIP LOCKED` 는 쓰고 ShedLock 은 쓰지 않는다 |
| 3. 충돌 | 기록까지. 해소 절차와 화면은 13주차 |

### 1번의 근거

완료 조건이 15초이고 폴링으로 충족된다. 웹훅 수신은 엔드포인트 하나가 아니라
**서명 검증과 인증 표면이 함께 붙는 일**이라, 13주차에 iCal 과 나란히 놓고
`ChannelAdapter.verifySignature()` 를 실제로 채우면서 보는 편이 낫다.

시뮬레이터의 웹훅 발신 기능은 11주차에 만들어 뒀고 13주차에 쓴다. 지금 노는 것이
낭비가 아니라, 그때 쓸 것을 미리 만들어 둔 것이다.

폴링이 iCal 과 코드 경로를 나눠 쓴다는 것도 이유다. 13주차의 iCal 수신도 폴링이다.

### 2번의 근거

**`SKIP LOCKED` 는 넣는다.** 워커가 하나여도 `claimBatch` 는 상태를 `RUNNING` 으로
바꾸며 원자적으로 집어야 하고, 개발 중에 앱을 두 번 띄우는 실수가 실제로 일어난다.
비용은 쿼리 한 줄이다.

**ShedLock 은 넣지 않는다.** 인스턴스가 하나뿐이라 지금 막을 것이 없다.
5~6주차에 `OutboxRelay` 에서 같은 판단을 했고 자리만 주석으로 남겼다. 여기도 같다.

### 3번의 근거

해소 절차 넷(업그레이드 배정, 인근 안내, 취소와 보상, 관리자 허용)은 각각 화면과
게스트 메시지가 따르고, 메시지 초안은 9장의 AI 기능이 만든다. 12주차에 넣으면
P5 를 앞당겨 오게 된다.

이번 주에 필요한 것은 **충돌이 실제로 기록되는지**까지다. 그게 D 의 3번을 검증한다.

## 6. 완료 조건

앞의 둘이 계획서 12.2 의 P3 완료 조건이다. **이 둘을 실제로 돌려서 판정한다.**

1. **Mock 채널에서 발생한 예약이 15초 이내에 캘린더에 반영되고, 같은 판매 단위에
   매핑된 다른 연결의 재고가 차감되는 테스트.** 시뮬레이터 하나에 Mock 연결 둘을
   붙여 확인한다
2. **에러율 5% 를 주입한 상태에서 ARI 100건을 보내고, 재시도 뒤 시뮬레이터가 가진
   값과 우리 값이 일치하는 테스트.** 시드를 고정해 재현되게 한다

송신.

3. 6초 안에 같은 날짜를 두 번 바꾸면 나중 값 하나만 나가는 테스트
4. 연속된 날짜의 같은 값이 하나의 구간으로 압축되는 테스트
5. 429 면 60초 뒤, 5xx 면 지수 백오프로 재시도되는 테스트
6. 8회를 넘기면 `DEAD` 가 되고 **행이 남아 있는** 테스트
7. 같은 연결의 작업이 순서대로 처리되는 테스트
8. `PUSH_RATE` 를 지원하지 않는 연결에는 작업이 만들어지지 않는 테스트.
   **`capabilities()` 가 실제로 거르는지 여기서 드러난다**

수신.

9. 같은 예약을 두 번 받으면 한 건만 생기는 테스트
10. `revision` 이 역전돼 도착하면 낮은 것이 무시되는 테스트
11. 취소가 오면 재고가 풀리는 테스트
12. **재고가 부족한 예약이 와도 거절되지 않고, 예약이 생기며
    `overbooking_conflict` 에 행이 남는 테스트.** 이번 주에서 가장 중요하다
13. 12번 뒤에 캘린더를 조회하면 해당 셀의 `conflict` 가 `true` 인 테스트
14. 수신이 롤백되면 예약·재고·이벤트·감사 기록이 모두 사라지는 테스트

전체.

15. `ModularityTest` 통과. channel → booking 방향이 지켜졌는지 드러난다
16. `InventoryConcurrencyTest` 계속 통과
17. `./gradlew test`, `./gradlew build`, `npm run build`, `npm run test` 통과

1번·2번·12번을 빠뜨리지 않는다. 앞의 둘은 단계 전체의 판정 기준이고, 12번은
정상 경로에서 증상이 없다 — 거절해 버려도 우리 쪽 로그는 깨끗하고, 문제가 드러나는
것은 게스트가 도착한 뒤다.

## 7. 브랜치와 기록

- `feat/channel-sync-push` — A, B, C, E
- `feat/channel-sync-pull` — D, F

A 가 양쪽에 필요하므로 push 쪽에 넣고 먼저 병합한다.

- **재시도와 백오프 정책을 ADR 0012 로 남긴다.** 오류를 세 갈래(일시·제한·영구)로
  나눈 근거, 상한을 8회·30분으로 잡은 근거, `DEAD` 행을 지우지 않는 이유를 적는다.
  이 정책이 12주차 완료 조건 2의 "최종 정합성"이 성립하는 이유다
- 병합 버퍼의 6초 윈도는 CLAUDE.md 에 이미 근거가 있다. ADR 을 새로 만들지 않고
