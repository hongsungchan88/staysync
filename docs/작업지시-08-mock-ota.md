## 1. 지금 상태

P3 10주차까지 `main` 에 병합·푸시돼 있다. 백엔드 157건 + 프론트 65건 통과.

어댑터 레지스트리, 채널 연결(자격 증명 암호화), 채널 매핑, 채널 화면 둘이 있다.
**레지스트리에 등록된 어댑터 구현은 아직 0개다.**

### 이번 주에 만드는 것은 우리 앱이 아니다

시뮬레이터는 **상대역**이다. 우리가 채널이라고 부르는 것을 흉내 내는 별도 애플리케이션이고,
12~13주차에 어댑터와 워커가 이것을 두드린다.

그래서 이번 주에는 `MockOtaAdapter` 를 만들지 않는다(계획서 12.2 가 12주차로 잡았다).
**레지스트리의 첫 등록자는 12주차다.** 11주차의 검증은 시뮬레이터가 명세대로
동작하는지까지다.

### 왜 이게 필요한가

계획서 3.3 이 적은 그대로다. iCal 은 요금을 동기화하지 못하고, Channex 스테이징은
남의 서버라 지연과 실패를 우리가 만들 수 없다. **두 방식으로는 검증할 수 없는 조건이
남는다** — 지연, 실패, 중복 전송, 순서 역전, 동시 예약.

12주차 완료 조건이 "5% 에러율을 주입한 상태에서 ARI 100건을 전송해도 최종 정합성이
유지된다"인데, 그 에러율을 만들 수 있는 것이 이것뿐이다.

## 2. 이번에 만드는 것

계획서 6.4 의 표가 명세다. 아홉 가지 기능이 있고 각각 검증 대상이 정해져 있다.

### A. 별도 애플리케이션

계획서 11.4 가 `mock-ota-simulator/` 를 그려 뒀다.

**기존 백엔드의 빌드와 테스트가 깨지지 않는 것이 조건이다.** 지금 `settings.gradle` 은
단일 프로젝트이고 소스가 `src/` 에 바로 있다. 멀티프로젝트로 바꾸든 독립 프로젝트로
두든 구성 방식은 맡긴다. **다만 `./gradlew test` 와 `./gradlew build` 가 지금처럼
동작해야 한다.**

- 포트는 백엔드(8080)와 테스트용 데이터베이스(15433, 15434) 를 피한다
- `docker-compose.yml` 에 자리를 넣는다. 계획서 11.4 가 그렇게 그려 뒀다

### B. 채널 노릇을 하는 엔드포인트 셋

| 엔드포인트 | 검증 대상 | 어느 주차가 쓰나 |
|---|---|---|
| ARI 수신 | 정상 전송 경로 | 12주차 워커 |
| 예약 목록 조회 | 폴링 수신 경로 | 12주차 어댑터 |
| 웹훅 발신 | 푸시 수신 경로 | 13주차 |

**웹훅을 받을 곳이 아직 없다.** 우리 앱의 수신 엔드포인트는 12~13주차다.
대상 URL 을 설정으로 두고, 지정한 곳으로 실제로 POST 를 보내는지까지 확인한다.

ARI 수신은 받아서 저장하고 조회할 수 있게만 한다. **시뮬레이터가 요금을 해석하거나
검증하지 않는다.** 우리가 무엇을 보냈는지 되돌려 보여 주는 것이 역할이다.
12주차의 "전송한 ARI 무시"(재동기화 배치 검증)가 이 저장소를 뒤집는 방식으로 동작한다.

### C. 자격 증명 검사

요청 헤더에 API 키를 요구한다. 틀리면 401 이다.

**어댑터가 자격 증명을 아예 안 보내는 결함을 잡기 위해서다.** 검사가 없으면 12주차에
어댑터를 만들 때 키를 빠뜨려도 전부 통과한다. 실제 OTA 로 바꾸는 순간 전부 401 이 된다.

키 자체는 단순한 문자열이면 된다. 서명이나 만료를 흉내 내지 않는다.

### D. 악조건 주입

계획서 6.4 의 `ChaosFilter` 가 명세다. 프로퍼티로 지연과 에러율을 준다.

- **지연** — 타임아웃과 서킷브레이커 검증용
- **에러율** — 재시도와 백오프 검증용. 12주차 완료 조건의 5% 가 여기서 나온다

주입은 **결정적으로 재현할 수 있어야 한다.** 난수 시드를 고정하는 경로를 남긴다.
"가끔 실패하는 테스트"는 결함을 숨긴다.

### E. 예약을 만들어 내는 시나리오 넷

시뮬레이터가 예약을 만들어 낼 수 있어야 12~13주차에 수신 경로를 검증한다.

| 시나리오 | 검증 대상 |
|---|---|
| 같은 예약 중복 전송 | 멱등성. `(channel_code, channel_booking_id)` 유니크 제약 |
| 동시 예약 다발 | 중복예약 방지. 재고 방어 4계층 |
| `revision` 순서 역전 | 버전 기반 충돌 해소. 낮은 버전이 나중에 와도 무시 |
| 재고보다 많은 예약 | 초과 판매 처리. **거절하지 않고 `overbooking_conflict` 에 기록** |

넷째가 P3 의 핵심이다. CLAUDE.md 가 "OTA 에서 이미 성사된 예약은 거절하지 않는다"고
못박아 뒀고, 그 상황을 만들 수 있는 것이 시뮬레이터뿐이다.

시나리오를 거는 방법은 맡긴다. 엔드포인트든 프로퍼티든, **테스트에서 부를 수 있으면
된다.**

### F. 시뮬레이터 자체 테스트

12주차가 이것을 신뢰하고 쓴다. **시뮬레이터가 틀리면 12주차의 모든 판정이 틀린다.**

## 3. 이번에 만들지 않는 것

- **`MockOtaAdapter`.** 12주차다. 레지스트리는 이번 주에도 비어 있다
- **동기화 워커, 재시도·백오프·실패 큐, ARI 병합 버퍼.** 12주차다
- **우리 앱의 웹훅 수신 엔드포인트.** 12~13주차다. 시뮬레이터는 발신만 한다
- **`BookingIngestService`.** 채널 예약을 우리 도메인에 넣는 자리이고 12주차다
- **시뮬레이터의 데이터베이스.** 5절 2번
- **chaos 를 런타임에 바꾸는 엔드포인트.** 5절 3번
- **화면.** 시뮬레이터에 UI 를 만들지 않는다. HTTP 로 두드리는 도구다
- **iCal 관련 전부.** 13주차다. 파서 명세는 조사-02 3절에 있다

## 4. 지켜야 할 제약

- **시뮬레이터는 우리 도메인을 모른다.** `com.staysync` 의 엔티티나 서비스를 참조하지
  않는다. 채널이 우리 코드를 아는 것은 말이 안 된다. 주고받는 것은 JSON 이다
- **기존 백엔드 빌드가 깨지지 않는다.** `./gradlew test`, `./gradlew build`,
  `./gradlew bootRun --args='--spring.profiles.active=local'` 이 지금처럼 동작한다
- **포트가 겹치지 않는다.** 8080, 15433, 15434 를 피한다
- **악조건 주입이 결정적이다.** 시드를 고정하면 같은 결과가 나온다
- **`.env` 를 시뮬레이터가 읽지 않는다.** 실제 Channex 키와 무관하다.
  시뮬레이터의 키는 그 자체의 설정이다
- 주석과 문서는 한국어, 식별자는 영어, 테스트 이름은 한국어 서술형

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. 구성 방식 | 별도 애플리케이션. 멀티프로젝트든 독립이든 맡긴다. 기존 빌드 불변이 조건 |
| 2. 상태 저장 | 메모리에 둔다. 데이터베이스를 붙이지 않는다 |
| 3. chaos 설정 | 프로퍼티만. 런타임 변경 엔드포인트를 만들지 않는다 |
| 4. 자격 증명 | 헤더의 API 키를 검사한다. 틀리면 401 |

### 2번의 근거

시뮬레이터는 테스트 도구다. 재기동하면 비어도 된다. 데이터베이스를 붙이면 스키마와
마이그레이션이 또 한 벌 생기고, 그걸 유지하는 비용이 얻는 것보다 크다.

12주차 테스트는 시뮬레이터를 띄우고, 두드리고, 내리는 단위로 돌 것이다. 그 사이에
상태가 남아야 할 이유가 없다.

### 3번의 근거

12주차 완료 조건이 "5% 에러율을 주입한 상태에서 ARI 100건"이다. 프로퍼티로 충분하다.
한 테스트 안에서 에러율을 바꿔야 한다면 컨텍스트를 나누면 된다.

런타임 변경 엔드포인트는 지금 쓸 곳이 없다. 12주차에 프로퍼티로 못 견디는 상황이
실제로 나오면 그때 넣는다. 5~6주차에 소비자 워커를 미리 만들지 않은 것과 같다.

### 4번의 근거

**검사가 없으면 어댑터가 키를 빠뜨려도 12주차 테스트가 전부 통과한다.** 드러나는 것은
실제 OTA 로 바꾸는 순간이고, 그때는 전부 401 이라 어디가 문제인지도 안 보인다.

정상 경로에서 증상이 없는 결함을 미리 막는 것이고, 이 프로젝트에서 반복된 모양이다.
서명 검증과 만료는 흉내 내지 않는다 — 그건 `ChannelAdapter.verifySignature()` 가
실제 채널에서 할 일이고, 지금 흉내 내면 검증하는 대상이 우리 흉내가 된다.

## 6. 완료 조건

엔드포인트.

1. ARI 를 보내면 저장되고, 조회하면 보낸 그대로 돌아오는 테스트
2. 예약 목록 조회가 만들어 둔 예약을 돌려주는 테스트
3. 웹훅이 지정한 URL 로 실제로 POST 되는 테스트. 받는 쪽을 테스트 안에 세운다
4. API 키가 없거나 틀리면 401 이 나오는 테스트. **세 엔드포인트 전부**

악조건.

5. 지연을 주입하면 응답이 그만큼 늦는 테스트
6. 에러율 100% 면 전부 503, 0% 면 전부 통과하는 테스트
7. **같은 시드로 두 번 돌리면 같은 순서로 실패하는 테스트.** 재현되지 않는 주입은
   12주차에 쓸 수 없다

시나리오.

8. 같은 예약을 두 번 보내면 채널 예약번호가 같은 두 건이 나오는 테스트.
   시뮬레이터는 중복을 막지 않는다 — **막는 것은 우리 쪽 일이고 그걸 검증하려고
   중복을 보내는 것이다**
9. 동시 예약 다발이 실제로 동시에 나가는 테스트
10. `revision` 이 역전된 순서로 나가는 테스트. 높은 버전이 먼저, 낮은 버전이 나중
11. 재고보다 많은 예약을 만들어 내는 시나리오가 동작하는 테스트

전체.

12. `./gradlew test`, `./gradlew build` 가 지금처럼 통과.
    **백엔드 157건이 그대로 통과하는지 확인한다**
13. `./gradlew bootRun` 으로 백엔드가 여전히 뜨고, 시뮬레이터도 따로 뜬다.
    포트가 겹치지 않는다
14. `npm run build`, `npm run test` 통과. 프론트는 건드리지 않았으므로 회귀 확인이다

4번과 7번을 빠뜨리지 않는다. 4번이 없으면 12주차에 어댑터가 키를 빠뜨려도 아무도
모르고, 7번이 없으면 12주차의 실패가 결함인지 운인지 구분되지 않는다.

8번의 방향을 헷갈리지 말 것. **시뮬레이터는 나쁘게 굴어야 한다.** 중복을 막거나
순서를 바로잡으면 검증할 것이 사라진다.

## 7. 브랜치와 기록

- `feat/mock-ota` 하나다. 시뮬레이터가 통째로 새 코드라 자를 지점이 없다

- **시뮬레이터를 어떻게 구성했는지 ADR 로 남긴다.** 0011 이 된다. 별도 애플리케이션으로
  둔 이유(우리 도메인을 모르는 상대역이어야 한다), 데이터베이스를 붙이지 않은 이유,
  자격 증명 검사를 넣은 이유를 적는다. **테스트 도구도 설계 결정이 있는 코드다**
- 끝나면 CLAUDE.md "현재 상태"를 갱신한다. 시뮬레이터가 저장소에 생겼다는 것과
  띄우는 명령을 "명령" 절에 넣는다
- 12주차 지시서는 이 결과를 보고 쓴다. **시뮬레이터로 어떤 악조건을 실제로 만들 수
  있는지가 12주차 완료 조건의 상한이다**
- 이 문서에 없는 판단이 필요해지면 임의로 정하지 말고 물어본다
