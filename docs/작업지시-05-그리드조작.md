- 관련: 계획서 8.2 / 11.2 / 12.2, ADR 0002, ADR 0009, 측정-01, 작업지시-04

새 세션이 이 문서로 시작한다면 CLAUDE.md 를 먼저 읽고 이 문서를 읽으면 된다.

## 1. 지금 상태

P2 7주차가 끝나 `main` 에 병합·푸시돼 있다. 백엔드 111건 + 프론트 5건 통과.

캘린더 조회 API, pricing 최소 구현, React 19 + Vite 프론트엔드, 로그인과 캘린더 화면,
30일 정적 그리드까지 있다. `clean-on-start` 는 꺼져 있어 V1 을 수정하지 않는다.

### 측정값이 이번 주의 근거다

30객실 × 90일, 2,700셀. 전체는 `docs/측정-01-*.md` 에 있다.

| 구간 | 값 |
|---|---|
| 브라우저 사이클 (요청 → 2,700셀 표시) | 996 ms |
| ├ 캘린더 API | 270 ms (27%) |
| └ 파싱 + 렌더 + 레이아웃 + 페인트 | 약 726 ms (73%) |
| DOM 노드 / 강제 레이아웃 1회 | 11,229개 / 130 ms |

**병목은 서버가 아니라 DOM 크기다.** 왕복을 0으로 만들어도 700ms 대에 머문다.
가상 스크롤이 이 수치의 직접적인 답이고, 그래서 이번 주 A 가 먼저다.

996 은 개발 서버와 `StrictMode` 이중 렌더 기준이며 달성으로 적지 않았다.
이번 주 재측정도 같은 조건에서 한다. 조건을 바꾸면 비교가 안 된다.

### 7주차에 미룬 의존

`@tanstack/react-virtual` 과 dnd-kit 은 이번 주에 들인다. React Router 는 여전히
넣지 않는다. 화면이 늘어나는 것은 P3 채널 화면(10주차)이다.

## 2. 이번에 만드는 것

순서가 있다. **A 를 먼저 끝내고 그 위에 B, C 를 얹는다.** 반대로 하면 드래그
좌표 계산을 두 번 짜게 된다.

### A. 가상 스크롤

세로(판매 단위)와 가로(날짜) 양방향이다. 90일이 가로 병목의 절반이라 세로만으로는
11,229개가 크게 줄지 않는다.

- 보이는 영역과 그 바깥 여유분만 렌더링한다
- 스크롤 중 헤더가 계속 붙어 있어야 한다. 좌측 목록은 가로 스크롤에, 날짜 헤더는
  세로 스크롤에 고정된다. 두 축이 동시에 움직일 때가 깨지기 쉬운 자리다
- **행 높이가 단위마다 다르다.** D 의 쌓기 규칙 때문에 그날 겹치는 예약 수에 따라
  높이가 바뀐다. 고정 높이를 전제로 짜면 D 에서 다시 뜯는다

### B. 기간 선택

셀을 드래그해 기간을 고른다. 와이어프레임에 동작이 있다.

- 여러 판매 단위에 걸친 사각 선택을 지원한다. 8.4 편집 패널이 "적용 대상"에
  단위를 여러 개 받는다
- 선택 결과를 우측 패널에 띄우되 **편집은 9주차다.** 이번 주는 무엇이 선택됐는지
  보여 주는 데까지다. 적용 버튼을 만들지 않는다
- 가상 스크롤 경계를 넘어 드래그하면 자동 스크롤된다. 이게 A 를 먼저 하는 이유다

### C. 예약 막대 드래그 이동

막대를 좌우로 끌어 날짜를 바꾼다. dnd-kit 을 쓴다.

**서버가 진실이다.** 놓는 순간 화면을 먼저 옮기되(낙관적 업데이트), 서버 응답이
오기 전까지는 확정이 아니다. 거절되면 원위치로 되돌리고 이유를 보여 준다.

거절되는 경우가 실제로 있다. 옮긴 날짜에 재고가 없으면 `chk_no_oversell` 까지
가기 전에 `InventoryService` 가 막는다. 화면만 옮겨 두고 서버 실패를 삼키면
**중복예약이 일어난 것처럼 보이는 화면**이 남는다. 이 프로젝트가 막으려는 바로 그것이다.

- 예약 날짜 변경 엔드포인트가 4주차 상태 머신에 이미 있는지 먼저 확인한다.
  있으면 그것을 쓰고 새로 만들지 않는다
- 옮길 수 있는 상태만 끈다. 취소·체크아웃된 예약은 잡히지 않아야 한다
- 숙박 일수는 유지한다. 길이를 바꾸는 것은 이번 범위가 아니다
- **키보드로도 옮길 수 있어야 한다.** 막대에 포커스를 주고 방향키로 날짜를 바꾸는
  경로를 남긴다. dnd-kit 이 키보드 센서를 제공한다. 드래그로만 되는 조작은
  마우스가 없으면 못 쓰는 기능이 된다

### D. 막대 쌓기 규칙

`totalUnits` 가 여럿인 단위에서 막대를 어떻게 놓을지다. 5절 3번이 결정이다.

- 자리 수가 아니라 **그날 실제로 겹치는 예약 수**만큼 줄을 만든다.
  4인 도미토리에 예약이 1건이면 1줄이다
- 상한은 3줄이다. 넘으면 "+N" 으로 접고, 클릭하면 그날의 목록을 띄운다
- 빈 자리 수는 셀의 `avail` 이 이미 보여 준다. 줄로 또 보여 주지 않는다

### E. 재측정

7주차와 같은 조건, 같은 데이터(30객실 × 90일)로 다시 잰다.

DOM 노드 수와 브라우저 사이클을 함께 적는다. **노드 수가 줄었는데 시간이 안 줄면
병목이 다른 데 있다는 뜻이므로 그 사실을 그대로 적는다.** 측정 전에 성과로 적지 않는다.

## 3. 이번에 만들지 않는 것

- **요금·제약 일괄 편집의 적용.** 9주차다. B 는 선택까지다
- **요금 규칙 엔진, SSE 실시간 갱신.** 9주차다
- **충돌 해소 절차.** 충돌을 만드는 경로가 P3 에 생긴다. `conflict` 는 여전히
  항상 `false` 다
- **좌측 목록 그룹.** 5절 1번
- **기간에 따라 칸 너비를 바꾸는 두 번째 모드.** 5절 2번
- **막대 길이 변경(양 끝 잡아 늘이기).** 숙박 일수 변경은 재고 계산이 다르다.
  필요해지면 그때 연다
- **React Router.** 화면이 여전히 둘이다

## 4. 지켜야 할 제약

- **낙관적 업데이트가 서버 판정을 우회하지 않는다.** 실패하면 반드시 되돌린다.
  화면과 원장이 어긋난 채 남는 상태를 만들지 않는다
- **재고 변경은 전부 `InventoryService` 를 통한다.** 프론트에서 재고를 계산해
  "옮겨도 되는지"를 미리 판단하지 않는다. 응답을 캐시에서 읽은 값으로 판단하면
  그 사이에 다른 채널 예약이 들어온 경우를 놓친다
- **모듈 경계.** 백엔드를 손대게 되면 작업지시-04 4절과 같다
- **`OwnedResources` 를 거친다.** 새 엔드포인트를 만들게 되면 조직 스코핑도 같다
- **키보드 경로.** C 의 드래그에 대응하는 키보드 조작을 남긴다
- TypeScript `strict`, 주석과 문서는 한국어, 식별자는 영어, API 응답 타입은 Zod 에서

## 5. 착수 전에 받은 결정

와이어프레임 미결 세 가지다. 7주차에 그리드에 실제 데이터를 올려 보고 정하기로
했던 것들이고, 이제 정했다.

| 항목 | 결정 |
|---|---|
| 1. 좌측 목록 그룹 | 두지 않는다. 세로 스크롤로 충분하다 |
| 2. 90일의 날짜 칸 | 고정 폭 + 가로 스크롤. 칸을 좁히는 모드를 만들지 않는다 |
| 3. 막대 쌓기 | 겹치는 예약 수만큼만. 상한 3줄, 초과는 "+N" |

### 1번의 근거

대상 사용자가 부업 개인 호스트라 판매 단위가 보통 1~5개다(계획서 2.3).
측정에 쓴 30객실은 성능 확인용 합성 데이터이지 실사용 분포가 아니다.
그룹을 두면 접기·펼치기 상태가 A 의 행 높이 계산과 섞인다.

### 2번의 근거

칸을 좁혀도 **DOM 노드 수는 그대로**라 11,229개라는 병목이 줄지 않는다.
게다가 요금(230,000)과 잔여 재고를 한 칸에 넣으려면 최소 폭이 있다.
두 가지 셀 레이아웃을 유지하는 비용만 남는다. 가로 가상 스크롤이 진짜 답이다.

### 3번의 근거

자리 수만큼 줄을 미리 나누면 8인실은 예약이 없어도 8줄이다. 행 높이가 자리 수에
비례해 늘어나고, 가상 스크롤이 다뤄야 할 높이 편차도 그만큼 커진다.
겹치는 수만큼만 만들면 대부분의 날이 1줄이고, 상한 3줄이 최악의 경우를 묶는다.

## 6. 완료 조건

1. 30객실 × 90일에서 DOM 노드 수가 7주차(11,229개)보다 유의하게 줄어드는 것을 확인
2. 세로·가로 스크롤 중 좌측 목록과 날짜 헤더가 계속 고정돼 있는지 확인
3. 행 높이가 단위마다 다른 상태에서 가상 스크롤이 어긋나지 않는지 확인하는 테스트.
   D 의 규칙 때문에 실제로 다르다
4. 기간 선택이 여러 판매 단위에 걸쳐 동작하고, 선택 범위가 우측 패널에 그대로
   나오는지 확인
5. 드래그로 화면 밖까지 끌면 자동 스크롤되는지 확인
6. 막대를 재고가 없는 날짜로 옮기면 **서버가 거절하고 막대가 원위치로 돌아오며
   이유가 표시되는** 테스트. 이번 주에서 가장 중요한 항목이다
7. 옮기기가 성공하면 재고 원장이 실제로 바뀌었는지 확인하는 테스트.
   화면만 바뀌고 끝나지 않아야 한다
8. 취소·체크아웃된 예약은 드래그로 잡히지 않는 테스트
9. 키보드만으로 막대를 옮길 수 있는지 확인
10. 4인 도미토리에 예약 1건이면 1줄, 4건이면 3줄과 "+1" 이 되는 테스트
11. 재측정. 7주차와 같은 조건에서 DOM 노드 수와 브라우저 사이클을 적는다
12. `npm run build`, `npm run test`, `./gradlew test` 통과

6번과 7번을 빠뜨리지 않는다. 낙관적 업데이트는 실패를 삼켜도 화면이 정상으로
보이고, 드러나는 것은 재고가 어긋난 뒤다. 5~6주차의 트랜잭션 경계와 같은 성질이다.

## 7. 먼저 처리할 것 — ADR 표기 정정

8주차에 들어가기 전에 한 커밋으로 끝난다. `main` 에 직접 한다.

P4 와 P5 를 맞바꾸면서(계획서 12.1, 12.2) 코드 주석과 `package-info` 는 7주차에
맞췄는데 ADR 세 곳이 남았다.

| 위치 | 지금 | 맞는 값 |
|---|---|---|
| `adr/0007-게스트-개인정보-암호화.md:109` | 조회 기록은 P5 | P4 |
| `adr/0007:127` | 마스킹·조회 기록은 P5 | P4 |
| `adr/0008-outbox-직접-구현.md:116` | 워커 셋은 P3, P5, P5 | P3, P4, P4 |

**결정과 근거 절은 손대지 않는다.** 이 세 줄은 "앞으로 여기서 다룬다"는 전방 참조라
없는 곳을 가리키고 있는 것이고, 결정 자체가 바뀐 것이 아니다. 시점 표기만 고치고
이유는 커밋 메시지에 남긴다. 작업지시 01~05 는 그때의 지시 기록이므로 손대지 않는다.
