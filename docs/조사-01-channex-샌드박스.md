# 조사 01. Channex 샌드박스 접근 조건

- 작성일: 2026-08-24
- 조사 근거: Channex 공식 문서와 요금 페이지 (하단 출처)
- 관련: 계획서 3.3, 10.3, 10.4, 부록 B 2번

---

## 1. 결론

**Channex 스테이징 서버는 무료이고, 문의나 승인 절차 없이 지금 바로 쓸 수 있다.**

계획서 10.3 은 Channex 를 "확보 난이도 높음, 최종 시연 1개월만 구독 검토"로,
10.4 는 "12주차 이후 선택적으로 문의"로 적어 두었다. 이 전제가 사실과 다르다.
가입에 영업 상담도 카드 등록도 필요 없다고 요금 페이지에 명시되어 있다.

더 중요한 것은 스테이징에서 **가짜가 아닌 연동**이 된다는 점이다. 부킹닷컴 테스트 숙소가
미리 준비되어 있고, 에어비앤비는 실제 호스트 계정을 연결한다. 부록 B 2번
("iCal·Channex·Mock 조합이 실제 연동으로 인정되는가")의 답을 준비하는 재료가 달라진다.

## 2. 접근 조건

| 항목 | 내용 |
|---|---|
| 스테이징 주소 | `staging.channex.io` |
| 비용 | 무료 |
| 카드 등록 | 불필요 |
| 영업 상담 | 불필요 |
| API 키 | 조직 페이지에서 직접 발급. 스테이징은 구독 없이 모든 사용자에게 열려 있다 |
| 인증 방식 | `user-api-key` 헤더. 만료 시각이 문서에 없다 |
| 키 범위 | 숙소 단위로 제한 가능. 발급 시 한 번만 보이므로 그때 저장해야 한다 |

프로덕션 API 키는 유료 구독이 있어야 발급되지만, 스테이징은 예외라고 문서가 명시한다.

## 3. 스테이징에서 실제로 무엇이 되는가

이 부분이 이번 조사의 핵심이다.

**부킹닷컴.** 커뮤니티 공용 테스트 숙소가 여러 개 준비되어 있다. 별도 승인이 필요 없고
연결하면 바로 쓴다. 통화가 다른 숙소가 GBP, EUR, USD, JPY 로 나뉘어 있으며 요금제 통화를
숙소와 맞춰야 매핑이 된다. 객실만 매핑하고 요금제를 빠뜨리면 채널이 활성화되지 않는다.
익스트라넷 접근은 없고 API 로만 다룬다. 공용이라 "Channel Already Exists" 가 나면 다른
숙소 식별자를 쓰라고 안내한다.

계획서 10.3 이 부킹닷컴 공식 연동을 "파트너 승인 수개월, 확보 난이도 매우 높음"으로
분류했는데, Channex 를 경유하면 그 관문을 지나지 않고 부킹닷컴 쪽 실제 테스트 숙소에
ARI 를 밀어 넣을 수 있다.

**에어비앤비.** 별도의 샌드박스 계정이 없다. 실제 호스트 계정을 스테이징에 연결하는
방식이다. 문서가 가짜 리스팅 생성을 경고한다(계정이 차단될 수 있다). 권장 흐름은
연결 → 설정 확인 → 매핑 → 활성화 → 예약·메시지 테스트 → 매핑 해제다.

이건 계획서 부록 A 의 "에어비앤비 호스트 계정 개설, 비공개 테스트 리스팅 확보" 항목과
같은 전제 위에 있다. 그 항목이 아직 체크되지 않았다면 iCal 경로와 Channex 경로가
동시에 막힌다. **P3 이전에 처리해야 할 선행 조건이다.**

## 4. 프로덕션 요금 (참고)

지금 필요한 정보는 아니지만 최종 시연에서 프로덕션을 쓸지 판단할 때 쓴다.

- 플랫폼 요금 월 $130
- 숙소당 요금은 채널이 활성화된 숙소에만 부과. 호텔 $7, 휴가용 임대 유닛당 $0.50
- 셋업 비용 없음, 인증 비용 없음, 예약 수수료 없음
- 계약 최소 기간 없음. 30일 전 통지로 해지
- 월초 선불, 첫 달은 일할 계산
- 별도 계약이나 보안 검토를 요구하면 $1,500

계획서 10.3 의 "월 $130 + 유닛당 $0.5" 는 정확하다. 다만 **프로덕션에 가려면 인증
절차를 통과해야 하고, 그 인증은 스테이징에서 수행한다.** 구독만 하면 되는 구조가 아니다.

## 5. 프로덕션 인증 절차 — P3 검증 시나리오로 쓸 수 있다

프로덕션 전환에는 자가 인증 14개 항목 통과가 필요하다. 화면 공유 세션도 포함된다.
프로덕션에 가지 않더라도 **이 목록 자체가 P3 의 완료 조건으로 쓸 만하다.**
외부 기관이 정한 기준이라 자체 기준보다 심사에서 방어하기 쉽다.

1. 전체 동기화 — 전 객실·요금제의 500일치 재고·요금·제약을 API 호출 2회로 전송
2. 단일 날짜 단일 요금 변경
3. 단일 날짜 복수 요금 — 3개 조합을 호출 1회로
4. 복수 날짜 복수 요금 — 기간 묶음을 호출 1회로
5. 최소 숙박일 제약을 호출 1회로
6. 판매 중지 플래그를 호출 1회로
7. 복합 제약 — 도착 불가, 최대 숙박 등을 호출 1회로
8. 6개월치 요금·제약을 호출 1회로
9. 단일 날짜 재고 변경
10. 복수 날짜 재고 변경
11. 예약 수신·수정·취소와 수신 확인 응답
12. 레이트 리밋 준수 — 큐와 묶음 전송이 분당 20 ARI 를 넘지 않음
13. 델타 전송 — 전체 재동기화 타이머가 아니라 변경이 전송을 유발함
14. 지원 기능 선언 설문

12번과 13번이 특히 이 프로젝트와 맞는다. 계획서 6.5 의 ARI 병합 버퍼와 6.6 의
정기 재동기화가 정확히 이 두 항목을 겨냥한 설계다.

## 6. 기존 설계와의 대조

CLAUDE.md 채널 연동 절의 서술을 문서와 맞춰 봤다.

| 기존 서술 | 문서 확인 결과 |
|---|---|
| "숙소당 분당 10회 제한" | 절반만 맞다. 제약·요금 10회 **와** 재고 10회로 나뉘어 합계 20회다 |
| "6초 윈도로 모아 보낸다" | 문서가 권고하는 값과 같다. 우연이 아니라 맞는 선택이다 |
| "연속된 같은 값을 날짜 구간으로 압축" | 인증 항목 3·4·8 이 요구하는 동작과 일치한다 |
| "30일 일괄 변경이 호출 한 번으로" | 인증 항목 8 은 6개월치를 호출 1회로 요구한다. 기준이 더 세다 |

초과하면 429 와 함께 "Too Many Requests" 오류 객체가 온다. 문서는 해당 숙소의 전송을
1분 멈춘 뒤 지수 백오프로 재시도할 것을 권한다. 요청 본문은 10MB 까지 받는다.

**두 가지를 고쳐야 한다.** CLAUDE.md 의 "분당 10회"를 "제약·요금 10회, 재고 10회,
합계 20회"로 바꾸고, 압축 목표를 30일이 아니라 6개월로 올린다. 후자는 P3 착수 전까지
결정하면 된다.

## 7. 부록 B 2번에 대한 함의

교수에게 물을 항목은 "iCal·Channex·Mock 조합이 실제 연동으로 인정되는가"였다.
조사 전에는 Channex 를 쓸 수 있을지조차 불확실해 질문이 공허했다. 지금은 다르다.

말할 수 있게 된 것.

- Channex 스테이징을 통해 **부킹닷컴 쪽 실제 테스트 숙소에 ARI 를 전송하고 예약을
  수신**할 수 있다. Mock 이 아니다
- 에어비앤비는 iCal 과 Channex 두 경로 모두 **실제 리스팅**에 붙는다
- Channex 가 정한 14개 인증 항목을 통과하면 "이 구현이 상용 채널 매니저의 연동 기준을
  충족한다"는 외부 근거가 생긴다
- 필요하면 최종 시연 한 달만 프로덕션을 구독하는 선택지도 남아 있다(월 $130, 최소 계약 없음)

남는 위험은 Channex 가 아니라 **에어비앤비 호스트 계정**이다. 실제 리스팅이 없으면
iCal 경로(계획서 P3 완료 조건 3번)와 Channex 에어비앤비 연결이 함께 막힌다.
가짜 리스팅은 문서가 명시적으로 경고한다.

## 8. 제안하는 다음 행동

1. **지금** — `staging.channex.io` 에 가입하고 API 키를 발급받는다. 무료이고 즉시 된다.
   P3 는 10월 하순이지만, 접근이 실제로 되는지 확인해 두면 위험 하나가 사라진다
2. **P3 전** — 에어비앤비 호스트 계정과 비공개 리스팅을 확보한다. 부록 A 의 미완 항목이며
   이제 두 경로의 공통 선행 조건임이 분명해졌다
3. **보고 자료 반영** — 부록 B 2번을 물을 때 위 사실을 함께 제시한다
4. **문서 수정** — 계획서 10.3 의 Channex 난이도와 10.4 의 "12주차 이후 문의"를 고친다.
   CLAUDE.md 의 레이트 리밋 서술도 함께 고친다

1번과 2번은 사람이 해야 하는 일이고, 3번과 4번은 이 세션에서 할 수 있다.
