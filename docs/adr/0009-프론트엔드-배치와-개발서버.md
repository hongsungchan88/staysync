# ADR 0009. 프론트엔드는 같은 저장소에 두고 개발 서버는 프록시로 같은 출처를 만든다

- 날짜: 2026-09-03
- 상태: 채택
- 관련: 계획서 11.2 / 11.4, ADR 0004, ADR 0005, ADR 0006, 작업지시 04 (5절 1·3번)

## 맥락

P2 7주차에 React 프로젝트를 처음 세운다. P1 까지는 백엔드 한 덩어리였다.

정할 것이 세 가지다. **어디에 둘 것인가**, **개발 서버를 어떻게 붙일 것인가**,
**토큰을 어디에 보관할 것인가**. 셋째가 특히 중요하다. P1 에서 리프레시 토큰을
`HttpOnly` 쿠키로 감춘 결정(ADR 0006)이 프론트엔드 쪽에서 쉽게 무너질 수 있다.

## 검토한 선택지

### 배치

**계획서 11.4 대로 `backend/` 와 `frontend/` 를 형제로.** 문서와 구조가 맞는다.
그러나 실제 저장소는 백엔드가 `staysync/src/` 에 바로 있고, 옮기려면 Gradle 설정과
경로, wrapper, `resetLocalDb` 의 데이터 디렉터리, CI 가 전부 따라 움직인다.
7주차 예산을 거기에 쓰는 것은 얻는 것에 비해 비싸다.

**별도 저장소.** 배포를 따로 가져갈 수 있다. 1인 개발에서 저장소가 둘이면 API 를
바꿀 때 두 곳에 커밋하고 순서를 맞춰야 한다. 지금 단계에서 얻을 것이 없다.

### 개발 서버

**프론트 5173, 백엔드 8080 을 그대로 두고 CORS 를 연다.** 설정이 한 줄이다.
그러나 **리프레시 토큰이 실리지 않는다.** ADR 0006 이 쿠키를 `SameSite=Strict` 로
정했기 때문에 출처가 다르면 갱신 요청에 쿠키가 붙지 않는다. CORS 를 열어도 이건
해결되지 않는다. `SameSite` 는 CORS 와 다른 층의 규칙이다.

`SameSite=Lax` 로 낮추면 실리지만, 그건 개발 편의를 위해 운영의 CSRF 방어를 깎는
것이다. 개발과 운영이 다른 설정으로 돌면 개발에서 통과한 것이 운영에서 깨진다.

### 토큰 보관

**`localStorage`.** 새로고침해도 남는다. 그러나 자바스크립트가 읽을 수 있는 곳에
액세스 토큰을 두면 XSS 하나로 30분치가 통째로 나간다. 리프레시를 `HttpOnly` 로 감춘
의미가 없어진다. 공격자가 리프레시를 못 읽어도 액세스 토큰만으로 충분한 시간을 쓴다.

**`sessionStorage`.** 탭을 닫으면 사라지지만 자바스크립트가 읽는 것은 같다. XSS 앞에서
`localStorage` 와 다르지 않다.

## 결정

**1. `staysync/frontend/` 를 추가하고 백엔드는 `staysync/src/` 에 그대로 둔다.**

계획서 11.4 를 실제 구조에 맞게 고쳤다. **문서를 코드에 맞추는 방향이다.** 코드를
문서에 맞추는 것이 원칙적으로는 맞지만, 이 경우 얻는 것이 문서와의 일치뿐이고
치르는 것은 빌드 설정 전체의 이동이다.

**2. Vite 개발 서버(5173)가 `/api` 만 8080 으로 프록시한다.**

브라우저가 보는 출처가 5173 하나가 된다. `SameSite=Strict` 쿠키가 그대로 실리고,
운영과 같은 설정으로 개발할 수 있다. 쿠키 `Path` 가 `/api/auth` 인 것도 프록시
경로와 자연스럽게 맞는다.

이 결정이 없으면 **로그인은 되는데 새로고침하면 풀리는** 증상이 나온다. 원인이
쿠키 정책에 있어 찾기 어렵다.

**3. 액세스 토큰은 메모리에만 둔다.**

Zustand 스토어에 담고 어디에도 영속하지 않는다. 대가는 새로고침하면 사라진다는
것이고, 그건 **앱이 뜰 때 갱신을 한 번 호출해 복구**한다. 쿠키는 브라우저가 들고
있으므로 그것으로 새 액세스 토큰을 받는다.

### 갱신은 한 번만 나가야 한다

이 결정에 딸린 제약이다. 리프레시 토큰은 갱신할 때마다 회전한다(ADR 0005).
액세스 토큰이 만료된 순간 화면에서 요청 셋이 동시에 나가면 셋 다 401 을 받고 셋 다
갱신을 시도하는데, 첫 번째가 토큰을 교체한 뒤 두 번째가 **이미 교체된 토큰**을
들고 간다. 서버는 그걸 재사용으로 판정해 **그 사용자의 토큰을 전부 무효화한다.**

증상은 "멀쩡히 쓰다가 갑자기 로그아웃"이고, 요청이 겹칠 때만 나므로 재현이 어렵다.
그래서 진행 중인 갱신 약속을 하나만 두고 나머지는 그것을 기다린다. 401 재시도는
**한 번뿐**이며, 그것도 실패하면 로그인으로 보낸다. 두 번 이상 재시도하면 죽은
토큰으로 서버를 계속 두드리는 것이 된다.

이 계약이 깨져도 정상 경로에서는 아무 증상이 없다. 그래서 동시에 401 을 받은
요청 셋으로 갱신이 한 번만 나가는지 확인하는 테스트를 두었다(`client.test.ts`).

## 근거

세 결정이 하나의 사슬이다. 리프레시를 쿠키로 감췄으니(ADR 0006) 출처가 같아야 하고,
출처를 같게 만들려니 프록시가 필요하며, 쿠키를 감춘 이유를 지키려니 액세스 토큰도
자바스크립트가 읽는 저장소에 두면 안 된다. 하나를 편하게 바꾸면 나머지가 무의미해진다.

## 결과

- 개발자는 서버 둘을 띄운다. 백엔드 `./gradlew bootRun`, 프론트 `npm run dev`.
  프론트만 띄우면 API 요청이 전부 실패한다
- 새로고침할 때마다 갱신 요청이 한 번 나간다. 리프레시 토큰이 그만큼 자주 회전하므로
  `refresh_token` 행이 개발 중에 빠르게 는다. 정리 배치가 지운다(ADR 0005)
- 운영 배포에서는 프록시가 아니라 리버스 프록시나 같은 도메인 서빙으로 출처를
  맞춰야 한다. 정적 파일과 API 가 다른 출처면 같은 문제가 그대로 돌아온다. P6 에서 정한다
- `shadcn/ui` 는 CLI 로 생성하지 않고 필요한 컴포넌트(버튼, 입력)만 같은 구조로 직접
  두었다. Radix 프리미티브는 쓰는 컴포넌트가 생길 때 들인다. 쓰지 않는 의존을 미리
  넣지 않는다는 규칙을 따른다
- React Router 는 아직 끼우지 않았다. 화면이 로그인과 캘린더 둘이고 인증 여부로만
  갈린다. 예약 목록과 인박스가 생기는 시점에 넣는다
- Vitest 는 3 을 쓴다. 2 는 자체 Vite 5 를 물고 있어 프로젝트의 Vite 6 과 타입이
  충돌한다
