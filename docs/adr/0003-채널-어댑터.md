# ADR 0003. 채널 연동은 어댑터 인터페이스 뒤에 감춘다

- 날짜: 2026-08-21
- 상태: 채택
- 관련: 계획서 3.3, 6.1

## 맥락

에어비앤비와 부킹닷컴의 공식 파트너 API는 심사에 수개월에서 1년이 걸리고, 사실상
엔터프라이즈 사업자에게만 열린다. 23주 안에 확보할 수 없다.

쓸 수 있는 것은 세 가지다. iCal은 승인 없이 바로 쓸 수 있지만 날짜만 오가고 지연이
크다. Channex 같은 화이트라벨 API는 요금까지 보낼 수 있지만 유료다. 자체 시뮬레이터는
공짜지만 진짜가 아니다.

## 결정

셋을 모두 쓰되 `ChannelAdapter` 인터페이스 하나 뒤에 감춘다. 도메인 로직은 어떤
채널과 이야기하는지 알지 못한다.

어댑터는 자신이 지원하는 기능을 `capabilities()`로 알린다. iCal 어댑터는
`PUSH_RATE`를 지원하지 않으므로, 사용자가 요금을 바꿔도 그 채널에는 전파 작업을
만들지 않고 화면에 지원하지 않는다는 표시만 남긴다.

## 근거

이 구조의 의미는 특정 OTA와 연동했다는 데 있지 않다. OTA 연동이라는 문제를 푸는 구조를
만들고, 그 구조가 서로 다른 세 종류의 프로토콜에서 동작함을 확인하는 데 있다.

폴링형(iCal), 푸시형(Channex REST + 웹훅), 장애 주입형(Mock)은 실패 양상이 서로 다르다.
세 가지를 모두 견디는 인터페이스라면 나중에 에어비앤비 공식 API가 열렸을 때
구현 클래스 하나만 추가하면 된다.

Mock 시뮬레이터의 역할이 특히 크다. iCal은 요금을 동기화하지 못하고 Channex는 유료
계정이 필요하므로, 두 방식으로는 검증할 수 없는 조건이 남는다. 지연, 실패, 중복 전송,
순서 역전, 동시 예약을 의도적으로 주입해야 재시도와 멱등성 로직을 정량적으로 검증할 수
있다.

## 결과

- 새 채널을 붙일 때 도메인 로직은 건드리지 않는다
- 기능 협상이 런타임에 일어나므로 채널마다 지원 범위가 달라도 화면이 깨지지 않는다
- 예약 수신은 `(channel_code, channel_booking_id)` 유니크 제약으로 멱등성을 보장한다
- 예약 수정은 `revision` 비교로 순서 역전을 방어한다. 낮은 버전이 나중에 도착하면 무시한다
- **`overbooking_conflict` 기록은 예약 수신 트랜잭션과 분리한다.** OTA 예약은 재고가
  없어도 받아들이고 충돌로 기록하는데(ADR 0002 4계층), 기록과 예외 던지기가 같은
  트랜잭션에 있으면 롤백이 기록까지 되돌려 운영자가 해소할 근거가 사라진다. P1 의
  리프레시 토큰 재사용 탐지에서 실제로 겪은 결함과 같은 모양이며, 해법과 검증 방법은
  ADR 0005 의 "무효화는 갱신 트랜잭션과 분리해야 한다" 항목에 적어 두었다
