# ADR 0013. 버전이 없는 채널은 값이 다르면 수정으로 본다

- 상태: 확정
- 결정일: 2026-09-05
- 범위: P3 13주차
- 관련: 계획서 3.4 / 6.2 / 13.2 / 13.4, ADR 0003·0007·0012, 조사-02, 작업지시 10

## 맥락

iCal 어댑터가 붙으면서 레지스트리에 성격이 다른 채널이 처음 들어왔다.
Mock 과 Channex 는 예약마다 수정 버전(`revision`)을 주고 취소를 상태로 알려 주지만,
**iCal 에는 둘 다 없다.**

`BookingIngestService`(계획서 13.2)는 `in.revision() > 기존` 으로 **크기를 비교한다.**
낮은 버전이 나중에 도착하면 무시해 순서 역전을 막는 장치다. iCal 에는 넣을 값이
없으므로 계획서 13.4 의 스케치는 이렇게 대신했다.

```java
.revision(hashOf(start, end, summary))   // iCal에는 revision이 없다
```

**해시에는 순서가 없다.** 같은 예약의 날짜가 9월 3일에서 9월 10일로 바뀌었을 때 새
해시가 옛 해시보다 작을 확률이 절반이고, 그때 수정이 무시된다.

증상이 없다는 것이 이 결함의 성질이다. 예약은 그대로 있고, 로그도 깨끗하고, 캘린더도
정상으로 보인다. **드러나는 것은 체크인 날 게스트가 다른 날짜를 들고 왔을 때다.**

같은 문서가 예약과 차단의 구분도 스케치했다.

```java
.guestName(extractGuestName(summary))
.isBlock(isBlockKeyword(summary))
```

조사-02 가 실제 에어비앤비 발행물을 받아 확인한 결과 `SUMMARY` 는
`Airbnb (Not available)` 하나뿐이었다. 게스트 이름도 없고, 예약인지 차단인지도 그
문자열로는 구분되지 않는다. 계획서 3.4 가 적은 iCal 의 구조적 한계 그대로다.

## 검토한 선택지

### 해시를 버전 자리에 그대로 쓰기 (계획서 13.4)

**기각했다.** 위의 이유다. 수정이 절반의 확률로 조용히 사라진다.

### 해시 대신 단조 증가하는 값 만들기

수신할 때마다 기존 값 + 1 을 넣는 방법을 봤다. **기각했다.** 값이 그대로여도 매 폴링이
수정으로 판정돼 15분마다 `outbox_event` 와 `audit_log` 가 한 줄씩 쌓인다. iCal 발행물은
바뀌지 않아도 계속 오는 것이 정상이라, 실제로 바뀐 것과 그냥 다시 온 것을 구분하지
못하면 이벤트가 무의미해진다. 채널 전파도 함께 도는 것이 더 나쁘다.

### 채널 종류로 분기하기

수신부에서 `adapterType == ICAL` 이면 다르게 다루는 방법. **기각했다.** 도메인 로직이
어떤 채널과 이야기하는지 몰라야 한다는 것이 ADR 0003 의 요점이고, 그 분기가 생기면
Channex 어댑터가 붙을 때 또 하나가 는다.

### 키워드로 예약과 차단 나누기 (계획서 13.4)

**기각했다.** 우리가 가진 실제 샘플로는 어느 쪽도 확인되지 않는다. **검증할 수 없는
코드**가 되고, 검증할 수 없으면 틀렸을 때 알 방법도 없다. 재고를 막는다는 점에서 둘은
같으므로 나눌 이유도 크지 않다.

## 결정

**하나. `revision` 을 `Integer` 로 두고 `null` 을 "이 채널에는 버전이 없다"로 읽는다.**

`InboundBooking.revision` 과 `ChannelBookingCommand.revision` 이 `Integer` 다.
`null` 이면 `ChannelBookingWriter` 가 크기 비교 대신 `Reservation.applyValues` 를
부른다 — 날짜나 금액이 실제로 달라졌을 때만 반영하고, 그대로면 아무것도 하지 않는다.

순서 역전을 걱정하지 않아도 되는 이유는 **스냅샷이기 때문**이다. iCal 은 매번 전 기간을
통째로 받으므로 "옛 값이 늦게 도착"하는 일이 없다. 마지막으로 받은 것이 곧 현재다.

**둘. 예약과 차단을 구분하지 않는다.** 전부 예약으로 받고 게스트 정보는 비운다.
`InboundBooking.isBlock` 을 지웠다 — 아무도 참을 넣지 않는 필드가 남아 있으면 언젠가
누군가 넣고, 그때 그 예약들이 조용히 사라진다.

**셋. 스냅샷 채널을 `Capability.SNAPSHOT_BOOKING` 으로 선언한다.** iCal 에는 취소
통지가 없고 발행물에서 `VEVENT` 가 사라지는 것이 취소다. 이 선언이 있는 채널만
"목록에 없는 예약을 취소"한다. Mock 과 Channex 에 켜지면 **아직 목록에 나타나지 않은
예약이 취소된다.**

## 근거

세 결정의 판별 기준이 하나다 — **틀렸을 때 증상이 있는가.**

해시 크기 비교는 틀려도 증상이 없다. 키워드 분류도 틀려도 증상이 없다(우리 샘플로는
확인이 안 된다). 스냅샷 여부를 잘못 켜는 것도 증상이 없다 — 취소가 반영되지 않거나
반영되지 말아야 할 취소가 반영되는데, 로그는 양쪽 다 정상이다.

이 프로젝트에서 반복된 모양이다. `DTEND` 배타성, `AdapterType` 의 기능 선언,
`NOT EXISTS` 순서 보장이 전부 "틀려도 화면은 정상"이었다. 그래서 셋 다 기계가 확인하게
두었다 — `AdapterContractTest` 가 선언과 구현의 어긋남을, `IcalFeedTest` 가 수정·취소
판정을, `IcalParserTest` 가 실제 발행물의 `DTEND` 를 본다.

## 결과

- `InboundBooking` 에서 `isBlock` 이 사라졌고 `revision` 이 `Integer` 가 됐다.
  `MockOtaAdapter` 는 그대로 정수를 싣는다 — 시뮬레이터가 버전을 주기 때문이다.
- `ChannelBookingWriter.applyToExisting` 의 감사 기록에서 `Map.of` 를 걷어냈다.
  `Map.of` 는 `null` 을 거부하므로 버전 없는 채널의 수신이 통째로 NPE 로 실패했다.
  폴링이 그 예외를 잡아 로그만 남기므로 **예약이 조용히 갱신되지 않았다.**
  13주차 테스트에서 실제로 걸렸다.
- `Capability.WEBHOOK_BOOKING` 을 `AdapterType.MOCK` 에서 뺐다. 10주차부터 적혀
  있었지만 `parseWebhook` 을 구현한 어댑터도 웹훅 엔드포인트도 없다. 12주차와 반대
  방향의 어긋남이고(선언이 실제보다 <b>넓다</b>) `AdapterContractTest` 가 잡았다.
  화면이 "예약 웹훅 지원"이라고 보여 주는데 실제로는 아무것도 받지 못하던 상태였다.
- `ChannelAdapter.exportCalendar` 를 지웠다. iCal 발행은 우리가 채널을 부르는 일이
  아니라 채널이 읽어 가는 공개 URL 이라 어댑터에 자리가 없다. 아무도 부르지 않는
  기본 구현은 선언과 실제가 어긋나는 자리를 하나 더 만든다.
- 기본 구현이 빈 값 대신 예외가 됐다. 조용한 빈 값은 "지원하지 않음"과 "예약이 없음"이
  구분되지 않고, 그게 12주차 `MOCK` 결함의 모양이었다.
