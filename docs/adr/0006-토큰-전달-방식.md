# ADR 0006. 액세스 토큰은 응답 본문, 리프레시 토큰은 HttpOnly 쿠키로 보낸다

- 날짜: 2026-08-24
- 상태: 채택
- 관련: ADR 0004, ADR 0005, 계획서 15.1, 작업지시 01 (5절 1번)

## 맥락

두 토큰을 브라우저에 어떻게 전달할지 정해야 한다. P2 에 React 프론트엔드가 붙으면
되돌리기 어려운 결정이 된다.

두 토큰의 성질이 다르다. 액세스 토큰은 30분짜리이고 모든 API 요청의
`Authorization` 헤더에 실린다. 리프레시 토큰은 14일짜리이고 갱신 요청에서만 쓰인다.

## 검토한 선택지

**둘 다 응답 본문.** 가장 단순하다. 클라이언트가 두 토큰을 모두 받아 알아서 보관한다.
그러나 14일짜리 리프레시 토큰을 자바스크립트가 읽을 수 있는 곳에 두게 된다.
`localStorage` 에 넣으면 XSS 한 번에 2주치 접근 권한이 통째로 넘어간다. 메모리에만 두면
새로고침할 때마다 로그인해야 한다. **기각.**

**둘 다 쿠키.** 자바스크립트가 어느 토큰도 읽지 못한다. 그러나 액세스 토큰까지 쿠키에
넣으면 모든 API 요청에 쿠키가 자동으로 실려 CSRF 방어를 따로 갖춰야 한다. ADR 0004 가
"세션 쿠키를 쓰지 않으므로 CSRF 공격 경로가 없다"며 CSRF 보호를 끈 근거가 무너진다.
토큰 기반 API 로 만든 이점을 스스로 없애는 선택이다. **기각.**

## 결정

**액세스 토큰은 응답 본문 JSON 으로, 리프레시 토큰은 `Set-Cookie` 로 보낸다.**

근거는 두 토큰의 위험도와 쓰임새가 다르다는 것이다. 액세스 토큰은 30분짜리이고
`Authorization` 헤더에 직접 실어야 하므로 자바스크립트가 읽을 수 있어야 한다. 리프레시
토큰은 14일짜리인데 갱신 요청에서만 쓰이므로 자바스크립트가 읽을 이유가 없다.
**읽을 이유가 없는 것은 읽히지 않게 한다.**

쿠키 속성은 다음과 같다.

```
HttpOnly; Secure; SameSite=Strict; Path=/api/auth; Max-Age=1209600
```

- **`HttpOnly`** — 자바스크립트가 읽지 못한다. XSS 가 나도 리프레시 토큰은 새어 나가지
  않는다. 이 결정의 핵심이다
- **`SameSite=Strict`** — 다른 출처에서 시작된 요청에는 실리지 않는다. 갱신 엔드포인트를
  겨냥한 CSRF 경로를 막는다
- **`Path=/api/auth`** — 쿠키가 실려 나가는 요청을 최소한으로 줄인다. 숙소 조회나 예약
  같은 대부분의 API 호출에는 아예 붙지 않는다
- **`Max-Age`** — 리프레시 토큰 수명과 같은 14일. 쿠키가 먼저 사라지면 아직 살아 있는
  토큰을 쓸 수 없고, 나중까지 남으면 만료된 토큰을 계속 보내게 된다

### `Path` 를 `/api/auth/refresh` 가 아니라 `/api/auth` 로 넓힌 이유

갱신만 생각하면 `/api/auth/refresh` 로 더 좁힐 수 있다. 그러나 로그아웃도 이 쿠키를
읽어 해당 토큰을 무효화해야 한다. 로그아웃을 갱신 경로 아래로 옮기는 방법도 있지만
경로 이름이 하는 일과 어긋난다. 한 단계 넓혀 두 엔드포인트를 포함시키는 쪽을 택했다.

`/api/auth` 아래에는 가입과 로그인도 있어 그 두 요청에도 쿠키가 실린다. 이미 인증을
마친 클라이언트가 다시 로그인하는 드문 경우이며, 서버는 그 쿠키를 읽지 않는다.

### local 프로파일에서 `Secure` 를 끈다

HTTPS 가 아니면 브라우저가 `Secure` 쿠키를 저장하지 않는다. 그대로 두면 로그인은
되는데 갱신이 되지 않는 상태가 되어 개발이 막힌다. `staysync.security.cookie.secure` 로
갈라 두고 **운영 기본값은 켜 둔다**. 값을 지정하지 않으면 켜진 쪽이 된다.

## 근거

두 토큰을 같은 방식으로 다루면 둘 중 하나는 반드시 과하거나 부족해진다. 액세스 토큰에
쿠키의 제약을 씌우면 CSRF 방어가 따라붙고, 리프레시 토큰을 본문으로 내보내면 14일치
접근 권한이 자바스크립트에 노출된다. 성질이 다른 둘을 다르게 다루는 편이 각각에 맞는
최소 권한이 된다.

## 결과

- P2 프론트엔드가 제약을 이어받는다. Vite 개발 서버에서 쿠키가 붙으려면 프록시로 같은
  출처를 만들어야 한다. `SameSite=Strict` 라 다른 출처에서는 실리지 않는다
- 갱신 요청은 `credentials: 'include'` 가 필요하다
- 액세스 토큰은 메모리에 둔다. 새로고침하면 쿠키로 갱신해 다시 받는 흐름이 된다
- 로그아웃 응답은 같은 이름·경로에 `Max-Age=0` 을 실어 쿠키를 덮어쓴다. 속성이 하나라도
  다르면 브라우저가 다른 쿠키로 보고 기존 것을 남겨 둔다
- MockMvc 의 `Cookie` 객체는 `SameSite` 를 표현하지 못한다. 속성 검증은 `Set-Cookie`
  원본 헤더 문자열을 직접 확인해야 한다. 그러지 않으면 속성이 빠져도 아무 테스트도
  실패하지 않는다
