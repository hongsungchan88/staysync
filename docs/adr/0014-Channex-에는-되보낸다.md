# ADR 0014. Channex 에는 원 채널이어도 재고를 되보낸다

- 상태: 확정
- 결정일: 2026-09-22
- 범위: P5 작업지시-17 브랜치 3 (`AdapterType.CHANNEX` 한정)
- 관련: 계획서 6.5, ADR 0012·0013, 확인-10 3.3, 작업지시-17 8.3

## 맥락

P3 12주차에 정했다 — **예약을 만든 채널 자신에게는 재고를 되보내지 않는다.** 계획서 6.5
수신 경로의 5번이 "**다른** 채널로 재고 차감 전파"인 이유이고, 근거는 OTA 의 성질이다:
OTA 는 자기가 판 예약만큼 자기 재고를 스스로 깎는다. 되보내면 낭비이고, 채널에 따라서는
되울림이 된다. `ChannelSyncService.propagate` 가 이벤트 페이로드의 `channelCode` 와 연결의
채널 코드를 견줘 거른다.

**Channex 는 OTA 가 아니다.** 부킹닷컴·에어비앤비 앞에 서는 채널 매니저이고, 우리 원장을
그쪽에 비추는 거울이다. 그 차이가 재고를 스스로 움직이는 범위에서 드러난다.

## 실측 (확인-10 3.3, 2026-09-22)

Booking CRS 로 만든 예약 하나(11-10~12, 우리 시험 숙소)로 생성 → 변경(3박) → 취소를
돌리고 Channex 의 `GET /restrictions` 로 매번 되읽었다.

| 한 일 | Channex 재고 |
|---|---|
| 생성 | 11-10·11 이 **0 으로 내려갔다** — Channex 가 스스로 줄인다 |
| 변경(11-12 추가) | 11-12 는 **1 그대로** |
| 취소 | 11-10·11 이 **0 으로 남았다** |

숙소 설정이 그렇게 되어 있다 — `allow_availability_autoupdate_on_confirmation: true`,
`allow_availability_autoupdate_on_modification: false`,
`allow_availability_autoupdate_on_cancellation: false` (Channex 숙소 생성 시 기본값).

즉 **취소된 날이 채널에 0 으로 남아 부킹닷컴이 계속 닫혀 있다.** 우리 캘린더는 1 이고 로그도
깨끗하다. 증상이 우리 쪽에 없는 모양이고, 드러나는 것은 "왜 부킹닷컴에서 안 팔리지"를
호스트가 묻는 날이다. 하루 한 번 재동기화(새벽 4시, 180일)가 결국 맞추지만 그때까지
최대 24시간 닫혀 있다.

## 검토한 선택지

1. **숙소 설정을 `true` 로 바꾼다.** Channex 가 변경·취소에도 스스로 재고를 움직이게 한다.
   우리 코드는 그대로다. 그러나 그 설정은 **호스트의 Channex 계정에 있다** — 제품이 남의
   계정 설정에 기대게 되고, 연결할 때마다 사람이 맞춰야 하며, 틀리면 위와 같이 조용히
   틀린다. 우리가 보증할 수 없는 자리다.
2. **재동기화에 맡긴다.** 이미 있는 장치이고 코드가 늘지 않는다. 대신 최대 24시간 동안
   팔 수 있는 날이 닫혀 있다. 이 제품의 존재 이유가 "한쪽에서 팔리면 나머지가 닫힌다"의
   반대 방향까지 포함하는 것이라 받아들일 수 없다.
3. **Channex 에는 원 채널이어도 되보낸다.** 아래.

## 결정

**`adapterType == CHANNEX` 인 연결에는 원 채널 필터를 적용하지 않는다.** 그 연결이 만든
예약이라도 재고 변경을 그대로 보낸다. iCal·Mock 은 12주차 결정 그대로다.

```java
if (originChannel != null && originChannel.equals(connection.getChannelCode())
        && connection.getAdapterType() != AdapterType.CHANNEX) {
    continue;
}
```

## 근거

- **Channex 는 거울이지 판매자가 아니다.** 12주차 결정의 전제("OTA 는 자기 예약을 스스로
  깎는다")가 이 어댑터에는 절반만 성립한다 — 생성 때만 성립하고 변경·취소에는 성립하지
  않는다. 전제가 깨진 자리에서만 예외를 둔다.
- **되울림이 생기지 않는다.** 우리가 보내는 것은 재고 숫자이고, Channex 는 그걸 받아도
  예약을 만들지 않는다. 되울림은 예약이 채널을 왕복할 때의 이야기다.
- **범위가 어댑터 종류 하나로 좁다.** iCal 연결에는 닿지 않는다 — 업체 실데이터가 그쪽에
  있다.

## 결과

- 대가는 **요청 하나**다. 같은 값을 한 번 더 보낸다(생성 직후 재고는 Channex 가 이미
  줄여 둔 값과 같다). 병합 버퍼가 6초 창으로 묶으므로 예약 하나에 요청 하나다.
- 실측: 고친 뒤 두 번째 주기에서 **취소 69초 뒤 Channex 재고가 1 로 돌아왔다**
  (폴링 60초 + 버퍼 6초 + 워커).
- `ChannexBookingFeedTest.취소된_재고는_Channex_로_돌아간다` 가 이 경로를 고정한다 —
  취소 뒤 스텁이 받은 `/availability` 본문의 `availability` 가 1 이고 기간이 체크인~마지막
  밤인지 본다.
- **뒤집을 조건**: 호스트의 Channex 숙소 설정에서
  `allow_availability_autoupdate_on_modification`·`_on_cancellation` 이 `true` 가 되면 이
  예외가 필요 없어진다(같은 값을 두 번 보내는 것이 된다). 상용 연결에서 그 설정을 우리가
  제어하게 되는 날 다시 본다. 그때까지는 설정이 어느 쪽이든 결과가 맞는 이 방향이 안전하다.
