# ADR 0002. 재고 잠금은 네 계층으로 방어한다

- 날짜: 2026-08-21
- 상태: 채택
- 관련: 계획서 7장

## 맥락

여러 채널에서 동시에 예약이 들어온다. 남은 방이 하나인데 두 요청이 동시에 재고를
읽으면 둘 다 판매 가능으로 판단하고, 결과적으로 중복예약이 발생한다.

한편 iCal은 최대 2시간까지 지연되므로, 이미 다른 채널에서 팔린 방을 우리가 모르는
구간이 구조적으로 존재한다. 이 구간의 예약은 어떤 잠금으로도 막을 수 없다.

## 결정

성격이 다른 네 계층으로 나눠 방어한다.

**1계층 — 애플리케이션 락.** `UnitLock` 인터페이스로 추상화한다. 단일 인스턴스에서는
JVM 내부 `ReentrantLock`으로 충분하고, 인스턴스가 여러 개가 되면 Redis 구현으로
갈아끼운다. 호출하는 쪽 코드는 바뀌지 않는다.

**2계층 — 데이터베이스 행 잠금.** `SELECT ... FOR UPDATE`로 재고 행을 잠근다.
여러 날짜를 잠글 때는 반드시 날짜 오름차순으로 획득한다. 한 스레드가 12/25 → 12/26
순으로, 다른 스레드가 12/26 → 12/25 순으로 잠그면 교착 상태가 발생한다.
`StayPeriod.nightDates()`가 정렬을 보장한다.

**3계층 — 데이터베이스 제약.** `CHECK (booked_units + held_units <= total_units)`.
1계층과 2계층에 결함이 있어도 초과 판매된 행 자체가 저장되지 않는다.

**4계층 — 충돌 감지.** 막을 수 없는 경우를 위한 사후 처리다. OTA에서 이미 성사된
예약은 받아들이고 `overbooking_conflict`에 기록해 운영자가 해소하게 한다.

## 근거

세 계층을 겹치는 것이 과해 보일 수 있으나 각 계층이 막는 것이 다르다. 1계층은 빠르고
데이터베이스 부하가 없지만 프로세스 밖은 모른다. 2계층은 확실하지만 락 대기가 길어질 수
있다. 3계층은 성능 비용이 사실상 없고 최후의 보증이 된다.

4계층이 특히 중요하다. OTA에서 성사된 예약을 시스템이 재고 없음으로 거절하면 게스트와
플랫폼 양쪽에서 문제가 된다. 거절이 아니라 수용 후 에스컬레이션이 맞다.

## 결과

- 락을 먼저 잡고 그 안에서 트랜잭션을 연다. 순서가 반대면 트랜잭션이 열린 채 락을
  기다리게 되어 커넥션 풀이 마른다
- 이 때문에 락을 잡는 빈(`InventoryService`)과 트랜잭션을 여는 빈
  (`InventoryLedgerWriter`)을 분리했다. 같은 클래스 안에서 `@Transactional` 메서드를
  호출하면 프록시를 거치지 않아 트랜잭션이 걸리지 않는다
- 지연이 큰 채널에는 재고를 일부 유보하는 버퍼를 둘 수 있다
  (`channel_connection.inventory_buffer`)
