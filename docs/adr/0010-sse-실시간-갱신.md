# ADR 0010. 캘린더 실시간 갱신은 SSE 로 한다

- 상태: 확정
- 결정일: 2026-09-04
- 범위: P2 9주차
- 관련: 계획서 8.2 / 11.2, ADR 0006, ADR 0008, ADR 0009

## 맥락

계획서 8.2 가 "다른 채널의 예약이 유입되면 SSE 로 즉시 반영"이라고 적었다. 화면을
열어 둔 채로 두는 것이 이 도구의 기본 사용 방식이라 — 호스트는 캘린더를 띄워 놓고
일한다 — 새로고침해야 최신이 되는 화면은 낡은 값을 보고 판단하게 만든다.

채널 수신은 P3 다. 지금 사건을 만드는 것은 수기 예약, 예약 변경, 요금·제약 일괄
편집 셋이다. 셋 다 이미 `outbox_event` 에 행을 남기고 있고, 작업지시 03 이 소비자를
붙일 자리(`DomainEventPublisher`)를 만들어 두었다.

## 검토한 선택지

### 전송 방식

**WebSocket 은 쓰지 않는다.** 화면이 서버로 보낼 것이 없다. 조작은 전부 REST 로
나가고 실시간 경로는 알림만 받는다. 양방향을 열면 연결 관리, 하트비트, 재연결,
프로토콜 정의가 따라오는데 그 비용에 대응하는 이득이 없다. 계획서 11.2 의 판단이
같고 여기서 뒤집을 근거가 나오지 않았다.

**폴링은 기각했다.** 30초 주기로 2,700셀을 다시 받으면 8주차에 줄인 것을 도로
쓰는 셈이고(측정-02), 그래도 최대 30초는 낡은 값을 본다. 사건이 드물다는 것이
폴링에 불리하다 — 대부분의 요청이 "바뀐 것 없음"을 받아 온다.

**SSE 를 고른다.** 단방향이고, HTTP 위에서 돌고, 브라우저가 형식을 이미 안다.

### 구독 인증

`EventSource` 는 헤더를 붙이지 못한다. 그래서 흔히 접근 토큰을 쿼리에 싣는데,
**그러면 토큰이 URL 로 새어 서버 접근 로그와 브라우저 이력에 남는다.** ADR 0006 이
리프레시 토큰을 `HttpOnly` 쿠키로 감추고 접근 토큰을 메모리에만 둔 이유가
무의미해진다.

쿠키의 `Path` 를 넓혀 SSE 요청에 실리게 하는 방법도 있으나 ADR 0006 의 결정을
바꾸는 일이라 열지 않았다.

**`fetch` 스트림으로 붙는다.** 헤더를 붙일 수 있어 토큰이 본래 자리에 그대로 있다.
대신 `EventSource` 가 공짜로 주던 재연결을 직접 해야 하는데, 그 코드가 지수 백오프
포함 40줄 남짓이고 파싱도 `event:` 와 `data:` 두 줄이면 끝난다. 라이브러리를 들이지
않았다.

## 결정

1. **`GET /api/calendar/stream` 을 SSE 로 연다.** 구독은 **인증 주체의 조직**으로
   좁힌다. 경로나 쿼리로 조직을 받지 않는다.
2. **Outbox 소비자 자리의 첫 입주자로 넣는다.** `DomainEventPublisher` 를 구현하고,
   `OutboxRelay` 가 등록된 구현을 전부 돌린다. P3 의 채널 워커가 그 옆에 들어온다.
3. **놓친 사건을 재생하지 않는다.** 재연결하면 캘린더를 통째로 다시 조회한다.
4. **사건에 변경 내용을 싣지 않는다.** `{type, propertyId}` 만 보낸다. 화면은 이걸
   받고 다시 조회한다.
5. **단일 인스턴스 전제다.**

## 근거

### 조직으로 좁히는 것이 이 결정의 핵심이다

조회 API 는 `OwnedResources` 로 막아 두었는데 실시간 경로에 구멍이 남으면 같은 자료가
그쪽으로 샌다. 그리고 **새는 쪽에서는 아무 증상이 없다.** 자기 화면에 남의 예약이
하나 더 보이는 것을 알아채는 사람은 드물고, 알아채도 무엇이 잘못됐는지 모른다.

그래서 보낼 때마다 조직을 고르는 것이 아니라 **애초에 조직별로 갈라 담는다**
(`CalendarStreamHub`). 사건의 `propertyId` 로 조직을 한 번 찾아 그 칸에만 넣고,
**조직을 못 찾으면 아무에게도 보내지 않는다.** 모르면 넓게 보내는 쪽으로 기울면
그게 곧 새는 경로다.

두 조직을 실제로 띄워 놓고 확인하는 테스트를 남겼다(`CalendarStreamApiTest`).
허브를 직접 부르지 않고 엔드포인트로 확인하는 이유는, 컨트롤러가 주체에서 조직을
꺼내는 그 한 줄이 정확히 새는 자리이기 때문이다. 스코핑을 빼면 그 테스트만 깨진다.

### 재생하지 않고 다시 조회하는 이유

Outbox 는 **최소 1회 전달**이고 순서 보장은 단일 스레드 전제 위에 있다(ADR 0008).
놓친 사건을 SSE 로 재생하려면 같은 사건이 두 번 와도 되고 순서가 뒤바뀌어도 되는
코드를 **화면 쪽에 다시 써야 한다.** 서버에서 이미 한 고민을 프론트에서 반복하는 것이다.

통째로 다시 조회하면 그 문제가 사라진다. 2,700셀 조회가 408ms 이고(측정-02) 재연결은
드문 사건이라 비용도 문제가 되지 않는다. 사건에 변경 내용을 싣지 않는 것도 같은
이유다 — 실으면 화면이 그것만 반영하고 싶어지고, 그 순간 같은 문제가 돌아온다.

### 단일 인스턴스 전제

구독자를 JVM 메모리에 들고 있으므로 여러 대가 되면 인스턴스마다 구독자가 갈라진다.
다른 인스턴스가 처리한 예약은 내 화면에 오지 않는다. `OutboxRelay` 와 `LocalUnitLock`
이 같은 전제 위에 있고, 그때는 Redis 발행/구독 같은 것이 함께 필요하다.

전제를 지키는 자리를 코드 주석으로 남겼다. 인스턴스를 늘리는 순간 조용히 깨지는
종류라 배포 구성을 바꿀 때 이 세 곳을 함께 봐야 한다.

## 결과

- **끊긴 구독자에게 보내다 실패해도 릴레이에 실패로 올리지 않는다.**
  `DomainEventPublisher` 의 계약은 "실패를 삼키지 말라"이지만, 여기서 실패하는 것은
  이미 끊긴 브라우저다. 실패로 올리면 그 사건이 다음 주기에 다시 나가고 살아 있는
  다른 화면들이 같은 알림을 또 받는다. 끊긴 화면은 다시 붙을 때 통째로 조회하므로
  그쪽으로 복구된다 — 재생하지 않는다는 결정이 여기서도 같다
- **소비자가 여럿이 되면서 한 소비자의 실패가 그 사건 전체의 실패가 된다.**
  다음 주기에 모든 소비자가 다시 받는다. 중복은 소비자 멱등성으로 흡수한다는 4.4 의
  전제가 여기서도 필요해졌다
- 연결은 30분 뒤 만료된다. 무한으로 두면 죽은 연결이 영원히 남는다. 만료되면
  브라우저가 다시 붙고 그때 다시 조회하므로 그 사이의 변경도 함께 복구된다
- **미리보기(`dryRun`)는 사건을 만들지 않는다.** 아무것도 쓰지 않았으니 알릴 것도
  없다. 알림이 가면 열려 있는 화면들이 이유 없이 다시 조회한다
- 화면은 자기가 보고 있는 숙소의 사건만 쓴다. 서버가 조직으로 좁혀 주지만 그건 남의
  조직을 막는 것이지 조직 안의 숙소를 가르지 않는다
- 프록시를 두는 경우 SSE 버퍼링을 꺼야 한다. 개발 서버(Vite)는 그대로 흘려보낸다.
  운영 배포에서 확인할 항목이며 P6 다
