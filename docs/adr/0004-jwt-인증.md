# ADR 0004. 인증은 대칭키로 서명한 JWT 로 한다

- 날짜: 2026-08-22
- 상태: 채택
- 관련: 계획서 15.1, ADR 0005

## 맥락

P1 3주차에 인증을 붙인다. 프론트엔드는 P2 에 React 로 시작하고, P3 부터 채널 웹훅이
들어오며, 최종적으로 브라우저와 서버가 분리된 형태가 된다. 서버는 단일 모듈러 모놀리스
한 프로세스다.

계획서 15.1 이 이미 방식을 못박아 두었다. JWT, 액세스 30분, 리프레시 14일, 회전과
재사용 탐지, BCrypt cost 12.

## 검토한 선택지

**세션 쿠키.** 서버가 세션 상태를 들고 있어 무효화가 즉시 되고 구현도 단순하다. 다만
채널 웹훅과 나중의 모바일 접근처럼 쿠키가 자연스럽지 않은 경로가 있고, 인스턴스를 늘리면
세션 저장소를 따로 둬야 한다. 계획서가 이미 JWT 로 정해 두기도 했다.

**JWT 를 직접 구현.** `io.jsonwebtoken:jjwt` 로 필터를 손으로 짠다. 코드가 눈에 보여
설명하기 좋지만, 서명 검증·만료 확인·알고리즘 혼동(alg=none, HS/RS 혼동) 방어를 직접
관리해야 한다. 인증은 틀렸을 때 대가가 큰 영역이라 직접 만들 이유가 약하다.

**RS256 비대칭키.** 개인키로 서명하고 공개키로 검증한다. 발급자와 검증자가 분리될 때
가치가 있다. 지금은 한 프로세스가 발급도 검증도 하므로 키를 나눌 상대가 없다. 키쌍 생성과
보관, 회전 절차만 늘어난다.

## 결정

**`spring-boot-starter-oauth2-resource-server` 를 쓰고 HS256 대칭키로 서명한다.**

발급은 `NimbusJwtEncoder`, 검증은 `NimbusJwtDecoder` 가 한다. 직접 작성한 암호 코드는
없다. 필터도 짜지 않고 `oauth2ResourceServer(jwt)` 설정으로 끝낸다.

토큰에는 사용자 식별자(`sub`), 조직(`org`), 역할(`role`)만 넣는다. JWT 는 서명될 뿐
암호화되지 않아 누구나 페이로드를 읽을 수 있으므로 이메일과 이름은 담지 않는다.

검증된 토큰은 `shared.security.AuthenticatedUser` 로 변환해 `SecurityContext` 에
넣는다. 다른 모듈은 클레임 이름을 알 필요가 없고 identity 를 참조하지도 않는다.

### 서명 키를 어디서 가져오는가

**환경 변수 `JWT_SECRET` 하나로 주입한다.** `application.yml` 이
`${JWT_SECRET:}` 로 받아 `staysync.security.jwt.secret` 에 넣는다. `.env.example` 에
항목과 생성 방법(`openssl rand -base64 48`)을 적어 두었고 `.env` 는 저장소에서 제외되어
있다.

**키가 없거나 32바이트 미만이면 기동을 막는다.** `JwtProperties` 의 컴팩트 생성자가
검사한다. HS256 은 256비트 이상을 요구하므로 짧은 키는 어차피 첫 발급에서 실패하는데,
그때는 이미 서비스가 떠 있는 상태다. 배포 실수를 기동 시점으로 당긴다.

**키는 재기동을 넘어 고정이다.** 기동할 때마다 난수를 만들면 배포할 때마다 전 사용자가
로그아웃된다. 액세스 토큰이 30분짜리라 피해가 제한적으로 보이지만, 무상태 검증의 이점을
스스로 버리는 선택이다. 고정 키를 쓰고, 키 유출 시에는 값을 바꾸는 것이 곧 전체 무효화
수단이 된다.

**local 프로파일만 예외로 개발용 고정값을 `application-local.yml` 에 둔다.** 저장소에
공개된 값이며 그 전제로만 쓴다. 이 값이 있어 `.env` 없이도 `./gradlew bootRun` 이 뜬다.

다만 local 은 `clean-on-start: true` 라 기동할 때마다 데이터베이스가 비워진다.
`user_account` 와 `refresh_token` 행이 함께 사라지므로, 키가 고정이어서 서명 검증을
통과하는 액세스 토큰이 남아 있어도 그 토큰이 가리키는 사용자는 존재하지 않는다.
**local 에서는 재기동 후 다시 로그인해야 한다.** docker 와 운영 프로파일에서는
데이터가 남으므로 토큰이 재기동을 넘어 그대로 쓰인다.

## 근거

RS256 의 이점은 "검증자가 발급 능력 없이 검증만 할 수 있다"인데, 지금 구조에는 그런
검증자가 없다. 나중에 서비스를 쪼개 검증 전용 노드가 생기면 그때 바꾼다. 발급과 검증이
`JwtTokenService` 한 곳에 모여 있어 교체 지점이 좁다.

직접 구현 대신 표준 라이브러리를 쓰는 편이 학술 프로젝트에서도 방어하기 쉽다. 설명할
것은 "무엇을 왜 선택했는가"이지 서명 바이트를 어떻게 맞췄는가가 아니다.

## 결과

- 액세스 토큰은 무상태다. 유출되면 만료(30분)까지 막을 방법이 없다. 즉시 차단이
  필요한 경우는 리프레시 토큰 무효화로 다음 갱신을 끊는 것이 최선이며, 그 설계는 ADR 0005
- `JWT_SECRET` 을 바꾸면 발급된 액세스 토큰이 전부 무효가 된다. 사실상의 비상 정지 장치다
- Nimbus 로 서명할 때 `JwsHeader` 에 HS256 을 명시해야 한다. 생략하면 RS256 을 가정해
  대칭키에서 서명 키를 고르지 못한다
- 인가는 `@EnableMethodSecurity` 로 켜 두었다. 역할 규칙과 조직 스코핑은 3~5단계에서 붙인다
