# ADR 0011. Mock OTA 시뮬레이터는 별도 애플리케이션으로 둔다

- 상태: 확정
- 결정일: 2026-09-05
- 범위: P3 11주차
- 관련: 계획서 3.3 / 6.4 / 11.4 / 12.2, ADR 0003, 조사-01, 조사-02

## 맥락

계획서 3.3 이 채널 연동을 iCal · Channex · Mock 셋으로 잡았고, 6.4 가 Mock 을 "실제
OTA 에서 발생하지만 재현하기 어려운 악조건을 만들어 내는 것"으로 정의했다.

**두 실제 채널로는 검증할 수 없는 조건이 남는다.**

- iCal 은 요금을 동기화하지 못하고 날짜만 오간다. 미게시 리스팅은 전 기간을 `VEVENT`
  하나로 막아 개별 예약도 구분되지 않는다(조사-02). 게시하면 실제 게스트가 예약하고
  결제까지 일어나므로 미게시를 유지하기로 했다
- Channex 스테이징은 **남의 서버**다. 지연을 만들 수도, 5% 만 실패하게 할 수도,
  같은 웹훅을 세 번 보내게 할 수도 없다

12주차 완료 조건이 "5% 에러율을 주입한 상태에서 ARI 100건을 전송해도 재시도 후 최종
정합성이 유지된다"인데, **그 에러율을 만들 수 있는 것이 이것뿐이다.** 지연·실패·중복
전송·순서 역전·동시 예약·초과 판매가 전부 같은 처지다.

11주차에는 시뮬레이터만 만든다. 이것을 두드리는 `MockOtaAdapter` 와 동기화 워커는
12주차이고, 레지스트리는 이번 주에도 비어 있다.

## 검토한 선택지

### 어디에 둘 것인가

**백엔드 안의 테스트 픽스처로 두는 방안을 기각했다.** `@TestConfiguration` 이나
MockWebServer 로 흉내 내면 파일은 줄지만, 그건 **우리 프로세스 안에서 우리가 우리를
상대하는 것**이다. 실제 HTTP 왕복, 타임아웃, 연결 실패가 재현되지 않고, 12주차의
타임아웃·서킷브레이커 검증이 겨냥하는 지점이 통째로 사라진다.

**별도 애플리케이션으로 둔다.** 계획서 11.4 가 `mock-ota-simulator/` 로 그려 둔 자리다.

### 어떻게 빌드에 붙일 것인가

**독립 프로젝트(자체 wrapper)를 기각했다.** 본체 빌드가 확실히 안 깨진다는 장점이
있지만, `./gradlew test` 에 실리지 않는다. **시뮬레이터가 깨져도 본체 빌드가
초록이고, 12주차는 그걸 신뢰하고 쓴다.** 시뮬레이터가 틀리면 12주차의 모든 판정이
틀린다. wrapper 를 한 벌 더 유지하는 비용도 붙는다.

**Gradle 멀티프로젝트로 둔다.** `include 'mock-ota-simulator'` 한 줄이고, 한 번의
`./gradlew test` 가 본체 157건과 시뮬레이터 33건을 함께 돌린다.

다만 **시뮬레이터에는 Spring Boot Gradle 플러그인을 적용하지 않는다.** 적용하면
`bootRun` 태스크가 두 프로젝트에 생기고, 멀티프로젝트에서 이름만 준 태스크는 모든
프로젝트에서 실행되므로 `./gradlew bootRun` 이 백엔드와 시뮬레이터를 함께 띄우려 든다.
작업지시 08 의 제약이 "`./gradlew bootRun` 이 지금처럼 동작한다"이므로 그 이름을 이
프로젝트에 만들지 않았다. 대신 `runSimulator` 라는 겹치지 않는 이름을 둔다.

플러그인을 빼면서 잃는 것은 `bootJar` 하나인데, 지금 jar 로 배포할 곳이 없다. 대신
**플러그인이 자동으로 넣어 주던 `-parameters` 를 직접 넣어야 한다** — 없으면 record 로
만든 `@ConfigurationProperties` 바인딩과 Jackson 역직렬화가 런타임에 실패한다.

### 상태를 어디에 둘 것인가

**데이터베이스를 붙이지 않는다.** 시뮬레이터는 테스트 도구이고 재기동하면 비어도 된다.
데이터베이스를 붙이면 스키마와 마이그레이션이 또 한 벌 생기고, 그것을 유지하는 비용이
얻는 것보다 크다. 12주차 테스트는 시뮬레이터를 띄우고, 두드리고, 내리는 단위로 돌 것이라
그 사이에 상태가 남아야 할 이유가 없다.

### 악조건을 어떻게 켤 것인가

**런타임 변경 엔드포인트를 만들지 않았다.** 프로퍼티로 충분하다. 한 테스트 안에서
에러율을 바꿔야 한다면 컨텍스트를 나누면 된다. 지금 쓸 곳이 없는 것을 미리 만들지
않는다 — 5~6주차에 Outbox 소비자 워커를 미리 만들지 않은 것과 같은 판단이다.

계획서 6.4 의 스케치는 `ThreadLocalRandom` 을 썼는데 **그대로 쓰지 않았다.** 시드를
줄 수 없어 재현이 안 된다.

## 결정

1. **별도 Spring Boot 애플리케이션.** 뿌리 패키지는 `com.mockota` 이고 포트는 8081 이다
2. **Gradle 멀티프로젝트의 하위 프로젝트.** Spring Boot Gradle 플러그인은 적용하지
   않고 `runSimulator` 로 띄운다
3. **상태는 메모리에만 둔다.** 데이터베이스 없음
4. **악조건은 프로퍼티로만 켠다.** `mockota.chaos.latency-ms`, `error-rate`, `seed`
5. **헤더 `X-Api-Key` 를 검사한다.** 없거나 틀리면 401
6. **시뮬레이터는 나쁘게 군다.** 중복을 막지 않고 순서를 바로잡지 않는다

## 근거

### 우리 도메인을 모르는 것이 요점이다

`com.staysync` 의 어떤 타입도 참조하지 않는다. 채널이 우리 코드를 아는 것은 말이 안
되고, 참조하면 12주차 어댑터가 하는 "채널 형식 → 우리 형식" 변환이 아무 일도 하지 않게
된다. 주고받는 것은 JSON 뿐이다.

**뿌리 패키지를 `com.mockota` 로 가른 것도 그래서다.** 규칙 위반이 import 한 줄로
드러나고, 12주차에 이 프로젝트를 백엔드 테스트 클래스패스에 올리더라도 백엔드의
컴포넌트 스캔(`com.staysync` 하위)에 시뮬레이터의 빈이 딸려 들어가지 않는다.

같은 이유로 **응답 JSON 을 `snake_case` 로 낸다.** 우리 API 는 `camelCase` 다. 이름이
우연히 맞아떨어져 통과하면 어댑터가 정말로 매핑을 하는지 알 수 없다. 상용 채널
매니저들의 형식이기도 하다.

### 자격 증명 검사가 없으면 12주차가 거짓말을 한다

**검사가 없으면 어댑터가 키를 빠뜨려도 12주차 테스트가 전부 통과한다.** 드러나는 것은
실제 OTA 로 바꾸는 순간이고, 그때는 모든 요청이 401 이라 어디서부터 잘못됐는지도 보이지
않는다. 정상 경로에서 증상이 없는 결함을 미리 막는 것이고, 이 프로젝트에서 반복된
모양이다(게스트 연락처, 채널 자격 증명, SSE 조직 스코핑).

**서명 검증과 만료는 흉내 내지 않는다.** 그건 실제 채널에서
`ChannelAdapter.verifySignature()` 가 할 일이고, 지금 흉내 내면 검증하는 대상이 실제
채널이 아니라 우리 흉내가 된다. 키는 단순한 문자열이면 된다.

### 재현되지 않는 주입은 쓸 수 없다

"가끔 실패하는 테스트"는 결함을 숨긴다. 실패가 주입 때문인지 코드 결함 때문인지
구분되지 않으면 그 테스트는 아무것도 보증하지 않는다.

그래서 시드를 받는 `Random` 하나를 `ChaosDice` 에 두고 뽑는 자리를 직렬화했다. 같은
시드면 순차 요청의 실패 순서가 같다. **에러율이 0 일 때도 눈을 뽑는다** — 건너뛰면 같은
시드가 에러율에 따라 다른 순서를 내고, 그러면 "시드가 같으면 같다"가 조건부 참이 된다.

시드를 주지 않으면 매번 새로 뽑되 **그 값을 기동 로그에 남긴다.** 우연히 만난 실패를
나중에 다시 만들 수 있어야 한다.

### 악조건은 채널 표면에만 건다

`/api/ari` 와 `/api/bookings` 에만 걸고 `/api/scenarios/**` 는 지나간다. 악조건이
겨냥하는 것은 **우리 클라이언트**의 타임아웃·재시도·백오프이고, 시나리오 엔드포인트는
채널의 표면이 아니라 테스트가 쥐는 손잡이다. 손잡이까지 실패시키면 에러율 100% 에서
시험 준비 자체가 불가능해진다.

반대로 **자격 증명 검사는 `/api/**` 전체에 건다.** 웹훅을 쏘게 만드는 것이 시나리오
경로라서, 여기를 열어 두면 "웹훅 발신에 자격 증명이 필요하다"가 검증되지 않는다.

## 결과

- **레지스트리는 11주차에도 비어 있다.** `MockOtaAdapter` 는 12주차다. 이번 주의 검증은
  시뮬레이터가 명세대로 동작하는지까지다
- **`./gradlew test` 가 190건이 된다**(백엔드 157 + 시뮬레이터 33). 백엔드 157건은
  그대로다. `./gradlew build` 도 두 프로젝트를 함께 빌드한다
- **`./gradlew bootRun` 은 백엔드만 띄운다.** 시뮬레이터는 `./gradlew runSimulator` 다.
  포트는 8080 과 8081 로 갈리고 테스트용 데이터베이스 포트(15433, 15434)와도 겹치지 않는다
- **`docker-compose.yml` 의 자리는 주석으로 뒀다.** 이 파일은 docker 프로파일의 인프라를
  띄우는 것이고 백엔드도 거기 없다. 컨테이너로 띄우려면 실행 가능한 jar 가 먼저
  필요한데 `bootJar` 를 만들지 않기로 했다. 필요해지면 플러그인과 Dockerfile 을 함께 넣는다
- **`.env` 를 읽지 않는다.** 실제 Channex 키와 무관하고, 시뮬레이터의 키는 그 자체의
  설정이다. 기본값이 `application.yml` 에 평문으로 있는 것이 정상이다
- **폴링과 푸시가 같은 형식으로 나가야 한다.** `RestClient` 를 그냥 두면 애플리케이션의
  `ObjectMapper` 가 아니라 자기 기본 변환기를 써서, 폴링은 `snake_case` 에 ISO 날짜인데
  웹훅은 `camelCase` 에 날짜가 배열로 나갔다. 그러면 12주차 어댑터가 매핑을 두 벌 갖게
  된다. 본문을 직접 직렬화해 고쳤고 테스트로 고정했다
- **12주차 완료 조건의 상한이 여기서 정해진다.** 시뮬레이터가 만들 수 있는 악조건이
  지연·에러율·중복·순서 역전·동시 다발·초과 판매 여섯이고, 12주차 지시서는 이 범위
  안에서 쓰인다. 여기에 없는 것(부분 실패, 응답 손상, 연결 리셋)은 지금 검증할 수 없다
