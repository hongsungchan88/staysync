# ADR 0005. 리프레시 토큰은 상태를 저장하고 회전시킨다

- 날짜: 2026-08-22
- 상태: 채택
- 관련: 계획서 15.1, ADR 0004

## 맥락

계획서 15.1 이 "Refresh 14일, 회전 및 재사용 탐지"를 약속했다.

재사용 탐지는 "이 토큰이 이미 쓰였는가"를 판단하는 일이다. 그러려면 서버가 발급한
토큰의 상태를 알아야 한다. 무상태 토큰으로는 성립하지 않는 요구다.

액세스 토큰은 무상태 JWT 라 유출돼도 30분 뒤 만료까지 막을 수단이 없다(ADR 0004).
리프레시 토큰은 14일짜리라 같은 방식이면 위험이 훨씬 크다. 이쪽만이라도 즉시 끊을 수
있어야 한다.

## 검토한 선택지

**무상태 리프레시 토큰.** 수명이 긴 JWT 를 그대로 쓴다. 테이블이 필요 없고 구현이 가장
싸다. 그러나 회전해도 이전 토큰이 만료 전까지 계속 유효해 재사용을 탐지할 수 없고,
로그아웃해도 토큰이 살아 있다. 계획서의 약속을 지키지 못한다. **기각.**

**토큰 원문을 저장.** 대조가 문자열 비교라 단순하다. 데이터베이스가 유출되면 저장된 값을
그대로 `Authorization` 에 실어 쓸 수 있다. 비밀번호를 평문으로 두는 것과 같은 문제다.
**기각.**

**BCrypt 로 해시.** 비밀번호와 같은 방식. 그러나 BCrypt 는 의도적으로 느리고(cost 12 는
수백 밀리초), 무엇보다 솔트가 매번 달라 해시로 조회할 수 없다. 사용자의 토큰을 전부
꺼내 하나씩 대조해야 한다. 느린 해시가 필요한 이유는 사람이 고른 비밀번호가 엔트로피가
낮아 사전 공격이 통하기 때문인데, 128비트 난수 토큰에는 해당하지 않는다. **기각.**

**토큰을 폐기 목록(blacklist)으로만 관리.** 무효화된 것만 기록한다. 저장량은 적지만
"발급된 적 있는가"를 모르므로 재사용과 위조를 구분할 수 없다. **기각.**

## 결정

**`refresh_token` 테이블에 SHA-256 해시를 저장하고, 갱신할 때마다 회전시킨다.**

리프레시 토큰 자체는 JWT 가 아니라 128비트 난수 문자열이다. 클레임을 실을 이유가 없다.
상태가 데이터베이스에 있으므로 토큰은 그 행을 가리키는 열쇠면 충분하다.

**저장은 SHA-256 해시로 한다.** 데이터베이스가 유출돼도 저장된 값을 그대로 제시할 수
없다. 토큰이 고엔트로피 난수라 느린 해시가 필요 없고, 솔트가 없어 해시값으로 바로 조회할
수 있다(`uq_refresh_hash` 유니크 인덱스).

**회전.** 갱신 요청이 오면 새 토큰을 발급하고, 쓰인 토큰의 `replaced_by` 에 새 토큰의
식별자를 적는다. 이 컬럼이 회전 체인을 잇는다. `NULL` 이면 아직 살아 있는 토큰이고,
값이 있으면 이미 교체된 토큰이다.

**재사용 탐지.** `replaced_by` 가 채워진 토큰이 다시 들어오면 도난으로 본다. 정상 사용자는
교체된 토큰을 다시 쓸 이유가 없다. 탐지되면 **해당 사용자의 리프레시 토큰을 전부
무효화**하고 재로그인을 강제한다.

체인을 거슬러 특정 갈래만 끊지 않고 전부 끊는 이유는, 어느 쪽이 유출된 것인지 알 수 없기
때문이다. 정상 사용자와 공격자가 같은 토큰에서 갈라져 나왔을 때 어느 쪽이 진짜인지
구분할 근거가 없다. 확실한 사실은 이 사용자의 토큰 하나가 새어 나갔다는 것뿐이므로,
전부 끊고 비밀번호를 아는 쪽만 다시 들어오게 한다.

### 만료 토큰 정리

세 가지를 검토했다.

- **`pg_cron`** — 데이터베이스가 알아서 지운다. 확장 설치가 필요해 local 프로파일의
  내장 PostgreSQL 에서는 쓸 수 없다. pgvector 를 V2 로 분리해야 했던 것과 같은 제약이다.
- **갱신 시 기회적 삭제** — 갱신 요청이 올 때 그 사용자의 만료분을 함께 지운다. 별도
  스케줄러가 없지만, 로그인하지 않는 사용자의 행은 영영 남는다.
- **주기 배치** — 애플리케이션이 하루 한 번 지운다.

**주기 배치를 택한다.** `RefreshTokenRepository.deleteExpiredBefore()` 를 하루 한 번
`@Scheduled` 로 호출한다.

만료 즉시 지우지 않고 **7일의 유예**를 둔다. 행이 사라지면 "만료된 토큰이 제시됐다"와
"존재한 적 없는 토큰이 제시됐다"를 구분할 수 없다. 앞은 흔한 일이고 뒤는 공격 신호라
로그에서 갈라 보고 싶다.

인스턴스가 하나인 지금은 `@Scheduled` 만으로 충분하다. 여러 대가 되면 배치가 중복
실행되므로 ShedLock 을 건다. `shedlock` 테이블은 V1 에 이미 있고 의존성은
`build.gradle` 에 주석으로 대기 중이다.

규모로 보면 정리는 위생 문제지 성능 문제가 아니다. 대상 사용자가 개인 호스트고 토큰
수명이 14일이라 테이블은 작게 유지된다.

## 근거

지금이 V1 을 고치기 가장 싼 시점이다. `clean-on-start: true` 로 기동할 때마다 스키마를
새로 만들고 있어 마이그레이션을 추가하는 대신 V1 을 직접 고칠 수 있다. 스키마가 안정된
뒤였다면 V3 를 새로 만들고 기존 데이터를 옮겨야 했다.

무상태 방식이 더 싸긴 하지만, 계획서에 적어둔 보안 조치를 구현 편의로 되무르는 선택이
된다. 심사에서 방어할 수 없다.

## 결과

- 갱신 요청마다 데이터베이스 읽기 한 번과 쓰기 두 번(기존 행 `replaced_by` 갱신, 새 행
  삽입)이 든다. 액세스 토큰이 30분짜리라 사용자당 하루 수십 회 수준이며 부담되지 않는다
- 로그아웃이 실제로 동작한다. 해당 행의 `revoked_at` 을 채우면 다음 갱신이 막힌다.
  다만 이미 발급된 액세스 토큰은 최대 30분 더 유효하다(ADR 0004)
- 재사용 탐지가 정상 사용자를 끊는 경우가 있다. 네트워크가 끊겨 갱신 응답을 받지 못한
  클라이언트가 이전 토큰으로 재시도하면 재사용으로 보인다. 클라이언트가 갱신 응답을
  받기 전에는 이전 토큰을 버리지 않도록 만들어야 하며, P2 프론트엔드에서 확인한다
- `token_hash` 는 항상 64자지만 `CHAR` 가 아니라 `VARCHAR(64)` 다. Hibernate 는 JDBC
  타입 코드로 비교해 `CHAR` 와 `VARCHAR` 를 다르게 보고, `ddl-auto: validate` 가 기동을
  막는다
- 회전과 재사용 탐지를 수행하는 `RefreshTokenService` 와 정리 배치는 2단계(인증
  엔드포인트)에서 구현한다. 이 ADR 은 테이블과 규칙을 정한다

### 무효화는 갱신 트랜잭션과 분리해야 한다

구현하면서 드러난 결함이다. 설계에 딸린 제약이라 여기 남긴다.

재사용을 탐지하면 **무효화한 뒤 갱신 실패 예외를 던진다.** 이 둘이 같은 트랜잭션 안에
있으면 뒤에 던지는 런타임 예외가 트랜잭션을 통째로 롤백시켜 **무효화까지 없던 일이
된다.** 탐지 로그만 남고 공격자의 토큰은 그대로 살아 있다. 이 ADR 이 정한 방어가
전혀 동작하지 않는 상태이면서, 응답은 401 이라 정상으로 보인다.

그래서 무효화를 `CompromisedTokenHandler` 라는 별도 빈으로 빼고
`@Transactional(propagation = REQUIRES_NEW)` 를 걸었다. 바깥 트랜잭션이 롤백돼도
무효화는 이미 커밋되어 남는다. 같은 클래스 안에서 부르면 프록시를 거치지 않아 전파
설정이 걸리지 않으므로 **반드시 다른 빈이어야 한다.** `InventoryService` 와
`InventoryLedgerWriter` 를 나눈 것과 같은 이유다(ADR 0002).

검증 방식도 함께 남긴다. 재사용 요청이 401 을 반환하는지만 확인하면 이 결함은 통과한다.
롤백되든 아니든 응답은 같기 때문이다. **무효화 뒤 살아 있는 토큰 수를 직접 세야**
드러난다. `RefreshTokenRotationTest` 가 그렇게 되어 있다.

일반화하면 이렇다. **실패로 끝나면서 기록을 남겨야 하는 처리는 그 기록을 별도
트랜잭션에 담는다.** 같은 모양이 P3 의 중복예약 충돌 기록에서 다시 나온다(ADR 0003).
