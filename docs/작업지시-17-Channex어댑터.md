# 작업지시 17. Channex 어댑터 — 예약 수신과 재고·요금 전송

- 작성일: 2026-09-17
- 작성: Cowork 세션 (문서·설계 담당)
- 대상: Claude Code (구현 담당)
- 범위: CMS·PMS 완성 단계. **작업지시-16 뒤에 한다**
- 관련: 조사-01(Channex 스테이징), 조사-04(중개 연동), 검토-01(3절 6·7·8번, 7절),
  CLAUDE.md 채널 연동 절, ADR 0011·0012·0013

이 문서는 무엇을 만들지와 어떤 제약을 지킬지를 적는다. 어떻게 짤지는 적지 않는다.
5절의 결정은 착수 전에 정했다. 다시 열지 말 것.

새 세션이 이 문서로 시작한다면 CLAUDE.md 를 먼저 읽고 이 문서를 읽으면 된다.

## 1. 지금 상태와 왜 이 주차가 생겼나

**교수 방향(09-17) — AI 보다 CMS·PMS 가 제대로 도는 것. 에어비앤비는 Channex 를 거친다.**
대상은 본업이 있고 숙소 한두 개를 부업으로 내놓는 호스트이고, 에어비앤비 공식 API 를 받지
않고 중개 서비스로 양방향 연동하는 것이 차별점이다(조사-04).

**Channex 어댑터는 없다.** `AdapterType.CHANNEX` 선언과 능력 목록만 있고 구현은 iCal·Mock
둘뿐이다(검토-01 3절 7번). CLAUDE.md 의 "세 구현을 감춘다"는 설계 의도였다.

**밑바닥은 있다.** P3 에서 Mock 으로 검증한 층이다.

| 있는 것 | 이번에 쓰는 자리 |
|---|---|
| `ChannelAdapter` 포트, 능력 선언, `ChannelAdapterRegistry` | Channex 구현을 꽂는다 |
| 동기화 워커·`sync_job`·재시도 | 전송 작업 |
| `AriCoalescingBuffer` — 6초 창, 같은 값 구간 압축 | ARI 묶음 |
| `ChannelBookingPoller`·`ChannelBookingCommand` — 금액 통로 포함 | 예약 수신 |
| `ChannelReconcileJob` — 하루 한 번 04:00, 180일 | 전체 동기화. **Channex 의 "24시간 1회"와 맞는다**(검토-01 3절 6번) |
| `ChannelCredentialStore` | API 키 보관 |
| `AdapterContractTest` | 선언과 구현이 맞는지 |

**지금 CMS 의 공백이 이것이다.** 배포 환경은 에어비앤비 예약을 받기만 하고, 재고·요금을
채널로 내보내는 동작은 Mock 으로만 검증했다. 시연 대본의 중심 장면("한쪽에서 팔리면 나머지가
닫힌다")이 배포 환경에서 돌지 않는 이유다(검토-01 2절).

### 이번 주가 위험한 이유

- **처음으로 남의 실제 API 에 쓴다.** 스테이징이지만 에어비앤비는 실제 리스팅이다(조사-04 3절).
  **이번 주차는 에어비앤비에 연결하지 않는다.** 부킹닷컴 테스트 숙소로만 한다(5절 2번)
- **이 프로젝트의 결함은 대부분 "정상 경로에 증상이 없는" 모양이다.** Channex 는 잘못된 값을
  **200 OK 와 경고로** 돌려준다. 경고를 안 읽으면 전송은 성공으로 끝나고 채널 값만 틀린다
- **웹훅은 순서가 뒤바뀌어 올 수 있고 서명이 없다**(Channex 문서)

## 2. 이번에 만드는 것

### A. 연결과 매핑

- 채널 연결 화면에서 **CHANNEX 유형으로 연결을 만든다.** 자격 증명은 API 키와 Channex 숙소
  식별자. **API 키는 iCal 주소처럼 가려서 보인다**
- 매핑 화면에서 **우리 판매 단위 ↔ Channex 객실 유형(`room_type_id`)**, **우리 요금제 ↔ Channex
  요금제(`rate_plan_id`)** 를 잇는다. Channex 는 ARI 의 최소 단위로 요금제를 요구한다
- Channex 쪽 숙소·객실·요금제는 **사람이 Channex 화면에서 만들고** 식별자를 옮겨 넣는다(5절 3번)
- 스테이징/운영 주소를 설정으로 가른다. 기본은 스테이징이다

### B. 재고·요금 전송

- 재고 → `POST /api/v1/availability`, 요금·제약 → `POST /api/v1/restrictions`.
  **두 종류를 한 메시지에 섞지 않는다**(Channex 권고)
- 기존 병합 버퍼로 묶고 같은 값은 날짜 구간으로 압축한다
- **요금은 소수 문자열로 보낸다**("170000.00" 꼴). 정수로 보내면 "통화의 최소 단위"로 읽히는데
  통화마다 소수 자리가 달라 조용히 100배가 틀릴 수 있다
- **레이트 리밋** — 숙소당 분당 요금·제약 10회, 재고 10회. 429 면 그 숙소 전송을 1분 멈추고
  지수 백오프(CLAUDE.md, 조사-01)
- **200 응답의 경고를 읽는다.** 경고가 있으면 그 값은 채널에 반영되지 않은 것이다 — 작업을
  성공으로 닫지 않는다(5절 5번)
- 하루 한 번 전체 동기화는 기존 `ChannelReconcileJob` 을 탄다

### C. 예약 수신

- **`GET /api/v1/booking_revisions/feed`** 로 확인 안 된 리비전을 가져와 처리하고,
  **처리가 커밋된 뒤에** `POST /api/v1/booking_revisions/:id/ack` 로 확인한다(5절 4번)
- 리비전 상태 `new`·`modified`·`cancelled` → 기존 `ChannelBookingCommand`
  (취소 플래그, 날짜, 게스트 이름)
- **금액(`amount`)을 `totalAmount` 로 넣는다.** 작업지시-16 의 "금액을 아는 경로"가 된다
- **리비전의 통화가 Channex 숙소 통화와 다르면** 조용히 숫자만 옮기지 않는다 — 막고 남긴다
- **매핑이 없는 객실·요금제의 예약을 조용히 버리지 않는다.** 확인(ack)하지 않으면 Channex 가
  30분 동안 다시 주고 메일을 보낸다. 어떻게 드러낼지는 Claude Code 가 정하고 8절에 적는다
- 게스트는 이름만 받는다. **연락처는 받지 않는다**(ADR 0007, `ChannelBookingCommand` 주석)
- 멱등성은 기존 `(channel_code, channel_booking_id)` 유니크가 맡는다. 식별자는 Channex 의
  `booking_id` 다(리비전 식별자가 아니다)
- **수정 순서.** Channex 리비전 식별자는 UUID 라 크기로 비교할 수 없다. 기존 규칙(ADR 0013 —
  revision 이 없으면 값이 달라졌는지로 판정)을 그대로 쓸지, 리비전의 생성 시각을 쓸지 정하고
  8절에 적는다. **피드는 순서대로 준다고 적혀 있지 않다.** 한 번에 여러 리비전이 오는 경우를
  테스트로 박는다

### D. 이중 수신 막기

- **같은 판매 단위에 iCal 연결과 Channex 연결을 함께 매핑하지 못하게 한다.** 같은 에어비앤비
  예약이 채널 코드만 다르게 두 번 들어오고, 유니크 제약이 이를 막지 못해 초과 판매 충돌로
  뜬다(조사-04 5절 3번)

### E. 능력 선언을 구현에 맞춘다

- `AdapterType.CHANNEX` 가 선언한 능력(PUSH_*·WEBHOOK·PULL) 중 **이번에 만들지 않은 것은
  선언에서 뺀다.** 12~14주차에 선언과 구현이 어긋난 결함이 세 번 났다 — 좁아서 조용히 건너뛰거나,
  넓어서 없는 구현을 불렀다.
  `AdapterContractTest` 에 Channex 를 넣는다

## 3. 이번에 만들지 않는 것

- **에어비앤비 연결.** 업체 허락이 먼저다. 교수 보고서 8절 2번으로 묻고 있다(5절 2번)
- **메시지(인박스).** Channex 메시징은 유닛당 별도 요금이다. 다음 지시서
- **상용 인증(14항목 + 화면 공유).** 판매 단계에서 한다. 다만 인증 요구와 어긋나는 설계는 하지
  않는다 — 폴링 루프로 ARI 를 보내지 않는다, 변경이 전송을 일으킨다, 전체 동기화는 하루 한 번
- **Channex 숙소·객실·요금제 자동 생성.** 사람이 만든다(5절 3번)
- **웹훅.** 피드 수신만 한다(5절 4번)
- **통화 지원.** 원화만 다룬다(검토-01 3절 8번). 시험용 숙소 문제는 5절 2번
- **숙소 등록 화면·회원가입·역할별 권한.** 다음 지시서들
- **배포 환경의 심사 조직에 Channex 연결을 만드는 것.** 코드는 배포하되 연결은 로컬에서 시험한다

## 4. 지켜야 할 제약

### Channex 에만 해당하는 것

- **API 키를 저장소·문서·로그·응답·대화에 남기지 않는다.** `.env` 와 자격 증명 저장소에만.
  **예외 메시지에 요청 헤더나 URL 이 실리지 않는지 본다** — iCal 연결 실패 예외에 주소가
  실리던 결함(`a7c9df2`)과 같은 자리다
- **부킹닷컴 테스트 숙소는 공용이다.** 수시로 지워지고 남도 쓴다. "Channel Already Exists" 면
  다른 숙소 식별자를 쓴다. **방과 요금제를 둘 다 매핑해야 채널이 켜진다**(Channex 문서)
- **테스트 예약은 Channex 문서가 안내하는 부킹닷컴 테스트 주소와 테스트 카드로만** 만든다.
  실제 카드를 쓰지 않는다. 이 문서에 카드 번호를 적지 않는다
- **픽스처는 스테이징의 실제 응답을 떠서 쓴다.** 손으로 적은 응답은 검증이 아니라 가정이다
  (인계메모 6절). 뜬 응답에서 키·개인정보는 지운다
- **ack 는 처리가 커밋된 뒤에만.** 롤백된 처리를 ack 하면 그 예약은 다시 오지 않는다.
  반대로 ack 가 실패하면 같은 리비전이 다시 온다 — 멱등성이 흡수해야 한다

### 그대로 가는 것

- **예외로 흐름을 제어하지 않는다.** 먼저 조회해 분기한다(트랜잭션 경계, 인계메모 6절)
- **`@Transactional` 메서드를 같은 클래스에서 부르지 않는다.** 스케줄러 진입점을 그대로 부르는
  테스트를 둔다 — Outbox 결함이 그 자리였다
- **자기 모듈 밖의 테이블을 SQL 로 읽지 않는다.** `JdbcTemplate` 없음
- **`ChannelRoundTripTest` 는 병렬로 돌리지 않는다**
- 주석과 문서는 한국어, 식별자는 영어, 테스트 이름은 한국어 서술형

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. 범위 | **예약 수신 + 재고·요금 전송**(사용자, 09-17). 메시지·인증·통화는 뒤 |
| 2. 시험 대상 | **Channex 스테이징의 부킹닷컴 테스트 숙소.** 에어비앤비는 연결하지 않는다 |
| 3. Channex 쪽 숙소·객실·요금제 | 사람이 Channex 화면에서 만들고 식별자를 매핑에 넣는다 |
| 4. 예약 수신 방식 | **리비전 피드를 주기적으로 가져온다.** 웹훅은 만들지 않는다 |
| 5. 200 의 경고 | **실패로 다룬다.** 성공으로 닫지 않는다 |

### 2번의 근거

**에어비앤비는 실제 리스팅이고 업체의 영업 데이터다.** 스테이징이라도 에어비앤비 연결은
실제 달력을 움직인다(조사-04 3절). 허락 없이 하지 않는다.

**부킹닷컴 테스트 숙소는 GBP·EUR·JPY·USD 뿐이다.** StaySync 는 원화만 다루지만 요금은 단위
없는 숫자라 **"150"을 USD 숙소로 보낼 수는 있다.** 화면은 "150원"으로 보이므로 —

- **시험은 로컬의 시험용 조직에서만 한다.** 심사 조직(`1차 심사`)에 만들지 않는다
- 시험용 판매 단위의 요금을 그 통화에 맞는 숫자로 넣고, Channex 숙소·요금제 통화를 그
  통화로 만든다. **이 불일치를 8절에 적어 둔다**

**KRW 는 받는다**(09-17, Channex `/currencies` 목록). 그러나 **부킹닷컴 테스트 숙소는 요금제
통화가 같아야 한다**(Channex 문서 — GBP 숙소는 GBP 요금제). 채널의 통화 칸은 호텔 ID 를 넣자
그 호텔 통화(EUR)로 잠겼고, 환산한다는 문서는 찾지 못했다. **그래서 EUR 시험 숙소를 따로
만들었다**(사용자 결정, 6절 표). 시험용 조직의 요금은 EUR 숫자로 넣는다. 채널 목록 응답의
`channel_restrictions`(Airbnb USD·1000, Booking.com EUR·500)의 뜻은 아직 모른다 — 에어비앤비
단계에서 원화 숙소를 쓸 수 있는지와 함께 본다

### 3번의 근거

자동 생성은 편하지만 **삭제·동기화 규칙이 따라온다**(Channex 문서가 "없어진 것은 지운다"까지
적는다). 한 숙소로 시험하는 지금은 손으로 만드는 편이 빠르고, 잘못 지울 위험이 없다.
판매 단계에서 등록 화면과 함께 다시 본다.

### 4번의 근거

**Channex 가 권하는 수신 방식이 피드 + ack 다.** 웹훅은 **서명이 없고 순서가 뒤바뀌어
오며**, 문서도 "웹훅은 가져오라는 신호로만 쓰라"고 한다. 신호 없이 주기적으로 가져와도 결과가
같다. 기존 `ChannelBookingPoller` 모양을 따르면 된다.

**주기는 Claude Code 가 정한다.** 확인 안 된 예약은 30분 동안 다시 오고 그 뒤 메일이 가므로
30분보다 훨씬 짧아야 한다.

**인증의 "폴링 루프 불가"는 ARI 전송에 대한 것이다.** 우리 DB 를 주기적으로 훑어 ARI 를 보내지
말라는 뜻이고, 예약 피드를 가져오는 것과는 다르다. ARI 는 지금처럼 변경이 전송을 일으킨다.

### 5번의 근거

**이 프로젝트의 결함은 거의 다 "정상 경로에 증상이 없는" 모양이었다.** 200 과 경고를
성공으로 보면 채널 재고가 틀린 채로 "동기화됨"이 된다. 12주차의 능력 선언 결함이 조용히
건너뛰던 것과 같은 모양이다.

**원래 있던 `StaySync 개발 테스트`(KRW, `디럭스 더블`)는 건드리지 않았다.** 나중에 원화 채널(업체
허락 뒤 에어비앤비 등)에 쓴다. **요금 정수 전송은 최소 단위다** — 요금제를 `rate: 10000` 으로
만들었더니 `"100.00"` 으로 저장됐다. 2절 B 의 "소수 문자열" 규칙의 근거다.

**API 키는 사람이 넣는다.** Channex 가 9월에 API 키에 IP 허용 목록을 붙였고 권장한다 — 배포
서버(`3.35.108.26`)와 개발 PC 를 넣을지 정한다.

연결.

1. 채널 연결 화면에서 CHANNEX 연결을 만들고 매핑할 수 있다. **API 키가 화면·응답·로그에
   보이지 않는다**
2. **같은 판매 단위에 iCal 과 Channex 를 함께 매핑하면 거절된다**

전송.

3. **캘린더에서 재고를 바꾸면 Channex 스테이징의 재고가 바뀐다.** Channex API 로 되읽어 확인한다
4. **요금을 바꾸면 Channex 요금이 바뀐다.** 소수 문자열로 갔는지 요청을 본다
5. 30일 요금 일괄 변경이 요청 몇 번으로 끝나는지 적는다(병합·압축이 도는지)
6. **429 를 받으면 그 숙소만 1분 멈추고 재시도하는 테스트**
7. **200 + 경고를 실패로 다루는 테스트** — 스테이징에서 뜬 실제 경고 응답으로

수신.

8. **부킹닷컴 테스트 예약이 StaySync 캘린더에 뜨고, 금액이 채워지고, ack 된다**
9. **수정(날짜 변경)과 취소가 반영된다.** 취소면 재고가 돌아온다
10. **같은 리비전을 두 번 받아도 예약이 하나인 테스트.** ack 실패 뒤 재수신이 이 경우다
11. **처리가 롤백되면 ack 하지 않는 테스트**
12. **매핑 없는 예약이 조용히 사라지지 않는 테스트**
13. 한 번에 여러 리비전(생성 → 수정 → 취소)이 오는 테스트
14. 통화가 다른 리비전을 막는 테스트

전체.

15. `AdapterContractTest` 에 Channex 가 들어가고 선언과 구현이 맞는다
16. **스케줄러 진입점을 그대로 부르는 테스트**(수신 주기, 전송 워커)
17. `./gradlew build`, `npm run build`, `npm run test`, `ModularityTest` 통과
18. **브라우저 확인** — 로컬에서 재고·요금 변경 → Channex 반영, 테스트 예약 → 캘린더 막대
    (색이 회색이 아닌지 — 라벨 맵에 Channex 경유 채널 코드가 있는지), 리포트 채널 믹스
19. 배포한다. **심사 조직에는 연결을 만들지 않고** 기존 화면이 그대로인지만 본다

**3·7·8·11·12 를 빠뜨리지 않는다.** 3은 이 주차의 존재 이유, 7은 성공처럼 보이는 실패,
8은 금액이 채워지는 첫 실제 경로, 11은 다시 오지 않는 예약, 12는 조용히 사라지는 예약이다.
