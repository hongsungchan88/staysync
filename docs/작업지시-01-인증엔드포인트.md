## 1. 지금 상태

1단계(보안 의존성과 JWT 기반)는 끝났다. `feat/identity-jwt-auth` 브랜치의 `a83a33a`
커밋이며 테스트 18건이 통과한 상태다. 저장소에 다음이 있다.

```
shared/security/       Role, AuthenticatedUser
identity/domain/       Organization, UserAccount, UserStatus, RefreshToken
identity/security/     JwtProperties, JwtTokenService, SecurityConfig
identity/              OrganizationRepository, UserAccountRepository, RefreshTokenRepository
test/identity/security/  JwtPropertiesTest, JwtTokenServiceTest, PasswordEncoderTest
```

`refresh_token` 테이블과 인덱스 세 개(`uq_refresh_hash`, `idx_refresh_user`,
`idx_refresh_expires`)가 V1 에 들어와 있다. `RefreshTokenRepository` 에
`findByTokenHash`, `revokeAllOfUser`, `deleteExpiredBefore` 가 이미 선언돼 있으므로
새로 만들지 말고 이것을 쓴다.

저장소 전체에 컨트롤러가 한 개도 없다. HTTP 표면이 아직 없는 상태다.

`Role` 을 `identity` 가 아니라 `shared/security` 에 둔 판단은 맞다. 되돌리지 말 것.
인가는 거의 모든 모듈의 웹 계층에서 일어나므로 identity 에 두면 그 모듈들이 전부
identity 를 참조하게 되고 `ModularityTest` 가 깨진다.

### 함께 처리할 스키마 수정 하나

`user_account.status` 에만 CHECK 제약이 없다. `role` 에는 `chk_user_role` 이 있고
`property.status`, `unit.unit_kind`, `unit.housekeeping` 에도 다 있는데 여기만 빠졌다.
enum 이 값 범위를 관리한다는 것만으로는 애플리케이션 밖에서 들어오는 값을 막지 못한다.

```sql
CONSTRAINT chk_user_status CHECK (status IN ('ACTIVE','SUSPENDED','WITHDRAWN'))
```

값 목록은 `UserStatus` enum 에 실제로 있는 상수에 맞춘다. 위는 예시다.
지금은 `clean-on-start: true` 라 V1 을 직접 고치면 된다. 스키마가 안정된 뒤였다면
새 마이그레이션을 만들고 기존 데이터를 옮겨야 했다.

## 2. 이번에 만드는 것

### A. RefreshTokenService

ADR 0005 마지막 항목이 "회전과 재사용 탐지는 2단계에서 구현한다"고 미뤄 둔 부분이다.
책임은 네 가지다.

1. 발급 — 128비트 난수를 만들어 원문은 호출자에게 주고, SHA-256 소문자 16진수 해시만
   저장한다. 만료는 14일
2. 검증 — 제시된 원문을 해시해 조회한다. `revoked_at` 이 있거나 만료됐으면 거절
3. 회전 — 새 토큰을 발급하고 이전 행의 `replaced_by` 에 새 행 식별자를 적는다
4. 재사용 탐지 — `replaced_by` 가 이미 채워진 토큰이 들어오면 도난으로 보고
   `revokeAllOfUser` 로 그 사용자의 살아 있는 토큰을 전부 무효화한다

거절 사유를 로그에서 구분할 수 있어야 한다. ADR 0005 가 "만료됐다"와 "존재한 적 없다"를
가르려고 정리에 7일 유예를 둔 이유가 이것이다. 유예를 두고 정작 로그가 둘을 뭉뚱그리면
설계가 무의미해진다.

클라이언트에게 돌려주는 오류는 갱신 실패 하나로 통일한다. 재사용이 탐지됐다는 사실을
응답으로 알려 줄 이유가 없다.

### B. 인증 엔드포인트

| 메서드 | 경로 | 인증 | 하는 일 |
|---|---|---|---|
| POST | `/api/auth/signup` | 불필요 | 조직과 OWNER 계정을 함께 만든다 |
| POST | `/api/auth/login` | 불필요 | 액세스 토큰을 본문에, 리프레시 토큰을 쿠키에 담아 준다 |
| POST | `/api/auth/refresh` | 불필요 | 쿠키의 리프레시 토큰을 회전시키고 새 쌍을 준다 |
| POST | `/api/auth/logout` | 필요 | 쿠키의 토큰을 무효화하고 쿠키를 지운다 |
| GET | `/api/auth/me` | 필요 | 현재 사용자 정보를 준다 |

**회원가입.** 가입 한 번에 조직 하나와 OWNER 한 명이 생긴다. 개인 호스트가 대상이라
조직을 따로 만드는 절차를 두지 않는다. 비밀번호는 BCrypt cost 12(계획서 15.1).
이메일은 `uq_user_email` 로 전역 유일하므로 중복이면 409 로 거절한다.

**토큰 전달.** 액세스 토큰은 응답 본문 JSON, 리프레시 토큰은 쿠키다. 근거는 ADR 0006
(5절 1번). 쿠키 속성은 다음과 같다.

```
HttpOnly; Secure; SameSite=Strict; Path=/api/auth/refresh; Max-Age=14일
```

`Path` 를 좁히는 것이 이 설계의 요점이다. 쿠키가 실려 나가는 요청이 갱신 하나로 줄어든다.
로그아웃도 이 쿠키를 읽어야 하므로 `Path` 를 어떻게 맞출지 결정해야 한다. 두 경로를
포함하도록 `/api/auth` 로 넓히거나, 로그아웃을 `/api/auth/refresh` 아래 두는 방법이 있다.
넓히는 쪽을 택하되 그 선택을 ADR 0006 에 한 줄로 적는다.

local 프로파일에서는 `Secure` 를 끈다. HTTPS 가 아니면 브라우저가 쿠키를 저장하지 않아
개발이 막힌다. 프로파일로 갈라 두고 운영 기본값은 켜 둔다.

**나머지 규칙.**

- 로그인 성공 시 `user_account.last_login_at` 을 갱신한다. 컬럼이 이미 있다
- 로그인 실패 응답에서 "없는 이메일"과 "틀린 비밀번호"를 구분하지 않는다.
  구분하면 계정 존재 여부가 새어 나간다
- `status` 가 `ACTIVE` 가 아닌 계정은 로그인을 거절한다. 이때도 같은 응답을 쓴다
- 갱신은 인증 없이 호출된다. 리프레시 토큰 자체가 자격증명이다.
  `SecurityConfig` 의 `permitAll` 경로에 넣는다
- 로그아웃은 멱등하다. 이미 무효화된 토큰이나 쿠키가 없는 상태로 불러도 200 이다

### C. 로그인 시도 제한

계정 기준으로 센다. 최근 15분 안에 연속 5회 실패하면 그 이메일의 로그인을 10분간
거절하고 429 를 준다. 성공하면 카운터를 지운다.

**존재하지 않는 이메일도 똑같이 센다.** 존재하는 계정에만 잠금이 걸리면 429 응답 자체가
"그 이메일은 가입되어 있다"는 신호가 된다. 위에서 로그인 실패 응답을 통일한 이유가
여기서 무너지면 안 된다.

저장은 메모리다. 인스턴스가 하나뿐이고, 재기동하면 초기화되는 것이 이 범위에서는
문제가 되지 않는다. 분산 저장이 필요해지는 시점은 인스턴스를 늘릴 때이며 그때 다시 본다.
만료된 항목이 계속 쌓이지 않도록 시간 기반으로 비워지는 구조를 쓴다.

### D. 만료 토큰 정리 배치

`RefreshTokenRepository.deleteExpiredBefore()` 를 하루 한 번 `@Scheduled` 로 부른다.
기준 시각은 현재에서 7일을 뺀 값이다(ADR 0005 의 유예).

인스턴스가 하나뿐이라 ShedLock 은 아직 걸지 않는다. `shedlock` 테이블과 의존성 주석이
이미 준비돼 있으니 그대로 둔다.

`@EnableScheduling` 이 켜져 있는지 확인한다. 켜져 있지 않으면 배치가 조용히 실행되지
않는다. 테스트에서는 스케줄러가 아니라 메서드를 직접 불러 검증한다.

### E. 숙소·판매 단위·요금제 REST API

서비스 계층(`UnitCatalogService`, `UnitRegistrationService`)은 이미 있고 HTTP 표면만
없다. 계획서 12.2 의 P1 3주차 항목이다.

```
GET    /api/properties                       숙소만. units 없음
POST   /api/properties
GET    /api/properties/{id}                  units 포함
PATCH  /api/properties/{id}
GET    /api/properties/{propertyId}/units
POST   /api/properties/{propertyId}/units
PATCH  /api/units/{id}
GET    /api/units/{unitId}/rate-plans
```

**응답 형태.** 목록은 평면이고 상세에만 `units` 를 싣는다(5절 4번). 페이지네이션은
넣지 않는다. 개인 호스트는 숙소가 한두 개다.

캘린더는 이 API 를 쓰지 않는다. 계획서 13.5 가 `/api/properties/{id}/calendar` 전용
엔드포인트와 자체 응답 형태를 이미 정해 뒀다. 그쪽은 P2 다.

요금제는 `UnitRegistrationService` 가 판매 단위를 만들 때 기본 요금제를 자동 생성한다
(CLAUDE.md 데이터 모델 절). 생성 엔드포인트를 따로 열지 않는다. 조회만 둔다.

**조직 스코핑이 이 작업의 핵심이다.** 모든 조회와 변경은 `AuthenticatedUser.orgId` 로
좁힌다. 요청 경로나 본문에 담긴 조직 식별자를 믿지 않는다. 다른 조직의 숙소 식별자를
넣었을 때 데이터가 새어 나가지 않아야 한다.

`unit` 과 `rate_plan` 에는 `org_id` 가 없다. 각각 `property_id` 와 `unit_id` 를 거슬러
올라가 소유를 확인해야 한다. 이 확인을 컨트롤러마다 손으로 반복하지 않도록 한곳에 모은다.

### F. 통합 테스트

완료 조건은 7절에 있다.

## 3. 이번에 만들지 않는 것

- 비밀번호 재설정, 이메일 인증, 사용자 초대. P5 이후다
- 역할별 인가 규칙(`@PreAuthorize`). ADR 0004 가 "3~5단계에서 붙인다"고 적어 뒀다.
  이번에는 인증 여부와 조직 스코핑까지만 한다
- 예약 API. 4주차다
- Outbox 발행과 감사 로그. 6주차다
- 캘린더 조회 API. P2 다

## 4. 지켜야 할 제약

이미 결정된 것들이다. 되돌리지 말고 확인만 한다.

- **모듈 경계.** `property` 컨트롤러가 `identity` 를 참조하면 `ModularityTest` 가 깨진다.
  인증 정보는 `SecurityContext` 에서 `shared.security.AuthenticatedUser` 로만 읽는다
- **오류 표현.** `shared/error` 의 `DomainException`, `ApiError`, `GlobalExceptionHandler`
  를 쓴다. 컨트롤러마다 예외 처리를 새로 만들지 않는다
- **엔티티에 setter 를 두지 않는다.** 상태 변경은 의미 있는 메서드로 표현한다.
  리프레시 토큰이라면 `rotateTo(newToken)`, `revoke(now)` 같은 이름이 된다
- **`ddl-auto: validate`.** 엔티티에 컬럼을 더하면 V1 과 JDBC 타입 코드까지 맞아야 한다.
  `token_hash` 가 `CHAR(64)` 가 아니라 `VARCHAR(64)` 인 이유가 이것이다
- **테스트 포트.** 앱과 다른 15433 과 `.localdb-test` 를 쓴다
- **주석은 "왜".** 코드를 읽으면 아는 것은 쓰지 않는다
- **테스트 이름은 한국어 서술형.** 예: `교체된_리프레시_토큰이_다시_오면_전부_무효화된다`

## 5. 착수 전에 받은 결정

| 항목 | 결정 |
|---|---|
| 1. 리프레시 토큰 전달 | 액세스는 응답 본문, 리프레시는 HttpOnly 쿠키. ADR 0006 으로 기록 |
| 2. 회원가입 | 이번에 연다. 가입 한 번에 조직 1개와 OWNER 1명 |
| 3. 로그인 시도 제한 | 넣는다. 계정 기준 메모리 카운터, 5회 실패 시 10분 거절 |
| 4. 숙소 목록 응답 | 목록은 평면, 상세는 `units` 포함. 페이지네이션 없음 |

1번의 근거는 두 토큰의 위험도가 다르다는 것이다. 액세스는 30분이고 헤더에 실어야 하니
자바스크립트가 읽을 수 있어야 한다. 리프레시는 14일인데 갱신 요청에서만 쓰이므로
자바스크립트가 읽을 이유가 없다. 읽을 이유가 없는 것은 읽히지 않게 한다.
ADR 0006 은 이 논거와 함께 검토한 대안(둘 다 본문, 둘 다 쿠키)을 남긴다.

## 6. P2 프론트엔드가 이어받을 때 알아야 할 것

지금 결정한 것들이 P2 에서 제약이 된다. 미리 적어 둔다.

- Vite 개발 서버에서 쿠키가 붙으려면 프록시로 같은 출처를 만들어야 한다.
  `SameSite=Strict` 라 다른 출처에서는 쿠키가 실리지 않는다
- 갱신 요청은 `credentials: 'include'` 가 필요하다
- 클라이언트는 갱신 응답을 받기 전에 이전 상태를 버리면 안 된다. 네트워크가 끊겨
  재시도하면 재사용 탐지에 걸려 전체 로그아웃이 된다. ADR 0005 결과 항목에 적혀 있다
- 액세스 토큰은 메모리에 둔다. 새로고침하면 쿠키로 갱신해 다시 받는 흐름이 된다

## 7. 완료 조건

다음 일곱 개가 모두 통과하면 2단계가 끝난 것으로 본다.

1. 가입 → 로그인 → 보호된 숙소 API 호출 → 갱신 → 로그아웃 → 갱신 실패까지 한 번에 도는
   통합 테스트 한 건
2. 회전된 리프레시 토큰을 다시 제시하면 그 사용자의 토큰이 전부 무효화되는 테스트
3. 다른 조직의 숙소 식별자로 조회했을 때 데이터가 나오지 않는 테스트.
   숙소, 판매 단위, 요금제 세 층에서 각각 확인한다
4. 토큰 없이 보호된 경로를 부르면 401, 만료된 액세스 토큰이면 401
5. 로그인을 5회 실패하면 429 가 나오고, 존재하지 않는 이메일도 같은 응답을 주는 테스트
6. 로그인 응답의 `Set-Cookie` 에 `HttpOnly`, `Secure`, `SameSite=Strict`, `Path` 가
   실제로 붙는지 확인하는 테스트
7. `ModularityTest` 와 `InventoryConcurrencyTest` 가 계속 통과

MockMvc 는 쿠키 속성을 강제하지 않는다. 6번을 빼면 쿠키 결정이 검증되지 않은 채
남고, 속성 하나가 빠져도 아무 테스트도 실패하지 않는다.

3번을 빠뜨리지 않는다. 계획서 15.1 의 인가 항목이 약속한 것이고, 나중에 붙이려면
컨트롤러를 전부 다시 봐야 한다.

## 8. 브랜치와 기록

- 브랜치는 `feat/identity-jwt-auth` 를 이어 쓴다. 새로 자르지 않는다
- 토큰 전달 방식은 ADR 0006 으로 남긴다. 기존 5건의 형식을 따른다
- 끝나면 CLAUDE.md 의 "인증" 절에 쿠키 결정을, "현재 상태" 절에 진척을 반영한다
- 이 문서에 없는 판단이 필요해지면 임의로 정하지 말고 물어본다
