## 1. 지금 상태

P1 이 끝났다. `p1-complete` 태그가 `9655460` 에 붙어 있고 `main` 은 `origin/main` 과
동기 상태다. 테스트 93건 통과. 로컬 브랜치는 `main` 하나다.

여기서 성격이 바뀐다. P1 까지는 백엔드 한 덩어리였는데 7주차는 React 프로젝트를
처음 세우는 단계다. 계획서 일정보다 한 달 가까이 앞서 있으니 그 여유를 여기에 쓴다.

### 준비돼 있는 것

- `inventory_ledger` — `(unit_id, stay_date)` 기본키, `total_units`, `booked_units`,
  `held_units`, `stop_sell`. 캘린더 셀의 잔여 재고와 판매중지가 여기서 나온다
- `rate_calendar` — V1 에 있다. **엔티티와 레포지토리가 아직 없다.** pricing 모듈이
  `package-info.java` 하나뿐이다
- `overbooking_conflict` — V1 에 있다. 마찬가지로 엔티티가 없고, 행을 만드는 경로도
  아직 없다. 충돌은 P3 의 채널 수신에서 처음 생긴다
- `reservation`, `reservation_night` — 4주차에 끝났다. 상태 전이가 전부 구현돼 있다
- `property.OwnedResources` — 조직 스코핑 확인이 한곳에 모여 있다. 컨트롤러는 반드시
  이걸 거친다
- `docs/와이어프레임-01-통합캘린더.html` — 화면이 이미 그려져 있다. 브라우저에서 열면
  드래그 기간 선택과 예약 막대 이동까지 동작한다. **화면 명세는 이 파일이다.**
  이 지시서가 화면을 다시 그리지 않는 이유다

### 없는 것

- 프론트엔드 전체. 저장소에 `frontend/` 디렉터리가 없다
- pricing, messaging, ops, payment, ai, analytics 모듈의 내용물
- 역할별 인가(`@PreAuthorize`). ADR 0004 가 3~5단계로 미뤄 뒀고 이번에도 대상이 아니다

## 2. 이번에 만드는 것

### A. 캘린더 조회 API

계획서 13.5 가 응답 모양의 명세다. 엔드포인트는 그대로 쓴다.

```
GET /api/properties/{propertyId}/calendar?from=2026-12-20&to=2027-01-18
```

**조직 스코핑이 먼저다.** `OwnedResources` 로 `propertyId` 가 요청자의 조직 것인지
확인하고, 아니면 404 로 답한다. 403 이 아니라 404 인 이유는 3주차와 같다 — 남의 숙소가
존재한다는 사실 자체를 알리지 않는다. 확인을 통과한 뒤의 그리드 조회는 `propertyId`
만으로 돈다. 스코핑과 조회 최적화가 서로 얽히지 않는다.

**범위 쿼리 세 번이다.** 셀마다 질의하지 않는다는 것이 12.2 가 말하는 최적화이지
SQL 문장을 하나로 만들라는 뜻이 아니다. 각 모듈이 자기 테이블만 한 번씩 범위로 읽고
조립한다.

```
inventory_ledger   (unit_id IN ..., stay_date BETWEEN from AND to)       booking
rate_calendar      (rate_plan_id IN ..., stay_date BETWEEN from AND to)  pricing
reservation        기간이 겹치는 것                                       booking
```

> 정정 (2026-09-02, 구현 중 확인). 초판은 `rate_calendar` 도 `unit_id` 로 적었으나
> 실제 V1 스키마는 `rate_plan_id` 가 키다. 판매 단위 → 요금제 매핑이 필요하고,
> `rate_plan` 은 property 의 테이블이므로 매핑도 property 가 준다.
> `UnitCatalog.summariesOf()` 가 `defaultRatePlanId` 를 함께 넘긴다.
> 이걸 안 넘기면 pricing 이나 조립부가 남의 테이블을 뒤지게 된다.

세 번 모두 기본키나 인덱스의 범위 스캔이다. 2,700셀이면 왕복 세 번에 수천 행이고,
8.2 의 1초 목표에 여유가 있다. 한 모듈이 다른 모듈의 테이블을 조인해 왕복을 하나
줄이는 대신 경계를 깨는 쪽은 택하지 않았다(5절 4번).

조립 규칙 네 가지.

- `avail` 은 `total_units - booked_units - held_units` 다. 원장에 행이 없는 날은
  아직 아무도 예약하지 않은 날이므로 `unit.total_units` 를 그대로 쓴다.
  **행이 없는 것과 재고가 0인 것을 같게 다루지 않는다**
- `price` 는 `rate_calendar` 값이고, 없으면 `unit.base_price` 로 떨어진다
- `minStay` 와 `stopSell` 도 같은 방식이다. `stop_sell` 은 `inventory_ledger` 에 있고
  `min_stay` 는 `rate_calendar` 에 있다. 출처가 다르다는 걸 알고 짠다
- `conflict` 는 항상 `false` 다. 5절 5번을 볼 것

**기간에 상한을 둔다.** 8.2 가 최대 365일이라고 잡았으니 `to - from` 이 365일을
넘으면 거절한다. 상한이 없으면 한 번의 요청으로 원장 전체를 긁을 수 있다.
`from > to` 도 거절한다.

**응답에 연락처를 담지 않는다.** 13.5 예시의 `guestName` 까지는 담는다. `guest.name`
은 평문이라 새로 새는 것이 없다. 전화번호와 이메일은 담지 않는다. ADR 0007 의 결정과
5~6주차 이벤트 페이로드에서 그은 선을 화면 응답에도 그대로 적용한다. 캘린더에서
연락처가 필요해지는 순간은 예약 상세이고 그건 이 API 가 아니다.

### B. pricing 모듈 최소 구현

`rate_calendar` 를 읽을 수 있게만 만든다. 요금 편집은 9주차다.

- 엔티티와 레포지토리. `ddl-auto: validate` 이므로 V1 의 컬럼 타입과 정확히 맞춘다
- **조회용 인터페이스를 pricing 최상위 패키지에 공개한다.** `property.UnitCatalog` 가
  그 형식이다. 캘린더 조립부는 이 인터페이스만 참조하고 `pricing.domain` 을 보지 않는다
- 값이 없는 날을 `unit.base_price` 로 채우는 책임을 어디에 둘지 정한다. pricing 이
  `unit.base_price` 를 알면 pricing → property 의존이 생긴다. 조립부에서 채우는 편이
  의존을 덜 만든다

### C. 프론트엔드 프로젝트 셋업

`staysync/frontend/` 에 만든다. 백엔드는 지금 자리(`staysync/src/`)에 그대로 둔다.

계획서 11.2 의 스택 중 7주차에 넣을 것과 미룰 것을 나눈다.

| 지금 넣는다 | 미룬다 |
|---|---|
| React 19, TypeScript 5.6, Vite 6 | `@tanstack/react-virtual` (8주차) |
| React Router 7, TanStack Query 5 | dnd-kit (8주차) |
| Zustand, Tailwind CSS 4, shadcn/ui | Recharts (P5 리포트) |
| Zod, React Hook Form | Playwright (8주차 이후) |
| Vitest, Testing Library | SSE (9주차) |

쓰지 않는 의존을 미리 넣지 않는다. 5~6주차에 워커 셋을 만들지 않은 것과 같은 이유다.

**Vite 프록시.** 개발 서버는 5173 이고 `/api` 로 시작하는 요청만 8080 으로 넘긴다.
브라우저가 보는 출처가 하나여야 한다. ADR 0006 이 리프레시 토큰을 `SameSite=Strict`
쿠키로 정했기 때문에, 출처가 다르면 갱신 요청에 쿠키가 실리지 않고 로그인 유지가
조용히 깨진다. 쿠키 `Path` 가 `/api/auth` 인 것도 프록시 경로와 맞아야 한다.

**토큰을 다루는 방식.** 액세스 토큰은 메모리에 둔다. `localStorage` 에 넣지 않는다.
XSS 하나로 30분짜리 토큰이 통째로 나가는데, 리프레시를 `HttpOnly` 로 감춘 결정이
그러면 의미가 없어진다. 새로고침하면 액세스 토큰이 사라지므로 앱이 뜰 때 갱신을 한 번
호출해 복구한다. 401 이 오면 갱신을 한 번 시도하고 그것도 실패하면 로그인으로 보낸다.
**갱신 요청이 동시에 여러 개 나가지 않게 한다.** 리프레시 토큰은 회전하므로
(ADR 0005) 두 번째 요청이 이미 교체된 토큰을 들고 가면 재사용으로 판정돼 그 사용자의
토큰이 전부 무효화된다. 정상 사용 중에 로그아웃되는 증상으로 나타난다.

**넣을 화면은 로그인과 캘린더 둘뿐이다.** 로그인은 캘린더를 보려면 필요해서 넣는다.
회원가입 화면은 개발용 계정 하나면 되므로 이번에는 만들지 않는다.

### D. 캘린더 그리드 렌더링

와이어프레임이 화면 명세다. 7주차에는 정적인 그리드까지 간다.

- 좌측 판매 단위 목록과 상단 날짜 헤더를 고정한다. 세로·가로 스크롤에도 붙어 있어야 한다
- 기본 30일을 그린다
- 셀에 잔여 재고, 요금, 최소숙박, 판매중지를 표시한다
- 예약을 막대로 그린다. 채널별 색 구분까지. **드래그로 옮기는 것은 8주차다**
- 빈 상태(판매 단위가 없음), 로딩, 오류 세 가지를 만든다. 와이어프레임에 있다

**가상 스크롤은 8주차다.** 30일 × 판매 단위 몇 개는 전부 그려도 문제가 없고,
가상 스크롤을 처음부터 넣으면 무엇이 느린지 알기 전에 최적화하는 셈이 된다.

### E. clean-on-start 해제

CLAUDE.md 가 "P2 무렵 스키마가 안정되면 끈다"고 적어 뒀고 지금이 그 시점이다.
프론트를 붙이는 동안 기동할 때마다 계정이 사라지면 매번 회원가입부터 다시 한다.

끄는 순간부터 규칙이 하나 바뀐다. **V1 을 수정하지 않는다.** Flyway 체크섬 관리가
시작되므로 스키마를 바꿔야 하면 새 버전을 더한다. CLAUDE.md "하지 말 것" 절의 괄호
예외가 이번에 사라진다.

`resetLocalDb` 태스크가 이제 실제로 필요해진다. 동작을 확인한다.

## 3. 이번에 만들지 않는 것

- **가상 스크롤, 예약 막대 드래그 이동, 기간 선택.** 8주차다
- **요금·제약 일괄 편집, 요금 규칙 엔진, SSE.** 9주차다
- **충돌 조회.** 행을 만드는 경로가 P3 에 생긴다. 지금 만들면 항상 빈 결과를 돌려주는
  쿼리가 된다
- **Redis 월 단위 캐시.** 8.2 가 언급하지만 `local` 프로파일에 Redis 가 없다.
  측정해서 필요하다고 나온 뒤에 본다. 지금 넣으면 무효화 로직만 늘고 검증할 수 없다
- **역할별 인가.** 3~5단계로 미뤄져 있다
- **회원가입·예약목록·인박스·요금관리 화면.** 8.1 의 나머지 경로는 각자의 단계에 있다
- **백엔드 디렉터리 재배치.** 5절 1번

## 4. 지켜야 할 제약

- **모듈 경계.** 캘린더 조립부가 **다른 모듈의** `domain` 하위 패키지를 직접 보지
  않는다. 각 모듈이 최상위에 공개한 인터페이스만 쓴다. `ModularityTest` 가 깨지면
  설계가 틀린 것이다.
  > 정정 (2026-09-02). 초판이 `booking.domain` 까지 금지 대상으로 적었는데 이는 잘못이다.
  > 조립부는 `booking.calendar` 에 있고 `InventoryLedger` 와 `Reservation` 이 자기 모듈의
  > 타입이라 볼 수밖에 없다. 실제로 막으려던 것은 `property.domain` 과 `pricing.domain`
  > 이며 그건 지켜졌다. 조립부를 별도 최상위 모듈로 빼지 않은 이유는 세 소스 중 둘이
  > booking 것이고, booking → property 와 booking → pricing 이 둘 다 허용된 방향이기
  > 때문이다. 읽기 모델 하나를 위해 최상위 모듈을 늘리지 않는다
- **`OwnedResources` 를 거친다.** 요청 본문이나 경로의 조직 식별자를 믿지 않는다.
  조직은 `AuthenticatedUser.orgId` 에서만 온다
- **소유가 아닌 자원은 404.** 403 을 쓰지 않는다
- **`ddl-auto: validate`.** 엔티티를 더하면 V1 과 JDBC 타입 코드까지 맞아야 한다
- **오류 표현.** `shared/error` 의 `DomainException`, `ApiError`, `GlobalExceptionHandler`
- **테스트 포트.** 앱은 15433/`.localdb-test`, API 테스트는 15434/`.localdb-api`
- **주석은 "왜".** 테스트 이름은 한국어 서술형
- **프론트엔드도 같은 규칙이다.** TypeScript `strict`, 주석과 문서는 한국어,
  식별자는 영어. API 응답 타입은 Zod 스키마에서 끌어낸다. 손으로 쓴 타입과 실제 응답이
  어긋나면 런타임에야 드러난다

## 5. 착수 전에 받은 결정

| 항목 | 결정 |
|---|---|
| 1. 프론트엔드 위치 | `staysync/frontend/` 만 추가한다. 백엔드는 `staysync/src/` 에 그대로 둔다 |
| 2. clean-on-start | 끈다 |
| 3. Vite 프록시 | 개발 서버 5173, `/api` 만 8080 으로 프록시 |
| 4. 조직 스코핑 | `OwnedResources` 로 먼저 확인하고, 통과한 뒤 그리드를 조회한다 |
| 5. 단일 쿼리의 범위 | 모듈별 범위 쿼리 세 번 + 조립. 네이티브 조인 쿼리를 쓰지 않는다 |
| 6. 요금과 충돌 | 요금은 붙인다. 충돌은 자리만 남긴다 |

### 1번의 결과

계획서 11.4 는 `staysync/backend/` 와 `staysync/frontend/` 를 형제로 그렸는데 실제
저장소는 백엔드가 `staysync/src/` 에 바로 있다. 계획서에 맞추려면 백엔드를 통째로
옮겨야 하고 Gradle 설정과 경로와 CI 가 전부 따라 움직인다. 7주차 예산을 거기에 쓰는
대신 **계획서 11.4 를 실제 구조에 맞게 고친다.** 문서를 코드에 맞추는 방향이다.

이건 Cowork 세션이 한다. Claude Code 는 저장소만 보면 된다.

### 5번을 택한 이유

`inventory_ledger` 는 booking, `rate_calendar` 는 pricing 이다. 한 문장으로 조인하면
왕복이 하나 줄지만 한 모듈이 다른 모듈의 테이블을 직접 읽게 된다. `ModularityTest` 는
자바 패키지 참조를 보므로 이걸 잡지 못한다. 테스트가 못 잡는 위반은 다음에 또 나오고,
그때는 근거가 "지난번에도 했으니까"가 된다.

성능이 목표에 못 미치면 그때 다시 연다. 그 판단에는 F 의 측정값이 근거로 붙는다.

### 6번의 구체

`overbooking_conflict` 에 행을 만드는 경로는 P3 의 채널 수신에서 처음 생긴다.
지금 조회를 만들면 **항상 빈 결과를 돌려주는 쿼리와 그걸 확인하는 테스트**가 남는다.
5~6주차에 워커 셋을 만들지 않은 것과 같은 판단이다.

`conflict` 필드는 응답에 두되 항상 `false` 로 채운다. 프론트엔드는 이 값을 보고
셀을 표시하도록 짜 둔다. P3 에서 값이 실제로 채워지면 화면은 손대지 않아도 된다.
채우는 자리에 P3 이라고 주석을 남긴다.

## 7. 브랜치와 기록

브랜치를 둘로 자른다. 며칠짜리 작업이 단위다.

- `feat/calendar-api` — A, B, E
- `feat/frontend-setup` — C, D

- ADR 0009 로 프론트엔드 배치와 개발 서버 구성을 남긴다. **`SameSite=Strict` 쿠키
  때문에 프록시로 같은 출처를 만들었다는 것과, 액세스 토큰을 `localStorage` 에 두지
  않은 이유가 반드시 들어가야 한다.** 계획서 11.4 와 실제 구조가 달라진 것도 여기 적는다
- `clean-on-start` 해제는 ADR 까지 갈 결정은 아니다. CLAUDE.md 의 "실행 프로파일" 절과
  "하지 말 것" 절의 괄호 예외를 고치는 것으로 끝낸다
- 끝나면 CLAUDE.md "현재 상태" 절을 P2 7주차로 갱신한다. "프론트엔드는 아직 없다"는
  문장도 바뀐다
- 13번의 측정값을 남긴다. 8주차 범위를 정하는 근거가 된다
- 와이어프레임 미결 세 가지(그룹, 날짜 칸 너비, 막대 쌓기)는 7주차가 끝난 뒤에 정한다.
  실제 데이터를 그리드에 올려 보고 답하기로 했다. **7주차에 임의로 정하지 않는다**
- 이 문서에 없는 판단이 필요해지면 임의로 정하지 말고 물어본다
