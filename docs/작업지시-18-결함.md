## 2. 이번에 고치는 것

### A. 투숙 중(CHECKED_IN) 예약 — 검토-01 3절 9번

**A-1. 피드에서 빠졌다고 자동 취소하지 않는다.**
`ChannelBookingWriter.cancelMissing` 이 `findActiveOfChannel`(HOLD·CONFIRMED·CHECKED_IN)을 돌고,
`cancel()` 이 CHECKED_IN → CANCELLED 를 허용한다. 그래서 체크아웃 전에 피드에서 빠진 투숙 중
예약이 조용히 취소된다. 에어비앤비는 끝난 예약을 체크아웃 다음 날 빼므로 실제로는 게스트 취소
때뿐이지만, **투숙 중인 손님을 시스템이 혼자 취소하는 경로**다.

- 스냅샷 경로(`cancelMissing`)에서 CHECKED_IN 은 **취소하지 않고 경고 로그를 남긴다**(5절 1번)
- **명시적 취소 통지**(`applyToExisting` 의 `command.cancellation()`)는 그대로 둔다. 채널이 "취소"라고
  말한 것은 최종 사실이다(기존 주석). 이번 범위는 "안 보인다"를 "취소"로 읽는 자리뿐이다

**A-2. 날짜가 바뀌면 재고 원장이 따라간다.**
`applyToExisting` 은 `reservation.isActive()` 일 때만 원장을 옮기는데 `isActive()` 는 HOLD·CONFIRMED
뿐이다. 반면 같은 클래스의 `ACTIVE` 목록은 CHECKED_IN 을 포함한다. **"재고를 차지하는 상태"의
정의가 두 곳에서 갈려 있다** — 이것이 원인 자리다.

- `isActive()` 의 **호출자를 먼저 전부 훑고** 8절에 적는다. 정의를 고칠지, 호출 자리를 고칠지는
  그 뒤에 정한다(인계메모 6절 "절반만 고치고 닫은 결함")
- 같이 볼 것 — **CHECKED_IN 예약을 취소하거나 옮길 때 재고가 반납되는가.** `cancel()`·
  `changeStay`·`moveToUnit` 이 같은 판정을 쓰면 투숙 중 예약의 원장이 새거나 남는다
- CHECKED_OUT 은 안전하다(검토-01). 건드리지 않는다

### B. 같은 (날짜, 판매 단위) 충돌이 여러 행으로 쌓인다 — 확인-08 3절 2번

`raiseConflicts` 가 기존 OPEN 충돌을 찾지 않고 날짜마다 `save` 한다. 초과 예약이 둘이면 카드가
둘 뜨고, 먼저 생긴 카드는 적은 예약을 담은 낡은 스냅샷으로 남으며, 하나를 해소해도 다른 하나는
열려 있다. `reservation_ids BIGINT[]` 는 날짜당 한 행을 의도한 모양이다.

- **(판매 단위, 날짜)에 OPEN 충돌이 있으면 새 행을 만들지 않고 그 행의 예약 목록을 갱신한다**
- 해소는 그 한 행을 닫는다. 해소된(OPEN 아닌) 충돌은 건드리지 않는다 — 기록이다
- `applyToExisting` 의 날짜 변경 경로도 `reserveOrForce` → `raiseConflicts` 를 탄다. 같은 예약의
  수정이 여러 번 와도 한 행이어야 한다
- **확인만 하고 8절에 적는다(고치지 않는다)** — 충돌에 걸린 예약이 나중에 취소되면 OPEN 카드가
  어떻게 되는가. 고칠 일로 보이면 멈추고 묻는다

### C. `GET /api/reservations` 에 `from`/`to` 를 주면 500 — 확인-08 3절 3번

`ReservationRepository.search` 의 `(:from is null or r.period.checkOut > :from)` 에서 형 추론이
실패한다. 화면이 부르지 않는 경로라 증상이 없다.

- 고치고, **HTTP 엔드포인트를 그대로 부르는 테스트**로 막는다(리포지토리 단위 테스트만으로는
  이번 결함이 나온 자리를 안 지난다)

### D. 공개 HOLD 경로의 속도 제한 — CLAUDE.md "알고 남긴 구멍"

- **공개 HOLD 생성 요청을 클라이언트 IP 당 시간 창으로 센다.** 넘으면 HOLD 를 만들지 않고
  429 와 한국어 메시지를 돌려준다. 위젯이 그 메시지를 보여 준다
- 창과 상한은 `application.yml` 값으로 둔다. 시작값 — **10분에 5건**(5절 2번)
- 판정에 쓴 IP 를 **끝자리를 가려** 로그에 남긴다 — 거절은 WARN, 통과는 배포 환경 로그 수준에서도
  한 번은 보이게. 6절 14번이 이것으로 IP 판정을 확인한다
- **`LoginAttemptLimiter` 를 재사용하지 않는다.** CLAUDE.md 에 적힌 그대로 — identity 내부
  타입이고, 실패를 세어 잠그는 장치라 성공 요청에 겨누면 정상 손님이 잠기며, 상수를 로그인과
  공유한다
- 메모리에 둔다. **인스턴스 하나 전제다** — `ponytail:` 주석으로 상한과 넘어갈 길(Redis 등)을
  적는다. 오래된 항목이 쌓이지 않게 한다(2GB 서버)

## 4. 지켜야 할 제약

- **클라이언트 IP 를 제대로 얻는다.** 배포 환경은 Caddy → `app:8080` 이다. `getRemoteAddr()` 를
  그대로 쓰면 **모든 요청이 Caddy 의 내부 주소 하나로 보여 속도 제한이 전역 차단이 된다** —
  한 사람이 다섯 번 누르면 모든 손님이 막힌다. `application.yml` 에 전달 헤더 설정이 없다.
  - Caddy 는 `reverse_proxy` 에서 `X-Forwarded-For` 를 붙인다. 신뢰하지 않는 클라이언트가 보낸 값을
    그대로 넘기는지 확인하고 8절에 적는다. 앱 포트가 밖에 열려 있지 않은지는 확인-09 5절이 봤다
  - **같은 문제가 `LoginAttemptLimiter` 에도 있는지 확인한다.** 있으면 배포 환경에서 누군가 로그인을
    틀리면 모두가 잠긴다. 있으면 **이번에 같이 고친다** — 원인이 같은 자리다
- **예외로 흐름을 제어하지 않는다.** 속도 제한은 트랜잭션 밖(락·트랜잭션 전)에서 판정한다.
  B 는 먼저 조회해 분기한다(14주차, 유일 제약 위반을 잡는 방식이 롤백으로 죽었다)
- **테스트는 실제 진입점으로.**
  - A-1 은 `UnknownAmountReportTest` 처럼 **스텁 발행자 → `IcalAdapter` → 폴러 → 수신부**로.
    체크인 상태는 실제 체크인 API 로 만든다(UPDATE 로 흉내 내지 않는다 — 17주차 `ReportTest`)
  - B 는 채널 수신 경로(`ChannelBookingIntake.ingest`)로 초과 예약을 만든다. Mock 시뮬레이터나
    스텁으로. 락을 거치는 진입점이어야 한다
  - D 는 HTTP 로 부른다. IP 판정은 `X-Forwarded-For` 가 있는 요청과 없는 요청 둘 다
- 그대로 가는 것 — 자기 호출 금지, `JdbcTemplate` 없음, `ChannelRoundTripTest` 병렬 금지,
  주석·문서 한국어
- **마이그레이션이 필요해지면 멈추고 묻는다.** 이번 범위는 스키마 변경 없이 닫힐 것으로 본다

### 1번의 근거

"피드에 안 보인다"는 추정이다. 투숙 중에 추정으로 예약을 지우면 재고가 풀려 **손님이 있는 방이
다시 팔린다.** 반대로 남겨 두면 최악이 "끝난 예약이 하루 늦게 정리된다"이고, 체크아웃이 지나면
기존 규칙(체크아웃 지난 예약은 건드리지 않음)대로 과거가 된다.

### 2번의 근거

시작값 10분 5건 — 정상 손님은 한 번, 결제창을 닫고 다시 해도 두세 번이다. 한 IP 가 동시에 잡을 수
있는 HOLD 는 15분 창과 겹쳐 대략 7건 안팎이다. **여러 IP 로 나눠 오는 공격은 막지 못한다** —
그것은 판매 단계에서 다시 본다.

## 6. 완료 조건

1. **CHECKED_IN 예약이 피드에서 빠져도 취소되지 않고 경고가 남는 테스트** — 실제 수신 경로로
2. **CONFIRMED 예약이 피드에서 빠지면 지금처럼 취소되는 테스트**(기존 동작 유지)
3. **CHECKED_IN 예약의 날짜가 피드에서 바뀌면 재고 원장이 옮겨지는 테스트**
4. `isActive()` 호출자 목록과 각 자리의 처리, CHECKED_IN 취소·이동 시 재고 반납 여부를 8절에 적는다
5. **같은 (판매 단위, 날짜)에 초과 예약이 셋 들어와도 OPEN 충돌이 한 행이고 예약 셋을 담는 테스트** — 채널 수신 경로로
6. **그 한 행을 해소하면 그 날짜에 OPEN 충돌이 없는 테스트.** 해소 뒤 새 초과 예약이 오면 새 행이 생긴다
7. **같은 예약의 날짜 수정이 두 번 와도 충돌이 늘지 않는 테스트**
8. **`GET /api/reservations?from=…&to=…` 가 200 이고 기간이 맞게 걸리는 테스트** — HTTP 로
9. **공개 HOLD 가 IP 당 상한을 넘으면 429 이고 HOLD 가 생기지 않는 테스트.** 다른 IP 는 그 사이에도 된다
10. **`X-Forwarded-For` 로 IP 를 가르는 테스트.** Caddy 뒤 구성에서 전역 차단이 되지 않는다
11. `LoginAttemptLimiter` 의 IP 판정 확인 결과를 8절에 적는다(같은 문제면 고치고 테스트)
12. 위젯이 429 메시지를 보여 주는 프론트 테스트 1건 — 서버가 실제로 보내는 응답 모양 그대로
13. `./gradlew build`, `npm run build`, `npm run test`, `ModularityTest` 통과. 테스트 건수를 적는다
14. **배포 뒤 확인.** 개발 PC 에서 위젯으로 **지니하우스 2027-09 말 날짜에 HOLD 한 건**을 만들고,
    서버 로그에 남은 판정 IP 가 Docker 내부 주소가 아니라 공인 주소인지 본다(로그에는 끝자리를 가린다).
    HOLD 는 15분 뒤 만료된다 — 만든 시각과 예약 번호를 8절에 적는다. 결제로 넘어가지 않는다

**1·5·9·10 을 빠뜨리지 않는다.** 1은 투숙 중 손님의 방이 다시 팔리는 자리, 5는 Channex 가 붙는 날
바로 드러날 자리, 9·10은 공개 경로이고 10을 놓치면 속도 제한이 서비스 전체를 막는다.

### 8.1 착수 전 조사 (09-17)

**IP 판정.**

| 자리 | 지금 | 판단 |
|---|---|---|
| `deploy/Caddyfile` | `reverse_proxy app:8080`, `trusted_proxies` 없음 | Caddy 2.5+ 는 `trusted_proxies` 에 없는 클라이언트가 보낸 `X-Forwarded-*` 를 **버리고** 실제 접속 IP 로 `X-Forwarded-For` 를 새로 붙인다(Caddy 문서). 즉 밖에서 헤더를 위조해 보내도 앱에는 진짜 IP 가 닿는다. **배포 뒤 6절 14번에서 위조 헤더를 실어 보내 실측한다** |
| `application.yml` | `server.forward-headers-strategy` 없음(기본 `NONE`) | `getRemoteAddr()` 가 Caddy 의 Docker 주소(172.x)다 — 그대로 세면 **전역 차단**. `framework`(`ForwardedHeaderFilter`)로 켠다. 필터라 MockMvc 에서도 돈다(완료 조건 10). 앱 포트가 밖에 열려 있지 않으므로(확인-09 5절) 헤더를 넣을 수 있는 것은 Caddy 뿐이다 |
| `LoginAttemptLimiter` | **IP 를 쓰지 않는다.** 이메일(소문자) 기준으로 실패를 센다 | 같은 문제 없음. 고칠 것 없음. 참고: 존재하지 않는 이메일도 똑같이 세는 설계라 IP 가 필요 없다 |

**`isActive()` 호출자.** "재고를 차지하는 상태"의 정의가 코드에 넷 있다.

| 자리 | 정의 | CHECKED_IN |
|---|---|---|
| `Reservation.isActive()` | HOLD·CONFIRMED | **빠짐** — 원인 자리 |
| `ChannelBookingWriter.ACTIVE` (겹침 조회) | HOLD·CONFIRMED·CHECKED_IN | 포함 |

`Reservation.isActive()` 를 부르는 곳 셋과 각 자리에서 CHECKED_IN 이 겪는 일:

| 호출자 | 하는 일 | CHECKED_IN 이면 지금 | 재고 |
|---|---|---|---|
| `ChannelBookingWriter.applyToExisting` | 날짜가 바뀌면 원장 반납 → 재확보 | `isActive()` 가 false 라 **원장을 건너뛰고 기간만 바뀐다** — A-2 결함. `applyIncoming` 이 먼저 기간을 갈아 끼운 뒤라 옛 날짜의 `booked` 가 남고 새 날짜는 안 잡힌다 | 샌다 |
| `Reservation.changeStay` (엔티티 가드) | 바꿀 수 있는 상태인지 | `IllegalReservationTransition`. 그런데 바깥 `ReservationWriter.changeStay` 의 switch 는 CHECKED_IN 을 release+reserve 로 **이미 다룬다** → 원장을 옮긴 뒤 엔티티가 거절 → 트랜잭션 롤백. 결과는 "투숙 중 연장 불가" | 안 샌다(롤백) |
| `Reservation.moveToUnit` (엔티티 가드) | 옮길 수 있는 상태인지 | 같은 모양. `ReservationWriter.moveToUnit` 의 switch 는 CHECKED_IN 을 다루고 엔티티가 거절 → 롤백. 결과는 "투숙 중 업그레이드 배정 불가" | 안 샌다(롤백) |
| `ReservationWriter.cancel` | 상태별 반납 | `isActive()` 를 안 쓴다. `case CONFIRMED, CHECKED_IN -> release` | **반납된다** |

**정한 것 — 정의를 고친다.** `Reservation.isActive()` = HOLD·CONFIRMED·CHECKED_IN. 넷 중 셋과
`ReservationWriter` 의 switch 둘이 이미 그렇게 보고 있고, 엔티티 하나만 다르다. 호출 자리를 고치면
정의가 다섯이 된다. 부수 효과: 투숙 중 예약의 날짜 변경(PATCH)과 업그레이드 배정이 **허용**된다 —
writer 가 처음부터 그렇게 짜여 있었다. CHECKED_OUT·CANCELLED·EXPIRED·NO_SHOW 는 그대로 거절.

**B 의 확인 항목 — 충돌에 걸린 예약이 나중에 취소되면 OPEN 카드는.** `ReservationWriter.cancel`
은 충돌 테이블을 건드리지 않고, 충돌을 닫는 경로는 `ConflictWriter.resolve*` 둘뿐이다. 그래서
채널 취소 통지·수기 취소·홀드 만료로 예약이 사라져도 **카드는 OPEN 그대로이고
`reservation_ids` 에 취소된 예약이 남는다.** 화면(`ConflictResponse.reservations`)은 예약의
현재 `status` 를 함께 보내므로 운영자는 CANCELLED 를 보고 ABSORBED 등으로 손수 닫아야 한다.
자동으로 닫지 않는 것이 결함인지는 판단하지 않았다 — **고치지 않고 적어만 둔다**(2절 B).
현재 배포 DB 충돌 0건이라 실데이터에는 없다.

**같이 보인 것(고치지 않음).** `InventoryLedger.forceBook` 은 초과 예약을 받으며 그 날의
`total_units` 를 **영구히** 올린다. 충돌을 취소로 해소해 재고가 반납돼도 올린 수량은 그대로라,

### 9.1 왜 앞에서

- **E 가 틀리면 이중 예약이 난다.** 채널이 하나인 지금은 충돌이 없어 증상이 없다. Channex 가 붙으면
  초과 예약 → 해소 → 그 날짜가 한 개 더 팔리는 흐름이 실제로 돈다. 재고가 늘어난 값이 ARI 로 채널에
  나가면 **채널에서도 한 개 더 팔린다**
- 리포트의 판매 가능 객실박(분모)이 원장의 총수량을 읽는다면 점유율도 같이 틀린다 — 9.3 에서 확인

### 9.2 고치는 것

**E. 초과 예약이 올린 총수량이 내려가지 않는다.**
`chk_no_oversell`(V1, `booked_units + held_units <= total_units`)을 만족시키려고 `forceBook` 이
`total_units` 를 올린다. 해소·취소로 반납돼도 그대로다.

- **`total_units` 는 언제나 판매 단위의 실제 수량이어야 한다.** 초과분은 따로 드러나게 둔다
- **초과분은 반납될 때 정확히 사라진다.** 기준 — 반납 뒤 `booked + held` 가 실제 수량 이하면 초과분 0
- **판매 가능 수량은 0 아래로 내려가지 않는다**(화면·위젯·ARI 모두). 초과 예약이 남아 있는 날(ABSORBED 등)은 0 이다
- **`chk_no_oversell` 의 뜻을 약하게 만들지 않는다.** 제약을 지우거나 "초과면 통과"로 풀어 버리지 않는다.
  초과 예약 경로 말고는 여전히 DB 가 초과 판매를 거부해야 한다
- 이미 부풀어 있는 행 — 배포 DB 는 충돌이 한 번도 없어 0 일 것이다. **마이그레이션이 필요하면 쓴다.** 로컬·테스트
  DB 에는 부푼 행이 있을 수 있으니 마이그레이션이 그것도 바로잡는다

**F. 충돌에 걸린 예약이 취소·만료·이동되어 초과가 풀리면 OPEN 카드를 자동으로 닫는다.**

- 닫는 기준은 E 와 같다 — 그 (판매 단위, 날짜)의 활성 예약이 실제 수량 이하가 되면
- **자동으로 닫힌 것이 기록에서 구분돼야 한다.** 해소 방법 값·해소자 없음·메모 중 무엇으로 남길지는
  훑은 뒤 정하고 9.4 에 적는다. `overbooking_conflict.resolution` 에는 CHECK 가 없다(V1)
- 감사 기록을 남긴다(사람이 닫을 때와 같은 모양, 행위자는 시스템)
- 아직 초과인 동안에는 닫지 않는다. 셋이 겹쳤다가 하나 취소돼 둘이 남으면 OPEN 유지, 예약 목록만 갱신

| RELOCATED | 없음(기록만) | **남는다.** 예약은 그대로 우리 재고를 차지한다. 가용 0 |
| ABSORBED | 없음 | **남는다.** 가용 0, 음수 아님(18) |

**반납 경로 전부.** 원장 `release`/`releaseHold` 로 모이는 자리 — `ReservationWriter.cancel`(수기·채널 취소
통지·충돌 CANCELLED·`cancelMissing`), `ReservationWriter.expire`(홀드 만료), `ReservationWriter.changeStay`(옛 기간),
`ReservationWriter.moveToUnit`(원래 단위), `ChannelBookingWriter.applyToExisting`(채널 수정의 옛 기간). 다섯.
초과분은 원장 안에서 반납 즉시 다시 계산되므로 경로마다 손댈 것이 없다. **F 의 자동 닫힘은 다섯 자리 끝에서
한 번씩 부른다** — 엔티티 상태(취소·기간·단위)가 확정된 뒤여야 "그날 활성 예약"이 맞게 세어진다.
원장 쓰기 안에 걸면 `changeStay` 처럼 원장을 먼저 옮기고 엔티티를 나중에 바꾸는 순서에 어긋난다.

#### 9.4.2 정한 것

- **초과분 = `inventory_ledger.overbooked_units`(V10).** 값은 언제나 `GREATEST(0, booked + held − total)` 이고
  DB 가 그 등식을 CHECK 로 강제한다. `forceBook` 만 그 값을 올린다(정확히 초과분만큼). 반납은 다시 계산해
  내린다 — "반납 뒤 `booked + held` 가 실제 수량 이하면 0" 이 등식 그대로다
- **`chk_no_oversell` 은 `booked + held <= total + overbooked` 로 바꾸되 위 등식 CHECK 를 같이 건다.** 초과
  예약 경로가 아닌 곳(bug)이 수량을 넘겨 쓰면 `overbooked` 가 0 인 채 등식이 깨져 DB 가 거부한다 — 최종
  방어선이 약해지지 않는다(완료 조건 19)
- **`total_units` 는 판매 단위 수량이다.** V10 이 원장 행 중 판매 단위와 다른 행을 판매 단위 수량으로 맞추고
  초과분을 계산해 넣는다(부푼 행과, 수량 변경이 안 흘러간 행 둘 다)
- **자동 닫힘 = `resolution = 'AUTO_CLOSED'`, `resolved_by = NULL`, memo 에 남은 예약 수/수량.** 해소 방법
  값으로 구분하는 이유 — 목록·화면·질의가 이미 `resolution` 으로 갈린다. 사람이 고를 수 있는 넷
  (`ConflictWriter.isKnown`)에는 넣지 않는다. 감사는 `CONFLICT_RESOLVE`, 행위자 SYSTEM(`actor_id` 없음)
- 자동 닫힘 판정은 **그날 그 판매 단위의 활성 예약 수 ≤ 판매 단위 수량** — `raiseConflicts` 의
  `overlappingIds` 와 같은 자료다. 아직 초과면 예약 목록만 갱신
