- 작성일: 2026-10-20
- 작성: Claude Code (읽기 전용 — 코드 수정·배포 없음)
- 계기: 1차 심사(10월 말) 전. 업체와 심사자가 `https://staysync.kr` 에서 직접 누르는 경로가 실패할 때 무엇이 남는지를 본다

  `amount_type` 이름, 인원 2, 수량 왕복 180일 상수, 매핑 없는 iCal 경고, 판매 중지 해제 화면 — 작업지시-25 로 고침), 일괄 편집 패널 라디오 접근성(인계메모)

공통 — 도메인 예외는 `GlobalExceptionHandler` 가 `{code, message, details}` 로 내보내고 화면은 `message` 를 그대로 보인다(`frontend/src/api/client.ts:15`).
**그 밖의 예외는 전부 500 "서버 오류가 발생했습니다." + ERROR 스택**(`shared/error/GlobalExceptionHandler.java:70`) — `IllegalArgumentException`,
DB 제약 위반(`DataIntegrityViolationException`), 경로 변수 타입 불일치, 없는 경로·메서드가 다 여기로 온다. 검증 실패(`@Valid`)는
"입력값이 올바르지 않습니다." 하나이고 어느 칸인지는 `details` 에만 있다 — 화면이 `details` 를 보이는 곳은 수량 줄이기 하나다.

## 3. 심사 전 고칠 것

번호가 작을수록 먼저.

**0. 충돌 해소가 아무 예약이나 취소하거나 옮긴다 — 다른 조직의 예약도.** (보안 · 데이터 손상)
- 근거: `ConflictResolutionService.resolve`(`booking/ConflictResolutionService.java:116`)는 충돌의 소유만 본다(`load`). 요청의 `reservationId` 가
  그 충돌의 예약인지는 아무 데서도 보지 않는다 — 취소는 `ConflictWriter.java:78` `reservationWriter.cancel(reservationId)`, 업그레이드는
  `ConflictResolutionService.java:138` 에서 읽어 `ConflictWriter.java:51` `moveToUnit(reservationId, targetUnitId)`. `ReservationWriter.cancel` 도
  식별자만 받는다
- 무엇이 되나: OPEN 충돌이 하나 있는 사람은 예약 식별자(1부터 세는 수)만 바꿔 보내 **남의 조직 예약을 취소**하거나 **자기 판매 단위로 옮긴다**
  (숙소가 다른 판매 단위로 옮겨진 예약 — 원장·리포트가 어긋난다). 충돌 하나에 한 번이지만, 공개 가입 + 자기가 발행한 iCal 주소를 연결하면
  충돌은 만들 수 있다. 화면은 충돌의 예약만 보내므로 평소 조작으로는 나지 않는다
- 되돌릴 수 있나: 취소는 아니다(취소된 예약을 살리는 길이 없다). 이동은 사람이 다시 옮겨야 한다
- 고칠 방향: `reservationId` 가 `conflict.getReservationIds()` 안에 있어야 한다 — 없으면 400. 테스트 하나(다른 예약 식별자 → 거절, 아무것도 안 바뀜)
- **고침: 작업지시-26**(10-20 배포 `10c7547`)

**1. 위젯이 지난 날짜를 팔고 실제 카드로 결제된다.** (데이터 · 돈)
- 근거: `PublicBookingService.hold`(`booking/PublicBookingService.java:145~`)는 팔 수 있는지·최소 숙박·금액만 본다. 체크인이 오늘 이후인지는
  어디서도 보지 않는다. 화면의 날짜 칸에도 `min` 이 없다(`frontend/src/widget/WidgetPage.tsx:127`·`139`). 원장에 행이 없는 지난 날은
  `available = total` 이라 팔 수 있는 날로 보인다
- 무엇이 되나: 손님(또는 심사자)이 지난 날짜를 고르면 HOLD → 결제 → CONFIRMED. 테스트 채널은 당일 자동 취소되지만 StaySync 예약은
  CONFIRMED 로 남는다(3절 3 과 겹쳐 화면에서 지울 수 없다)
- 고칠 방향: 서버 — HOLD 의 체크인이 숙소 시간대 오늘보다 앞이면 `INVALID_PUBLIC_BOOKING`("지난 날짜는 예약할 수 없습니다."). 화면 —
  날짜 칸 `min` 을 오늘로. 서버가 진짜 방어선이다
- **고침: 작업지시-26**(10-20 배포 `10c7547`)

**2. 에어비앤비(iCal) 예약을 끌어 옮기면 성공처럼 보이고, 나중에 되돌아가며 초과 예약이 생길 수 있다.** (데이터)
- 근거: 막대를 끌 수 있는 상태는 채널과 상관없이 `HOLD`·`CONFIRMED`(`frontend/src/calendar/useReservationMove.ts:18`), 서버
  `BookingService.changeStay` 도 채널을 보지 않는다. iCal 은 우리가 바꾼 날짜를 에어비앤비로 보내지 않는다(받기만 한다). 그 예약이 다음에
  피드에서 다시 읽히면(피드가 바뀐 주기 — 304 면 그대로) 값이 다르므로 `ChannelBookingWriter.applyToExisting` 이 피드 날짜로 되돌린다
  (`booking/ChannelBookingWriter.java:240`, 날짜가 바뀌면 반납 → 다시 확보, 모자라면 `forceBook` + 충돌)
- 무엇이 되나: 업체가 에어비앤비 예약을 옮기면 화면은 성공. 에어비앤비 쪽은 그대로이고, 비워진 원래 날짜는 위젯에서 팔린다. 피드가 다시
  읽히는 순간 원래 날짜로 돌아오며 **초과 예약 충돌**. 업체가 가장 먼저 해 볼 조작 가운데 하나다(작업지시-25 1절과 같은 이유)
- 되돌릴 수 있나: 충돌 화면에서 사람이 정리한다. 위젯 손님이 이미 결제했으면 환불이 필요하다
- 고칠 방향: 채널 예약(`DIRECT` 가 아닌 것)은 끌 수 없게 — 화면에서 막고, 서버 `PATCH /api/reservations/{id}` 도 채널 예약의 날짜 변경을
  409 로 거절(문구 예: "채널에서 들어온 예약은 그 채널에서 날짜를 바꿔야 합니다."). 인원 변경은 남겨도 된다
- **고침: 작업지시-26**(10-20 배포 `10c7547`)

**3. 업체가 화면에서 예약을 취소할 수 없다.** (되돌림)
- 근거: 서버에는 `POST /api/reservations/{id}/cancel` 이 있다(`booking/web/ReservationController.java:123`). 화면의 전이는 체크인·체크아웃과
  그 되돌리기 넷뿐이다(`frontend/src/api/reservations.ts:27`). 예약 패널에 취소가 없다
- 무엇이 되나: 위젯 직접예약(심사자의 시험 결제 포함)이 CONFIRMED 로 남으면 그 날짜는 위젯·캘린더에서 계속 막힌다. 결제사 쪽 취소와 별개로
  StaySync 예약은 그대로다. 지난번처럼 브라우저 콘솔에서 API 를 부르는 것 말고는 길이 없다
- 고칠 방향: 예약 패널에 "예약 취소" — 체크인·체크아웃과 같은 화면 안 확인 단계. **`DIRECT` 예약에만** 연다(채널 예약은 채널에서 취소해야
  하고, 여기서 취소하면 채널은 그대로인데 우리 재고만 풀린다 — 2번과 같은 모양). 결제 환불은 하지 않는다고 문구로 밝힌다
- **고침: 작업지시-26**(10-20 배포 `10c7547`)

**4. 일괄 편집에서 음수 요금·-100% 이하를 넣으면 "서버 오류가 발생했습니다."** (문구)
- 근거: 값 검사가 요청 DTO 의 `@Valid` 가 아니라 도메인 생성자의 `IllegalArgumentException`(`booking/calendar/BulkEdit.java:27`·`45`)이라 공통
  처리기에서 500 이 된다. 화면 입력에 `min` 이 없다(`frontend/src/calendar/SelectionPanel.tsx:295`·`305` 부근)
- 데이터: 안 망가진다(쓰기 전에 실패). 로그에 ERROR 스택이 남는다
- 고칠 방향: 같은 검사를 `InvalidBulkEditException`(400)으로 — 문구 "요금은 0 이상이어야 합니다." / "비율은 -100% 보다 커야 합니다."
- **고침: 작업지시-26**(10-20 배포 `10c7547`)

**5. 비밀번호를 바꾸면 같은 계정의 다른 로그인이 전부 끊긴다 — 심사자 셋이 한 계정을 쓴다.** (운영 결정, 코드 변경 아님)
- 근거: `AuthService.changePassword` → `refreshTokenService.revokeOtherLogins`(`identity/AuthService.java:182`). 의도된 동작이다
- 무엇이 되나: 심사자 한 명이 비밀번호 화면을 시험하면 나머지 둘이 로그아웃되고 새 비밀번호를 모른다
- 정할 것: 심사 안내에 "비밀번호 변경은 시험하지 말 것"을 적거나, 심사용으로 시험 조직(`온보딩 시험 조직`) 계정을 따로 안내한다. 사용자가 정한다

## 5. 확인하지 못한 것

- 3절 2 의 "피드가 다시 읽힐 때 되돌아간다"는 코드 읽기다. 실제 에어비앤비 피드로 끌어 옮겨 본 적은 없다 — 고치기 전에 로컬(iCal 스텁)에서 한 번
