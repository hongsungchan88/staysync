# 확인 04. P3 완료 조건 셋째 — 실제 에어비앤비 iCal 양방향

- 확인일: 2026-09-05
- 범위: P3 13주차, 작업지시 10 의 완료 조건 1·2
- 관련: 계획서 6.2 / 12.2, 조사-02, ADR 0013

계획서 12.2 의 P3 완료 조건 셋 중 셋째다.

> 실제 에어비앤비 리스팅이 발행한 iCal 피드를 수신해 캘린더에 반영하고,
> StaySync 가 발행한 iCal 을 에어비앤비가 읽어 해당 날짜를 막는다.

앞의 둘은 `docs/확인-03-P3완료조건.md` 에 있다.

**이 문서는 절반이 끝나 있고 절반은 사람이 해야 한다.** 아래 3절이 요청이다.

---

## 1. 수신 — 실제 발행물을 받아 확인했다

`.env` 의 `AIRBNB_ICAL_URL` 로 실제 리스팅의 발행물을 받아 우리 파서에 통과시켰다.

| 항목 | 값 |
|---|---|
| 응답 | `HTTP 200` |
| `ETag` 헤더 | **없다** |
| 본문 | 315바이트, `VEVENT` 1건 |
| `DTSTART` / `DTEND` | `20260903` / `20270906` (둘 다 `VALUE=DATE`) |
| `SUMMARY` | `Airbnb (Not available)` |
| 줄 끝 | CRLF 12줄, 접힌 줄 없음, BOM 없음 |
| 저장소 픽스처와의 구조 비교 | `UID`·`DTSTAMP` 를 빼면 **완전히 같다** |

조사-02 2절이 적은 그대로다. 미게시 리스팅이라 2026-09-03 부터 2027-09-06 까지
1년치를 `VEVENT` 하나로 막고 있다.

**저장소의 픽스처가 실제 발행물과 구조적으로 동일하므로 `IcalParserTest` 가 실제
피드를 검증한 것과 같다.** 그 테스트가 `DTEND` 배타성을 못박는다 — `20270906` 은
9월 5일까지 막힌 것이다.

주소는 이 문서에도 로그에도 남기지 않았다. 조사-02 1절대로 API 키와 같이 다룬다.

### 확인하면서 알게 된 것 둘

- **에어비앤비는 `ETag` 를 주지 않는다.** 조건부 요청이 매번 200 으로 떨어진다.
  결함은 아니다 — `IcalAdapter` 는 `knownEtag` 가 없으면 헤더를 싣지 않고 전체를
  받으며, 15분에 315바이트는 아낄 것이 없다. `Last-Modified` 도 없었다.
  **캐싱이 실제로 도는지는 스텁 서버가 검증한다**(`IcalFeedTest`).
- **이 연결에는 대량 소실 방어가 걸리지 않는다.** 발행물의 `VEVENT` 가 1건이고
  방어는 직전 이벤트 수가 4를 넘을 때만 동작한다(계획서 13.4). 한두 건짜리 발행물에
  방어를 걸면 정상적인 취소가 영영 반영되지 않기 때문이고, 의도된 값이다.
  실제 예약이 여럿 잡히는 채널에서 의미를 갖는다.

## 2. 발행 — URL 을 만들었다

`GET /public/ical/{token}.ics` 가 열려 있다. 토큰은 매핑마다 하나이고 32바이트 난수다.

발행물은 이렇게 나간다.

```
BEGIN:VCALENDAR
PRODID:-//StaySync//Channel Calendar 1.0//EN
VERSION:2.0
CALSCALE:GREGORIAN
BEGIN:VEVENT
DTSTAMP:...
DTSTART;VALUE=DATE:20261225
DTEND;VALUE=DATE:20261228     ← 배타적. 3박이면 체크아웃일 그대로다
SUMMARY:StaySync (Not available)
UID:20261225-20261228@unit-5.staysync
END:VEVENT
END:VCALENDAR
```

- **게스트 이름이 없다.** 인증이 URL 하나뿐이고 읽는 쪽은 에어비앤비 서버다.
  `IcalExportApiTest` 가 발행물 전체를 문자열로 훑어 확인한다.
- **토큰이 발행물에도, 매핑 목록 응답에도 없다.** 꺼내는 경로는
  `GET /api/channels/{id}/mappings/{mappingId}/export-url` 하나다.
- 틀린 토큰은 404 다. 401·403 으로 답하면 존재를 알려 주는 셈이 된다.
- 5분 캐시(`Cache-Control: max-age=300`).

## 3. 사람이 해야 할 것 — 에어비앤비에 등록

작업지시 10 의 5절 1번이 "사람이 한다"로 정해 둔 부분이다. 아래 순서로 하면 된다.

### 3.1 발행 URL 을 공개 주소로 만든다

에어비앤비 서버가 우리 URL 을 읽어야 하므로 `localhost` 로는 안 된다.
`staysync.public-base-url` 을 실제로 닿는 주소로 두고 그 주소로 앱을 노출한다.

```bash
./gradlew bootRun --args='--spring.profiles.active=local --staysync.public-base-url=https://<공개주소>'
```

터널을 쓴다면 그 도구가 준 https 주소를 `--staysync.public-base-url` 에 넣는다.
이 값을 안 주면 기본값이 `http://localhost:8080` 이라 에어비앤비가 닿지 못한다.

### 3.2 화면에서 URL 을 받는다

1. 브라우저에서 **채널 연결** → 에어비앤비 연결의 **매핑** 으로 간다
2. 매핑된 판매 단위 아래의 **`발행 URL 보기`** 를 누른다
3. 나온 주소를 복사한다

### 3.3 에어비앤비에 넣는다

에어비앤비 호스트 화면에서
**달력 → 예약 가능일 → 달력 연결하기 → 다른 웹사이트에 연결하기 → 2단계(가져오기)**
에 그 주소를 넣고 달력 이름을 아무거나 적는다(조사-02 1절에서 확인한 경로다).

### 3.4 막히는지 확인한다

1. StaySync 캘린더에서 아무 날짜를 골라 **판매중지**로 바꾼다
2. 에어비앤비가 우리 달력을 읽을 때까지 기다린다 — **최대 2시간**이다
3. 에어비앤비 달력에서 그 날짜가 막혔는지 본다

### 3.5 수신 쪽도 브라우저에서 본다

`.env` 의 `AIRBNB_ICAL_URL` 로 연결을 하나 만들고(**채널 연결 → 추가**,
어댑터 종류 `ICAL`, 자격 증명 칸에 그 주소), 판매 단위를 하나 매핑한다.
iCal 폴링은 15분 주기이므로 기다리거나 앱을 다시 띄운다.

**1절의 그 `VEVENT` 한 건이 2026-09-03 ~ 2027-09-05 구간을 막은 것으로 캘린더에
나타나면 수신은 성립한다.** 하루라도 밀려 있으면 `DTEND` 해석이 틀린 것이다.

## 4. 남는 것

- **3절의 결과를 이 문서에 이어 적어야 P3 완료 조건 셋째가 판정된다.** 지금은 우리
  쪽 절반만 끝나 있다.
- 미게시 리스팅이라 개별 예약 수신은 이 채널로 검증할 수 없다(조사-02 4절).
  그 검증은 Mock 시뮬레이터가 맡고 있고 `IcalFeedTest` 가 수정·취소·급감·조건부
  요청을 전부 스텁 발행자로 확인한다.
