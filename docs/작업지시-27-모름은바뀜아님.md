## 1. 왜 필요한가

10-20 12:06 되찾은 지니하우스 예약 12건이 Channex 금액·인원을 가지고 있었는데, 12:21 다음 iCal 폴링이 iCal 의 "금액 모름(NULL)·인원 0"을
"값이 바뀜"으로 읽어 덮었다(작업지시-24 8.3.1, Cowork 이 14:xx 화면 점검에서 발견). 지금 리포트·예약 패널에 그 12건이 "금액 미상"으로 보인다.
원인은 되찾기가 아니라 **일반 갱신 경로(`applyToExisting` → `applyValues`·`changeGuests`)가 "모름"과 "바뀜"을 구분하지 않는 것**이다.
다음 Channex 연결에서 넘겨받기·되찾기를 다시 쓰면 같은 일이 난다.

## 2. 이번에 만드는 것

### A. "모름"은 "바뀜"이 아니다

- 버전 없는 채널(iCal)의 갱신에서 들어온 금액이 NULL 이면 **금액을 비교하지도 덮지도 않는다.** 인원이 0(모름)이면 인원도 건너뛴다
- 날짜가 같고 나머지가 전부 "모름"이면 그 갱신은 **아무것도 하지 않은 것**(DUPLICATE)으로 끝난다 — 박 행 재작성·이벤트·`CHANNEL_REVISION` 감사가 없다
- 날짜가 바뀐 갱신은 지금처럼 날짜를 옮긴다. 이때도 저장된 금액·인원은 "모름"으로 지우지 않는다. **박 단가는 저장된 총액을 새 박 수로 다시 나눈다**
  (`ReservationNight.split` 규칙). 총액이 NULL 이면 지금처럼 NULL
- 버전 있는 채널(Channex `applyRevision`)도 같은 규칙 — 수정 리비전에 금액이 빠지면 저장된 값을 유지한다(5절 2번)
- 원인 자리 한 곳에서 고친다. `applyValues`·`changeGuests` 의 호출자를 다 훑고 8.1 에 한 줄(인계메모 6절 "절반만 고치고 닫은 결함")

### B. 지워진 12건을 되살린다 (업체 데이터 — 사용자 승인 뒤)

- 값은 작업지시-24 8.3.1 3) 표 그대로 — 금액 12건(합 7,476,250), 성인 2·아동 0, 박 단가는 `ReservationNight.split` 규칙
- 방법은 **(ㄱ) 서버에서 한 트랜잭션 SQL**(5절 3번): 12건 `reservation` 금액·성인·아동 + `reservation_night` 단가 + 감사 한 행씩(행위자·사유가 보이게,
  예: `DATA_RESTORE`, 근거 "작업지시-27, 8.3.1 표")
- 직전 덤프. 실행 전에 SQL 전문과 "바뀔 행 수 기대값"을 8.2 에 적고 **사용자 승인 뒤** 실행. 기대와 다르면 롤백하고 멈춘다
- **A 를 배포한 뒤에만** 한다. 지금 코드로 되살리면 다음 폴링(≤15분)이 다시 지운다

## 3. 이번에 만들지 않는 것

- 청소비가 박 단가에 섞이는 것(작업지시-24 8.2 결함 3) — 되살릴 때도 넘겨받기 때와 같은 값(청소비 포함 총액)으로 둔다
- 화면에서 금액·인원을 고치는 기능, 일반 관리 경로(5절 3번에서 (ㄴ)을 고르지 않았다)
- 작업지시-24 8.2 의 나머지 심사 뒤 결함

## 4. 지켜야 할 제약

- **배포 환경 업체 데이터는 B 의 승인된 SQL 로만 바꾼다.** A 의 확인은 로컬에서
- 마이그레이션 없음으로 본다. 생기면 8.2 에 덤프·되돌림
- **테스트는 실제 진입점** — iCal 수신 입구로 넣고 폴링을 두 번 이상 돌린다. 고치기 전 코드로 실패하는지 확인한다(작업지시-25·26 과 같다)
- 기존 iCal 예약(금액 NULL·인원 0 에서 시작한 것)의 동작이 바뀌지 않는다 — 날짜 변경·취소는 그대로
- 브라우저 모달·새 의존성 없음

## 5. 착수 전에 정한 것 (Cowork 제안, 사용자가 바꾸지 않으면 이대로)

1. 순서 — A 구현·테스트 → 배포 → B 승인·실행 → 다음 폴링 뒤 값 유지 확인
2. Channex 수정 리비전에 금액이 없으면 **유지**(iCal 과 같은 규칙. 작업지시-16 의 "미상" 은 **새** 예약의 금액이 없을 때의 규칙이다)
3. 되살리기는 (ㄱ) SQL. 한 번 쓰고 버릴 경로를 코드로 짓지 않는다
4. 배포·SQL 실행은 각각 사용자 승인 뒤

## 6. 완료 조건

1. 테스트 — 되찾은 예약이 **같은 피드로 두 번 더 폴링해도** 금액·인원·박 단가 그대로, 감사 `CHANNEL_REVISION` 0(고치기 전 코드로 실패)
2. 테스트 — 금액이 있는 iCal 예약의 날짜가 피드에서 바뀌면 날짜는 옮겨지고 금액·인원은 유지, 박 단가는 새 박 수로 다시 나뉨
3. 테스트 — 금액 NULL·인원 0 인 보통 iCal 예약의 날짜 변경·취소가 전과 같다
4. 테스트 — Channex 수정 리비전에 금액이 없으면 유지
5. 백엔드·시뮬레이터·프론트 전체 통과

   12건 줄어든다. Cowork 이 화면(예약 패널 금액·리포트)으로 확인한다
