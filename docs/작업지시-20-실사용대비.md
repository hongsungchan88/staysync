## 1. 왜 필요한가

**심사 방식이 바뀌었다(34차, 교수 말씀·사용자 전달).** 업체가 **사이트 기능을 전체적으로 직접 써 보고**
출품할 만하면 그쪽 수강생(잠재 고객)에게 제공해 판매하는 식이다. 대본 따라가는 12분 시연이 아니라
업체가 자기 실데이터로 화면을 돌아다니는 자리다.

그래서 기준이 바뀐다.

- 심사자가 **업체 본인**이다. 실데이터 편집은 막을 것이 아니라 **써야 하는 기능**이다.
  막아야 하는 것은 **되돌릴 수 없는 것** 하나뿐이다
- 대본이 없으므로 **화면이 스스로 설명해야 한다.** 빈 화면이 "고장"으로 읽히면 그걸로 끝이다
- **Cowork 이 09-23 에 배포 환경을 한 바퀴 돌아 아래 목록을 만들었다**(확인-11 1절). 자동 테스트
  364건이 통과하는 상태에서 나온 것들이고, 전부 화면에만 있다

## 2. 이번에 만드는 것

### A. 빈 상태 문구

- **청소 칸반(`/ops/tasks`)에 빈 상태 문구가 아예 없다.** 네 칸이 `할 일 (0) / 진행 중 (0) / 완료 (0) /
  막힘 (0)` 만 떠 있다. **청소 태스크는 체크아웃할 때 자동으로 생긴다**(`CheckoutTaskTrigger`,
  `RESERVATION_CHECKED_OUT`). 고장이 아니라 아직 아무도 체크아웃을 누르지 않은 것이다. 그 사실을 적는다
- 인박스(`/inbox`)는 "아직 대화가 없습니다"까지는 있다. 언제 생기는지를 한 줄 더한다
- **본은 충돌 화면의 "해소할 충돌이 없습니다"다.** 그 문장은 정상 상태를 뜻한다고 읽힌다. 같은 결로 쓴다

### B. "이름 없음"에 이유를 붙인다

캘린더 막대와 예약 패널에서 에어비앤비 예약이 전부 `이름 없음` 으로 뜬다. 업체가 가장 먼저 보는 화면에서
가장 먼저 눈에 띄고, **설명이 화면 어디에도 없어 고장으로 읽힌다.**

- 이유는 **에어비앤비 iCal 이 게스트 이름을 주지 않아서**다. `DESCRIPTION` 의 예약 상세·전화 뒷자리는
  **읽지 않기로 한 결정이 그대로 유효하다**(계획서 15.3, 조사-02 7절). 이 지시는 그 결정을 열지 않는다
- 막대에는 짧게, 예약 패널에는 한 문장으로. 채널이 iCal 인 예약에만 붙인다

### C. 되돌릴 수 없는 조작 — 채널 연결 삭제

**채널 연결 화면(`/channels`)의 연결마다 `삭제` 버튼이 있다.** iCal 주소는 서버 `.env` 에만 있고 화면에는
`http••••e=ko` 로 가려져 있다. **업체가 지우면 스스로 다시 붙일 수 없고, 그 판매 단위의 예약 수신이 끊긴다.**

- 지금 확인 단계가 있는지부터 본다. 없으면 만들고, 있으면 문구를 고친다
- 확인 문구에 **주소를 다시 알려 줄 수 없다는 사실**을 적는다. "정말 삭제하시겠습니까?"로는 부족하다
- **브라우저 모달(`window.confirm`·`alert`)을 쓰지 않는다.** 화면 안의 확인 단계로 만든다
- 다른 삭제·되돌릴 수 없는 조작이 더 있는지 같이 훑는다(숙소·판매 단위·매핑·예약 취소). 발견만 하고
  고칠지는 8절에 적어 돌려보낸다

### D. 설명이 없어 오해되는 자리

- **채널 카드가 "재고 전파 미지원 · 요금 전파 미지원 · 제약 전파 미지원 · 예약 수집 지원" 으로 시작한다.**
  업체 눈에는 미지원 셋이 먼저 보인다. iCal 은 원래 받기만 하는 연결이라는 한 줄을 앞에 둔다
- **연결 추가의 어댑터 종류에 `MOCK` 이 노출돼 있다.** 업체가 고를 수 있다. 운영 빌드에서 감춘다
- **캘린더 범례에 `네이버` 가 있는데 연동이 없다.** 연결이 있는 채널만 범례에 넣거나, 없는 것은 흐리게 둔다

### E. 예약 패널이 너무 적게 보여 준다

지금 패널에 있는 것은 **기간 · 채널 · 상태 · 체크인 버튼**뿐이다.

- **금액이 없다.** 금액이 있는 예약(직접예약)에서도 안 보이는지 먼저 확인한다. 안 보이면 넣고,
  **미상이면 "미상"으로** 보인다(작업지시-16 의 규칙 그대로 — 0원으로 쓰지 않는다)
- 인원이 있으면 같이 보인다. 없는 값은 칸을 만들지 않는다
- 게스트 연락처·예약 상세 URL 은 **넣지 않는다**(B 의 결정)

### F. 확인만 하는 것 — 체크아웃에서 청소 태스크까지

**로컬에서 확인한다. 배포 환경의 업체 실데이터는 건드리지 않는다**(사용자 결정, 34차).

- 로컬 시드로 예약 하나를 **체크인 → 체크아웃** 하고 청소 칸반에 태스크가 뜨는지 본다
- **되돌리는 길이 화면에 있는지 같이 본다.** 잘못 누른 체크인·체크아웃을 업체가 스스로 되돌릴 수 있는가.
  없으면 그 자체가 발견이다 — 고치지 말고 8절에 적어 돌려보낸다

## 3. 이번에 만들지 않는 것

- **역할별 인가·심사자 읽기 전용 계정.** 심사자가 업체 본인이라 편집은 기능이다. C 하나면 충분하다.
  **단 이 판단은 교수 보고서 8절 1번의 답에 걸려 있다** — 보고서에 "심사자마다 데이터를 분리합니다"라고
  적었고, 그대로 가면 심사자는 업체 실데이터가 아니라 **자기 빈 조직**에서 시작한다. 그러면 실데이터를
  잘못 건드릴 위험은 사라지는 대신 **빈 화면이 더 큰 문제가 되고**(캘린더까지 빈다) 이 항목을 다시 봐야
  한다. 답이 오면 Cowork 이 이 절을 고친다. 그때까지는 A~E 를 그대로 진행한다 — 어느 쪽이든 필요한 일이다
- 통합 캘린더 한 화면(P6), 환불 계산, 원화 외 통화, AI(작업지시-14)
- 캘린더 가로 스크롤·빈 세로 공간의 레이아웃 손질. 좁은 창에서만 두드러진다. 걸리면 그때 연다

## 4. 지켜야 할 제약

- **배포 환경의 업체 데이터(`1차 심사` 조직)를 바꾸지 않는다.** 확인은 로컬에서
- **iCal 주소를 화면·로그·문서·커밋에 남기지 않는다.** 가려진 지금 상태를 그대로 둔다
- 브라우저 모달(`confirm`·`alert`)을 쓰지 않는다
- 프론트가 바뀌므로 **번들 해시가 달라진다.** 배포 뒤 개발 PC·서버·https 셋이 같은지 본다
- 문구는 담백하게. 이모지·느낌표·과잉 볼드를 쓰지 않는다(인계메모 7절)

## 5. 착수 전에 정한 것

1. **`DESCRIPTION` 은 계속 읽지 않는다.** "이름이 없다"는 제약을 다시 만나도 그 칸을 열지 않는다
2. **읽기 전용 계정은 만들지 않는다.** 위 3절
3. **금액 미상은 0원으로 쓰지 않는다.** 작업지시-16 의 규칙을 예약 패널에도 그대로 적용한다
4. **체크아웃 실측은 로컬에서** 한다

## 6. 완료 조건

1. 청소 칸반이 비었을 때 **왜 비었고 언제 채워지는지**가 화면에 적힌다
2. 인박스 빈 상태에 같은 한 줄이 있다
3. iCal 예약의 `이름 없음` 옆(또는 패널 안)에 이유가 보이고, **iCal 이 아닌 예약에는 안 보인다**
4. 채널 연결 삭제에 화면 안 확인 단계가 있고, **주소를 다시 알려 줄 수 없다는 사실**이 그 문구에 있다
5. 운영 빌드의 어댑터 종류 드롭다운에 `MOCK` 이 없다
6. 채널 카드가 "받기만 하는 연결"이라는 설명으로 시작한다
7. 캘린더 범례에 연동 없는 채널이 그대로 서 있지 않다
8. 예약 패널에 금액이 보인다 — 값이 있으면 금액, 없으면 `미상`
9. **로컬에서 체크인 → 체크아웃 → 청소 칸반에 태스크 한 건**을 실제로 확인했다. 되돌리는 길의 유무를 8절에 적었다
10. 백엔드·시뮬레이터·프론트 테스트가 전체 실행에서 통과한다
11. **브라우저 확인** — 배포 뒤 위 1~8을 배포 환경 화면에서 눈으로 본다(읽기만. 업체 데이터를 바꾸지 않는다)

| | 체크인(`CONFIRMED → CHECKED_IN`) | 체크아웃(`CHECKED_IN → CHECKED_OUT`) |

| 재고 | 그대로 — 둘 다 재고를 쥔 상태(`isActive`) | **그대로 — 반납하지 않는다**(`ReservationWriter.checkOut` "재고는 그대로다"). 퇴실 뒤에도 그 박들은 이 예약 몫이다 |
| Outbox 이벤트 | 없음("체크인은 아직 소비자가 없다") | `RESERVATION_CHECKED_OUT` 하나 |
| 소비자가 만드는 것 | 없음 | 청소 태스크(TODO)·판매 단위 DIRTY·인박스 청소 알림(`CheckoutTaskTrigger` → `OpsTaskService.createCleaningFor`) |
| 자동 발송 | 영향 없음. 넷 가운데 `RESERVATION_CONFIRMED` 는 확정 사건, 나머지 셋은 날짜 기반이고 대상 목록(`ReservationDirectoryService.ACTIVE`)이 CONFIRMED·CHECKED_IN 을 같게 다룬다 | 날짜 기반 셋의 대상에서 빠진다(ACTIVE 에 CHECKED_OUT 이 없다) — 아래 |
| 감사 | `CHECK_IN` 한 행 | `CHECK_OUT` 한 행 |

**그래서 되감을 것.** 체크인 취소는 **되감을 것이 없다** — 상태만 돌리고 감사 행을 더한다. 체크아웃 되돌리기는
청소 태스크만 거둔다(할 일이면 지우고, 그 밖이면 막는다). 판매 단위 DIRTY 는 두고(손님이 다시 방에 있으니
어차피 청소할 방이고 체크아웃 전 값을 모른다), 인박스 알림도 둔다(9절 지시).

**지시와 다른 점 하나 — 체크아웃 되돌리기는 재고를 다시 잡지 않는다.** 9절 3번은 "되돌리면 재고를 다시 잡고,
그 사이 팔렸으면 막는다"였는데, 체크아웃이 재고를 반납하지 않으므로 그 사이 그 날이 팔릴 수가 없다. 초과 판매는
구조적으로 안 생긴다. 막는 판정을 넣으면 일어날 수 없는 경우를 지키는 코드가 된다. 대신 테스트가 "체크아웃 전후·
되돌린 뒤 `booked_units` 가 같다"를 고정한다 — 체크아웃이 반납하도록 바뀌면 그 테스트가 먼저 깨지고, 그때 여기서
다시 잡아야 한다(`Reservation.undoCheckOut` javadoc).

**같이 보인 것(고치지 않음).** 날짜 기반 자동 발송 `ON_CHECK_OUT`·`AFTER_CHECK_OUT` 의 대상이 ACTIVE(HOLD·CONFIRMED·
CHECKED_IN)라 **화면에서 체크아웃을 누른 예약은 그 두 메시지를 못 받는다.** 후기 요청이 `AFTER_CHECK_OUT` 에 붙으므로
체크아웃을 성실히 누르는 호스트일수록 후기 요청이 안 나간다. 배포 환경에는 메시지 규칙이 없어(`message_rule` 0건, 09-24 읽기만) 지금 증상은 없다.

### 8.4 마이그레이션과 백업 (9절)

**마이그레이션 없음.** 새 상태가 없고(`CONFIRMED`·`CHECKED_IN` 으로 돌아갈 뿐), 사유는 기존 `audit_log.after_value`
(JSONB)에, 누가·언제는 기존 `actor_id`·`occurred_at` 에 들어간다. 되돌림(롤백 배포)은 이전 jar·번들을 다시 올리는
것으로 끝나고 덤프 복원이 필요 없다 — 옛 코드는 `CHECK_IN_UNDONE`·`CHECK_OUT_UNDONE` 감사 행을 읽지 않을 뿐이다.
그래도 상태 전이를 건드리는 배포라 배포 직전 `pg_dump` 를 하나 떠 둔다(확인-09 의 절차 그대로, 8.5 에 파일명).

## 9. 되돌릴 수 있게 — 체크인·체크아웃 확인 단계와 되돌리기, 매핑 해제 확인, 취소 경고

- 작성: Claude Code (09-24, 사용자 지시로 이 절을 붙인다)
- 근거: 확인-11 4절의 ①·②·⑤. ③(채널 예약의 인원)은 작업지시-21 로, ④·⑦ 은 범위 밖
- 기준: 주요 PMS 의 흔한 모양 — 확인 단계는 Cloudbeds, 체크인 취소는 Mews·Guesty, 체크아웃 되돌리기는
  OPERA Cloud·RoomKey
- 제약: 20과 같다(업체 데이터 불변, 확인은 로컬, 배포 뒤 번들 해시 셋). 화면 확인은 Cowork — 번들에 확인 단계가
  들어간 것을 먼저 보고, 실데이터 화면에서는 열어 보고 `취소` 만 누른다
- 기록: 확인-11 5절

### 9.1 만드는 것

1. **체크인·체크아웃 확인 단계.** 화면 안(20의 채널 삭제와 같은 모양), `window.confirm`·`alert` 없음. 문구에 예약
   기간. 체크아웃이면 청소 태스크와 인박스 알림이 따라 생긴다는 것
2. **체크인 취소** `CHECKED_IN → CONFIRMED`. 퇴실 전이면 언제든. 사유 한 줄 필수(Mews)
3. **체크아웃 되돌리기** `CHECKED_OUT → CHECKED_IN`. **퇴실일 당일까지**(OPERA·RoomKey). 청소 태스크가 "할 일"이면
   함께 거두고, 진행 중·완료·막힘이면 막는다. 인박스 알림은 남긴다. 재고는 8.3 대로
4. **매핑 해제 확인 단계** — 그 판매 단위의 예약 수신이 끊긴다, iCal 이면 발행 주소가 바뀌어 에어비앤비에 다시
   등록해야 한다
5. **충돌 해소 "취소와 보상"** — 예약 취소는 되돌릴 수 없다는 문구
6. **되돌리기는 감사 기록에 남긴다**(누가·언제·사유). 원래 행을 고치지 않고 행을 더한다 — 한 일과 되돌린 일이 둘 다
   남는다

### 9.2 정한 것

- **"퇴실일"은 예약의 체크아웃 날짜다**(Asia/Seoul 오늘 ≤ `check_out`). 실제로 체크아웃을 누른 시각은 저장하지 않는다
  — 감사 행에 있지만 그걸 판정에 쓰려면 booking 이 감사 기록을 읽어야 한다. 조기 퇴실이면 원래 퇴실일까지 되돌릴 수
  있다. 판정은 서버가 하고, 화면은 지난 예약에 버튼을 두지 않을 뿐이다
- **사유는 두 되돌리기 모두 필수**(1~200자). 6번의 "누가·언제·사유"를 되돌리기 전부에 적용했다
- **청소 태스크는 booking 이 ops 를 부르지 않고 거둔다.** `booking.CheckOutFollowUps` 인터페이스를 booking 에 두고 ops
  (`CheckoutTaskWithdrawal`)가 구현한다 — 의존 방향은 그대로 ops → booking. 같은 트랜잭션이라 "청소가 시작됐다"로
  막히면 전부 롤백되고, 되돌리기가 롤백되면 지운 태스크도 되살아난다. Outbox 배달 전에 되돌리면 늦게 온 이벤트는
  `createCleaningFor` 가 지금 상태(CHECKED_IN)를 다시 읽어 버린다
- **되돌리기는 이벤트를 내지 않는다.** 재고가 안 바뀌어 채널에 보낼 것이 없고, 화면은 응답으로 갱신한다
- **감사 행을 보여 주는 화면은 없다.** 둘 다 `audit_log` 에 남는 것까지다(`CHECK_IN`·`CHECK_IN_UNDONE`,
  `CHECK_OUT`·`CHECK_OUT_UNDONE`, 뒤 값에 `reason`). 화면이 필요하면 따로 연다

### 9.3 완료 조건

1. 체크인·체크아웃이 화면 안 확인 단계를 거치고, 문구에 기간이, 체크아웃에는 청소 태스크·인박스 알림이 있다
2. 체크인 취소가 사유 없이는 안 되고, 되면 확정으로 돌아가 다시 체크인할 수 있다
3. 체크아웃 되돌리기가 할 일 청소를 거두고, 진행 중이면 409 로 막히며 아무것도 안 바뀐다. 퇴실일이 지나면 막힌다
4. 되돌려도 재고(`booked_units`)가 그대로다
5. 감사 기록에 한 일과 되돌린 일이 둘 다, 되돌린 쪽에 사유가 있다
6. 매핑 해제에 확인 단계, iCal 이면 발행 주소 문구
7. "취소와 보상"을 고르면 되돌릴 수 없다는 문구
8. 백엔드·시뮬레이터·프론트 전체 통과, 로컬 API 로 1~5 실측
9. 배포 뒤 번들 해시 셋이 같다. 화면 확인은 Cowork(실데이터에서는 `취소` 만)
