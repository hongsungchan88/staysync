## 1. 왜 필요한가

10-19~20 지니하우스 연결 검증(작업지시-24 4절 10번)에서 둘이 드러났다.

1. **화면으로 판매 중지를 해제할 수 없다.** "요금·제약 편집" 패널의 판매 중지는 체크박스 하나이고(`stop-sell-input`),
   체크하면 `stopSell: true`, 풀면 `null`(바꾸지 않음)을 보낸다. `false` 를 만드는 길이 없다. 서버 `bulk-edit` 는 `false` 를 받는다.
   10-20 에 2027-03-03 판매 중지를 풀 때 사용자가 브라우저 콘솔에서 API 를 직접 불러야 했다. **심사자가 판매 중지를 걸어 보면 되돌릴 수 없다**
2. **일괄 편집의 판매 중지(와 해제)가 채널로 바로 나가지 않는다.** `RATE_BULK_EDITED` 이벤트가 요금 갈래만 타고 그 갈래가 `stopSell` 을
   `null` 로 둔다. 원장의 판매 중지 변경도 재고 이벤트를 내지 않는다. 그래서 04:00 재동기화(`ChannelReconcileJob`) 때에야 맞춰진다 —
   최대 하루 늦다. 10-19 16:57 에 건 판매 중지가 에어비앤비에 닫힘으로 보인 것은 10-20 04:00 뒤였다

둘 다 "업체가 직접 써 보는" 심사에서 바로 걸린다. 판매 중지는 숙소 운영자가 가장 먼저 해 보는 조작 가운데 하나다.

## 2. 이번에 만드는 것

### A. 판매 중지를 셋 중에 고른다

패널의 판매 중지를 **바꾸지 않음 / 판매 중지 / 판매 재개** 셋 중 하나로 고르게 한다. 처음 값은 "바꾸지 않음".

- 요청은 그대로 `stopSell: null | true | false`. 요청 모양은 바꾸지 않는다
- 미리보기 문구에 무엇으로 바뀌는지 보인다(예: `… · 1칸 · 판매 재개`). 작업지시-23 의 한 줄 문구를 따른다
- 셋 중 무엇이 기본인지, 어느 쪽이 위험한지 보는 사람이 헷갈리지 않게 한다. 문구는 담백하게
- 새 의존성 없이

### B. 일괄 편집의 판매 중지·해제를 바로 채널로 보낸다

일괄 편집에서 `stopSell` 이 바뀌면 **매핑된 채널로 즉시 `stop_sell` 이 나간다** — 04:00 을 기다리지 않는다.

- 원인 자리에서 고친다(이벤트가 `stopSell` 을 싣지 않는 곳, 또는 그것을 버리는 갈래). 호출자를 다 훑는다(인계메모 6절 "절반만 고치고 닫은 결함")
- `true` 와 `false` 둘 다 나간다. 요금 행이 없는 날의 동작은 지금 규칙(건너뜀)을 따른다
- 요금·최소 숙박만 바꾼 일괄 편집은 지금처럼 `stop_sell` 을 보내지 않거나, 보낸다면 원장 값 그대로여야 한다 — 바꾸지 않은 판매 중지를
  풀거나 걸면 안 된다
- 04:00 재동기화는 그대로 둔다(안전망)
