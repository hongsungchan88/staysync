## 2. 이번에 만드는 것

### A. iCal 수신

계획서 6.2 와 13.4 가 명세다. 다만 13.4 스케치에 그대로 따르면 안 되는 곳이 둘 있다.

- 15분 주기 폴링. `ETag` 와 `Last-Modified` 를 캐싱해 변화 없으면 파싱하지 않는다
- 타임아웃 10초, 지수 백오프 3회. 12주차의 재시도 정책 위에 얹는다
- `DTSTART` / `DTEND` 는 `VALUE=DATE` 다. **`DTEND` 는 배타적이다**(조사-02 3절).
  포함으로 읽으면 모든 예약이 하루씩 밀리고, 화면은 정상으로 보인다
- `UID` 를 `channel_booking_id` 로 쓴다. 멱등성이 여기서 나온다
- **대량 소실 방어.** 이번 응답의 이벤트 수가 직전 대비 절반 이하로 줄면 취소 처리를
  보류하고 알린다. 파싱 실패나 일시적 오류로 전체 예약이 취소되는 사고를 막는다

**13.4 의 `revision(hashOf(...))` 를 그대로 쓰지 않는다.** iCal 에는 `revision` 이
없어서 해시로 대신한 것인데, `BookingIngestService` 는 `in.revision() > 기존` 으로
크기를 비교한다. **해시에는 순서가 없다.** 같은 예약의 날짜가 바뀌어도 새 해시가
옛 해시보다 작으면 수정이 무시된다. iCal 은 값이 다르면 수정으로 판정한다(5절 2번).

**`extractGuestName` 과 `isBlock` 도 만들지 않는다.** 5절 3번을 볼 것.

### B. iCal 발행

`GET /public/ical/{token}.ics` 다. 계획서 6.2 그대로.

- 토큰은 추측 불가능한 난수이고 **URL 자체가 인증**이다. 공개 경로이므로
  `SecurityConfig` 에서 열어야 한다
- 확정 예약과 판매 중지 구간을 `VEVENT` 로 낸다
- **우리가 내는 `DTEND` 도 배타적이어야 한다.** 받을 때 배타적으로 읽고 낼 때
  포함으로 쓰면 왕복에서 하루가 어긋난다. A 와 같은 규칙이다
- 5분 캐시
- **게스트 이름을 넣지 않는다.** 이 URL 은 인증이 URL 하나뿐이고 상대는 에어비앤비
  서버다. `SUMMARY` 는 `StaySync (Not available)` 같은 고정 문자열이면 된다.
  ADR 0007 이 그은 선의 연장이다

### C. 실제 에어비앤비 연동

**P3 완료 조건 셋째를 실제로 판정한다.**

- **수신** — `.env` 의 `AIRBNB_ICAL_URL` 로 연결을 만들고, 실제 피드가 캘린더에
  반영되는지 확인한다. 조사-02 2절대로 지금 그 피드에는 1년치를 막는 `VEVENT` 가
  하나 있다. **그 한 건이 캘린더에 나타나면 수신은 성립한다**
- **발행** — B 의 URL 을 에어비앤비의 "다른 웹사이트에 연결하기" 2단계에 넣고,
  우리가 막은 날짜가 에어비앤비 달력에서 막히는지 확인한다

발행 쪽은 사람이 에어비앤비 화면에서 해야 한다. **URL 을 만들고, 무엇을 어디에
넣어야 하는지까지 준비해 두면 된다.** 실제 등록과 확인은 사용자에게 요청한다.

`AIRBNB_ICAL_URL` 은 비밀이다. 로그·응답·커밋 어디에도 남기지 않는다.

### D. 재동기화 배치

계획서 6.6 이 명세다. 매일 새벽 4시, 향후 180일을 전수 대조한다.

- 활성 연결마다 우리 스냅샷과 채널 스냅샷을 비교한다
- 차이가 있으면 `AriCoalescingBuffer` 에 넣어 다시 보내고 경고를 남긴다
- **이 배치가 12주차에 남긴 두 구멍을 덮는다** — `RUNNING` 인 채 앱이 죽어 유실된
  작업과, 메모리 버퍼에 있다가 사라진 6초치. 둘 다 결국 여기서 수렴한다.
  그 사실을 주석에 적는다
- 사슬 밖이다. 15초 경로에 끼어들지 않는다

**효과 측정은 계획서 6.6 이 적은 대로 한다** — Mock 에 에러율을 주입한 상태로
불일치 누적을 재고, 배치 적용 전후를 비교한다. **측정 전에 성과로 적지 않는다.**

### E. 충돌 해소

계획서 7.4 다. 12주차부터 `overbooking_conflict` 에 행이 쌓이고 있다.

화면은 `/channels/:id/logs` 가 아니라 충돌 목록이다. 경로는 맡긴다.

- 충돌한 예약 목록과 해소 방법 넷을 제시한다 — 상위 판매 단위 업그레이드,
  인근 제휴 숙소 안내, 취소와 보상, 관리자 허용
- **게스트 안내 메시지 초안은 만들지 않는다.** 계획서 7.4 가 9장 AI 기능에 맡겼고
  그건 P5 다. 지금은 해소 방법을 고르고 기록하는 데까지다
- 해소하면 `status`, `resolution`, `resolved_by`, `resolved_at` 을 남긴다
- **업그레이드 배정은 재고를 옮기는 일이다.** `InventoryService` 를 거치고 락은
  날짜 오름차순이다. **여기서 락이 두 개가 된다** — ADR 0002 결과 절이 예고한 자리다.
  판매 단위 식별자 오름차순으로 잠근다

### F. 고아 작업 되살리기

`RUNNING` 인 채 앱이 죽으면 그 연결이 영영 막힌다. 12주차의 `NOT EXISTS` 조건이
앞선 작업을 기다리기 때문이다.

일정 시간이 지난 `RUNNING` 을 `PENDING` 으로 되돌린다. 한 곳에서 주기적으로 보면
된다. D 가 결국 덮지만 하루를 기다리는 것과 몇 분은 다르다.

### G. 선언과 구현이 맞는지 확인

12주차에 `AdapterType.MOCK` 이 `PULL_BOOKING` 을 선언하지 않아 **그 채널만 조용히
건너뛰는** 결함이 있었다. 로그도 안 남았다.

iCal 에서 같은 자리가 다시 온다. iCal 은 `PUSH_RATE` 가 **없는 것이 정상**이라
"없는 게 맞는지 빠뜨린 건지"가 눈으로 구분되지 않는다.

각 어댑터의 선언과 실제 동작이 맞는지 확인하는 테스트를 둔다. 선언한 기능은
실제로 동작하고, 선언하지 않은 기능은 호출되지 않아야 한다.

- **웹훅 수신 엔드포인트.** 12주차에 폴링으로 정했다. 시뮬레이터의 웹훅 발신은
  그대로 둔다. 필요해지면 P6 예비 시간에 본다
- **채널별 재고 버퍼(계획서 7.4 의 `exposedUnits`).** 계획서 12.2 의 13주차 목록에

- **게스트 안내 메시지 초안.** P5 의 AI 기능이다
- **ShedLock.** 여전히 인스턴스가 하나다
- **모니터링 지표(계획서 14.4).** P6 이다

## 4. 지켜야 할 제약

- **15초 사슬에 무엇도 더하지 않는다.** 여유가 2초다. D 와 E, F 는 전부 사슬 밖이다
- **`DTEND` 는 받을 때도 낼 때도 배타적이다.** 한쪽만 맞추면 왕복에서 하루가 어긋난다
- **재고 변경은 전부 `InventoryService`.** E 의 업그레이드 배정은 락을 둘 쥔다 —
  **판매 단위 식별자 오름차순.** ADR 0002 결과 절
- **모듈 경계.** `channel` 이 `booking.domain` 을 보지 않는다
- **`AIRBNB_ICAL_URL` 과 발행 토큰을 로그·응답·커밋에 남기지 않는다**
- **발행 응답에 게스트 이름을 넣지 않는다**
- **`ddl-auto: validate`, V1 수정 금지.** 컬럼이 모자라면 V5 를 더한다
- 주석과 문서는 한국어, 식별자는 영어, 테스트 이름은 한국어 서술형

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. 실제 에어비앤비 발행 등록 | 사람이 한다. URL 과 절차를 준비해 사용자에게 요청 |
| 2. iCal 의 수정 판정 | `revision` 크기 비교를 쓰지 않는다. 값이 다르면 수정 |
| 3. 예약과 차단 구분 | 구분하지 않는다. 전부 예약으로 받고 게스트 정보는 비운다 |

### 2번의 근거

iCal 에는 `revision` 이 없다. 계획서 13.4 는 `hashOf(start, end, summary)` 로
대신했는데, `BookingIngestService` 가 `in.revision() > 기존` 으로 **크기를 비교한다.**
해시에는 순서가 없어서, 날짜가 바뀐 뒤의 해시가 우연히 더 작으면 수정이 무시된다.

정상 경로에서 증상이 없다. 예약은 그대로 있고 로그도 깨끗하며, 드러나는 것은
체크인 날 게스트가 다른 날짜를 들고 왔을 때다.

같은 `UID` 의 날짜나 내용이 달라졌으면 수정으로 처리한다. 순서 역전은 iCal 에서
일어나지 않는다 — 매번 전체 스냅샷을 받기 때문이다.

### 3번의 근거

**조사-02 가 확인한 실제 발행물에 구분 정보가 없다.** `SUMMARY` 는
`Airbnb (Not available)` 하나뿐이고 게스트 이름도 없다. 계획서 3.4 가 적은 iCal 의
구조적 한계 그대로다.

키워드로 예약과 차단을 나누는 로직을 만들면 **검증할 수 없는 코드**가 된다.
우리가 가진 실제 샘플로는 어느 쪽도 확인되지 않는다.

전부 예약으로 받는다. 재고를 막는다는 점에서 둘은 같고, `UID` 로 멱등성과 취소가
관리된다. `channel_code` 는 `AIRBNB_ICAL` 이고 계획서 13.5 의 응답 예시가 이미
그 값을 보여 준다. 게스트 이름은 비운다 — 9주차에 `nullish()` 로 고친 것이
이 경우를 위한 것이었다.

게스트 정보가 필요한 경로는 Channex 와 Mock 이 맡는다.

## 6. 완료 조건

**앞의 둘이 P3 완료 조건 셋째다. 실제 계정으로 판정한다.**

1. `.env` 의 실제 에어비앤비 피드로 연결을 만들고, 그 `VEVENT` 가 캘린더에
   나타나는 것을 브라우저에서 확인한다
2. 우리 발행 URL 을 에어비앤비에 등록하고, 우리가 막은 날짜가 에어비앤비 달력에서
   막히는 것을 확인한다. **등록은 사람이 한다**

iCal 수신.

3. 저장소의 실제 픽스처(`airbnb-unpublished.ics`)를 파싱하는 테스트.
   `DTEND` 가 배타적으로 해석되는지 확인한다 — `20270906` 이면 9월 5일까지다
4. 같은 `UID` 의 날짜가 바뀌면 수정으로 처리되는 테스트.
   **해시 크기를 비교하지 않는다**
5. `UID` 가 사라지면 취소로 처리되는 테스트
6. 이벤트 수가 직전 대비 절반 이하로 줄면 취소를 보류하고 알리는 테스트
7. `ETag` 가 같으면 파싱하지 않는 테스트(304)

iCal 발행.

8. 확정 예약과 판매 중지가 `VEVENT` 로 나오는 테스트
9. **우리가 낸 `DTEND` 가 배타적인 테스트.** 3박 예약이면 체크아웃일이 그대로 `DTEND` 다
10. **발행물 어디에도 게스트 이름이 없는 테스트.** 문자열로 훑는다
11. 토큰이 틀리면 404 인 테스트. 존재를 알리지 않는다

재동기화와 충돌.

12. 우리 값과 채널 값이 다르면 차이를 찾아 다시 보내는 테스트
13. `RUNNING` 인 채 오래 남은 작업이 `PENDING` 으로 돌아오는 테스트
14. 충돌을 해소하면 `status`·`resolution`·`resolved_by`·`resolved_at` 이 남는 테스트
15. **업그레이드 배정이 락을 둘 쥘 때 판매 단위 식별자 오름차순인지 확인하는 테스트.**
    ADR 0002 가 예고한 교착 자리다
16. 재동기화 효과 측정. Mock 에 에러율을 주입해 불일치 누적을 재고 배치 전후를
    비교한다. **측정값을 그대로 적는다**

전체.

17. **각 어댑터의 선언과 실제 동작이 맞는지 확인하는 테스트**
