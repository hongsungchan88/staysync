## 1. 원화 요금 전송 형식 (09-27, 스테이징 KRW 개발 숙소)

숙소 `2aacda1a-4f87-4ad4-b31d-5d996079427f`(`StaySync 개발 테스트 KRW`, 통화 KRW)에는 객실 `디럭스 더블`
(`40a98492-…`) 하나만 있고 요금제가 없었다. 측정용 요금제를 하나 만들었다 — **`[측정] 원화 형식 (작업지시-21 D)`
`28d1320b-8ebb-4451-b627-3c69680d3057`**(per_room · manual · 2인 primary). 생성 때 `"rate":"100000.00"` 을 줬더니
`options[0].rate` 가 `"100000"` 으로 돌아왔다. 숙소의 다른 것은 건드리지 않았다(작업지시-21 5절 3번).

`POST /api/v1/restrictions {"values":[{property_id, rate_plan_id, date, rate}]}` 를 날짜마다 따로 보내고
`GET /api/v1/restrictions?filter[property_id]=…&filter[date][gte]=…&filter[restrictions]=rate` 로 되읽었다.

| 날짜 | 보낸 `rate` | 응답 | 되읽은 값 |
|---|---|---|---|
| 2027-03-01 | `"170000.00"` (문자열, 소수 둘째 자리 — **지금 어댑터 형식**) | 200 `Success`, 경고 없음 | **`"170000"`** |
| 2027-03-02 | `170000` (정수) | 200 `Success` | **`"170000"`** |
| 2027-03-03 | `"170000"` (문자열, 소수 없음) | 200 `Success` | **`"170000"`** |
| 2027-03-04 | `"170000.50"` (원 미만) | 200 `Success`, 경고 없음 | `"170001"` — **조용히 반올림** |
| 2027-03-05 | `"99"` | 200 `Success` | `"99"` |

**결론 — 어댑터 형식을 바꾸지 않는다.** 원화는 소수 자리가 없는 통화라 최소 단위가 1원이고, 세 형식 모두 같은
값으로 들어간다. USD 에서 정수 `10000` 이 100.00 으로 읽힌 것(확인-10 1절)은 최소 단위가 1센트라서다. 지금 형식
`"170000.00"` 은 USD·KRW 모두에서 맞는 유일한 형식이므로 통화별 분기가 필요 없다. 원 미만은 반올림되지만 우리 요금은
원 단위 정수다. 되읽기 값에 소수가 없어도 대조 배치는 `compareTo` 로 비교해(`ChannelReconcileJob`) 불일치로 잡지
않는다. 근거는 `ChannexAdapter.money` 의 javadoc 에 옮겼다.

**금액.** KRW CRS 예약의 리비전 `amount` 를 어댑터가 그대로 읽어 340000.00·510000.00 으로 저장했다. 통화 검사(숙소
통화 KRW = 예약 통화 KRW)를 통과했다.

**리허설에서 보인 것 — 새 Channex 객실의 재고는 0 에서 시작한다.** 되읽기에서 우리가 보낸 적 없는 날은 전부 0 이었다
(10-20~22 만 1 — 취소 되보내기가 보낸 날). 리허설에서는 취소 되보내기만 돌았기 때문이다. 실물 전환은 9절 3번 "재고·요금을
먼저 내보낸다"가 이 구멍을 막는다 — **빠뜨리면 연결하는 순간 Channex 가 에어비앤비 달력을 전부 닫는다.**

## 4. 대조

### 4.1 전환 뒤 남은 앞으로의 iCal 예약 — 0 이어야 한다

```sql
-- 판매 단위마다, 앞으로 남은 살아 있는 iCal 예약(그 숙소 iCal 연결의 채널 코드로 들어온 것).
SELECT u.name AS unit, count(r.id) AS remaining_ical,
       min(r.check_in) AS first_check_in, max(r.check_out) AS last_check_out
FROM unit u
JOIN property p ON p.id = u.property_id
LEFT JOIN reservation r
       ON r.unit_id = u.id
      AND r.status IN ('HOLD', 'CONFIRMED', 'CHECKED_IN')
      AND r.check_out > (now() AT TIME ZONE 'Asia/Seoul')::date
      AND r.channel_code IN (SELECT c.channel_code FROM channel_connection c
                             WHERE c.property_id = r.property_id AND c.adapter_type = 'ICAL')
GROUP BY u.id, u.name
ORDER BY u.id;
```

서버에서 읽기 전용으로 돌린다(09-27 에 실제로 쓴 모양 — 위 쿼리를 `f21.sql` 로 저장해 둔다):

```bash
scp -q f21.sql staysync:/tmp/f21.sql
ssh staysync 'cd /opt/staysync && docker compose exec -T postgres psql -U staysync -d staysync -v ON_ERROR_STOP=1 -c "SET default_transaction_read_only = on;" -f - < /tmp/f21.sql; rm -f /tmp/f21.sql'
```

**전환 전 기준값(09-27, 배포 환경, 읽기만)** — 지니하우스 **12**(첫 체크인 09-25 ~ 마지막 체크아웃 11-30), 메종드서촌
2층 22, 3층 16, 시험 객실 0. 첫 체크인이 09-25 라 **지금 묵고 있는 손님이 있을 수 있다** — 넘겨받기에 CHECKED_IN 을
넣은 이유다(작업지시-21 8절).

**쿼리가 iCal 연결에 기대는 이유.** 넘겨받기도 같은 규칙이다(같은 숙소 iCal 연결들의 채널 코드). **전환 때 iCal
연결은 지우지 않고 매핑만 푼다** — 연결을 지우면 넘겨받기가 코드를 몰라 새 예약 + 충돌이 되고, 이 쿼리도 0 을 거짓으로
보인다.

**리허설에서 쿼리가 할 일을 보였다.** 정리 뒤 남은 iCal 122 가 바로 "Channex 가 같은 날짜로 넘겨주지 않은 예약"의
모양이다(R3 이 하루 어긋나 새 예약이 됐다). 실물에서 이 수가 0 이 아니면 그 예약은 앞으로 변경·취소를 받을 길이
없다 — 에어비앤비 호스트 화면과 날짜를 맞춰 보고, 같은 예약이면 충돌 해소로 정리한다.

### 4.2 기존 예약 가져오기 — Channex "Pull Future Bookings" (09-28 고침)

**자동으로는 안 넘어온다.** 연결 전에 만들어진 예약은 채널 화면의 **Actions 메뉴 → "Pull Future Bookings"** 로
가져온다. Channex 문서 "Channels Management" — 부킹닷컴·익스피디아·에어비앤비에만 있고, *"This will pull all bookings
that were created before connection"*. 스테이징 에어비앤비 어댑터 서술자(`GET /api/v1/channels/adapter?code=AirBNB`)의
`actions: ["load_future_reservations"]` 가 그 동작의 API 이름이다(09-27, 읽기만). 콘솔 메뉴로 한다 — API 경로는 문서에
없고 추측해 쏘지 않았다.

**9절에서의 자리**(새 순서 8번): Channex 리스팅 매핑·활성화가 끝난 뒤 한 번 누른다 → 우리 쪽 Channex 폴링(60초)을 두 번
기다린다 → 4.1 쿼리가 0 인지 본다. 0 이 아니면 남은 예약의 날짜를 에어비앤비 호스트 화면과 맞춰 보고(날짜가 다르게
넘어와 새 예약 + 충돌이 된 경우), 같은 예약이면 충돌 해소로 정리한다.

## 5. 공용 계정 동시 사용 (09-28, 로컬 재현 — 고치지 않았다)

1차 심사에서 심사자 약 3명이 업체 계정 하나를 같이 쓴다. ADR 0005(리프레시 토큰 회전·재사용 탐지)와 `LoginAttemptLimiter`
가 그 모양에서 어떻게 도는지 로컬 앱(`bootRun` local)에서 재현했다. 새 계정 하나, 파이썬으로 세션마다 쿠키 저장소를 따로
두고(= 브라우저 셋), "탭 둘"은 같은 쿠키로 보내는 동시 요청 두 개다 — 같은 브라우저의 두 탭이 보내는 것과 같다.

### 5.1 결과

| 재현 | 결과 |
|---|---|
| 세 세션 동시 로그인 | 200 · 200 · 200. 로그인마다 서로 다른 리프레시 토큰 |
| 한 세션의 탭 둘이 **정확히 동시에** 갱신(간격 0) | **둘 다 200** — 둘이 같은 토큰을 회전 전에 읽어 **회전이 두 갈래로 갈린다.** 재사용 탐지가 아예 안 걸린다(아래 ③) |
| 탭 둘, 두 번째가 **30ms·100ms·500ms 뒤** 같은 옛 쿠키로 | 첫째 200, **둘째 401 → 재사용 탐지 → 그 사용자 토큰 전부 무효화.** 이어서 다른 두 세션의 갱신도 **401·401** |
| 갱신 응답을 잃고 옛 토큰으로 재시도(네트워크 재시도) | 재시도 401, **다른 세션 갱신 401** |
| 한 명이 비밀번호 5회 틀림 | 다섯째 401. **다른 사람의 정상 로그인 429**(10분 잠금). 이미 로그인해 있던 세션의 갱신은 **200** — 잠금은 새 로그인만 막는다 |

**①(재사용 탐지가 셋을 다 끊는다) — 재현됐다.** 무효화 범위가 "그 토큰의 사슬"이 아니라 "그 사용자의 살아 있는 토큰 전부"
(`RefreshTokenRepository.revokeAllOfUser`)라, 한 사람의 브라우저에서 난 일이 세 사람을 모두 로그아웃시킨다. 접근 토큰(30분)은
살아 있어 **각자 다음 갱신 때**(늦어도 30분 안, 또는 새로고침) 로그인 화면으로 떨어진다. 다시 로그인하면 된다.
- **표의 100·500ms 는 과장이다.** 실제 브라우저에서는 첫 갱신 응답이 도착한 뒤 시작한 탭은 새 쿠키를 싣는다. 위험한 창은
  **첫 갱신의 왕복 시간**(로컬 수 ms, 배포 환경 수십~수백 ms)이다. 그 창에 두 요청이 겹치는 흔한 경우 —
  **브라우저가 탭 여럿을 한꺼번에 복원할 때**(재시작·세션 복원), 탭 복제, 그리고 응답을 잃은 재시도
- 프론트의 "갱신은 한 번에 하나"(`client.ts` 의 `refreshInFlight`)는 **탭 하나 안에서만** 지켜진다. 탭끼리는 조율이 없다

**②(한 명이 틀리면 셋이 막힌다) — 조건부로 재현됐다.** 이메일 기준 15분 안 5회 실패면 10분 동안 **새 로그인만** 막힌다.
이미 들어와 있는 사람은 계속 쓴다. 한 번 성공하면 카운터가 지워지므로, 셋이 번갈아 들어오는 동안 한 명이 다섯 번 연속
틀려야 걸린다. 그래도 ①로 로그아웃된 직후에 겹치면 셋 다 10분 동안 못 들어온다 — 둘이 맞물리는 것이 최악이다.

**③ 새로 보인 것 — 동시 회전 경합.** 간격 0 에서 둘 다 200 인 것은 `rotate` 가 토큰 행을 잠그지 않고 읽기 때문이다. 결과로
살아 있는 사슬이 둘 생기고(쿠키에는 하나만 남는다) 재사용 탐지가 우회된다. 정상 사용에는 해가 없지만, **탈취한 토큰을 정상
사용자와 같은 순간에 쓰면 탐지를 피한다** — 보안 쪽 구멍이다.

### 5.2 고칠 방향 — 비교

| | 하는 일 | 흔한 예 | 고치는 것 | 비용·남는 것 |
|---|---|---|---|---|
| **A. 유예(재사용 간격)** | 교체된 토큰이 **교체 뒤 N초 안**에 다시 오면 재사용으로 보지 않고 성공 처리(같은 후계 토큰을 다시 주거나 새로 발급) | Auth0 "Reuse Interval"(leeway, 기본 꺼짐, 초 단위 — *"to account for potential network concurrency issues"*), Okta "Grace period for token rotation"(0~60초, 기본 30초) | ①의 흔한 경우(복원·복제·재시도) | 서버만. `refresh_token` 에 교체 시각이 필요하다(지금 `replaced_by` 만 있음 → 마이그레이션 하나, 또는 후계 행의 발급 시각으로 대신). N 을 짧게(10~30초) |
| **B. 무효화 범위를 사슬로** | 재사용이 탐지되면 **그 로그인에서 이어진 사슬만** 끊는다(사용자 전체가 아니라) | Auth0 — *"the entire set of refresh tokens issued since that invalidated token was issued"*, Okta — 그 인증 이후 발급된 토큰 | ①이 **한 사람에게서 멈춘다.** 다른 둘은 안 끊긴다 | 서버만. `replaced_by` 를 따라가면 사슬이 나오므로 마이그레이션 없이도 되지만, `family_id` 칸을 두면 한 번에 지운다 |
| **C. 회전을 조건부 갱신으로** | `UPDATE … SET replaced_by = ? WHERE id = ? AND replaced_by IS NULL` 의 행 수로 이긴 쪽만 발급(또는 `FOR UPDATE`) | — (경합 일반) | ③ | 서버만, 작다. A 와 함께 두면 진 쪽은 유예로 처리된다 |
| **D. 탭끼리 갱신 조율** | Web Locks(`navigator.locks.request('refresh', …)`)로 브라우저 안에서 갱신을 하나로 줄 세운다. 뒤 탭은 새 쿠키로 간다 | 표준 브라우저 API | ①의 복원·복제 경우(재시도는 못 덮는다) | 프론트만, 작다 |
| **E. 로그인 제한을 (이메일, IP)로** | 잠금 키에 IP 를 더한다(끝자리 가림 로그는 이미 있다) | OWASP 인증 치트시트가 계정 잠금의 서비스 거부 위험을 경고 | ② — 심사자가 서로 다른 곳이면 | 서버만, 작다. 같은 방(같은 IP)이면 그대로 걸린다. 계정 전체 상한을 느슨하게 하나 더 두는 것이 흔하다 |
| **F. 조직에 계정 셋** | 심사자마다 계정 — 토큰·잠금이 사람마다 갈린다 | — | ①②③ 전부(사람 사이로는), **감사 기록에 누가 했는지가 남는다** | **계정을 만들 길이 없다** — 가입은 새 조직을 만들고, 조직 안 초대가 없다(작업지시-19). 배포 DB 에 직접 넣으면 업체 데이터 변경이고, 초대 화면은 새 기능이다. 역할은 셋 다 OWNER(역할별 인가 없음). 교수께는 공용 계정으로 제안해 이의가 없었다(작업지시-20 지시) |

**권고.** 10월 말 전에 하려면 **B + C + A(짧은 유예)** 를 서버에서 한 번에 — 셋이 같은 자리(`RefreshTokenService.rotate`)라
한 변경이고, ①이 "한 사람의 한 로그인"으로 줄고 흔한 경우는 아예 안 일어나며 ③도 닫힌다. ADR 0005 결과 절을 고쳐 적어야
한다(재사용 탐지의 범위와 유예). **D·E 는 작고 독립적**이라 여유가 있으면 더한다. **F 는 계정을 만드는 길(초대)이 먼저**라
이번 심사에는 크다 — 감사 기록에 사람이 남는 것이 필요해지면 그때 초대와 함께 연다. 결정은 사용자 몫이다.


### 5.3 고친 것 (10-02, 사용자 결정 — 유예 + 그 로그인의 체인만 + 조건부 회전)

`RefreshTokenService.rotate` 한 자리, V11(`refresh_token.family_id`·`rotated_at`), ADR 0005 결과 절. 유예는 **30초**(Okta 기본값,
Auth0·Okta 범위 안) — 근거는 ADR. 로그인 제한의 (이메일, IP) 전환과 계정 셋은 하지 않았다(사용자 결정).

5.1 의 재현 표가 `RefreshTokenRotationTest` 의 테스트가 됐다:

| 재현 | 고친 뒤 |
|---|---|
| 탭 둘, 30ms 어긋남 | 둘 다 200, 두 토큰 모두 이어서 갱신된다, **다른 세션 200** |
| 응답을 잃고 옛 토큰으로 재시도 | 재시도 200, 이어서 갱신, **다른 세션 200** |
| 같은 순간 둘 | 둘 다 200 이지만 **회전 표시는 하나**(원래 토큰의 `replaced_by` 는 한 토큰만 가리킨다), 두 토큰은 같은 묶음 — 유예 뒤 원래 토큰을 다시 쓰면 **두 갈래가 함께 401** |
| 유예 밖의 진짜 재사용 | 재사용 401, 같은 체인의 새 토큰 401, **같은 계정의 다른 로그인 200** |
| (더함) 로그아웃 뒤 유예 안의 옛 토큰 | 401 — 로그아웃이 그 로그인 묶음을 끊는다. 다른 세션 200 |
| (더함) 조건부 회전 | 같은 토큰에 두 번째 회전 표시는 0 행 |

"같은 순간 둘 → 하나만 이김"은 **회전 표시가 하나만 남는다**로 고정했다. 진 쪽 요청은 실패시키지 않는다 — 방금 교체된
토큰의 유예 안 재사용과 같은 경우라(탭 둘이 정확히 겹친 것) 같은 묶음의 갈래로 받는다. 탐지가 우회되지 않는 것은 마지막
줄(유예 뒤 원래 토큰 → 두 갈래 401)이 보인다. V11 의 기존 사슬 채우기는 `V11MigrationTest` 가 V10 상태의 사슬에 실제로 적용해 본다.

### 6.2 호스트에게 보낼 연결 링크 — 만드는 법(아직 안 만들었다)

**Channex 문서(Airbnb 매핑 가이드)** — 채널 추가에서 Airbnb 를 고르고 제목·숙소·설정을 넣은 뒤 "Connect to Airbnb" 단계에서,
*"If you have no access to the Airbnb account but need to setup on behalf of the host. Copy the link and provide to them."*
호스트가 에어비앤비 화면에서 승인하면 채널이 생긴다. **비밀번호를 받지 않는 OAuth 위임이다.**

**API 로는 만들지 않았다.** 에어비앤비 어댑터 서술자의 `payload` 에 OAuth `client_id`·`redirect_uri`(`…/api/v1/meta/airbnb/
auth_redirect`)·`scope`(`property_management,messages_read,messages_write`)가 있지만, 링크가 어느 Channex 계정·숙소로
돌아올지를 담는 값(`state`)은 콘솔이 만든다. 손으로 조립한 링크는 승인 뒤 엉뚱한 곳으로 돌아가거나 실패한다.
**콘솔은 로그인이 필요하다** — 내장 브라우저의 스테이징 콘솔은 로그인 화면이었고, 비밀번호는 넣지 않았다.
**만드는 사람이 할 일:** 스테이징 콘솔 로그인 → Channels → Create → Airbnb → 제목 `에어비앤비 지니하우스`, 숙소
`StaySync 지니하우스 (KRW)`, 아래 설정 → "Connect to Airbnb" 단계의 링크 복사 → **보내지 않고** 확인-12 에 "만듦"만 적는다(링크
자체는 적지 않는다). 내장 브라우저에 로그인해 두면 Claude Code 가 이어서 할 수 있다.

**연결 설정 — 9절 전에 정할 것**(서술자 `params`):
- **Booking Amount = `Total Paid Amount`**(10-02 사용자 결정). `Payout Amount`(기본)는 호스트 정산액이다. 근거 둘 — 직접예약
  금액은 손님이 낸 총액이고, **에어비앤비는 소프트웨어로 연결된 리스팅에 호스트 전용 수수료(15.5%)를 적용하므로 게스트
  결제액이 리스팅 가격과 같아**(사용자 근거) 우리 요금·직접예약과 같은 기준이 된다. 수수료를 `channel_commission` 에 채우는
  일은 하지 않는다
- **Min Stay Type** — `Arrival`(기본) / `Through`. 우리 최소 숙박은 도착일 기준(`min_stay_arrival`)이라 **`Arrival`**
- Send Property Notification — 끔(기본). Enable Rate Plans — 끔(기본). 요금제 하나다
- 서술자 `channel_restrictions: {currency: USD, min_price: 1000}` — 채널이 받는 최소 요금이 10.00 USD 로 읽힌다(확인-10 4절과
  같은 모양). 원화 170,000 은 넘는다

### 6.3 승인만으로 리스팅이 바뀌는가 — 안 바뀐다(근거 둘, 실물 확인은 없음)

1. **문서 순서** — 가이드는 승인 → "Once the connection is active, Click on the 'Mapping' tab" 이다. 동기화는 매핑된 리스팅
   단위로 돈다(`mapping_mode: listing`, 매핑 설정이 `listing_id`·`airbnb_rate_plan_id`). 매핑되지 않은 리스팅에 보낼 대상이
   없다
2. **Channex 변경 이력** — *"Open closed dates for Airbnb on connect listing"*. 리스팅을 **연결(매핑)하는 순간** 닫힌 날을
   연다 — 동기화가 매핑에서 시작한다는 뜻이고, 동시에 **매핑 전에 우리 재고가 Channex 에 들어가 있어야 한다**는 뜻이다(재고 0 인
   채로 매핑하면 에어비앤비 달력이 닫힌다, 2절)
3. 스테이징 부킹닷컴 채널은 만들면 `is_active: false` 였고 `activate` 를 따로 불렀다(확인-10 1.1)

**실물 확인은 없다** — 에어비앤비 계정을 연결하지 않았으니 "승인 직후 리스팅이 그대로인지"는 9절 4번(호스트 승인)과 5번 사이에
에어비앤비 달력을 한 번 보는 것으로 닫는다.

### 6.4 같이 보인 것 — 체크인·체크아웃 시각과 청소 마감 (10-02 다시 봄, 고치지 않음)

**09-28 에 "`01:00`·`20:00`"이라 적은 것은 DB 원시 값이다.** 배포 환경 `GET /api/properties` 는 지니하우스 16:00 / 11:00 이다
(사용자 확인). 다른 숙소도, Channex 스테이징 숙소도 아니다 — 같은 행을 psql 로 읽으면 `01:00:00 | 20:00:00` 이다(읽기만).
**API 값 + 9시간**이다.

**원인 — 시간대 변환이 두 번 엇갈린다.** `application.yml` 의 `hibernate.jdbc.time_zone: Asia/Seoul` 인데 배포 컨테이너의 JVM 은
**UTC** 다(`date` → UTC, `TZ` 비어 있음, `-Duser.timezone` 없음). Hibernate 가 `LocalTime` 을 쓸 때 JVM 시간대에서 JDBC 시간대로
옮겨 16:00 → 01:00 으로 저장하고, 읽을 때 되돌려 16:00 으로 보인다. 화면·API 는 멀쩡하고 원시 값만 어긋난다. 개발 PC 는 JVM 이
Asia/Seoul 이라 두 시간대가 같아 어긋나지 않는다 — 테스트가 못 잡은 이유다.

**결함 — 청소 마감이 9시간 늦다.** `OpsTaskService.createCleaningFor` 가 읽은 체크아웃 시각(11:00, 되돌린 값)을
`ZoneId.systemDefault()` 로 시각에 붙인다. 배포 컨테이너에서는 그게 UTC 라 **11:00 UTC = 20:00 KST** 가 된다. 기한의 끝(다음
체크인 16:00)도 **다음 날 01:00 KST** 가 된다. 재현 — 테스트 컨텍스트에서 JVM 기본 시간대를 바꿔 같은 원시 값으로 체크아웃했다
(커밋하지 않은 1회용 테스트):

| JVM 기본 시간대 | 숙소 원시 값(입·퇴실) | 청소 마감(KST) |
|---|---|---|
| Asia/Seoul (개발 PC) | 16:00 · 11:00 | **11:00** |
| UTC (배포 컨테이너와 같음) | 01:00 · 20:00 (배포 환경 지니하우스와 같음) | **20:00** |

배포 환경에는 아직 청소 태스크가 0 건이라(읽기만) 틀린 마감이 저장된 적은 없다. 첫 체크아웃부터 드러난다. 체크인·체크아웃
시각은 9절 1번의 질문에서 뺐다.

**고칠 방향(보고만).** 한 가지로는 안 된다.
- `OpsTaskService` 가 `ZoneId.systemDefault()` 대신 **숙소 시간대**(`property.timezone`, 기본 Asia/Seoul)를 쓴다 — 서버 시계와
  무관해진다. 다른 `systemDefault()` 자리도 같이 훑는다
- `LocalTime` 저장의 어긋남은 두 길 — 컨테이너 JVM 을 Asia/Seoul 로(`-Duser.timezone`) 두면 이후 쓰기·읽기가 그대로가 되지만
  **이미 +9시간으로 저장된 원시 값이 그대로 읽혀** 화면이 01:00/20:00 이 된다 → 원시 값을 되돌리는 마이그레이션이 함께 필요하다
  (덤프 선행). 반대로 `jdbc.time_zone` 을 빼는 길도 같은 데이터 문제를 낳는다. `LocalDate`·`TIMESTAMPTZ` 칸이 같은 변환을 타는지
  (날짜가 밀리는지)도 함께 확인해야 한다 — 이번에는 보지 않았다
