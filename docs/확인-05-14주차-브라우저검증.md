# 확인 05. P4 14주차 브라우저 검증과 거기서 나온 결함

- 확인일: 2026-09-07
- 범위: 작업지시 11 의 완료 조건 14·15, P3 완료 조건 셋째의 나머지 절반
- 관련: 확인-04, 조사-02, 작업지시-11, ADR 0003(Outbox), ADR 0011

브라우저로 14주차 화면 조건을 보다가 **로그에서 결함 셋이 나왔다.** 화면 검증이

## 1. 화면 검증 결과

### 완료 조건 14 — 성립

Mock 시뮬레이터에 게스트 메시지를 만들어 넣고 받은편지함까지 따라갔다.

```bash
curl -X POST http://localhost:8081/api/scenarios/guest-message \
  -H 'X-Api-Key: mock-ota-dev-key' -H 'Content-Type: application/json' \
  -d '{"booking_id":"BK-INBOX-1","body":"체크인 시간을 늦출 수 있을까요?","count":3}'
→ {"scenario":"guest-message","emitted":3,...}
```

| 본 것 | 결과 |
|---|---|
| 시뮬레이터가 내놓은 건수 | 3 (같은 `msg-BK-INBOX-1`, 시각 역순) |
| 받은편지함 목록 | **대화 1줄**, 안 읽음 배지 `1` |
| 대화창 | 메시지 **1통**, `(예약 미연결)` 표시 |
| 답장 발송 | 호스트 말풍선으로 붙음 |
| 시뮬레이터 `/api/messages/sent` | `sender:"HOST"`, 본문 그대로 1건 |
| 콘솔 오류 | 없음 |

**세 통이 한 통이 됐다.** 수신 멱등성이 화면 경로에서 성립한다. 발송도 화면의
말풍선이 아니라 시뮬레이터 도착으로 확인했으므로 `sync_job` 이 끝까지 돈 것이다.

이 멱등성은 지금도 매 주기 돌고 있다 — 로그에 `이미 받은 메시지라 넘긴다.
channel=MOCK messageId=msg-BK-INBOX-1` 이 계속 찍힌다.

### 완료 조건 15 — 판정 불가. 결함이 아니다

iCal 연결에 스레드가 생기지 않아 미지원 표시를 볼 자리가 없었다.

이유가 구조적이다. iCal 은 메시징을 지원하지 않아 `MessagePoller` 가 아예 긁어
오지 않는다. 그쪽 스레드는 **iCal 예약에 자동 발송이 말을 거는 경로**로만 생기는데,
이 리스팅은 예약이 아니라 1년치 차단 한 건뿐이라 대화가 만들어질 상대가 없다.

**단위 테스트(완료 조건 6)가 같은 것을 이미 확인하고 있다.** 화면 확인은 실제
채널 예약이 들어오는 채널이 생긴 뒤로 미룬다.

## 2. P3 완료 조건 셋째 — 발행 방향은 성립, 반영 확인은 환경 한계

확인-04 3절의 나머지다.

### 된 것

VS Code 포트 포워딩(8080, Public)으로 `https://<터널>` 을 열고
`--staysync.public-base-url` 에 그 주소를 주어 앱을 띄웠다. 매핑 화면의
`발행 URL 보기` 가 터널 주소로 바뀌었고, 그 URL 을 에어비앤비의 2단계에 넣었다.

**에어비앤비 화면에 `StaySync / 최종 수정일: 9월 7일 오후 8:01` 이 떴다.**
에어비앤비 서버가 우리 URL 로 실제로 요청을 보내 발행물을 읽어 갔다는 뜻이다.
`발행 → 에어비앤비 수신`까지는 여기서 성립한다.

수신 쪽도 같이 확인했다. 매핑을 붙이자 객실 01 에 차단이 들어왔다.

```
2026-09-02  avail=1   ← 열려 있음
2026-09-03  avail=0   ← DTSTART 그대로
...
2027-09-07  avail=0
2027-09-08  avail=1   ← 여기서 열림
```

시작이 `DTSTART` 와 정확히 일치한다. 끝은 확인-04 1절이 적은 `DTEND:20270906`
기준이면 09-05 까지여야 하는데 09-07 까지다. **확인-04 를 쓴 9월 5일 이후 이틀이
지났고 차단 구간의 끝이 그만큼 밀린 것으로 보이나, 지금 피드를 다시 읽어 확인하지
않았다.** 아래 5절에 남긴다.

발행물 자체의 `DTEND` 는 맞다. 객실 01 이 2026-09-07 ~ 2027-09-07 막혀 있는데
`DTEND:20270908` 로 나간다. 받을 때와 낼 때가 같은 규칙이다.

### 안 되는 것 — 그리고 앞으로도 안 된다

확인-04 3.4 절의 "우리가 막은 날짜가 에어비앤비 달력에서 막힌다"를 **이 리스팅으로는
판정할 수 없다.**

리스팅을 게시하려면 대한민국 숙박업 영업신고증이 필요하다. 개인이 지자체 신고를
하지 않는 한 이 리스팅은 계속 미게시로 남고, 미게시 리스팅은 전 기간이 이미 차단
상태다. **열린 날짜가 없으므로 날짜가 닫히는 것을 볼 수 없다.**

차단 사유로 우회하려 했으나 에어비앤비는 날짜 상세에 "예약이 차단된 날짜입니다"만
보여 주고 **출처를 표시하지 않는다.** 우리 달력 때문인지 미게시 때문인지 구분되지
않는다.

**일시적 상태가 아니라 영구 제약이다.** 계획서 12.2 의 P3 완료 조건 셋째를 다음과
같이 판정한다.

> **수신** — 성립. 실제 에어비앤비 발행물이 캘린더에 반영된다
> **발행** — 에어비앤비가 우리 발행물을 읽어 가는 것까지 성립.
> 읽은 결과가 달력에 반영되는지는 **미게시 리스팅에서 관측 불가**

구현 결함이 아니라 검증 환경의 한계다. 실무에서 채널 매니저를 붙일 때도 게시된
리스팅 없이는 같은 벽에 부딪힌다. **계획서 12.2 의 문구를 이에 맞게 고쳐야 한다.**

## 3. 고칠 것

로그 파일: 5분치 574KB. 아래 숫자는 그 한 번의 기동에서 나온 것이다.

### A. Outbox 가 앞으로 못 나간다 — 최우선

```
20:08:27  이벤트 발행. type=RESERVATION_CONFIRMED aggregate=RESERVATION#1
20:08:57  이벤트 발행. type=RESERVATION_CONFIRMED aggregate=RESERVATION#1
20:09:29  이벤트 발행. type=RESERVATION_CONFIRMED aggregate=RESERVATION#1
   ... 5분 동안 37번, 약 32초 주기
```

| 항목 | 값 |
|---|---|
| 총 발행 | 973건 |
| 고유 예약 | 94개 |
| `RESERVATION#1` 발행 횟수 | 37 |

그리고 매 주기 이것이 함께 나온다.

```
OutboxRelay : 이벤트 100건을 발행했다
OutboxRelay : 이벤트 발행이 한 주기 상한 100건에 닿았다. 남은 건은 다음 주기로 넘긴다.
```

**발행한 행을 처리됨으로 남기지 못하고 있다.** 재기동하면 다시 `RESERVATION#1`
부터 시작한다. at-least-once 는 중복을 허용하지만 이것은 중복이 아니라 **수렴하지
않는 재생**이다.

- **큐가 절대 비지 않는다.** 새 이벤트가 옛날 것 뒤에 줄을 서므로 **완료 조건 1의
  15초 사슬이 성립하지 않는다**. 지금은 데이터가 적어 눈에 안 띌 뿐이다
- 상한 경고의 문구가 오해를 부른다. 처리량 문제가 아니므로 **상한이나 주기를
  올려도 아무것도 나아지지 않는다**
- 게스트에게 스팸이 안 나가는 것은 순전히 방어 두 겹 덕이다 — 자동 발송이 예약
  상태를 다시 보고 `CANCELLED` 면 건너뛰고(완료 조건 11), 발송 멱등성이 중복을
  흡수한다(완료 조건 10). **둘 중 하나만 없었어도 옛날 예약에 계속 말을 건다**

원인은 소스에서 확인할 것. 발행 후 상태 갱신이 같은 트랜잭션에 없거나, 갱신은
하는데 조회 조건이 그것을 안 보고 있을 가능성이 높다. 계획서 13.2 와 인계메모 5절이
적은 되풀이 두 가지가 모두 이 자리에 해당한다.

**증상이 안 보이는 결함이 아니라 증상을 방어가 가려 준 결함이다.** 방어를 믿고
넘기지 않는다.

### B. 일괄 편집이 채널에 안 나간다

```
WARN  일괄 편집 이벤트에 범위가 없어 전파하지 않는다.
      payload={"changed":["price"],"cellCount":30,"propertyId":1}
```

셀 30개의 요금을 바꿨는데 페이로드에 **날짜 범위가 없어** 전파를 포기한다.
화면에는 값이 바뀐 것으로 보이고 채널에는 안 나간다. 조용히 어긋난다.

전파하는 쪽이 아니라 **이벤트를 만드는 쪽**을 봐야 한다. 범위 없이 만들어진 것이
원인이고, 전파하는 쪽에서 추측으로 메우면 틀린 구간을 밀게 된다.

`cellCount` 는 있는데 범위가 없다는 것이 단서다.

### C. CHANNEX 연결이 유령으로 남아 있다

```
WARN  채널 예약 수집에 실패했다. 다음 주기에 다시 읽는다. connectionId=2
      사유=AdapterNotRegisteredException: 등록된 채널 어댑터가 없습니다. type=CHANNEX
```

`connectionId=2` 가 CHANNEX 인데 어댑터가 없어 매 주기 실패한다. 화면의 연결
목록에는 나타나지 않는다. **목록에 안 보이는 연결을 폴러가 잡고 있다는 것 자체가
질문거리다** — 비활성 연결을 폴링에서 제외하는 조건이 목록 조회 조건과 다르다는
뜻이다. 그 어긋남이 진짜 문제이고, 행을 지우는 것은 증상만 없앤다.

### D. SSE 끊김이 ERROR 로 올라온다 — 결함은 아니나 고쳐야 한다

```
ERROR  처리하지 못한 예외
       AsyncRequestNotUsableException: ServletOutputStream failed to flush ...
```

브라우저가 캘린더 스트림 연결을 끊으면 나는 정상적인 상황인데 `GlobalExceptionHandler`
까지 올라와 ERROR 로 스택 트레이스를 찍는다. **진짜 오류를 덮는다.** 5분에 3건 났다.

### E. SQL 로그가 두 번 찍힌다 — 사소함

`application-local.yml` 에 `show-sql: true` 와 `org.hibernate.SQL: DEBUG` 가 함께
있다. `show-sql` 쪽을 지운다. 표준출력으로 바로 뱉어 로거로 제어할 수 없다.

지우고 나면 `guest ... where id in (?)` 이 물음표 하나로 반복되는 것이 눈에 띌
것이다. N+1 로 보이나 지금은 데이터가 적어 비용이 없다. **A 를 고친 뒤에 다시
본다** — 재생이 멈추면 그 반복도 같이 사라질 수 있다.

## 4. 완료 조건

1. **같은 이벤트가 두 번 발행되지 않는 테스트.** 릴레이를 두 번 돌려 확인한다
2. **재기동해도 이미 발행한 이벤트가 다시 나가지 않는 테스트**
3. **큐가 비면 상한 경고가 멈추는 것을 로그로 확인한다.** 5분 띄워 두고
   `RESERVATION#1` 이 한 번만 나오면 성립
4. 일괄 편집 이벤트에 날짜 범위가 실리는 테스트. **범위 없이 만들어지면 실패해야
   한다** — 조용히 건너뛰지 않는다
5. 일괄 편집이 채널로 전파되는 테스트
6. 목록에 보이지 않는 연결은 폴러도 잡지 않는 테스트. 두 조회의 조건이 같아야 한다
7. SSE 끊김이 ERROR 로 올라오지 않는 테스트
8. `./gradlew test`, `./gradlew build` 통과

**1·2·3 이 하나의 결함이다.** 셋 다 없으면 고쳤다고 할 수 없다.

## 6. 3절 처리 결과

- 처리일: 2026-09-07
- 처리: Claude Code. 백엔드 253 + 시뮬레이터 37 통과, `./gradlew build` 통과

### A — 원인은 자기 호출이었다

`OutboxRelay.run()` 이 같은 클래스의 `relayPending()` 을 불렀다. 프록시를 거치지 않아
**스케줄러 경로에만 트랜잭션이 열리지 않았다.** `findPending` 이 돌려준 엔티티가 곧바로
준영속이 되어 `markPublished` 가 아무 데도 반영되지 않는다. 발행은 되는데
`published_at` 이 비어 있으니 매 주기 같은 이벤트가 다시 나갔다.

로그의 스택 트레이스가 그대로 보여 준다 — `run(OutboxRelay.java:71)` 과
`relayPending(:86)` 사이에 프록시 프레임이 없다.

**테스트가 못 잡은 이유도 같다.** 기존 테스트는 전부 `relayPending()` 을 직접 불렀고,
그건 주입받은 프록시라 트랜잭션이 열린다. 인계메모 5절의 "프록시를 거치지 않는 자기
호출"이 세 번째로 났다.

`run()` 에 `@Transactional` 을 붙였다. 상한 경고 문구도 고쳤다 — 상한을 올리라고
읽히던 자리를 "`published_at` 이 남는지를 먼저 보라"로 바꿨다.

완료 조건 1·2·3 은 `OutboxRelayTest` 의 새 테스트 셋이 덮는다. **셋 다 `run()` 을
부른다** — `relayPending()` 을 부르면 고치기 전에도 통과한다. 고치기 전 상태로 되돌려
셋이 실패하는 것을 확인했다.

**완료 조건 3 의 "5분 띄워 두고" 는 아직 못 했다.** 8080 에 20:08 기동한 그 인스턴스가
아직 떠 있어서다. 앱을 다시 띄우면 밀린 973건이 100건씩 열 주기에 걸쳐 빠지고 그 뒤로
상한 경고가 멎어야 한다.

### B — 만드는 쪽은 이미 옳다. 문제의 행은 12주차 이전 것이다

`BulkEditWriter.recordEvent` 는 `unitIds`·`from`·`to` 를 싣는다. **12주차 커밋
(e2d1181, 송신 경로)에서 더해졌다.** 로그에 걸린 그 이벤트는 그 이전에 만들어진 행이고,
A 때문에 지워지지 않은 채 매 주기 다시 나오고 있었다.

즉 B 는 새 결함이 아니라 **A 가 옛 행을 살려 두고 있었던 것**이다. A 를 고치면 그 행은
한 번 나가고 발행 완료로 남는다. 전파하는 쪽의 경고는 그대로 둔다 — 범위를 추측으로
메우면 틀린 구간을 밀게 된다는 판단이 맞다.

완료 조건 4 는 만드는 쪽에 테스트를 붙였다(`BulkEditTest`). 요일 필터를 건 편집에서
페이로드의 양끝이 **필터를 거친 실제 대상**의 양끝인지까지 본다. 완료 조건 5 는
`ChannelPropagationTest` 가 이미 덮고 있다.

### C — 유령이 아니다. 다른 조직의 행이다

`.localdb` 의 힙을 직접 읽어 확인했다.

| 연결 | 숙소 | 조직 |
|---|---|---|
| 1 (AIRBNB_ICAL, ICAL) | 2 성수동 오피스텔 | 3 |
| **2 (BOOKING_COM, CHANNEX)** | **2** | **3** |
| 3·4 (MOCK) | 1 성능측정 숙소 | 2 |
| 5 (AIRBNB_ICAL, ICAL) | 1 | 2 |

**화면에 안 보인 이유는 로그인한 조직이 2 이고 그 연결이 조직 3 의 것이기 때문이다.**
목록은 조직으로 좁히는 것이 맞고, 폴러는 모든 조직을 돌아야 하므로 두 조회의 조건은
같아질 수 없다. 이 어긋남은 결함이 아니다.

**진짜 어긋남은 다른 자리에 있었다.** 폴러가 할 일을 고를 때는 `AdapterType` 의 기능
*선언*을 보고, 실제로 실행할 때는 등록된 *구현*을 찾는다. `CHANNEX` 는
`PULL_BOOKING` 을 선언하지만 어댑터가 없다. 그래서 매 주기 집었다가
`AdapterNotRegisteredException` 으로 실패했다. 인계메모 5절의 "선언이 실제보다 넓은"
쪽이고 13주차의 그것과 같은 모양이다.

`ChannelAdapterRegistry.isRegistered` 를 더하고 폴러가 고르는 자리에서 걸렀다.
**조용히 넘기지는 않는다** — 종류당 기동에 한 번 경고를 남긴다. 매 주기 남기면 진짜
경고를 덮고, 아예 안 남기면 그 연결이 영영 동기화되지 않는 것을 아무도 모른다.

행은 지우지 않았다. 조직 3 의 데이터이고 지울 이유가 없다.

### D·E

D 는 `AsyncRequestNotUsableException` 전용 핸들러를 더해 DEBUG 로 내렸다. `void` 를
돌려준다 — 응답이 이미 끊겼으므로 본문을 쓰려 하면 같은 예외가 다시 난다.

E 는 `show-sql` 을 지웠다. **N+1 로 보이던 반복은 아직 못 봤다** — `show-sql` 은
표준출력이라 `backend.log` 에 남지 않았다. A 를 고친 뒤 앱을 다시 띄워야 판단된다.
