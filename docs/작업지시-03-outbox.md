- 작성일: 2026-08-24
- 작성: Cowork 세션 (문서·설계 담당)
- 대상: Claude Code (구현 담당)
- 범위: P1 5~6주차
- 관련: 계획서 4.4 / 12.2 / 15.1, ADR 0002, ADR 0005, ADR 0007

이 문서는 무엇을 만들지와 어떤 제약을 지킬지를 적는다. 어떻게 짤지는 적지 않는다.
5절의 결정은 착수 전에 받았다. 다시 열지 말 것.

## 1. 지금 상태

P1 4주차까지 `main` 에 병합·푸시돼 있다. 테스트 77건 통과. 로컬 브랜치는 `main` 하나다.

### 재고 원장은 보강할 것이 없다

계획서 12.2 는 5주차를 "재고 원장과 방어 계층 구현"으로 잡았지만 그건 P0~P1 초반에
이미 끝났다. `InventoryLedger`, `InventoryService`, `InventoryLedgerWriter`,
`LedgerAction` 은 4주차에도 손대지 않았고 그럴 필요가 없었다. 4주차의 예약 상태 머신이
이 계층 위에 그대로 얹혔다는 것이 그 증거다.

**없는 일을 만들지 말 것.** 계획서에 5주차 항목이 있다는 이유로 원장을 다시 손대면
동시성 테스트가 검증하고 있는 것을 흔들게 된다. 5~6주차에 남은 것은 Outbox 와
감사 로그 둘뿐이다.

계획서 12.2 의 6주차 항목 중 동시성 테스트도 이미 통과한 상태다.

### 준비돼 있는 것

- `outbox_event` 테이블. `aggregate_type`, `aggregate_id`, `event_type`, `payload`(JSONB),
  `created_at`, `published_at`, `retry_count`, `last_error`
- `idx_outbox_pending` — `created_at` 부분 인덱스, 조건은 `published_at IS NULL`
- `audit_log` 테이블. `actor_id`, `actor_kind`(USER|SYSTEM|CHANNEL|AI), `entity_type`,
  `entity_id`, `action`, `before_value`, `after_value`(JSONB), `occurred_at`
- `idx_audit_entity` — `(entity_type, entity_id, occurred_at DESC)`
- `shared/outbox` 패키지. 지금은 비어 있다
- `shedlock` 테이블. 인스턴스가 하나뿐이라 아직 쓰지 않는다

## 2. 이번에 만드는 것

### A. 이벤트 기록

계획서 4.4 가 명세다. 도메인 변경과 `outbox_event` 삽입이 **한 트랜잭션에서 커밋된다.**

```
[예약 확정 트랜잭션]
  ├─ reservation      갱신
  ├─ inventory_ledger 갱신
  └─ outbox_event     삽입     ← 같은 트랜잭션
```

트랜잭션 경계 문제가 이 프로젝트에서 세 번째로 나온다. 판별 기준은 같다 —
**바깥이 롤백될 때 이 쓰기가 남아야 하는가, 사라져야 하는가.** 예약이 롤백되면
"예약이 확정됐다"는 이벤트도 사라져야 한다. 따라서 같은 트랜잭션이다.
ADR 0005 의 `REQUIRES_NEW` 를 여기에 가져오지 않는다.

이 패턴이 푸는 문제는 4.4 에 적힌 그대로다. 트랜잭션 안에서 외부를 호출하면 실패해도
롤백되지 않고, 트랜잭션 밖에서 호출하면 이벤트가 유실된다. 둘 다 피하려고 이벤트를
데이터베이스에 먼저 적는다.

기록할 이벤트는 4주차에 만든 예약 전이다. 어떤 전이가 이벤트를 낳는지 정한다.
확정, 취소, 날짜 변경, 체크아웃은 바깥이 알아야 하는 사건이고, 체크인은 아직
소비자가 없다. 없는 소비자를 위해 이벤트를 만들지 않는다.

### B. OutboxRelay

커밋된 이벤트를 꺼내 발행한다. 주기는 1초다(계획서 4.4).

- `published_at IS NULL` 인 것을 `created_at` 오름차순으로 꺼낸다.
  `idx_outbox_pending` 이 이 질의를 위한 인덱스다
- 성공하면 `published_at` 을 채운다
- 실패하면 `retry_count` 를 올리고 `last_error` 에 사유를 남긴다
- 한 번에 꺼낼 건수에 상한을 둔다. HOLD 만료 배치와 같은 이유이고,
  **상한에 닿으면 경고 로그를 남긴다.** 4주차에서 겪은 그대로다

**같은 애그리게이트의 이벤트는 순서대로 발행돼야 한다.** 취소가 확정보다 먼저 나가면
채널 쪽 상태가 뒤집힌다. 지금은 단일 스레드로 `created_at` 순서를 지키면 성립한다.
나중에 병렬로 바꾸면 깨지므로 그 전제를 주석에 남긴다.

**최소 1회 전달이다.** 발행 직후 `published_at` 기록 전에 죽으면 다음 주기에 다시
나간다. 중복은 소비자의 멱등성으로 흡수한다는 것이 4.4 의 전제이며,
예약 수신은 `(channel_code, channel_booking_id)` 유니크 제약이 이미 그 역할을 한다.

인스턴스가 하나뿐이라 `FOR UPDATE SKIP LOCKED` 도 ShedLock 도 지금은 필요 없다.
여러 대가 되면 둘 다 필요해지므로 그 자리를 주석으로 남긴다.

### C. 소비자는 등록만 하고 비워 둔다

계획서 4.4 는 `ChannelSyncWorker`, `OpsWorker`, `MessagingWorker` 를 그린다.
셋 다 각각 P3, P5, P5 다. **지금 만들면 할 일이 없는 워커가 된다.**

이벤트 타입에 소비자를 붙이는 지점만 만들고, 지금은 로그만 남기는 구현 하나를 둔다.
P3 에서 채널 워커를 붙일 때 그 지점에 끼우면 되게 한다.

### D. 감사 로그

계획서 15.1 이 "예약·요금 변경을 주체, 대상, 시각, 변경 전후로 기록"이라고 약속했다.
요금 변경은 P2 라 이번에는 예약이다.

- **주체.** 사용자 요청은 `SecurityContext` 의 `AuthenticatedUser` 에서 가져와
  `actor_kind = USER`, `actor_id` 를 채운다. **배치에는 `SecurityContext` 가 없다.**
  HOLD 만료는 `actor_kind = SYSTEM`, `actor_id` 는 비운다. 컬럼이 nullable 인 이유다.
  P3 의 채널 수신은 `CHANNEL` 이 된다
- **변경 전후.** 전이 전후의 상태와 바뀐 값만 담는다. 엔티티를 통째로 직렬화하면
  무엇이 바뀌었는지가 오히려 안 보인다
- **같은 트랜잭션이다.** 변경이 롤백됐는데 "변경했다"는 기록이 남으면 그 로그는
  거짓말이 된다. A 와 같은 이유다

### E. 테스트

완료 조건은 6절에 있다.

## 3. 이번에 만들지 않는 것

- **재고 원장 손대기.** 1절에 적은 대로 할 일이 없다
- **소비자 워커 세 개.** P3 와 P5 다
- **요금 변경 감사.** 요금 캘린더가 P2 라 대상이 아직 없다
- **모니터링 지표(계획서 14.4).** Grafana 대시보드와 함께 P6 에서 본다
- **ShedLock 과 `SKIP LOCKED`.** 인스턴스가 하나뿐이다. 자리만 주석으로 남긴다
- **역할별 인가(`@PreAuthorize`).** 3~5단계로 미뤄져 있다

## 4. 지켜야 할 제약

- **모듈 경계.** `outbox` 는 `shared` 에 있어 모든 모듈이 참조한다. 반대로 `shared` 가
  `booking` 을 참조하면 안 된다. 이벤트 타입을 문자열이나 `shared` 의 타입으로 다루고
  도메인 타입을 `shared` 로 끌어올리지 않는다
- **원장을 직접 쓰지 않는다.** 재고 변경은 전부 `InventoryService` 를 통한다
- **오류 표현.** `shared/error` 의 `DomainException`, `ApiError`, `GlobalExceptionHandler`
- **`ddl-auto: validate`.** 컬럼을 더하면 V1 과 JDBC 타입 코드까지 맞아야 한다.
  `retry_count` 는 `SMALLINT` 다
- **테스트 포트.** 앱은 15433/`.localdb-test`, API 테스트는 15434/`.localdb-api`
- **주석은 "왜".** 테스트 이름은 한국어 서술형

## 5. 착수 전에 받은 결정

| 항목 | 결정 |
|---|---|
| 1. 개인정보 | 식별자만 담는다. 이름도 넣지 않는다 |
| 2. Outbox 구현 | 직접 구현한다. ADR 0008 로 기록 |
| 3. 재시도 상한 | 상한에 닿으면 조회 대상에서 빼고 경고를 남긴다. 행은 지우지 않는다 |

### 1번을 지키는 방법

`outbox_event.payload` 와 `audit_log.before_value`/`after_value` 는 평문 JSONB 다.
4주차에 게스트 연락처를 AES-256-GCM 으로 암호화했는데(ADR 0007) 이벤트 페이로드에
평문으로 실리면 **암호화를 우회하는 두 번째 경로가 생긴다.** 데이터베이스 덤프 하나로
둘 다 새는데 한쪽만 잠근 셈이 된다.

- 페이로드에는 `guestId` 만 담는다. 소비자가 필요하면 그때 조회해 복호화한다
- 이름도 넣지 않는다. `guest.name` 이 평문이라 새로 새는 것은 없지만, 예외를 하나 두면
  다음 사람이 "이름이 되면 전화번호도 되지 않나"로 넘어간다. 경계는 단순해야 지켜진다
- 감사 로그의 전후 값에는 **어떤 필드가 바뀌었는지만** 남기고 연락처 값 자체를 넣지 않는다.
  값이 필요한 조회는 P5 의 마스킹·조회 기록과 함께 다룬다

### 3번의 구체

`retry_count` 가 상한에 닿은 이벤트는 조회 대상에서 뺀다. **행은 지우지 않는다.**
`last_error` 가 남아 있어야 나중에 사람이 원인을 보고 다시 넣을 수 있다.

상한에 닿는 순간 경고 로그를 남긴다. 매 주기가 아니라 그 한 번이다.
매번 남기면 B 절에서 막으려던 로그 채우기가 그대로 재현된다.

## 6. 완료 조건

1. 예약 확정 트랜잭션이 롤백되면 `outbox_event` 행도 남지 않는지 확인하는 테스트
2. 감사 기록도 같은 성질인지 확인하는 테스트. 변경이 롤백되면 기록도 사라진다
3. Relay 가 미발행 이벤트를 발행하고 `published_at` 을 채우는 테스트
4. 발행이 실패하면 `retry_count` 가 오르고 `last_error` 가 남으며,
   `published_at` 은 비어 있어 다음 주기에 다시 시도되는 테스트
5. 같은 애그리게이트의 이벤트가 `created_at` 순서대로 발행되는 테스트
6. 상한에 닿으면 경고 로그가 나오고, 닿지 않으면 나오지 않는 테스트.
   4주차 `HoldExpiryBatchLimitTest` 와 같은 방식
7. HOLD 만료가 남긴 감사 기록의 `actor_kind` 가 `SYSTEM` 이고 `actor_id` 가 비어 있는 테스트
8. 재시도 상한에 닿은 이벤트가 다음 주기 조회에서 빠지고, 경고는 한 번만 나오는 테스트
9. **이벤트 페이로드와 감사 기록에 연락처가 들어가지 않는지 확인하는 테스트.**
   게스트를 만들고 예약을 확정한 뒤 `outbox_event.payload` 와 `audit_log` 의 전후 값을
   문자열로 훑어 전화번호와 이메일이 나오지 않아야 한다
10. `ModularityTest` 와 `InventoryConcurrencyTest` 가 계속 통과

1번, 2번, 9번을 빠뜨리지 않는다. 이 패턴 전체가 "한 트랜잭션에서 커밋된다"는 전제 위에
서 있고, 그게 깨져도 정상 경로에서는 아무 증상이 없다. 9번도 같다 — 연락처가 페이로드에 실려도
기능은 정상으로 보이고, 드러나는 것은 데이터베이스가 유출된 뒤다.

## 7. 브랜치와 기록

- 새 브랜치를 판다. `feat/outbox-audit` 정도가 맞다
- ADR 0008 로 Outbox 직접 구현을 남긴다. **Spring Modulith 의 이벤트 발행 레지스트리를
  쓰지 않은 이유가 반드시 들어가야 한다.** 같은 패턴을 제공하는 기성 구현을 두고 직접
  만든 것이라 심사에서 나올 질문이다. 최소 1회 전달과 순서 보장의 전제도 함께 적는다
- 페이로드에 식별자만 담는 결정은 ADR 0007 의 결과 절에 이어 적는다. 같은 결정의 연장이다
- 끝나면 CLAUDE.md "현재 상태" 절을 갱신한다. P1 완료 시점이 된다
- P1 이 끝나므로 태그를 남긴다. `p1-complete`
- 이 문서에 없는 판단이 필요해지면 임의로 정하지 말고 물어본다
