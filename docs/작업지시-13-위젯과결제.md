## 2. 이번에 만드는 것

### A. HOLD 생성 이벤트 — 위젯보다 먼저다

**현재 재고 계산에는 `held` 가 들어가는데 HOLD 를 만들 때 이벤트가 안 나간다.**

```
InventoryLedger.available() = totalUnits - bookedUnits - heldUnits
ChannelSyncService 가 채널로 내보내는 값이 바로 이 available() 이다
ReservationWriter.createHold — 감사만 남기고 outbox.record 가 없다
```

그래서 HOLD 를 만들면 **채널에 나갈 재고는 줄었는데 채널은 그 사실을 못 받는다.**
15분 홀드 창 동안 채널이 옛 재고를 들고 있고, 그 사이 채널 예약이 들어오면
`available()` 이 이미 줄어 있어 재고 부족으로 판정된다. 채널 예약은 거절하지 않으므로
`overbooking_conflict` 행이 생긴다.

**지금은 이 구멍이 열리지 않는다. HOLD 를 만드는 REST 경로가 없기 때문이다.**
`BookingService.hold(...)` 는 서비스로만 열려 있고 부르는 것은 테스트뿐이다.
**이번 주의 위젯이 그 첫 경로다.** 그러므로 구멍을 먼저 메우고 위젯을 올린다.

- HOLD 생성 시점에 재고 변경 이벤트를 낸다
- `ChannelSyncService` 의 `INVENTORY_EVENTS` 에 그 타입을 더한다.
  **소비 쪽은 손대지 않아도 된다** — 페이로드 값이 아니라 현재 원장을 다시 읽는 설계다
- 근거를 `ReservationWriter` 주석과 확인 문서에 남긴다. 5절 1번이 그 문구다

### B. 직접예약 위젯

계획서 8.7 이다. 흐름은 날짜·인원 선택 → 가용과 요금 조회 → 게스트 정보 →
HOLD 생성 → 결제 → 확정이다.

- **공개 경로다.** 로그인 없이 열리고, 숙소 하나에 묶인다
- 가용과 요금은 서버가 계산한 값만 보여 준다
- HOLD 는 15분이다. **이 값이 설정값인지 상수인지 확인하고, 상수면 설정으로 뺀다**
- 만료는 `HoldExpiryJob` 이 이미 처리한다. 새로 만들지 않는다

`OwnedResources` 를 거치지 않는 유일한 경로이므로, **숙소 식별자 외에는 아무것도
클라이언트를 믿지 않는다.** 금액, 재고, 요금 모두 서버가 다시 구한다.

### C. 포트원 테스트 결제

계획서 8.7 의 둘째 문단이 명세다.

- 결제창 호출은 클라이언트, **확정은 웹훅으로만 한다**
- 웹훅 수신 시 **서명을 검증**하고, **결제사 API로 금액과 주문번호를 재조회해 대조**한다
- 대조가 맞아야 HOLD → CONFIRMED 로 올린다
- **웹훅이 두 번 와도 예약이 하나여야 한다.** Outbox 와 같은 성질이고 14·15주차에
  두 번 다룬 문제다
- 카드 정보는 저장하지 않는다. `payment` 행에 남는 것은 결제사 식별자와 금액과 상태다

**로컬에서 웹훅을 받으려면 공개 터널이 필요하다.** 인계메모 4절에 절차가 있고,
`staysync.public-base-url` 을 주는 것과 PowerShell 따옴표 함정이 그대로 적용된다.

## 4. 지켜야 할 제약

- **클라이언트가 보낸 금액을 신뢰하지 않는다.** 서버가 재고와 요금 캘린더로 다시
  계산하고, 웹훅에서 결제사 재조회로 한 번 더 대조한다
- **웹훅은 서명 검증 없이 처리하지 않는다.** 계획서 15.2 의 시나리오 10 이 이것이다
- **예외로 흐름을 제어하지 않는다.** 3·12·14주차에 같은 함정에 세 번 빠졌다.
  먼저 조회해 분기한다
- **`@Transactional` 메서드를 같은 클래스에서 부르지 않는다.** 14주차에만 두 번 났다.
  **스케줄러나 웹훅이 부르는 진입점을 테스트가 그대로 부른다**
- **픽스처는 서버가 실제로 보내는 형태로 적는다.** 15주차에 시각 픽스처를 `+09:00` 으로
  적어 둔 탓에 9시간 어긋난 화면이 테스트를 통과했다
- **모듈 경계.** 결제는 `payment`, 예약 전이는 `booking` 이 공개한 인터페이스로 한다
- **`ddl-auto: validate`, V1 수정 금지**
- 주석과 문서는 한국어, 식별자는 영어, 테스트 이름은 한국어 서술형

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. HOLD 생성 이벤트 | 낸다. 위젯보다 먼저 |
| 2. 리포트 지표 | 여덟 중 여섯. 순수익률과 진척도는 뺀다 |
| 3. 위젯 임베드 | 별도 라우트 + iframe 한 줄. 스크립트 로더를 만들지 않는다 |

### 1번의 근거

`ReservationWriter.createHold` 주석은 "확정되지 않은 점유를 바깥이 알 이유가 없다"이다.
그러나 **채널이 알아야 하는 것은 홀드가 아니라 재고가 바뀌었다는 사실이다.**
`ChannelSyncService` 는 페이로드가 아니라 현재 원장을 다시 읽으므로, 이벤트를 내도
채널은 홀드의 존재를 알지 못한다. 숫자만 받는다.

**그리고 지금 코드가 이미 그 원칙의 절반을 어기고 있다.** `RESERVATION_EXPIRED` 는
홀드 만료 이벤트이고 그것이 채널로 나간다. 홀드 생애주기 중 재고가 느는 쪽만 알리고
줄어드는 쪽은 알리지 않는다. **비대칭이 결함이지 새 이벤트가 원칙 위반이 아니다.**
문서에 남길 문구는 "판단을 뒤집었다"가 아니라 **"만료만 내보내던 것을 생성까지 맞췄다"**이다.

`inventory_buffer` 컬럼과 `InventoryLedger.exposedTo()` 로 완화하는 길도 있으나
**구멍을 없애지 못하고 확률만 낮춘다.** 게다가 그 둘은 지금 아무도 쓰지 않는 죽은
코드다. 쓰거나 지우거나는 별건이고 이번 주가 아니다. 열린 항목에 남긴다.

### 2번의 근거

**순수익률은 채널 수수료와 결제 수수료를 뺀 값인데, 그 둘이 실제로 기록되는지가
확실하지 않다.** Mock 도 iCal 도 수수료를 알려 주지 않는다. 데이터가 없는데 계산해
내면 화면에 그럴듯한 숫자가 뜨고 그것이 보고서에 실린다.

**진척도는 전년 동일 시점 대비인데 전년 데이터가 없다.** 이 프로젝트는 8월에
시작했다. 만들 수 없다.

인계메모 6절의 규칙이 그대로 적용된다 — **아직 측정하지 않은 수치를 성과처럼 적지
않는다.** 둘 다 계획서에 남겨 두되 "데이터가 생기면"으로 적고, 왜 못 만들었는지를
확인 문서에 남긴다. **못 만든 것을 만든 것처럼 적지 않는다.**

수수료 데이터가 실제로 있다면 순수익률은 넣어도 된다. **확인한 뒤에 판단하고 근거를
남긴다.**

### 3번의 근거

계획서 8.7 은 "스크립트 한 줄"이라고 적었다. iframe 한 줄도 한 줄이다.

스크립트 로더를 만들면 호스트 페이지의 CSS 격리, 높이 자동 조절, 버전 관리,
CSP 가 따라온다. **위젯이 하는 일보다 로더가 커진다.** iframe 은 격리가 기본이고
한 줄로 끝난다.

축소 순서 1번에 있는 기능이다. 얇게 만들어 동작시키는 편이 낫다.

## 6. 완료 조건

HOLD 이벤트.

1. HOLD 를 만들면 재고 변경 이벤트가 나가는 테스트
2. 그 이벤트로 `PUSH_AVAILABILITY` 연결에 줄어든 재고가 전파되는 테스트
3. **HOLD 생성 → 만료 → 재고 복귀가 채널 값으로 왕복하는 테스트.**
   지금은 만료만 나가므로 이것이 비대칭을 잡는다

위젯.

4. 로그인 없이 공개 경로가 열리는 테스트
5. 가용하지 않은 날짜로는 HOLD 가 만들어지지 않는 테스트
6. **클라이언트가 보낸 금액과 서버 재계산이 다르면 거절하는 테스트**
7. 15분이 지나면 HOLD 가 만료되고 재고가 돌아오는 테스트

결제.

8. **서명이 틀린 웹훅을 거부하는 테스트.** 계획서 15.2 시나리오 10
9. 결제사 재조회 금액이 다르면 확정하지 않는 테스트
10. **같은 웹훅이 두 번 와도 예약이 하나이고 결제 행도 하나인 테스트**
11. 결제 성공 웹훅으로 HOLD → CONFIRMED 가 되고 `RESERVATION_CONFIRMED` 가 나가는 테스트

리포트.

12. 지표 여섯의 산식 테스트. 분모가 0일 때 터지지 않는다
13. 기간·숙소 필터가 동작하는 테스트

전체.

14. **브라우저에서 위젯으로 예약을 만들고 테스트 결제까지 통과시킨다.**
    공개 터널이 필요하다
15. 같은 화면에서 리포트에 그 예약이 반영되는 것을 본다
16. `ModularityTest`, `InventoryConcurrencyTest` 통과
17. `./gradlew test`, `./gradlew build`, `npm run build`, `npm run test` 통과

3번·6번·10번을 빠뜨리지 않는다. 3번은 이번 주에 고치는 비대칭 그 자체이고,
6번과 10번은 **돈이 걸린 자리에서 화면이 정상으로 보이는 결함**이다.

**14번을 미루지 않는다.** 브라우저 확인은 7·9·10·14·15주차에서 매번 결함을 잡았다.
15주차는 자동 테스트 264 + 83건이 전부 통과하는 상태에서 둘이 나왔다.

## 7. 순서와 기록

- `feat/hold-inventory-event` — A
- `feat/booking-widget` — B
- `feat/payment-portone` — C
- `feat/report` — D

**A 를 먼저 병합한다.** B 가 HOLD 를 만드는 첫 경로이므로 A 없이 올리면 구멍이 열린다.

**D 는 A·B·C 와 독립이다.** 시간이 모자라면 D 를 먼저 끝내고 C 를 줄인다 —
계획서 12.4 의 축소 순서가 위젯과 결제를 1번으로 두었기 때문이다. 그 판단을 하게 되면
**무엇을 줄였는지 문서에 남긴다.**

- **순수익률 데이터가 있는지 확인한 결과를 남긴다.** 5절 2번
- **HOLD 창 15분이 설정값인지 확인한 결과를 남긴다.** 상수였으면 설정으로 뺀 것을 적는다
- 끝나면 CLAUDE.md "현재 상태"를 갱신한다
- **끝나면 `origin/main` 에 푸시하고 `p4-complete` 태그를 단다**
- **P4 가 닫히므로 Cowork 세션이 교수 보고서를 쓴다.** 무엇이 들어갔고 무엇을 왜
  줄였는지만 알려 주면 된다
- 이 문서에 없는 판단이 필요해지면 임의로 정하지 말고 물어본다
