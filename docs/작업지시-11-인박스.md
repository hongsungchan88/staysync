## 1. 지금 상태

P3 코드가 끝났다. `p3-complete` 태그가 붙어 있고 `origin/main` 과 동기다.
완료 조건 셋 중 셋째의 발행 등록만 사람 손을 기다린다(확인-04 3절).
**그 확인은 이번 주 작업을 막지 않는다.**

### 성격이 또 바뀐다

P3 까지는 기계와 이야기했다. 채널이 상대였고 검증은 "값이 맞는가"였다.

**P4 는 사람과 이야기한다.** 게스트가 메시지를 보내고 호스트가 답한다. 여기서부터
"틀렸다"가 데이터 불일치가 아니라 **잘못된 메시지가 게스트에게 나가는 것**이다.
보내고 나면 되돌릴 수 없다는 점이 P3 와 다르다.

### 준비돼 있는 것

- `message_thread`, `message` — V1 에 테이블이 있고 엔티티는 없다
- `Capability.MESSAGING` — 6.1 에 정의만 돼 있다. 선언한 어댑터가 없다
- **Mock OTA 시뮬레이터** — 채널 노릇을 한다. 지금은 ARI 와 예약만 다룬다
- `OutboxRelay` 와 소비자 자리 — SSE(9주차), 채널 전파(12주차)에 이어
  **세 번째 입주자가 이번 주다**
- `AdapterContractTest` — 선언과 구현이 맞는지 본다. B 가 여기에 걸린다

## 2. 이번에 만드는 것

### A. 시뮬레이터에 메시징을 더한다

**게스트 메시지를 만들어 낼 곳이 없으면 인박스는 빈 화면이고 자동 발송은 허공에
쏜다.** 5절 1번이 근거다.

시뮬레이터에 최소한으로 더한다.

- 게스트 메시지를 만들어 내는 시나리오 (우리 쪽에서 보면 수신)
- 우리가 보낸 메시지를 받아 저장하고 조회하게 하는 엔드포인트 (발신)
- 악조건은 채널 표면에 이미 걸려 있다. 메시징도 같은 표면이다

**시뮬레이터는 여전히 나쁘게 굴어야 한다.** 같은 메시지를 두 번 보내고, 순서를
뒤집어 보낸다. 막거나 바로잡지 않는다.

### B. MockOtaAdapter 에 MESSAGING

`AdapterType.MOCK` 이 `MESSAGING` 을 선언하고 어댑터가 실제로 구현한다.

**12주차와 13주차에 각각 한 번씩 어긋났던 자리다.** 선언이 좁으면 조용히 건너뛰고,
넓으면 없는 구현을 부른다. `AdapterContractTest` 가 이번에도 본다.

iCal 은 `MESSAGING` 이 없다. 그건 정상이고, 인박스 화면이 그 사실을 보여 줘야 한다.

### C. 메시지 도메인

`message_thread` 와 `message` 엔티티, 저장, 조회.

- 스레드 하나가 예약 하나에 붙는다. 채널과 게스트가 스레드의 신원이다
- **수신 멱등성.** 같은 메시지가 두 번 와도 한 건이다. 채널 쪽 메시지 식별자로
  거른다. 예약 수신의 `(channel_code, channel_booking_id)` 와 같은 방식이다
- 발신은 `sync_job` 을 거친다. **12주차의 재시도·백오프·`DEAD` 를 그대로 쓴다.**
  메시지 발송이 실패했을 때 조용히 사라지면 안 되고, 그 문제는 이미 풀려 있다
- `OwnedResources` 를 거친다. 남의 조직 스레드는 404

**게스트 연락처를 메시지 본문 밖으로 흘리지 않는다.** ADR 0007 의 선이 그대로다.
스레드는 `guestId` 로 게스트를 가리키고, 표시할 때 복호화한다.

### D. 통합 인박스 화면

계획서 8.5 가 명세다. 경로는 8.1 의 `/inbox`, `/inbox/:threadId` 다.

**스레드 목록**
- 채널 표시, 미읽음 여부, 체크인 임박 순 정렬, 필터

**대화 화면**
- 시간순 메시지, 발신자 구분(게스트·호스트·시스템)
- 우측 패널에 해당 예약 요약
- **채널이 `MESSAGING` 을 지원하지 않으면 입력창 대신 그 사실을 표시한다.**
  6.1 이 말하는 `capabilities()` 의 세 번째 사용처다

**첨부 파일은 만들지 않는다**(5절 3번).

### E. 메시지 템플릿

자주 쓰는 답변을 저장하고 변수를 치환한다.

- 게스트 이름, 체크인·체크아웃 날짜, 숙소명 정도면 충분하다
- **치환할 값이 없으면 발송을 막는다.** 빈칸이나 `{{guestName}}` 이 그대로 나간
  메시지는 되돌릴 수 없다. 이번 주 제약의 성격이 여기서 드러난다

### F. 자동 발송 스케줄러

계획서 8.5 의 트리거 넷이다. **경로가 둘로 갈린다.**

| 트리거 | 경로 |
|---|---|
| 예약 확정 | Outbox 이벤트 소비 |
| 체크인 하루 전 / 체크아웃 당일 / 체크아웃 다음 날 | 시간 기반 스케줄러 |

- 규칙은 켜고 끌 수 있다
- **같은 트리거로 같은 예약에 두 번 보내지 않는다.** 발송 이력을 남기고 그걸로
  거른다. 스케줄러가 재기동되거나 이벤트가 중복 전달돼도(Outbox 는 최소 1회 전달이다)
  게스트에게는 한 번만 간다
- **취소된 예약에는 보내지 않는다.** 체크인 하루 전 알림이 취소된 예약에 나가는 것이
  이 기능의 가장 흔한 사고다
- 발송도 C 와 같이 `sync_job` 을 거친다

## 3. 이번에 만들지 않는 것

- **AI 답변 초안.** 계획서 8.5 가 말하지만 9장 AI 기능이고 P5 다
- **첨부 파일.** 5절 3번
- **청소·태스크 자동화(계획서 8.6).** 15주차다
- **리포트, 직접예약 위젯, 결제.** 16주차다
- **Channex 메시징.** 계획서 3.2 의 Could 항목이다
- **게스트 포털(`/g/:token`).** P5 다
- **읽음 처리의 실시간 동기화.** SSE 를 여기에 붙이지 않는다. 새로고침으로 충분하다

## 4. 지켜야 할 제약

- **보낸 메시지는 되돌릴 수 없다.** 발송 경로에 있는 모든 판단이 이 전제 위에 있다.
  중복 발송, 취소된 예약, 치환 실패 셋 다 여기서 나온다
- **모듈 경계.** `messaging` 이 `booking.domain` 을 보지 않는다. 예약 정보는 booking 이
  공개한 인터페이스로 받는다. 방향은 messaging → booking 이다
- **발송은 `sync_job` 을 거친다.** 채널 호출을 직접 하지 않는다. 재시도와 `DEAD` 가
  12주차에 이미 풀려 있다
- **게스트 연락처를 메시지·로그·이벤트에 넣지 않는다.** ADR 0007
- **`OwnedResources` 를 거친다.** 소유가 아니면 404
- **15초 사슬을 건드리지 않는다.** 메시지 발송은 그 사슬 밖이다
- **`ddl-auto: validate`, V1 수정 금지.** 컬럼이 모자라면 V6 를 더한다
- 주석과 문서는 한국어, 식별자는 영어, 테스트 이름은 한국어 서술형

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. 메시지 출처 | 시뮬레이터에 메시징을 더한다. Mock 이 유일한 메시징 채널이다 |
| 2. 발송 경로 | `sync_job` 을 거친다. 새 큐를 만들지 않는다 |
| 3. 첨부 파일 | 만들지 않는다 |

### 1번의 근거

iCal 은 메시징이 없고 Channex 는 Could 항목이다. **실제 게스트 메시지를 만들어 낼
곳이 시뮬레이터뿐이다.**

없이 만들면 인박스는 빈 화면이고, 자동 발송 규칙은 도착하는지 확인할 수 없는 곳으로
쏜다. 11주차에 시뮬레이터를 만든 이유가 그대로 반복된다 — 상대역이 없으면 검증이
성립하지 않는다.

더하는 양은 작다. 엔드포인트 둘과 시나리오 하나다.

### 2번의 근거

메시지 발송은 채널 호출이고, 채널 호출의 실패 처리는 12주차에 이미 풀었다.
재시도, 백오프, `DEAD`, 순서 보장이 전부 `sync_job` 에 있다.

**메시지 전용 큐를 새로 만들면 그 정책을 두 벌 유지하게 된다.** 그리고 두 벌이
갈라지는 순간의 증상은 "어떤 메시지는 재시도되고 어떤 메시지는 사라진다"이다.

`job_type` 을 하나 더하면 된다.

### 3번의 근거

계획서 8.5 가 "첨부 파일을 표시한다"고 적었지만, 첨부는 저장소와 크기 제한과
바이러스 검사와 만료가 따라오는 별개의 일이다. **메시지 본문 하나도 아직 오간 적이
없다.**

시뮬레이터가 만들어 낼 첨부도 지금은 없다. 필요해지면 P6 예비 시간에 본다.

## 6. 완료 조건

수신.

1. 시뮬레이터가 만든 게스트 메시지가 스레드에 나타나는 테스트
2. 같은 메시지가 두 번 와도 한 건인 테스트
3. 남의 조직 스레드를 조회하면 404 가 나오는 테스트

발신.

4. 보낸 메시지가 `sync_job` 을 거쳐 시뮬레이터에 도착하는 테스트
5. 발송이 실패하면 재시도되고, 상한을 넘으면 `DEAD` 로 남는 테스트.
   **행을 지우지 않는다**
6. 채널이 `MESSAGING` 을 지원하지 않으면 발송 작업이 만들어지지 않는 테스트

템플릿.

7. 변수가 치환되는 테스트
8. **치환할 값이 없으면 발송이 막히는 테스트.** `{{guestName}}` 이 그대로 나가면 안 된다

자동 발송.

9. 예약 확정 이벤트로 메시지가 한 번 나가는 테스트
10. **같은 이벤트가 두 번 전달돼도 한 번만 나가는 테스트.** Outbox 는 최소 1회 전달이다
11. **취소된 예약에는 나가지 않는 테스트**
12. 규칙을 끄면 나가지 않는 테스트
13. 시간 기반 트리거 셋이 각각 제 시점에 도는 테스트

화면.

14. 로그인 후 `/inbox` 에서 스레드 목록과 대화가 뜨고, 메시지를 보내면 시뮬레이터에
    도착하는 것을 브라우저에서 확인한다
15. iCal 연결의 스레드에 입력창 대신 미지원 표시가 뜨는지 확인

전체.

16. `AdapterContractTest` 가 `MESSAGING` 선언과 구현의 일치를 확인
17. `ModularityTest`, `InventoryConcurrencyTest` 통과
18. `./gradlew test`, `./gradlew build`, `npm run build`, `npm run test` 통과

8번·10번·11번을 빠뜨리지 않는다. 셋 다 **잘못된 메시지가 게스트에게 나가는** 경우이고,
나간 뒤에는 되돌릴 수 없다. 우리 쪽 로그에는 "성공"으로 남는다.

## 7. 브랜치와 기록

- `feat/messaging-core` — A, B, C, E
- `feat/inbox-ui` — D, F

앞엣것을 먼저 병합한다. 화면과 자동 발송이 도메인을 필요로 한다.

- **시뮬레이터 메시징 확장을 ADR 0011 결과 절에 이어 적는다.** 새 ADR 이 아니라
  같은 결정(상대역이 없으면 검증이 성립하지 않는다)의 두 번째 적용이다
- **메시지 발송을 `sync_job` 에 얹은 것을 ADR 0012 결과 절에 이어 적는다.**
  재시도 정책을 한 벌로 유지한 근거다
- 끝나면 CLAUDE.md "현재 상태"와 "아직 비어 있는 모듈"을 갱신한다. messaging 이 빠진다
- **끝나면 `origin/main` 에 푸시한다**
- 15주차 지시서는 이 결과를 보고 쓴다. 청소·태스크 자동화(계획서 8.6)이고,
  **체크아웃 이벤트가 Outbox 소비자의 네 번째 입주자가 된다**
- 이 문서에 없는 판단이 필요해지면 임의로 정하지 말고 물어본다
