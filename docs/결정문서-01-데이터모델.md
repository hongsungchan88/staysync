## 1. 무엇을 결정하는가

객실을 데이터로 어떻게 표현할 것인가. 두 가지 안이 있고, 이 선택이 재고 테이블, 예약 테이블, 채널 매핑, 캘린더 화면에 모두 파급된다. 나중에 바꾸는 비용은 8절에서 따로 다룬다.

---

## 2. 결정의 전제 — 대상 사용자가 바뀌었다

최초 계획서는 대상을 "소규모 숙박 사업자"로 뭉뚱그렸고, 데이터 모델은 사실상 소형 호텔을 상정해 설계했다. 확인된 대상은 그보다 좁다.

> 부업으로 자신이 소유했거나 임대한 공간의 일부를 숙소로 제공해 수익을 얻는 사람

이 정의에서 파생되는 사실이 세 가지다.

**하나. 판매 단위가 곧 물리 공간이다.** 오피스텔 한 채를 통째로 빌려주는 호스트에게 "객실타입"과 "객실"은 같은 것을 두 번 부르는 이름이다. 호텔에서는 "디럭스 더블"이라는 상품과 "1204호"라는 실체가 분리되지만, 개인 호스트에게는 그 공간 자체가 상품이다.

**둘. 채널 구성이 다르다.** 개인 호스트는 에어비앤비 비중이 압도적이고 그다음이 네이버 예약과 부킹닷컴이다. 야놀자와 여기어때는 모텔·펜션 중심이라 비중이 낮다. 그리고 에어비앤비는 리스팅 하나가 판매 단위 하나이며, iCal URL도 리스팅마다 하나씩 발급된다.

**셋. 운영 규모가 작다.** 관리 대상이 1~5개 수준이다. 호실 배정, 객실 상태 전환, 층별 관리 같은 호텔 운영 기능은 쓸 일이 없다.

## 3. 두 가지 안

### 안 A — 3계층 (현행 계획서)

```
Property (숙소)
  └── RoomType (객실타입)        예: "디럭스 더블"
        ├── Room (개별 객실)      예: 201호, 202호, 203호
        └── RatePlan (요금제)     예: "기본", "조식포함"
```

`reservation`은 `room_type_id`로 들어오고, 나중에 `room_id`를 배정한다(배방).

### 안 B — 2계층 (제안)

```
Property (숙소)
  └── Unit (판매 단위)           예: "성수동 오피스텔", "본가 게스트룸"
        └── RatePlan (요금제)     예: "기본"
```

`Unit.total_units`가 수량을 담는다. 대부분 1이고, 도미토리처럼 같은 조건의 자리를 여러 개 파는 경우에만 2 이상이 된다. 물리 호실을 개별 식별하지 않으므로 `Room` 테이블과 배방 로직이 사라진다.

`RatePlan`은 두 안 모두 유지한다. 부킹닷컴과 Channex가 요금제 축을 필수로 요구하기 때문이며, 이 부분은 7절에서 다룬다.

---

## 4. 실제 시나리오로 비교

대상 사용자가 실제로 마주할 네 가지 경우를 두 모델로 표현해 봤다.

### 시나리오 1 — 오피스텔 한 채를 통째로 대여 (가장 흔한 경우)

| | 안 A | 안 B |
|---|---|---|
| Property | 성수동 오피스텔 | 성수동 오피스텔 |
| 중간 계층 | RoomType "전체" (total_units=1) | Unit "전체" (total_units=1) |
| 하위 | Room "본실" | (없음) |
| RatePlan | 기본 | 기본 |
| **행 수** | **4** | **3** |

안 A의 RoomType과 Room은 항상 1:1이며 이름도 사실상 같다. 화면에서 호스트는 의미 없는 계층을 한 번 더 클릭해 들어가야 한다.

### 시나리오 2 — 자기 집의 방 두 개를 각각 별도 판매

| | 안 A | 안 B |
|---|---|---|
| Property | 우리집 | 우리집 |
| 중간 계층 | RoomType "작은방", RoomType "큰방" | Unit "작은방", Unit "큰방" |
| 하위 | Room "작은방", Room "큰방" | (없음) |
| **행 수** | **5** | **3** |

방마다 크기·요금·에어비앤비 리스팅이 다르므로 RoomType을 나눌 수밖에 없고, 그러면 Room은 또다시 1:1이 된다.

### 시나리오 3 — 게스트하우스 4인 도미토리 (침대 단위 판매)

| | 안 A | 안 B |
|---|---|---|
| 중간 계층 | RoomType "4인 도미토리" (total_units=4) | Unit "4인 도미토리" (total_units=4) |
| 하위 | Room "1번 침대"~"4번 침대" | (없음) |
| **행 수** | **6** | **2** |

안 A는 침대를 개별 식별할 수 있지만, 실무에서 침대 번호는 현장에서 배정하지 소프트웨어가 미리 정하지 않는다. 안 B는 "4자리 중 3자리 판매됨"까지만 관리한다.

### 시나리오 4 — 소형 호텔 디럭스 5실 (확장 시나리오)

| | 안 A | 안 B |
|---|---|---|
| 중간 계층 | RoomType "디럭스" (total_units=5) | Unit "디럭스" (total_units=5) |
| 하위 | Room 201~205호 | (없음) |
| 배방 | 가능 | **불가능** |
| **행 수** | **7** | **2** |

여기서만 안 A가 실질적으로 우월하다. 다만 이 시나리오는 이번 프로젝트의 대상이 아니다.

## 5. 항목별 비교

| 항목 | 안 A (3계층) | 안 B (2계층) |
|---|---|---|
| 테이블 수 | 4 (RoomType, Room, RatePlan, InventoryLedger) | 3 (Unit, RatePlan, InventoryLedger) |
| 관리 화면 | 객실타입 목록, 객실 목록, 요금제 | 판매 단위 목록, 요금제 |
| 예약 생성 시 절차 | 타입 선택 → 재고 확인 → (나중에) 호실 배정 | 단위 선택 → 재고 확인 |
| 객실 상태 관리 | Room에 상태 컬럼, 상태 머신 별도 | Unit에 상태 컬럼 |
| 캘린더 행 구성 | 타입 행 + 호실 행 2단 트리 | 단위 행 1단 |
| 에어비앤비 매핑 | 리스팅 ↔ RoomType (Room은 매핑 대상 없음) | 리스팅 ↔ Unit (1:1) |
| 부킹닷컴/Channex 매핑 | room_type + rate_plan | Unit + rate_plan (동일하게 가능) |
| 호텔 확장 | 즉시 가능 | 마이그레이션 필요 |
| 물리 호실 식별 | 가능 | 불가능 |

## 6. 개발 시간 차이

안 B로 갈 때 사라지는 작업을 항목별로 추산했다.

| 사라지는 작업 | 안 A 소요 | 안 B 소요 |
|---|---|---|
| Room 엔티티·리포지토리·CRUD API | 4시간 | 0 |
| 객실 목록 화면 | 3시간 | 0 |
| 배방 UI (캘린더에서 호실로 드래그) | 8시간 | 0 |
| 객실 상태 머신 (사용중/청소필요/청소완료/점검) | 4시간 | 2시간 (Unit에 직접) |
| `reservation.room_id`, `reservation_night.room_id` 처리 | 2시간 | 0 |
| 위 항목들의 테스트 | 4시간 | 1시간 |
| **합계** | **25시간** | **3시간** |

**약 22시간이 확보된다.** 전체 460시간의 약 5%이며, 계획서 기준으로는 AI 요금 추천 엔진 하나를 통째로 만들 수 있는 분량이다. 또는 P3(채널 동기화)의 버퍼로 돌릴 수 있다. R1(채널 동기화 지연)이 가장 높은 위험으로 잡혀 있으므로 후자가 나을 수 있다.

---

## 7. RatePlan을 남기는 이유

Unit까지 줄였으니 RatePlan도 없애면 어떤가 하는 질문이 가능하다. 없애면 안 된다.

에어비앤비만 보면 요금제 개념이 약해서 필요 없어 보인다. 그러나 부킹닷컴과 Channex는 ARI 전송의 최소 단위가 `rate_plan_id`다. 계획서 6.3절의 요청 형식을 보면 `property_id`와 `rate_plan_id`가 함께 필수다.

```json
{ "property_id": "...", "rate_plan_id": "...", "date_from": "...", "rate": 250000 }
```

RatePlan을 없애면 채널 어댑터마다 가짜 요금제 ID를 만들어 끼워 넣는 우회 코드가 생긴다. 그 편이 계층 하나를 유지하는 것보다 지저분하다. 대신 **숙소 생성 시 "기본" 요금제를 자동 생성**해 호스트가 요금제라는 개념을 의식하지 않게 하고, 필요할 때만 추가하도록 한다. 이러면 사용성은 2계층처럼 느껴지고 채널 호환성은 유지된다.

---

## 8. 되돌리는 비용

안 B를 택했다가 나중에 호텔 지원이 필요해지면 어떻게 되는가.

필요한 작업은 세 가지다. `Room` 테이블 추가, `reservation`과 `reservation_night`에 `room_id` 컬럼 추가, 기존 Unit마다 `total_units` 개수만큼 Room을 생성하는 데이터 마이그레이션 한 번. 배방 UI는 새로 만들어야 한다.

기존 데이터를 잃지 않으며, 재고 계산 로직은 손댈 필요가 없다. `InventoryLedger`가 이미 수량 기반이기 때문이다. 작업량은 하루 남짓으로 추산된다.

즉 **되돌리기 어려운 결정이 아니다.** 반대로 안 A를 택했다가 안 B로 가는 것은 데이터 손실(호실 정보)이 따르므로 오히려 더 번거롭다.

## 9. 권장안과 근거

**안 B (2계층)를 권장한다.**

근거를 정리하면 다음과 같다.

대상 사용자의 네 시나리오 중 셋에서 안 A의 Room 계층이 1:1 껍데기이거나 실무에서 쓰지 않는 정보다. 안 A가 우월한 유일한 경우(소형 호텔)는 이번 프로젝트 범위 밖이며, 계획서 3.2절에서 명시적으로 제외한 영역이다.

에어비앤비가 주 채널인데, 에어비앤비의 리스팅 개념은 안 B의 Unit과 1:1로 대응한다. 안 A에서는 Room에 대응하는 채널 개념이 없어 매핑 테이블에 빈 축이 생긴다.

약 22시간이 확보되고, 이를 가장 위험도가 높은 채널 동기화 단계의 버퍼로 돌릴 수 있다.

되돌리는 비용이 하루 수준으로 낮다.

## 10. 안 B 채택 시 변경되는 것

승인하시면 다음을 반영한다.

**계획서 수정 범위**

- 5.1 애그리게이트 구조 — `RoomType`/`Room`을 `Unit`으로 통합, 배방 관련 서술 삭제
- 5.2 ERD — `ROOM` 개체 삭제
- 5.3 DDL — `room` 테이블 삭제, `room_type` → `unit`으로 개명, `reservation_night.room_id` 삭제
- 8.3 예약 관리 — 배방 항목 삭제
- 8.2 통합 캘린더 — 2단 트리를 1단 목록으로
- 2장 — 대상 사용자를 개인 부업 호스트로 명시하고 채널 우선순위 조정 (에어비앤비 > 네이버 예약 > 부킹닷컴)
- 12장 — 확보된 22시간을 P3 버퍼로 재배치

**새 DDL 초안 (안 B 기준)**

```sql
CREATE TABLE unit (
    id              BIGSERIAL PRIMARY KEY,
    property_id     BIGINT NOT NULL REFERENCES property(id),
    name            VARCHAR(200) NOT NULL,   -- "성수동 오피스텔", "작은방"
    unit_kind       VARCHAR(20) NOT NULL,    -- ENTIRE_PLACE | PRIVATE_ROOM | SHARED_ROOM
    occupancy_std   SMALLINT NOT NULL DEFAULT 2,
    occupancy_max   SMALLINT NOT NULL DEFAULT 4,
    total_units     SMALLINT NOT NULL DEFAULT 1,
    housekeeping    VARCHAR(20) NOT NULL DEFAULT 'CLEAN',  -- CLEAN | DIRTY | INSPECTING
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- inventory_ledger, rate_plan, rate_calendar는 room_type_id → unit_id 로만 변경
-- room 테이블 삭제
-- reservation.room_type_id → unit_id, reservation_night.room_id 삭제
```

`unit_kind`는 에어비앤비의 숙소 유형 구분(공간 전체/개인실/다인실)과 대응시킨 필드로, 나중에 채널 매핑과 요금 추천의 입력으로 쓸 수 있다.
