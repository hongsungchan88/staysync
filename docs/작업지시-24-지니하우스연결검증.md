## 2. 확정된 사실 — 21 의 9절과 다른 곳

1. **채널 설정 이름이 문서와 다르다.** 콘솔의 Booking Total Type 선택지는 `Payout Amount`·`Amount including Commission` 둘뿐이다.
   21 9절·확인-12 6.2 의 "Total Paid Amount" 대신 **`Amount including Commission`** 으로 만들었다(취지 — 게스트 결제액 = 리스팅 가격, 호스트 전용
   수수료 15.4%). Min Stay Type `Arrival`, 알림 메일 끔. 21 9절 3번과 확인-12 6.2 의 그 이름을 고친다(4절 A)
2. **호스트 계정에 리스팅이 8개다.** 고양 숙소 여러 개, 서울 메종드서촌 여러 개, **고양에 이름이 같은 "지니하우스"가 하나 더 있다.**
   **대상은 서울 홍대 지니하우스 — 리스팅 id `1450311972082292442`.** 고양 "지니하우스/호수공원…"(`1050365893618564330`)은 다른 숙소다.
   다른 리스팅은 매핑하지 않는다. 잘못 매핑하면 그 숙소 요금·달력이 우리 값으로 덮인다
3. **요금 기준값(호스트 답, 10-04·07)** — 평일 170,000 · 금·토 221,000 · 최소 숙박 1. StaySync 는 10-06 에 이미 맞췄다(2026-10-04~2027-10-03,
   금·토 104일 221,000, 나머지 261일 170,000, 최소 숙박 전부 1). 할인 넷 — 주간 7박+ 3%, 월간 28박+ 5%, **막바지 10% = 체크인 당일~1일 전**,
   **조기예약 5% = 체크인 3개월 전**. 날짜 지정 맞춤 프로모션은 연결 동안 못 만들 수 있다고 호스트에게 알렸다
4. **연결 링크는 짧게만 유효하다**(10-14 실측 — 몇 시간 뒤 `invalid_state`). 다시 승인이 필요해지면 "호스트 대기 → 만들자마자 전달 → 즉시 승인"
5. 승인 직후 호스트 화면에 "Connection is unsuccessful"이 떴지만 Channex 쪽은 성공했다(Host ID 채워짐, 채널 생성). 같은 화면이 다시 떠도 콘솔로 판단한다

## 8. 진행 상황

### 8.1 사전 확인 (10-19 전)

**A — 고쳤다(10-14).** 작업지시-21 9절 3번과 확인-12 6.2 의 "Booking Amount = `Total Paid Amount`" → **`Booking Total Type =
Amount including Commission`**, 근거 한 줄(콘솔 선택지가 `Payout Amount`·`Amount including Commission` 둘뿐, 2절 1번)을 붙였다.

**B — 중복이 생긴다. 막으려면 코드를 바꿔야 해서 여기서 멈췄다(사용자 결정 대기).**

코드: 넘겨받기는 `ChannelBookingWriter.replaceable` 이 명령의 `supersedes` 로만 고르고, `ChannelBookingPoller.supersedes` 는 **Channex
연결일 때만** 같은 숙소 iCal 코드를 채운다. iCal 연결의 명령은 늘 빈 집합이다. 그래서 10-21 에 iCal 매핑을 되살리면 iCal 이벤트는
`(AIRBNB_ICAL, UID)` 로 찾고 — 그 예약은 이제 `(AIRBNB, Channex id)` 라 — 못 찾고, 넘겨받을 후보도 없어 **새 예약을 만든다.**

로컬 재현(1회 테스트, 커밋하지 않음 — `ChannelBookingIntake.ingest` 를 폴러가 만드는 명령 그대로 불렀다. 판매 단위 수량 1):

| 단계 | 결과 |
|---|---|
| 연결 전 iCal 예약 A(11-01→03) | 예약 1 `AIRBNB_ICAL` |
| 연결 — Channex 가 A 를 넘겨받음, 연결 기간에 새 예약 B(11-10→13)가 Channex 로 | 1 → `AIRBNB:chx-A`(UPDATED, id 그대로), 2 `AIRBNB:chx-B`(CREATED) |
| 해제 — iCal 매핑 되살림, 피드에 A·B 둘 다 | **둘 다 `CONFLICT`** — 새 예약 3 `AIRBNB_ICAL:uid-A`, 4 `AIRBNB_ICAL:uid-B` |
| 그 뒤 상태 | 예약 4건(실제 2건), **OPEN 충돌 5**(박마다), 원장 다섯 밤 모두 `booked 2 · overbooked 1` |
| 그 뒤 에어비앤비에서 A 가 취소돼 피드에서 빠지면 | iCal 의 `cancelMissing` 은 `AIRBNB_ICAL` 만 본다 — 3 만 취소되고 **1(`AIRBNB`)은 영영 남아 그 밤을 잡는다** |

넘겨받힌 예약과 연결 기간에 Channex 로 새로 들어온 예약이 **같은 모양으로** 겹친다. 그리고 Channex 매핑을 푼 뒤에는 `AIRBNB` 예약의
변경·취소를 알려 줄 길이 없다 — 겹침을 사람이 충돌 화면에서 정리해도, 남긴 쪽이 `AIRBNB` 면 이후 취소가 반영되지 않는다.

**길 셋 — 사용자가 정한다.**
1. **반대 방향 넘겨받기(코드 변경).** iCal 연결의 명령에도 같은 숙소 Channex 연결의 코드(`AIRBNB`)를 `supersedes` 로 실어, 같은 판매
   단위·같은 체크인·체크아웃의 살아 있는 `AIRBNB` 예약을 iCal 이 넘겨받는다(id·원장 그대로, 감사 `CHANNEL_TAKEOVER`). 지금 코드의 거울이고
   크기는 `supersedes()` 의 조건 하나 + 테스트(위 재현이 그대로 테스트가 된다). 넘겨받으면 금액·이름·인원은 남기는가(iCal 은 안 준다) —
   함께 정할 것. **10-19 전에 배포해야 한다**(10-21 해제에 쓰인다). 날짜가 하루라도 다르면 지금처럼 새 예약 + 충돌
2. **해제 뒤 iCal 을 되살리지 않는다(코드 변경 없음).** Channex 예약은 그대로 남지만, 10-21 뒤 에어비앤비 새 예약·변경·취소가 하나도
   들어오지 않는다. 업체 실데이터라 며칠도 위험하다 — 권하지 않는다
3. **되살리고 사람이 정리한다(코드 변경 없음).** 해제 직후 충돌 화면에서 겹친 쌍마다 `AIRBNB` 쪽을 취소. 예약 id 가 바뀌고 금액·이름·인원이
   사라지며, 취소가 자동 발송·채널 전파를 타는지 건마다 확인해야 한다. 연결 기간이 사흘이라 건수는 적겠지만 업체 데이터를 사람이 손으로
   지운다
