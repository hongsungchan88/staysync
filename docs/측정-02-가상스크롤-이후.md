## 서버 왕복 (Python 클라이언트, 브라우저 없음)

10회 반복.

| 구분 | 7주차 | 8주차 |
|---|---|---|
| 첫 호출 (cold) | 422 ms | 321 ms |
| 이후 중앙값 | **342 ms** | **270 ms** |
| 최소 / 최대 | 296 / 485 ms | 259 / 317 ms |

**서버는 손대지 않았다.** 이번 주 변경은 전부 프론트엔드다. 차이는 측정 잡음과 기동 이후
경과 시간(JIT, 커넥션 풀, 페이지 캐시)에서 온 것으로 본다. 개선으로 적지 않는다.

## DOM 규모 — 이번 주의 핵심 수치

| 항목 | 7주차 | 8주차 | 비 |
|---|---|---|---|
| DOM 노드 | 11,229개 | **1,234개** | 0.11배 |
| 그려진 셀 | 2,700개 (전부) | **208개** (13행 × 16칸) | 0.08배 |
| 그려진 행 | 30개 (전부) | 13개 | |
| 그리드 크기 | 6,156 × 1,798 px | 6,156 × 2,038 px | |
| **강제 레이아웃 1회** | **130 ms** | **1.2 ms** | 0.009배 |

그리드 **너비가 그대로**인 것이 가로 가상 스크롤이 제대로 붙었다는 신호다. 스크롤 범위는
90일치 그대로 두고 그 안에서 보이는 16칸만 그린다. 칸을 좁히는 모드를 만들지 않기로 한
결정(5절 2번)이 여기에 기대고 있다.

**높이가 1,798 → 2,038 로 늘었다.** 줄어든 것이 아니라 늘어난 것이 맞다. D 의 쌓기 규칙
때문에 겹치는 예약이 있는 판매 단위의 행이 7주차의 고정 58px 보다 높아졌다. 노드 수와
레이아웃 비용은 이것과 무관하게 줄었다.

강제 레이아웃 130 ms → 1.2 ms 가 가장 직접적인 결과다. 스크롤할 때마다 재현되던 비용이다.

## 브라우저 사이클 — 이 환경에서는 잴 수 없다

7주차의 **996 ms** 는 요청부터 2,700셀이 **화면에 보일 때까지**, 즉 페인트를 포함한 값이다.

측정에 쓴 내장 브라우저 페인은 **요청이 있을 때만 페인트한다.** 화면 갱신 스크린샷은
정상으로 나오는데, 그 직후에 `requestAnimationFrame` 을 걸어도 한 프레임도 돌지 않는다.
일시적인 상태가 아니라 이 페인의 동작 방식이다. 페인트 시각을 관찰할 수단이 rAF 와
페인트 타이밍 항목뿐인데 둘 다 렌더링 단계가 돌아야 나오므로, **페인트를 포함한 사이클은
이 환경에서 잴 수 없다.** 실제 Chrome(Claude in Chrome)도 연결돼 있지 않아 대안이 없었다.

그래서 잰 것은 **요청 시작 → 새 범위의 셀이 DOM 에 들어올 때까지**이고 페인트가 빠져 있다.

| 구분 | 값 (3회) |
|---|---|
| 요청 → DOM 갱신 (**페인트 제외**) | 388 / 385 / 381 ms |
| 그중 캘린더 API | 268 / 271 / 281 ms |
| 나머지 (파싱 + React 렌더) | 약 110 ms |

**이 385 ms 를 996 ms 와 나란히 놓고 "2.6배 빨라졌다"고 적지 않는다.** 재는 것이 다르다.
7주차에 프론트엔드 몫으로 적은 726 ms 안에는 레이아웃과 페인트가 들어 있고 여기에는 없다.

같은 조건의 사이클 값은 **눈에 보이는 브라우저에서 개발자 도구 Performance 로 다시 재야
한다.** 그전까지 완료 조건 11 의 "브라우저 사이클" 칸은 비어 있는 것으로 둔다.

말할 수 있는 것은 API 몫이 270 → 271 ms 로 사실상 같다는 것이고, 이는 7주차와 같은 데이터·
같은 서버에서 쟀다는 확인이 된다.

## 실제 브라우저에서 확인한 동작

수치와 별개로, 단위 테스트가 흉내로 대신하던 자리를 실제 화면과 **실제 서버**에 대고
확인했다. jsdom 은 배치를 하지 않고 `fetch` 도 가짜라, 이 확인이 없으면 테스트가 통과하는데
화면은 동작하지 않는 상태를 놓친다. 실제로 `min-w-0` 결함이 그렇게 숨어 있었다.

| 완료 조건 | 확인한 것 |
|---|---|
| 2 | 세로 700px·가로 1800px 로 동시에 민 상태에서 날짜 헤더가 컨테이너 상단에, 좌측 목록이 좌단에 붙어 있음(둘 다 오프셋 0). 셋 다 계산된 `position` 이 `sticky` |
| 4 | 셀을 가로질러 끌어 6개 판매 단위 × 9일 = 54칸이 선택되고, 우측 패널에 기간·대상 단위 6개·54칸이 그대로 표시됨 |
| 6 | **막대를 재고 없는 날짜로 끌었을 때 화면이 먼저 옮겨졌다가(낙관적) 서버 거절 뒤 원위치로 돌아오고 이유가 뜸.** 아래에 따로 적는다 |
| 7 | 키보드로 3박 예약을 이틀 옮긴 뒤 서버 조회 — 예약 날짜와 **박별 스냅샷 행이 함께** 새 날짜로 다시 쓰여 있음 |
| 9 | 방향키 한 번에 정확히 66px(한 칸)씩 이동하고, 놓으면 서버에 반영됨 |

### 완료 조건 6 — 실제 거절

총 1실인 판매 단위에 다른 예약이 09-11~09-14 를 차지한 상태에서, 09-06~09-09 예약을
그 위로 끌었다.

1. 놓는 즉시 막대가 **09-11~09-14 로 옮겨져 보였다**(낙관적 업데이트)
2. 서버가 409 로 거절했다 — `InventoryService` 가 `chk_no_oversell` 까지 가기 전에 막는다
3. 막대가 **09-06~09-09 로 되돌아왔다**
4. 화면에 이유가 떴다 — "2026-09-11 에 판매 가능한 재고가 없습니다. (사유: SOLD_OUT)"

이번 주에서 가장 중요한 항목이고, 흉내가 아니라 실제 원장에 대고 확인했다.

확인에 쓴 막는 예약은 취소했고 옮긴 예약도 원래 날짜로 되돌려, 데이터셋을 7주차와 같은
30객실 · 예약 90건으로 복원했다.

### 자동화로는 확인하지 못한 것

키보드로 **화면 밖까지 멀리** 옮기는 경우(20회 이상 연속 방향키)는 확인하지 못했다.
자동화 도구가 보내는 키 이벤트에 `event.code` 가 비어 있어 dnd-kit 이 반응하지 않고,
합성 이벤트로 대신하면 도구 호출 사이에서 드래그가 취소된다(dnd-kit 이
`visibilitychange`·`resize` 에 드래그를 취소한다). 짧은 이동은 확인됐다.
**멀리 옮길 때 화면이 따라 스크롤되는지는 열려 있는 문제로 둔다.**

## 판단

**노드 수는 확실히 줄었다.** 11,229 → 1,234 이고 완료 조건 1 을 만족한다. 강제 레이아웃도
130 ms → 1.2 ms 로 함께 줄었으므로, 노드 수만 줄고 시간이 그대로인 경우는 아니다.

**전체 사이클이 얼마나 줄었는지는 아직 모른다.** 페인트를 포함한 값을 못 쟀기 때문이고,
못 쟀다는 사실을 성과로 바꿔 적지 않는다. 완료 조건 11 은 여기까지가 닫힌 것이고
사이클 칸은 열려 있다.

측정 중에 **가로 가상 스크롤이 통째로 죽어 있는 것을 발견했다.** 처음 잰 값은 노드 5,864개에
셀 1,080개(90칸 전부)였다. `main` 이 flex 항목인데 `min-width: 0` 이 없어 안쪽 내용
5,940px 만큼 늘어났고, 그러면 스크롤 컨테이너의 `offsetWidth` 가 곧 전체 너비가 돼
"보이는 구간"이 전부가 된다. 세로가 멀쩡했던 것은 `min-h-0` 이 이미 있었기 때문이다.
**단위 테스트로는 잡히지 않는 종류다** — 테스트는 컨테이너 크기를 직접 지정해 흉내 내므로
실제 배치가 만드는 이 문제를 재현하지 못한다. 재측정이 잡아낸 유일한 결함이다.
