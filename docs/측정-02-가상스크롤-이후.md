그리드 **너비가 그대로**인 것이 가로 가상 스크롤이 제대로 붙었다는 신호다. 스크롤 범위는

레이아웃 비용은 이것과 무관하게 줄었다.

강제 레이아웃 130 ms → 1.2 ms 가 가장 직접적인 결과다. 스크롤할 때마다 재현되던 비용이다.

## 브라우저 사이클

내장 브라우저 페인으로는 잴 수 없었다. 그 페인은 **요청이 있을 때만 페인트한다.**
화면 갱신 스크린샷은 정상으로 나오는데 그 직후 `requestAnimationFrame` 을 걸어도 한
프레임도 돌지 않는다. 일시적인 상태가 아니라 그 페인의 동작 방식이다. 페인트 시각을
관찰할 수단이 rAF 와 페인트 타이밍 항목뿐인데 둘 다 렌더링 단계가 돌아야 나온다.

그래서 잰 것은 **요청 시작 → 새 범위의 셀이 DOM 에 들어올 때까지**였고 페인트가 빠져
있었다(388 / 385 / 381 ms). 이 값을 996 ms 와 나란히 놓지 않았다. 재는 것이 다르다.

**2026-09-04, 실제 Chrome 에서 다시 쟀다.** 페인트를 포함한 값이 나왔다.

| 구간 | 7주차 | 8주차 | 비 |
|---|---|---|---|
| **브라우저 사이클** | **996 ms** | **408 ms** | 0.41배 |
| ├ 캘린더 API | 270 ms (27%) | 297 ms (73%) | |
| └ 파싱 + 렌더 + 레이아웃 + 페인트 | 726 ms (73%) | **111 ms** (27%) | 0.15배 |
| 클릭 → 첫 반응 페인트 | — | 14 ms | |

3회 측정값은 420 / 408 / 402 ms, 중앙값 408 ms. API 는 5회 중앙값 297 ms
(227 ~ 341, 259 ~ 273 KB).

**비율이 뒤집혔다.** 7주차에 "병목은 서버가 아니라 DOM 크기"라고 적었던 것이 해소됐고,
이제 시간의 73%가 서버 왕복이다. 더 줄이려면 서버 쪽(응답 크기, 캐시)을 봐야 하지만
계획서 8.2 목표 1초 대비 408 ms 라 여유가 충분하다. **지금 건드리지 않는다.**

`클릭 → 첫 반응 페인트 14 ms` 는 사이클과 다른 지표다. 클릭 직후 데이터가 오기 전
리렌더까지의 시간이고, 조작이 즉각 반응한다는 것을 보여 준다. 사이클 대신 쓰지 않는다.

### 두 환경이 비교 가능한가

7주차 996 ms 는 내장 페인에서, 8주차 408 ms 는 실제 Chrome 에서 쟀다. **엄밀히 같은
환경이 아니다.** 다만 두 가지가 비교 가능하다는 근거가 된다.

- **API 몫이 270 → 297 ms 로 사실상 같다.** 서버를 손대지 않았으니 그래야 맞다
- **DOM 노드 수가 1,234개(내장 페인)와 1,310개(실제 Chrome)로 맞는다.**
  차이 76개는 스크롤 위치 차이다

두 환경의 서버 왕복과 렌더 결과가 같으므로, 사이클 차이를 환경 차이로 돌리기 어렵다.
그래도 **환경이 달랐다는 사실은 지운 것이 아니라 여기 적어 둔다.**

측정 구간에도 차이가 있다. 7주차는 **요청 시작** 기준이고 8주차는 **클릭** 기준이라,
408 ms 쪽이 오히려 몇 ms 더 긴 구간을 담고 있다. 개선을 과장하는 방향의 오차는 아니다.

## 실제 브라우저에서 확인한 동작

확인했다. jsdom 은 배치를 하지 않고 `fetch` 도 가짜라, 이 확인이 없으면 테스트가 통과하는데
화면은 동작하지 않는 상태를 놓친다. 실제로 `min-w-0` 결함이 그렇게 숨어 있었다.

### 자동화로는 확인하지 못한 것

키보드로 **화면 밖까지 멀리** 옮기는 경우(20회 이상 연속 방향키)는 확인하지 못했다.
자동화 도구가 보내는 키 이벤트에 `event.code` 가 비어 있어 dnd-kit 이 반응하지 않고,
합성 이벤트로 대신하면 도구 호출 사이에서 드래그가 취소된다(dnd-kit 이
`visibilitychange`·`resize` 에 드래그를 취소한다). 짧은 이동은 확인됐다.
**멀리 옮길 때 화면이 따라 스크롤되는지는 열려 있는 문제로 둔다.**

## 판단

**노드 수는 확실히 줄었다.** 11,229 → 1,234 이고 완료 조건 1 을 만족한다. 강제 레이아웃도
130 ms → 1.2 ms 로 함께 줄었으므로, 노드 수만 줄고 시간이 그대로인 경우는 아니다.

**전체 사이클도 줄었다. 996 → 408 ms.** 실제 Chrome 에서 페인트를 포함해 쟀고,
계획서 8.2 의 목표 1초 안에 여유 있게 들어온다. 7주차의 996 ms 는 목표를 4 ms 차이로
겨우 통과한 값이었다. **완료 조건 11 이 닫혔다.**

줄어든 588 ms 는 거의 전부 프론트엔드 몫이다(726 → 111 ms). 서버는 손대지 않았고
API 몫은 270 → 297 ms 로 같다. 가상 스크롤이 한 일이 수치로 분리돼 보인다.

측정 중에 **가로 가상 스크롤이 통째로 죽어 있는 것을 발견했다.** 처음 잰 값은 노드 5,864개에
셀 1,080개(90칸 전부)였다. `main` 이 flex 항목인데 `min-width: 0` 이 없어 안쪽 내용
5,940px 만큼 늘어났고, 그러면 스크롤 컨테이너의 `offsetWidth` 가 곧 전체 너비가 돼
"보이는 구간"이 전부가 된다. 세로가 멀쩡했던 것은 `min-h-0` 이 이미 있었기 때문이다.
**단위 테스트로는 잡히지 않는 종류다** — 테스트는 컨테이너 크기를 직접 지정해 흉내 내므로
실제 배치가 만드는 이 문제를 재현하지 못한다. 재측정이 잡아낸 유일한 결함이다.

### 사이클 측정

개발자 도구 Performance 패널은 쓰지 않는다. 녹화 구간 전체의 카테고리별 합계를 보여 줄
뿐이라 클릭 한 번의 구간을 읽어내기 번거롭고, 범위를 손으로 좁혀야 한다.
**콘솔에 아래를 붙여넣고 "다음" 을 세 번 누르는 편이 정확하고 빠르다.**

```js
(() => {
  let t0 = 0, waiting = false;
  const mo = new MutationObserver(() => {
    if (!waiting) return;
    waiting = false; mo.disconnect();
    requestAnimationFrame(() => requestAnimationFrame(() =>
      console.log('cycle', Math.round(performance.now() - t0), 'ms')));
  });
  addEventListener('click', () => { t0 = performance.now(); }, { capture: true });
  const orig = window.fetch;
  window.fetch = async (...a) => {
    const r = await orig(...a);
    if (String(a[0]).includes('calendar')) {
      waiting = true;
      mo.observe(document.body, { childList: true, subtree: true });
    }
    return r;
  };
})();
```

클릭 시점부터 재서, 캘린더 응답이 온 뒤 화면이 바뀌고 페인트가 끝난 순간에 찍는다.
`fetch` 를 덮어쓰므로 측정이 끝나면 새로고침해 원상복구한다.

**응답을 기다리지 않고 첫 DOM 변경에서 끊으면 13~15 ms 가 나온다.** 그건 데이터가 오기
전 리렌더까지의 시간이지 사이클이 아니다. 위 코드가 `fetch` 를 거치는 이유다.

DOM 노드 수와 강제 레이아웃은 콘솔에서 바로 잴 수 있다.

```js
document.getElementsByTagName('*').length
// 강제 레이아웃 1회
const inner = document.querySelector('[data-testid="calendar-grid"] > div');
inner.style.paddingBottom = '1px';
const t = performance.now(); void document.body.offsetHeight; performance.now() - t;
```
