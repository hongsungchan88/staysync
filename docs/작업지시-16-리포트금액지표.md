# 작업지시 16. 리포트 금액 지표 — 금액을 모르는 예약을 0원으로 세지 않는다

- 작성일: 2026-09-17
- 작성: Cowork 세션 (문서·설계 담당)
- 대상: Claude Code (구현 담당)
- 범위: CMS·PMS 완성 단계의 첫 주차. 작다
- 관련: 검토-01(3절 7번, 7절), 인계메모 5절, 작업지시-13(리포트), ADR 없음

이 문서는 무엇을 만들지와 어떤 제약을 지킬지를 적는다. 어떻게 짤지는 적지 않는다.
5절의 결정은 사용자가 정했다(09-17). 다시 열지 말 것.

새 세션이 이 문서로 시작한다면 CLAUDE.md 를 먼저 읽고 이 문서를 읽으면 된다.

## 1. 지금 상태와 왜 이 일이 먼저인가

`https://staysync.kr` 리포트(2026-09-01 ~ 2027-09-30, 업체 실데이터)가 이렇게 나온다.

| | 값 |
|---|---|
| 판매 / 판매 가능 | 253 / 1,185 객실박, 점유율 21.3% |
| 객실 매출 | **2,000원** |
| ADR | **8원** |
| RevPAR | **2원** |
| 채널 믹스 | DIRECT 1건 2,000원 **100%** · AIRBNB_ICAL 53건 0원 0% |

**원인.** iCal 에는 금액이 없다. `IcalAdapter` 가 `totalAmount` 에 `BigDecimal.ZERO` 를
넣고(검토-01 3절 7번), `ChannelBookingCommand` 도 `null` 을 0 으로 바꾼다. 그래서 에어비앤비
예약 253박 중 251박이 **0원짜리 박**으로 판매 객실박에는 들어가고, 결제 확인용 2,000원이
그 박 수로 나뉜다.

**0원과 "모른다"가 같은 값으로 저장되고 있다.** 이것이 본체다. 리포트 화면은 그 결과일 뿐이다.

**먼저 하는 이유.**

- **교수 보고서가 "1차 심사 전에 고치겠다"고 적었다.** 심사자가 리포트에서 가장 먼저 볼 숫자다
- **Channex 가 와도 풀리지 않는다.** Channex 예약은 금액을 준다. 그러나 iCal 로 받는
  예약(에어비앤비 iCal, 곧 붙일 아고다·위홈)은 앞으로도 금액이 없다
- 작다. Channex 어댑터(작업지시-17) 앞에 끝낸다

## 2. 이번에 만드는 것

### A. "금액 미상"을 저장한다

- **금액을 모르는 채널 예약은 0 이 아니라 "미상"으로 남긴다.** 5절 1번
- **이미 들어와 있는 iCal 예약도 미상으로 바로잡는다.** 배포 DB 의 53건(취소 포함 54건)이다
- 금액을 아는 경로(수기 예약, 위젯, Mock, 앞으로의 Channex)는 그대로다

### B. 리포트가 미상을 따로 센다

- 기간 안에 **금액 미상 박이 하나라도 있으면 ADR·RevPAR 를 계산하지 않는다.** 5절 2번
- 응답에 **금액 미상 건수(예약 수와 박 수)** 를 싣는다
- 객실 매출은 **금액이 확인된 것의 합**으로 남기되, 미상이 있으면 그 사실을 함께 싣는다
- 채널 믹스 — 미상 예약이 있는 채널의 매출은 "미상"이다. **미상이 하나라도 있으면
  매출 비중을 계산하지 않는다**(지금처럼 DIRECT 100% 가 뜨면 거짓이다)
- 점유율·판매 객실박·리드타임·취소율은 그대로다. 금액과 무관하다

### C. 화면

- ADR·RevPAR 칸에 숫자 대신 **"금액 미상 N건 — 계산하지 않음"** 같은 문구
- 객실 매출 칸은 **"확인된 금액"** 임을 밝힌다
- 채널 믹스의 미상 매출·비중 표시
- **0 과 미상을 화면에서도 구분한다.** 예약이 없어 0 인 기간(분모 0)과 미상인 기간이 같은
  모양이면 안 된다. `ReportMetrics` 주석이 "값이 없다와 0이다를 구분해 보여 주는 것은 화면의
  몫"이라고 적어 둔 그 자리다

## 3. 이번에 만들지 않는 것

- **요금표 금액으로 채우기.** 5절 1번
- **금액 있는 예약만으로 ADR 을 따로 구하는 표시.** 사용자가 고르지 않은 안이다
- **추정 RevPAR.** 같은 이유
- 순수익률·진척도. 작업지시-13 에서 뺀 그대로다
- 통화. 원화만 다룬다(검토-01 3절 8번)

## 4. 지켜야 할 제약

- **`total_amount` 를 읽는 곳을 먼저 전부 훑는다.** 결제(금액 대조), 위젯, 인박스 템플릿,
  예약 패널, 재고·충돌 로직 어디든 미상을 만나면 어떻게 되는지 본다. **호출자를 다 훑고 원인
  자리에서 한 번 고친다** — 리포트만 고치고 닫지 않는다(인계메모 6절 "절반만 고치고 닫은 결함")
- **`RevPAR = ADR × 점유율` 항등식 테스트를 지우지 않는다.** 금액이 전부 확인된 경우에 그대로
  성립해야 한다. 미상이 있는 경우는 "둘 다 계산하지 않음"으로 따로 박는다
- **미상 예약의 픽스처는 실제 iCal 수신 경로로 만든다.** 수기 예약을 UPDATE 로 바꿔 흉내 내지
  않는다 — 17주차 `ReportTest` 가 그렇게 해서 `reservation_night` 결함을 못 봤다
- **집계는 booking 이 한다.** analytics 가 예약 테이블을 SQL 로 읽지 않는다.
  `BookingStatistics` 에 미상 합계를 더하는 방식으로 간다. 비율 계산과 "계산하지 않음" 판단은
  analytics 한 곳에 둔다
- **배포 DB 를 고치는 일은 마이그레이션으로 한다.** 손으로 SQL 을 치지 않는다. 적용 뒤
  `flyway_schema_history` 와 행 수를 확인-09 방식으로 본다
- **재기동 뒤 첫 iCal 폴링이 미상을 0 으로 되돌리지 않는지 본다.** 폴링은 `applyValues` 로
  금액을 다시 쓴다(검토-01 3절 9번)
- 그대로 가는 것 — 예외로 흐름을 제어하지 않는다, 자기 호출 금지, `JdbcTemplate` 없음,
  `ChannelRoundTripTest` 병렬 금지, 주석·문서 한국어

### 1번의 근거

**받지 않은 금액을 숫자로 적지 않는다.** 이 프로젝트가 순수익률을 만들지 않은 이유와 같다 —
데이터가 없는데 계산하면 그럴듯한 숫자가 뜨고 그것이 보고서에 실린다.

**표현 방식(NULL 로 둘지, 별도 표시를 둘지)은 Claude Code 가 4절 첫 항목을 훑은 뒤 정하고
8절에 적는다.** 다만 **"0원이면 미상으로 본다"는 규칙은 쓰지 않는다** — 무료 숙박이나
0원 조정이 생기면 조용히 틀린다. 어느 경로에서 왔는지(금액을 주는 채널인지)로 정한다.

### 2번의 근거

사용자가 세 안 중에서 골랐다.

| 안 | 내용 | 고르지 않은 이유 |
|---|---|---|
| **미상이면 표시 안 함** | 채택 | 변경이 가장 작고 거짓 숫자가 없다 |
| 금액 있는 예약만으로 계산 | ADR 을 확인분으로만 | RevPAR 는 여전히 작게 나오고 항등식이 조건부가 된다 |
| 추정치로 채움 | 확인분 ADR 을 전체 박에 적용 | 받지 않은 금액을 숫자로 보인다 |

**대가.** 지금 업체 데이터는 에어비앤비 iCal 이 대부분이라 **ADR·RevPAR 칸이 당분간 비어
보인다.** 직접예약만 있는 기간(예: 지니하우스 2027-05)에는 숫자가 뜬다. Channex 로 받는
예약은 금액이 있으므로 그쪽으로 옮겨 가면 칸이 찬다.

## 6. 완료 조건

1. **iCal 로 수신한 예약이 금액 미상으로 저장되는 테스트** — 실제 수신 경로로
2. **기존 iCal 예약이 마이그레이션으로 미상이 되고, 다른 예약의 금액은 그대로인 테스트**
3. **미상 박이 있는 기간은 ADR·RevPAR 가 "계산하지 않음"이고 미상 건수가 실리는 테스트**
4. **미상이 없는 기간은 지금과 같은 값이고 항등식이 성립하는 테스트**(기존 테스트 유지)
5. **예약이 없는 기간(분모 0)과 미상 기간이 응답에서 구분되는 테스트**
6. 채널 믹스 — 미상 채널의 매출이 미상이고, 미상이 있으면 비중을 계산하지 않는 테스트
7. **재수신(다음 폴링)이 미상을 0 으로 되돌리지 않는 테스트**
8. `total_amount` 를 읽는 곳 목록과 각 자리의 처리를 8절에 적는다
9. 결제·위젯 경로가 그대로 도는 테스트(금액 대조가 미상을 만나지 않는다)
10. `./gradlew build`, `npm run build`, `npm run test`, `ModularityTest` 통과
11. **배포하고 브라우저로 본다.** `staysync.kr` 리포트 — 2026-09-01~2027-09-30 에서 ADR·RevPAR
    가 미상 문구, 미상 53건 안팎, 점유율 21.3% 그대로. 지니하우스 2027-05 에서 ADR 1,000.
    **Cowork 이 사용자 로그인 뒤 확인한다**
12. `flyway_schema_history` 에 새 마이그레이션 `success = t`, 적용 전후 예약 행 수가 같다

**1·2·7·11 을 빠뜨리지 않는다.** 1은 경로를 우회한 픽스처가 결함을 가린 자리, 2는 이미
틀린 채 저장된 실데이터, 7은 고친 값을 다음 폴링이 되돌리는 자리, 11은 남이 보는 화면이다.

### 8.2 고른 미상 표현 — `NULL`

`reservation.total_amount` 와 `reservation_night.price` 를 nullable 로 풀고 **NULL = 모른다**.

- 별도 플래그 컬럼을 두면 두 값이 어긋날 수 있다(금액 5,000 에 플래그 "미상"). NULL 은 한 자리다
- `sum()` 이 NULL 을 건너뛰므로 "확인된 금액의 합"이 질의 그대로다
- `net_amount` 생성 컬럼도 NULL 이 된다 — 모르는 금액에서 수수료를 뺀 값도 모르는 것이 맞다
- "0 원이면 미상" 규칙은 쓰지 않는다. 어댑터가 정한다 — iCal 은 항상 `null`, Mock·Channex 는 채널이 준 값
- 기존 행의 판정도 경로다: `channel_connection.adapter_type = 'ICAL'` 인 연결의 채널 코드로 들어온 예약(V9)

### 8.3 마이그레이션 V9 (`V9__unknown_amount.sql`)

`reservation.total_amount` DROP NOT NULL·DEFAULT, `reservation_night.price` DROP NOT NULL·DEFAULT.
