- 작성일: 2026-10-07

- 대상: Claude Code (구현 담당)
- 범위: CMS·PMS 사용성. 1차 심사(10월 말) 전에 배포한다. 작업지시-21 9절(지니하우스 검증 10-19~21)과 독립
- 관련: 인계메모 5절(금·토 221,000원 반영), 작업지시-20(업체가 직접 써 보는 자리), ADR 0005(리프레시 토큰 묶음)

## 1. 왜 필요한가

10-06 에 사용자가 배포 환경에서 지니하우스 금·토 요금을 1년 치(2026-10-04~2027-10-03, 104칸) 221,000원으로 바꿨다.
캘린더는 30일씩 보이고 일괄 편집은 **화면에 보이는 칸을 드래그로 고른 범위**에만 걸리므로, 같은 조작을 13번 되풀이했다.

서버 `POST /api/properties/{id}/calendar/bulk-edit` 는 `from`·`to` 를 받고 365일 범위도 받는다(Cowork 이 `dryRun` 으로 확인 —
104칸, 바뀌는 것 price 하나). **제약은 화면에만 있다.**

1차 심사는 업체가 사이트를 직접 써 보는 자리다(작업지시-20 1절). 요금을 시즌 단위로 고치는 것은 숙소 운영자가 가장 먼저
해 보는 조작이고, 같은 자리에서 걸릴 가능성이 높다.

**비밀번호를 바꿀 길이 없다.** 배포 번들의 인증 경로는 `login`·`signup`·`refresh`·`logout` 넷뿐이다(Cowork 이 번들에서 확인).
업체 계정(`review@staysync.kr`)의 비밀번호가 길고 복잡해 사용자가 바꾸고 싶어 하는데, 지금은 서버 DB 를 손으로 고치는 길뿐이다.
별도 계정은 답이 아니다 — 가입하면 새 조직이 생겨 업체 데이터가 안 보인다(초대 기능 없음). 판매를 생각하면 원래 있어야 하는
기본 기능이고, 심사자도 찾을 수 있다.

## 2. 이번에 만드는 것

### A. 패널의 기간을 고칠 수 있게

"요금·제약 편집" 패널(`selection-panel`)의 기간(`selection-range`, 지금은 글자)을 **시작일·종료일 입력 두 칸**으로 바꾼다.

- 처음 값은 지금처럼 드래그로 고른 범위
- 사람이 고치면 그 값으로 미리보기·적용한다. **화면에 보이는 30일 밖도 된다**
- 판매 단위는 지금처럼 드래그로 고른 행 그대로
- 시작일 > 종료일, 빈 칸 등은 미리보기·적용 버튼을 막고 이유를 한 줄로 보인다
- 날짜 입력은 브라우저 기본 날짜 입력으로 충분하다(새 의존성 없이)

### B. 미리보기 문구에 기간을 넣는다

지금 미리보기는 "판매 단위 N개 × …" 모양이다. **어느 기간에 몇 칸이 바뀌는지**가 한 줄에 보여야 한다 — 화면 밖 날짜를 바꾸는
것이라 눈으로 확인할 길이 이 문구뿐이다. 예: `2026-10-04 ~ 2027-10-03 · 판매 단위 1개 · 104칸 · 요금`.

### C. 서버 상한 확인 (만들지 않고 확인만)

- `bulk-edit` 의 기간 상한이 있는지, 있으면 얼마인지. **1년(366일)이 한 번에 되어야 한다.** 상한이 그보다 작으면 366 으로
  올린다. 상한이 없으면 화면에서 366일로 막는다(실수로 몇 년을 바꾸지 않게)
- **요금 행이 없는 날짜**에 적용하면 어떻게 되는지 — 지니하우스는 2027-10-03 까지만 행이 있다. 행을 만드는지, 건너뛰는지,
  오류인지 8절에 적는다. 바꾸지는 않는다(다음 해 요금을 넣는 방법을 정할 때 쓴다)

### D. 비밀번호 변경

로그인한 사용자가 자기 비밀번호를 바꾼다.

- 입력: 현재 비밀번호, 새 비밀번호(확인 입력 포함). **새 비밀번호 규칙은 가입과 같다**(길이 10~100, 작업지시-19) — 같은 검사를 쓴다
- **현재 비밀번호가 틀리면 로그인 실패와 같은 제한에 센다**(`LoginAttemptLimiter`, 이메일 기준). 안 그러면 이 경로가 무차별 대입 구멍이 된다
- **바꾸면 그 계정의 다른 로그인은 전부 끊고, 바꾼 로그인은 유지한다** — 리프레시 토큰 묶음(V11 `family_id`, ADR 0005) 단위로.
  업체 계정은 심사자가 같이 쓰므로 바꾸는 순간 다른 사람은 다시 로그인해야 한다. 흔한 방식이고 그대로 간다
- 감사 행 하나(`PASSWORD_CHANGED`, 비밀번호 값·해시는 남기지 않는다)
- 화면: 상단 로그아웃 옆에 `비밀번호 변경`. 작은 화면 하나로 충분하다. 성공·실패 문구는 담백하게, 틀린 칸을 알려 준다

## 3. 이번에 만들지 않는 것

- 드래그 선택 방식 자체(그대로 둔다)
- 판매 단위 고르는 입력(드래그 행 그대로)
- 요금 행 자동 연장
- 미리보기를 거쳐야만 적용되게 하는 강제(지금 흐름 그대로)
- **비밀번호 찾기(이메일 재설정)** — 메일 발송 경로가 없다. 판매 단계(순서 10)
- 조직 초대·역할별 권한(작업지시-19 5절 3번 그대로)

## 4. 지켜야 할 제약

- **배포 환경의 업체 데이터(`1차 심사` 조직)를 바꾸지 않는다.** 확인은 로컬에서
- 일괄 편집 API 의 요청 모양은 그대로(`from`·`to`·`weekdays`·`priceMode`…). 화면만 바뀌는 것이 기본이다. C 에서 상한을 바꾸는 경우만 서버
- 비밀번호·해시를 로그·감사·응답·문서·커밋에 남기지 않는다. **배포 환경에서 비밀번호를 바꾸는 것은 사용자가 한다** — Claude Code·Cowork 은
  배포 환경 비밀번호를 입력하지 않는다
- 마이그레이션이 생기면(감사 종류 등) 배포 전 덤프와 되돌림 방법을 8절에 적는다
- 프론트가 바뀌므로 **번들 해시가 달라진다.** 배포 뒤 개발 PC·서버·https 셋이 같은지 본다
- 브라우저 모달(`confirm`·`alert`)을 쓰지 않는다. 문구는 담백하게(인계메모 7절)

## 5. 착수 전에 정한 것

1. **지금 한다(사용자, 10-07).** 원래 "업체 피드백 뒤"(순서 9)로 미뤘던 것을 심사 전으로 당겼다
2. 기간 입력은 패널 안에 둔다. 캘린더 표시 범위(30일)는 바꾸지 않는다
3. **비밀번호 변경을 같이 넣는다(사용자, 10-07).** 별도 테스트 계정·DB 직접 수정 대신. 바꾸면 다른 로그인을 끊는다

## 6. 완료 조건

1. 패널에 시작일·종료일 입력이 있고, 드래그 범위가 처음 값으로 들어간다
2. **로컬에서 30일 밖까지 기간을 늘려 미리보기 → 적용 → 되읽기**가 맞다 — 예: 1년, 금·토만, 고정값. 칸 수가 요일 수와 같다
3. 미리보기 문구에 기간·칸 수·바뀌는 항목이 한 줄로 보인다
4. 잘못된 기간(시작 > 종료, 빈 칸, 366일 초과)은 버튼이 막히고 이유가 보인다
5. 2절 C 의 결과(상한, 행 없는 날짜의 동작)가 8절에 있다
6. 프론트 테스트에 기간 입력 경로가 하나 있다(드래그 범위 → 고친 기간이 요청 `from`·`to` 로 나가는지)
7. 비밀번호 변경 테스트 — 틀린 현재 비밀번호(실패, 제한에 셈), 규칙에 안 맞는 새 비밀번호, 확인 불일치, 성공(새 비밀번호로 로그인 됨,
   옛 비밀번호 안 됨, **다른 로그인 묶음 401, 바꾼 로그인은 계속 200**), 감사 행 1
8. 백엔드·시뮬레이터·프론트 테스트가 전체 실행에서 통과한다
9. 배포 — 배포 전후 예약·원장 행 수 같음, 번들 해시 셋 일치. **화면 확인은 Cowork 이 업체 계정에서 패널을 열어 미리보기까지만**
   한다(적용은 누르지 않는다). 비밀번호 변경 화면이 뜨는지까지만 보고, **실제 변경은 사용자가 한다**
