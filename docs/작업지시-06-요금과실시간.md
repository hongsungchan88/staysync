## 1. 지금 상태

P2 8주차까지 `main` 에 병합돼 있다. 가상 스크롤, 기간 선택, 막대 드래그 이동,
막대 쌓기 규칙까지 동작한다. 프론트 32건 + 백엔드 112건 통과.

### 이번 주가 P2 를 닫는다

계획서 12.2 의 P2 완료 조건은 이것이다.

> 브라우저에서 수기 예약을 만들면 캘린더에 즉시 표시되고
> 30일 요금을 한 번에 변경할 수 있는 상태

"즉시 표시"가 C 의 SSE 이고 "한 번에 변경"이 A 의 일괄 편집이다. 6절의 완료 조건은
전부 이 한 문장을 쪼갠 것이다.

이 시점에 지도교수 중간 점검을 요청하고 계획서 진척 현황과 발표자료를 갱신한다.
그건 Cowork 세션이 한다.

### 준비돼 있는 것

- `rate_calendar` — pricing 이 **읽기만** 한다. 7주차에 조회용으로 최소 구현했다.
  이번에 쓰기가 붙는다
- `inventory_ledger.stop_sell` — 컬럼은 있고 바꾸는 경로가 없다
- `outbox_event` 와 `OutboxRelay` — 1초 주기로 발행한다. 소비자는 로그만 남기는
  구현 하나가 자리를 잡고 있다(작업지시-03 C절). **C 의 SSE 가 그 자리에 들어간다**
- `booking.calendar` — 7주차의 조립부. A 도 여기에 둔다(5절 1번)

### 아직 없는 것

- 요금 규칙을 저장하는 테이블. V1 에 없다. 5절 2번을 볼 것
- 채널 전파. P3 다. 요금을 바꿔도 아직 나갈 곳이 없다
- `clean-on-start` 는 꺼져 있다. **V1 을 수정하지 않는다.** 스키마를 바꿔야 하면
  V3 를 더한다

## 2. 이번에 만드는 것

### A. 요금·제약 일괄 편집

계획서 8.4 의 편집 패널이 명세다. 8주차의 기간 선택이 무엇을 고를지까지 왔고
여기서 적용이 붙는다.

받는 것은 여섯 가지다.

| 항목 | 값 |
|---|---|
| 적용 대상 | 판매 단위 여럿 |
| 기간 | 시작일 ~ 종료일 |
| 요일 필터 | 선택한 요일에만 적용 |
| 요금 | 고정값, 또는 기존 대비 ±% |
| 최소 숙박 / 체크인 금지 | 값 |
| 판매 중지 | 참·거짓 |

**미리보기는 같은 코드 경로여야 한다.** 8.4 패널에 [미리보기]와 [적용]이 따로
있는데, 별도 엔드포인트로 만들면 둘이 어긋난 채로 아무도 모르게 지나간다.
같은 요청에 `dryRun` 을 하나 두고 마지막에 커밋하느냐 마느냐만 다르게 한다.
미리보기는 바뀔 셀 수와 요약을 돌려준다.

**요금·최소숙박은 `rate_calendar`, 판매중지는 `inventory_ledger` 다.** 출처가 다르고
모듈도 다르다. 이 둘을 한 트랜잭션에 묶는다 — [적용] 한 번이 절반만 반영되면
화면과 원장이 어긋난다. 5~6주차와 같은 판별 기준이다.

**`stop_sell` 을 원장에 직접 쓰지 않는다.** 재고 변경은 전부 `InventoryService` 를
거친다(CLAUDE.md). 판매중지는 재고를 깎지는 않지만 원장 행을 건드리는 일이고,
락 순서 규칙(날짜 오름차순)도 그대로 적용된다.

**변경을 감사 로그에 남긴다.** 계획서 15.1 이 "예약·요금 변경을 주체, 대상, 시각,
변경 전후로 기록"이라고 했고 5~6주차에는 예약만 했다. 이번에 요금이 붙는다.
셀 하나마다 한 줄씩 남기면 30일 × 10단위가 300줄이다. **일괄 편집 한 번을 한 줄로
남기고 범위와 바뀐 항목을 적는다.**

### B. 요금 규칙 엔진

계획서 8.4 의 `RateRule` 이 명세다. 다섯 가지 규칙(시즌, 요일, 숙박일수, 임박,
점유율)에 우선순위가 있고, 기준가에 순서대로 적용한 뒤 하한·상한으로 자르고
100원 단위로 반올림한다.

**계산만 만든다. 저장도 자동 적용도 만들지 않는다**(5절 2번).

A 의 "기존 대비 +20%"가 이 엔진을 호출하는 첫 사용처다. 규칙 하나짜리 호출인 셈이다.

순수 계산이라 데이터베이스도 화면도 없이 테스트할 수 있다. **이 프로젝트에서 가장
테스트하기 쉬운 부분이므로 경계값을 아끼지 말 것** — 우선순위가 같은 규칙 둘,
하한과 상한이 뒤집힌 입력, 반올림 경계, 곱셈 순서에 따라 결과가 달라지는 경우.

### C. SSE 실시간 갱신

계획서 8.2 가 "다른 채널의 예약이 유입되면 SSE 로 즉시 반영"이라고 했다.
채널 수신은 P3 라 지금 이벤트를 낳는 것은 수기 예약, 예약 변경, A 의 일괄 편집이다.

**Outbox 소비자 자리에 끼운다.** 작업지시-03 C절이 "이벤트 타입에 소비자를 붙이는
지점만 만들고 지금은 로그만 남기는 구현 하나를 둔다"고 했고, 그 자리의 첫 입주자다.
P3 의 채널 워커가 그 옆에 들어간다.

- **구독을 `orgId` 로 좁힌다.** 이것을 빠뜨리면 남의 조직 예약이 화면에 뜬다.
  조회 API 는 `OwnedResources` 로 막았는데 실시간 경로에 구멍이 남는 모양이다
- 재연결과 끊김을 다룬다. 탭을 오래 두면 끊긴다
- **놓친 이벤트를 SSE 로 복구하려 하지 않는다.** 재연결하면 캘린더를 다시 조회한다.
  이벤트 재생을 만들면 Outbox 의 최소 1회 전달과 순서 보장을 화면 쪽에도 다시
  구현하게 된다
- 단일 인스턴스 전제다. 여러 대가 되면 인스턴스마다 구독자가 갈라진다.
  ADR 0008 이 같은 전제 위에 있고, 그 자리를 주석으로 남긴다

### D. 재검증

A 와 C 가 붙으면 7주차·8주차의 조회 경로가 다시 흔들릴 수 있다.

- 일괄 편집 후 캘린더를 다시 조회했을 때 값이 바뀌어 있는지
- SSE 갱신이 가상 스크롤과 부딪히지 않는지. 보이지 않는 행의 갱신이 스크롤 위치를
  건드리면 안 된다
- 성능 재측정은 하지 않는다. 8주차 측정이 기준이고 이번 주는 렌더링 경로를 바꾸지 않는다

## 3. 이번에 만들지 않는 것

- **요금 규칙의 저장과 자동 적용.** 5절 2번. AI 요금 추천(P5)이 첫 실사용처다
- **채널 전파.** P3 다. `ChannelAdapter.capabilities()` 로 `PUSH_RATE` 를 거르는 것도
  그때다. 지금 요금을 바꿔도 나갈 곳이 없다
- **충돌 해소.** `conflict` 는 여전히 항상 `false` 다
- **WebSocket.** 단방향이면 충분하다는 것이 계획서 11.2 의 판단이다
- **Redis 월 단위 캐시.** `local` 프로파일에 Redis 가 없다. 측정해서 필요하다고
  나온 뒤에 본다
- **역할별 인가.** 여전히 3~5단계다
- **React Router.** 화면이 여전히 둘이다. P3 채널 화면(10주차)에서 넣는다

## 4. 지켜야 할 제약

- **모듈 경계.** A 는 `booking.calendar` 에 있고 pricing 이 공개한 쓰기 인터페이스를
  쓴다. `pricing.domain` 을 보지 않는다. **pricing 이 booking 을 참조하면 순환이다**
- **재고 변경은 전부 `InventoryService`.** `stop_sell` 도 포함이다
- **락은 날짜 오름차순.** `StayPeriod.nightDates()` 의 정렬을 우회하지 않는다
- **한 트랜잭션.** 요금과 판매중지, 그리고 감사 기록이 함께 성공하거나 함께 실패한다
- **`OwnedResources` 를 거친다.** A 의 엔드포인트도 C 의 구독도 마찬가지다
- **`ddl-auto: validate`, V1 수정 금지.** 스키마를 바꾸면 V3 를 더한다
- **감사 기록에 연락처를 넣지 않는다.** ADR 0007 의 선이 그대로다
- TypeScript `strict`, 주석과 문서는 한국어, 식별자는 영어, 테스트 이름은 한국어 서술형

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. 일괄 편집의 위치 | `booking.calendar`. pricing 이 아니다 |
| 2. 요금 규칙 엔진 | 계산만. 저장도 자동 적용도 만들지 않는다 |
| 3. 미리보기 | 별도 엔드포인트가 아니라 같은 요청의 `dryRun` |

### 1번의 근거

일괄 편집은 요금(pricing)과 판매중지(booking)를 한 번에 바꾼다. pricing 에 두면
pricing → booking 참조가 생기고, 7주차의 조립부가 만든 booking → pricing 과 맞물려
**순환이 된다.** `ModularityTest` 가 잡을 것이고 잡는 게 맞다.

`booking.calendar` 에 두면 방향이 기존과 같다. 이름이 "요금 편집"이라 어색해 보이지만
바꾸는 대상은 캘린더 셀이고 셀은 조립부가 이미 다루는 것이다. 7주차에 조립부를
`booking.calendar` 에 둔 것과 같은 논리이며, 그때의 근거("세 소스 중 둘이 booking
것이고 booking → property·pricing 이 허용된 방향")가 여기서도 성립한다.

### 2번의 근거

규칙을 저장하려면 테이블과 마이그레이션과 CRUD 화면이 따라온다. 그런데 **저장된
규칙을 실제로 읽는 곳이 아직 없다.** 자동 적용은 계획서 8.6 의 운영 자동화와 P5 의
AI 요금 추천에 있고, 지금 만들면 아무도 안 쓰는 테이블이 하나 생긴다.
5~6주차에 소비자 워커 셋을 만들지 않은 것과 같은 판단이다.

계산 엔진은 지금 만든다. A 의 "기존 대비 ±%"가 실사용처이고, P5 가 이 위에 얹힌다.
`sealed interface` 로 규칙 종류를 닫아 두면 P5 에서 규칙을 더할 때 컴파일러가
빠진 분기를 잡아 준다.

### 3번의 근거

미리보기와 적용을 다른 코드로 만들면 언젠가 갈라진다. 갈라진 순간의 증상은
"미리보기에 20건이라 했는데 22건이 바뀌었다"이고, 그건 사용자가 적용한 뒤에야 안다.
같은 경로에 `dryRun` 하나면 갈라질 수가 없다.

## 6. 완료 조건

일괄 편집.

1. 30일 요금을 한 번에 바꾸고 캘린더 재조회에서 바뀐 값이 나오는 테스트.
   **P2 완료 조건의 절반이다**
2. 요일 필터가 걸리면 해당 요일만 바뀌는 테스트
3. "기존 대비 +20%"가 셀마다 다른 기준가에 각각 적용되는 테스트.
   전부 같은 값이 되면 기준가를 한 번만 읽은 것이다
4. `dryRun` 의 결과 건수와 실제 적용 건수가 같은 테스트
5. `dryRun` 이 아무것도 쓰지 않는 테스트. 요금도 원장도 감사 로그도
6. 요금 갱신은 성공하고 판매중지가 실패하는 상황에서 **둘 다 롤백되는** 테스트.
   5~6주차 1번과 같은 성질이다
7. 일괄 편집이 감사 로그에 한 줄로 남고, 범위와 바뀐 항목이 들어 있는 테스트
8. 남의 조직 판매 단위를 적용 대상에 넣으면 404 가 나오는 테스트

요금 규칙 엔진.

9. 다섯 규칙이 우선순위 순으로 적용되는 테스트
10. 하한·상한으로 잘리고 100원 단위로 반올림되는 테스트. 경계값을 포함한다
11. 우선순위가 같은 규칙 둘이 들어왔을 때의 동작이 정의돼 있고 테스트가 있는 것

SSE.

12. 수기 예약을 만들면 열려 있는 캘린더에 반영되는 테스트.
    **P2 완료 조건의 나머지 절반이다**
13. **다른 조직의 이벤트가 구독자에게 가지 않는 테스트.** 이번 주에서 가장 중요하다
14. 연결이 끊겼다 붙으면 캘린더를 다시 조회해 복구하는지 확인
15. 보이지 않는 행이 갱신돼도 스크롤 위치가 흔들리지 않는지 확인

전체.

16. `ModularityTest` 통과. 1번 결정이 순환을 만들지 않았는지 여기서 드러난다
17. `InventoryConcurrencyTest` 계속 통과
18. `./gradlew test`, `npm run build`, `npm run test` 통과

6번과 13번을 빠뜨리지 않는다. 6번은 절반만 반영된 화면이 정상으로 보이고,
13번은 새는 쪽에서는 아무 증상이 없다. 둘 다 이 프로젝트에서 반복된 모양이다.

## 7. 브랜치와 기록

- `feat/rate-bulk-edit` — A, B
- `feat/calendar-sse` — C, D

A 가 B 를 호출하므로 한 브랜치다. 순서대로 하고 앞엣것을 먼저 병합한다.

- **SSE 를 ADR 0010 으로 남긴다.** WebSocket 을 쓰지 않은 이유, 놓친 이벤트를
  재생하지 않고 재조회로 복구하는 이유, 단일 인스턴스 전제를 적는다.
  Outbox 소비자 자리의 첫 입주자라는 것도 함께 적어 ADR 0008 과 이어 둔다
- 일괄 편집을 `booking.calendar` 에 둔 근거는 ADR 을 새로 만들 만한 결정은 아니다.
  5절 1번이 근거이고, 코드 주석에 "pricing 에 두면 순환"이라고 남긴다
- P2 가 끝나므로 태그를 남긴다. `p2-complete`
- 끝나면 CLAUDE.md "현재 상태" 절을 P2 완료로 갱신한다.
