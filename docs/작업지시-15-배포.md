## 1. 지금 상태와 왜 이 주차가 생겼나

P4 16주차 코드까지 `origin/main` 에 있다. 백엔드 295 + 시뮬레이터 37 + 프론트 100
통과. **완료 조건 15·16(위젯 결제 라이브 확인)은 아직 미판정이다.**

**9월 11일 업체 회의에서 마감이 정해졌다 — 10월 말까지 배포해서 테스트 가능한 정도.**
7주다. 그 뒤는 두 단계로 간다.

| | |
|---|---|
| **1차** | 업체 관계자가 보고 "출품 가능성"을 판단한다. 소수. **이번 주차의 목표다** |
| 2차 | 통과하면 그쪽 수강생들에게 제공해 실제로 쓰게 한다 |

**지금까지 전부 로컬이었다.** 내장 PostgreSQL, localhost, 공개 터널. 배포는 이
프로젝트가 한 번도 해 보지 않은 일이다.

### 이번 주가 위험한 이유

**처음 하는 일이라 미지수가 많다.** 그래서 마감 7주의 맨 앞에 놓았다. 뒤로 밀면
10월 말에 배포도 AI 도 반쯤인 상태가 된다.

**그리고 남이 접속한다.** 지금까지 화면이 잘못 보이면 우리만 봤다. 이제 아니다.
4절의 제약이 평소보다 길고, 특히 **로컬 전용 값이 배포로 새는 것**을 겨눈다.

### 배포가 같이 풀어 주는 것 셋

- **포트원 웹훅이 고정 공개 URL 을 얻는다.** 터널이 필요 없어지고 완료 조건 15·16 을
  판정할 수 있다
- **에어비앤비 iCal 발행 주소가 고정된다**
- **관리형이 아니어도 pgvector 가 실제로 있다.** `docker-compose.yml` 이 이미
  `pgvector/pgvector:pg16` 을 쓴다. 작업지시-14 의 in-memory 우회가 진짜 경로가 된다

## 2. 이번에 만드는 것

### A. `reservation_night` 결함 수정 — 가장 먼저다

확인-08 3절 1번이다. `ReservationWriter` 는 `writeNights` 를 부르는데
`ChannelBookingWriter` 는 부르지 않는다. 리포트의 판매 객실박·매출·채널 믹스가 전부
그 테이블을 읽으므로 **채널로 들어온 예약이 리포트에서 빠진다.**

**재고 원장은 정상이라 캘린더는 맞게 보이고 리포트만 조용히 적게 센다.**

배포 전에 고치는 이유는 하나다 — **1차 심사자가 리포트를 본다.** 업체 실제 예약이
iCal 로 들어오는데 리포트에 안 잡히면 그 화면은 거짓이다.

- **완료 조건 13·14 가 이걸 못 잡았다.** 13은 산식, 14는 필터만 본다. 채널로 들어온
  예약이 리포트에 반영되는지를 보는 테스트가 없었다. **고칠 때 그 테스트를 함께 박는다**
- 고친 뒤 리포트 숫자가 달라진다. 시연 시드로 전후를 재어 기록에 남긴다

### B. 컨테이너로 뜨는 앱

지금은 백엔드도 프론트도 Gradle 과 vite dev 로 띄운다. 배포하려면 둘 다 산출물이
필요하다.

- **백엔드 Dockerfile.** `bootJar` → JRE 이미지. 빌드와 실행을 나눈 다단계로
- **프론트 정적 빌드.** `npm run build` 산출물을 Caddy 가 서빙한다
- **배포용 compose.** app + postgres(pgvector) + redis + caddy 넷. 기존
  `docker-compose.yml` 은 **인프라 둘만 띄우는 개발용**이므로 배포용을 따로 둔다
- **시뮬레이터는 배포하지 않는다.** 5절 5번

### C. 서버, 도메인, HTTPS

- **Lightsail 2GB, 서울 리전(ap-northeast-2).** 5절 1번
- 도메인 하나. **Caddy 가 Let's Encrypt 로 인증서를 자동으로 받는다**
- 방화벽은 80·443·22 만. **5432·6379 를 인터넷에 열지 않는다.** 4절
- 시크릿은 서버의 `.env` 파일. 5절 2번
- **자동 스냅샷을 켠다.** 한 대에 전부 있으므로 그 상자가 단일 장애점이다

### D. 배포 프로파일

**로컬 전용 값이 배포로 새면 안 된다.** 이 절이 이번 주차에서 가장 조용히 틀리기
쉬운 자리다.

| 항목 | 배포에서 |
|---|---|
| `JWT_SECRET` | **실제 난수.** `application-local.yml` 의 고정값을 절대 쓰지 않는다 |
| `GUEST_DATA_KEY` | **실제 난수.** 같은 이유. 바꾸면 기존 암호문을 못 읽으니 처음에 정한다 |
| `security.cookie.secure` | `true`. 운영 기본값이 이미 true 이고 local 만 끈다 |
| `staysync.public-base-url` | 실제 도메인. 터널 주소가 아니다 |
| `spring.flyway.locations` | **pgvector 를 포함해야 한다.** 지금은 docker 프로파일만 V2 를 적용한다 |
| 로그 레벨 | `com.staysync` 를 DEBUG 에서 내린다. 지금 설정은 개발용이다 |
| `embedded-postgres.enabled` | `false` |
| `lock.type` | `redis` |
| `vector.type` | `pgvector` |

**`ddl-auto: validate` 는 그대로다. V1 을 고치지 않는다.**

### E. 체크인·체크아웃 화면

확인-08 3절 4번이다. **화면에서 예약에 하는 쓰기는 막대를 끌어 날짜를 바꾸는 PATCH
하나뿐이다.** 체크인도 체크아웃도 화면이 없어 리허설에서는 명령으로 걸었다.

1차 심사에 이것만은 있어야 한다. **청소 태스크 자동 생성이 체크아웃에 걸려 있어서**,
없으면 운영 흐름의 절반이 화면에서 보이지 않는다.

- **새 화면을 만들지 않는다.** 캘린더에서 예약을 눌러 열리는 최소 패널이면 된다.
  기존 `SelectionPanel` 자리를 쓸 수 있는지 먼저 본다
- 상태 전이는 이미 서버에 있다. 화면에서 부르기만 한다

### F. 초기 데이터

**빈 데이터베이스에서 시작한다.**

- 심사자 계정 몇 개. **회원가입 화면이 없으므로** 만드는 방법을 정하고 절차에 남긴다
- **업체 실제 숙소와 판매 단위, 요금.** 등록 화면이 없으므로 우리가 넣는다
- **업체 iCal 연결 하나.** 5절 6번
- **`tools/seed_demo.py` 를 쓰지 않는다.** 시연용 가짜 게스트 이름이 남의 눈에 띈다

## 3. 이번에 만들지 않는 것

2차에서 하거나, 이 프로젝트가 감당할 것이 아니다.

- **회원가입 화면.** 1차는 계정을 우리가 만든다. 2차에 필요하다
- **숙소·판매 단위·요금제 등록 화면.** 1차는 우리가 넣는다. 2차에 필요하다
- **역할별 인가(`@PreAuthorize`).** 심사자마다 조직이 다르면 조직 스코핑으로 버틴다.
  한 조직에 여러 사람이 들어오는 2차에는 필요하다
- **이용약관과 개인정보 처리방침.** 수강생이 실제 게스트 정보를 넣는 2차의 일이다.
  계획서 15.3 이 "상용 운영에는 추가 절차가 필요하다"고 적어 둔 그 자리다
- **CI/CD 자동 배포.** 손으로 한다. 7주에 파이프라인까지 만들지 않는다
- **무중단 배포, 오토스케일링, 다중 AZ, 로드밸런서**
- **관리형 서비스(RDS·ElastiCache·ALB).** 5절 1번
- **모니터링 대시보드.** Actuator 헬스체크까지다
- **Mock OTA 시뮬레이터 배포.** 5절 5번
- **실결제.** 테스트 모드 그대로다

## 4. 지켜야 할 제약

### 배포에만 해당하는 것

- **5432·6379 를 인터넷에 열지 않는다.** 지금 `docker-compose.yml` 은 둘 다 `ports`
  로 호스트에 노출한다. 개발용이라 맞지만 **배포용 compose 에서는 빼고 내부
  네트워크로만 통신한다.** 인터넷에 열린 PostgreSQL 은 며칠이면 발견된다
- **로컬 프로파일의 고정 키를 배포에 쓰지 않는다.** `application-local.yml` 에
  "공개되어 있다는 전제로만 쓴다"고 적혀 있는 그 값들이다
- **`.env` 를 저장소에 넣지 않는다.** 권한은 소유자만 읽게 둔다
- **업체 iCal 주소를 저장소·문서·로그·대화에 남기지 않는다.** 주소를 아는 사람은
  누구나 그 숙소 예약 일정을 읽는다. API 키와 같이 취급한다
- **StaySync 가 발행하는 iCal 주소를 업체의 실제 리스팅에 등록하지 않는다.**
  등록하는 순간 우리 달력이 영업 중인 리스팅의 날짜를 막거나 푼다. **업체의 명시적
  허락이 있어야 하고 이번 주차의 범위가 아니다.** 수신만 한다
- **시연 시드를 배포 데이터베이스에 넣지 않는다**
- **재기동해도 데이터가 남아야 한다.** 볼륨을 붙인다

### 2GB 에 넷을 올리므로 지킬 것 셋

앱·PostgreSQL·Redis·Caddy 를 합치면 대략 1.2~1.5GB 다. 들어가지만 여유가 없다.

- **서버에서 이미지를 빌드하지 않는다.** `bootJar` 를 2GB 상자에서 돌리면 위험하다.
  로컬에서 빌드해 올리거나 레지스트리를 거친다
- **커넥션 풀을 줄인다.** `application-docker.yml` 이 `hikari.maximum-pool-size: 20`
  이다. 커넥션 하나에 PostgreSQL 백엔드 프로세스가 하나 붙으므로 2GB 에서는 10 쯤이다
- **JVM 힙을 명시하고 스왑을 켠다.** 컨테이너에서 힙을 안 정하면 JVM 이 호스트 메모리
  기준으로 잡는다

### 그대로 가는 것

- **예외로 흐름을 제어하지 않는다.** 먼저 조회해 분기한다
- **`@Transactional` 메서드를 같은 클래스에서 부르지 않는다**
- **픽스처는 서버가 실제로 보내는 형태로 적는다**
- **자기 모듈 밖의 테이블을 SQL 로 읽지 않는다.** 프로덕션 코드에 `JdbcTemplate` 을
  쓰는 곳이 없다는 것이 기준이다
- **`ChannelRoundTripTest` 는 벽시계 15초 예산이라 다른 것과 병렬로 돌리지 않는다**
- 주석과 문서는 한국어, 식별자는 영어, 테스트 이름은 한국어 서술형

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. 구성 | **Lightsail 2GB 한 대 + docker compose + Caddy.** EC2 도 관리형 서비스도 쓰지 않는다 |
| 2. 시크릿 | 서버의 `.env` 파일. Parameter Store 를 쓰지 않는다 |
| 3. 배포 방식 | 손으로 한다. CI/CD 를 만들지 않는다 |
| 4. 1차 범위 | 심사용. 회원가입·등록 화면·역할별 인가는 2차 |
| 5. 시뮬레이터 | 배포하지 않는다 |
| 6. iCal | 링크 하나로 시작해 파서를 검증한 뒤 늘린다 |

### 1번의 근거

**`docker-compose.yml` 이 이미 있고 `pgvector/pgvector:pg16` 을 쓴다.** 그대로 한
대에 올리면 된다. RDS·ElastiCache·ALB 로 가면 관리 서비스 셋을 새로 배우고
**로드밸런서만 월 $16~20** 이 붙는다. 얻는 것은 이 규모에서 쓰이지 않는 가용성이다.

**EC2 대신 Lightsail 인 이유는 비용과 설정 항목 수다.**

| | Lightsail 2GB | EC2 t3.small |
|---|---|---|
| 인스턴스 | **$12/월 고정** | 미국 기준 $15.18, 서울은 더 비싸다 |
| 디스크 | 60GB SSD 포함 | EBS 별도 |
| 고정 IP | 포함 | **공인 IPv4 주소 요금 별도** |
| 데이터 전송 | 3TB 포함 | 별도 |
| 합계 | **$12** | 대략 $25 |

성능은 사실상 같다. 밑단이 같은 버스터블이고, 다른 것은 버스트를 다 쓴 뒤다 —
t3 는 unlimited 모드로 돈을 더 내고 계속 돌고 Lightsail 은 기준 성능으로 떨어진다.
**이 서비스는 CPU 를 꾸준히 태우지 않는다.** 폴링이 15분 주기이고 P5 의 임베딩도
CPU 가 아니라 외부 API 대기다. 예상 밖 요금이 안 붙는 쪽이 낫다.

**2차까지 봐도 Lightsail 로 버틴다.** 수강생 수십 명 규모면 세로로 키우면 된다 —
2GB → 4GB($24) → 8GB($48) 가 스냅샷 뒤 리사이즈 한 번이다. 로드밸런서와 다중화가
필요해지는 것은 수백 명 동시 접속부터이고 이 프로젝트의 사정이 아니다.
**그때가 오면 스냅샷으로 EC2 로 옮긴다.**

**대신 2차에 진짜로 중요해지는 것이 바뀐다.** 한 대에 앱·DB·Redis 가 다 있어
**그 상자가 단일 장애점이다.** 실사용자가 생기면 백업이 장식이 아니다 —
완료 조건 8번이 복원까지 요구하는 이유이고, 자동 스냅샷을 함께 켠다.

**서울 리전인 이유가 둘이다.** 심사자도 수강생도 한국에 있고, **계획서 15.2 와 결이
맞는다** — LLM 국외이전을 마스킹으로 피하겠다고 적어 두었는데 서버와 DB 가 서울이면
우리가 저장하는 게스트 정보는 국내에 남는다. 업체 실제 예약 일정을 다루므로 더 그렇다.

**EC2 를 고를 이유는 기술이 아니라 이력이다** — VPC·보안그룹·EBS 를 직접 다룬 경험.
그것이 목적이면 EC2 가 맞다. **이번 마감의 위험은 성능이 아니라 처음 하는 일이
예상보다 오래 걸리는 것이므로 단순한 쪽을 골랐다.**

### 2번의 근거

**시크릿이 셋뿐이고 서버가 한 대다.** Parameter Store 나 Secrets Manager 는 인스턴스
역할과 SDK 호출이 따라온다. 얻는 것에 비해 이번 주차에 더할 것이 많다.

**대신 지킬 것을 4절에 적었다** — 저장소에 넣지 않고 권한을 막는다.

### 3번의 근거

**배포를 일곱 번 할 프로젝트가 아니다.** 1차 심사 전에 몇 번, 2차 전에 몇 번이다.
파이프라인을 만드는 시간이 손으로 배포하는 시간보다 길다.

**대신 절차서를 남긴다.** 7절이 그것이다. 손으로 하되 **다음 사람이 그대로 따라
할 수 있으면 된다.** 자동화보다 재현 가능성이 먼저다.

### 4번의 근거

1차는 **보고 판단하는 자리**이고 2차가 **쓰는 자리**다. 둘을 같은 범위로 잡으면
10월 말에 못 끝낸다.

- 계정이 몇 개면 회원가입 화면 없이 우리가 만들어 주면 된다
- 숙소 등록도 마찬가지다. **오히려 낫다** — 심사자가 자기가 아는 숙소와 자기 실제
  예약 일정이 화면에 떠 있는 것을 본다. 빈 화면에서 시작하는 것보다 강하다
- 요금 편집은 이미 캘린더에 있다(기간 선택 → 일괄 편집)
- **체크인·체크아웃만 없어서 못 넘어간다.** 그래서 2절 E 가 있다

**역할별 인가는 2차의 조건으로 명확히 적어 둔다.** 한 조직에 여러 사람이 들어오는
순간 필요하고, 지금은 인증 여부와 조직 스코핑까지다.

### 5번의 근거

**Mock 은 개발용 도구다.** 배포된 서비스에 가짜 OTA 가 떠 있을 이유가 없고, 심사자가
그것을 보면 무엇이 진짜인지 헷갈린다.

기술적으로도 막혀 있다 — 시뮬레이터에는 Spring Boot Gradle 플러그인을 적용하지 않아
`bootJar` 가 없다(ADR 0011). **지금 그 결정을 뒤집지 않는다.**

### 6번의 근거

**업체가 준 iCal 링크는 우리 파서가 한 번도 본 적 없는 모양이다.**

조사-02 는 **미게시** 리스팅으로 명세를 썼다. 미게시는 전 기간이 하나의 차단
일정이라 개별 예약을 구분할 수 없었고, 그것이 계획서 12.2 의 P3 완료 조건 셋째를
좁혀야 했던 이유다.

**게시된 리스팅의 피드는 예약마다 이벤트가 하나씩 온다.** 처음 만나는 것이 여럿이다 —
이벤트 여러 개, 취소되면 사라지는 이벤트, UID 형식, 요약 문구의 종류,
`DTEND` 경계, 시간대, 그리고 재동기화의 축소 방지(`shrink-guard-ratio`)가 처음으로
진짜 데이터를 만난다.

**하나에서 잡고 늘린다.** 여러 개를 한꺼번에 붙이면 어느 피드가 문제인지 가리기
어렵고, 남의 실제 데이터를 다루는 양도 커진다.

**파서가 통과하면 2~3개로 늘린다.** "여러 방을 한 판에서 본다"가 이 제품의 핵심인데
한 줄만 실데이터이면 1차 심사 화면이 약하다.

**어느 링크가 어느 판매 단위인지 업체에 확인한 뒤 매핑한다.** 링크만 봐서는 모르고,
틀리면 엉뚱한 방의 일정이 들어온다.
