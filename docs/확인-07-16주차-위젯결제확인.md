- 관련: 작업지시-13 8절, 계획서 8.7 / 8.8 / 14.2, 인계메모 4절, CLAUDE.md
- 작성: Cowork 세션 (절차). 결과 칸은 확인 후 채운다

코드는 끝났고 자동 테스트 백엔드 295 + 시뮬레이터 37 + 프론트 100 이 통과한다.
**남은 둘은 사람 손이 필요하다.** 공개 터널과 포트원 콘솔 등록이 있어야 웹훅이
들어오고, 웹훅이 들어와야 예약이 확정되며, 확정돼야 리포트에 나타난다.

**이 확인을 통과하기 전에 `p4-complete` 태그를 달지 않는다.**

브라우저 확인은 7·9·10·14·15주차에서 매번 결함을 잡았다. 15주차는 자동 테스트
264 + 83건이 전부 통과하는 상태에서 둘이 나왔다. 이번에는 돈이 걸린 경로다.

## 1. 무엇을 판정하는가

| | 조건 |
|---|---|
| 15 | 브라우저에서 위젯으로 예약을 만들고 테스트 결제까지 통과시킨다 |
| 16 | 같은 화면에서 리포트에 그 예약이 반영되는 것을 본다 |

**16 은 15 에 딸려 있다.** 위젯이 만드는 것은 HOLD 이고 HOLD 는 매출로 세지 않으므로
리포트에 나타나지 않는다. 확정된 예약이 있어야 하고, 확정은 결제 웹훅으로만 된다.
15 가 실패하면 16 은 판정 자체가 불가능하다.

## 2. 시작하기 전에 알고 들어갈 것

여기 적은 여덟은 전부 **정상 동작인데 결함처럼 보이는 자리**이거나, 앞 주차에서
실제로 시간을 잡아먹은 자리다. 먼저 읽는다.

- **국민카드는 테스트에서 결제되지 않는다.** 다른 카드를 쓴다
- **매일 23:00~23:50 에 테스트 결제가 자동 취소된다.** 그 시간대에 하면 확정된 예약에
  취소 웹훅이 뒤따라 들어온다. 지금 시각이 그 구간이면 미룬다
- **웹훅 시크릿이 비어 있으면 웹훅이 처리되지 않는다.** 설계가 그렇다. 검증 없이
  통과시키면 아무나 결제 완료 웹훅을 보내 예약을 확정시킬 수 있다. 3절 3단계를
  건너뛰면 결제창은 성공하는데 예약이 영영 HOLD 로 남는다
- **결제창의 성공이 우리 확정이 아니다.** 확정은 웹훅으로만 일어나고 그 사이에 시차가
  있다. 화면이 `GET /public/payments/status/{확인코드}` 로 확인한다
- **터널은 8080(백엔드)을 연다.** 5173(프론트)이 아니다. 웹훅을 받는 쪽은 백엔드다
- **`staysync.public-base-url` 을 반드시 준다.** `baseUrl` 은 요청의 `Host` 헤더에서
  만들지 않으므로 터널로 들어와도 자동으로 안 바뀐다. **끝에 슬래시를 붙이지 않는다**
- **PowerShell 에서 `--args='...'` 형태가 통하지 않는다.** 작은따옴표를 벗기고 공백에서
  잘라 뒤엣값을 버린다. `local` 은 기본값이라 앱은 멀쩡히 뜨고 **공개 주소만 조용히
  빠진다.** Git Bash 에서 하거나, PowerShell 이면 `"--args=..."` 로 통째로 감싼다
- **고아 postgres.** 앱을 내려도 자식 프로세스가 남아 `.localdb` 를 잡는다. 15주차에
  두 번 다 남았다. `Get-Process postgres | Stop-Process -Force` 로 치운다

로그의 한글이 깨지면 `2>&1 | tee ../backend.log` 를 붙인다. `CMSPMS\backend.log` 에
제대로 남고 Cowork 세션이 읽을 수 있다. **14주차 결함 넷이 다 이 파일에서 나왔다.**

## 3. 절차

### 1단계. 공개 터널

VS Code **포트** 탭에서 `8080` 을 전달하고 표시 여부를 **Public** 으로 바꾼다.
주소를 받아 둔다.

### 2단계. 포트원 콘솔에 웹훅 등록

결제알림(Webhook) 관리에 이 URL 을 등록한다. 경로는 16주차에 확정됐다.

```
https://<공개-터널-주소>/public/payments/portone/webhook
```

등록하면 웹훅 시크릿이 발급된다.

### 3단계. `.env` 채우기

```
PORTONE_WEBHOOK_SECRET=<2단계에서 발급된 값>
```

나머지 셋(`PORTONE_STORE_ID`, `PORTONE_CHANNEL_KEY`, `PORTONE_API_SECRET`)은 이미
들어 있는 것을 확인했다. **앞의 둘과 뒤의 둘을 같은 자리에서 다루지 않는다** —
위젯에 내려가는 설정 응답에 실려야 하는 것은 `STORE_ID` 와 `CHANNEL_KEY` 뿐이다.
4단계에서 그것을 눈으로 본다.

### 4단계. 기동

```bash
./gradlew bootRun --args='--spring.profiles.active=local --staysync.public-base-url=https://<터널주소>' 2>&1 | tee ../backend.log
cd frontend && npm run dev
```

시뮬레이터(`./gradlew runSimulator`)는 이번 확인에 필요 없다.

**여기서 한 번 확인한다.** 브라우저 개발자도구 네트워크 탭에서 위젯이 받는 설정
응답을 열어 `apiSecret` 이나 `webhookSecret` 이라는 이름이 **없는 것**을 본다.
프론트 번들이나 응답 본문에 섞이면 테스트 키라도 그 구조가 그대로 굳는다.

### 5단계. 확인용 데이터

숙소 하나에 판매 단위와 요금이 있어야 위젯이 금액을 계산한다. 15주차의
`Week15 Check Org`(숙소 3, 판매 단위 33)를 그대로 써도 되고 새로 만들어도 된다.
**요금이 설정된 날짜 구간을 골라야 한다** — 요금이 없으면 금액이 0 이거나 조회가 빈다.

위젯 주소에 넣을 숙소 식별자를 적어 둔다.

### 6단계. 위젯으로 예약 (조건 15)

`http://localhost:5173/widget/{숙소ID}` 를 연다.
**시크릿 창이나 다른 브라우저 프로필에서 연다.** 로그인 없이 열리는 것이 정상이고,
호스트 세션이 섞이면 공개 경로인지 아닌지가 확인되지 않는다.

| 단계 | 확인할 것 |
|---|---|
| 날짜·인원 선택 | 인원을 2 가 아닌 값으로 고른다. 3 이나 1 이 낫다 |
| 가용·요금 조회 | 금액이 서버 계산값으로 뜬다 |
| 게스트 정보 입력 | |
| HOLD 생성 | 이 시점에 예약이 생긴다. 확인 코드를 받아 둔다 |
| 결제창 | 국민카드 말고 다른 카드를 쓴다 |
| 확정 | 화면이 확정으로 바뀐다 |

**인원을 2 가 아닌 값으로 고르는 이유가 있다.** `Reservation.adults` 의 기본값이 2 라
인원이 안 내려가도 화면에는 아무 이상이 없다. 16주차에 지시서 밖의 판단으로 메운
자리이고, 여기서만 눈으로 확인된다. 확정된 예약을 호스트 화면에서 열어 인원이
고른 값인지 본다.

### 7단계. 리포트 (조건 16)

호스트로 로그인해 `/reports` 를 연다.

**기간의 뜻은 숙박이다.** 예약한 날이 아니라 묵기로 한 날 기준이므로, 6단계에서 고른
**체크인 날짜가 들어가는 기간**으로 걸러야 한다. 오늘이 든 기간으로 걸러 놓고 다음 달
숙박을 예약하면 아무것도 안 나온다. 결함이 아니다.

| 볼 것 | 있어야 할 모습 |
|---|---|
| 그 예약이 지표에 반영됨 | 점유율·ADR·RevPAR 가 0 이 아니다 |
| 항등식 | `RevPAR = ADR × 점유율` 이 화면의 세 값으로 맞는다 |
| 채널 믹스 | 직접예약이 한 건으로 잡힌다 |
| 취소율 | 이 예약 때문에 오르지 않는다 |

**항등식을 화면에서 곱해 본다.** 테스트에 한 줄로 박아 뒀지만 화면이 셋을 나란히
띄우므로 누구든 곱해 보고, 안 맞으면 셋 다 의심받는다. 반올림 자리(소수 4자리) 때문에
끝자리가 어긋나는 것은 결함이 아니다.

## 4. 볼 만한 것 — 결함이면 여기서 나온다

절차를 통과하더라도 아래 셋은 따로 본다. 앞 주차의 결함이 전부 이 모양이었다 —
테스트가 통과하고 화면도 정상인데 틀려 있는 자리다.

**하나. 웹훅이 15분 안에 오지 않으면 어떻게 되는가.** HOLD 는 15분이고
(`staysync.hold-expiry-minutes`, `application.yml` 37행) 만료는 `HoldExpiryJob` 이
처리한다. 결제는 됐는데 웹훅이 늦으면 **돈은 받고 예약은 만료된 상태**가 나올 수
있다. 정상 경로에서는 몇 초라 안 보이는 자리다. 이번에 일부러 만들어 볼 필요는
없으나, 웹훅이 늦게 오는 일이 실제로 생기면 그 기록을 남긴다.

**둘. 같은 웹훅이 두 번 왔을 때.** 완료 조건 11 이 테스트로 덮고 있고 포트원은 응답이
실패면 재시도한다. 백엔드 로그에서 같은 결제 식별자의 웹훅이 두 번 이상 들어왔는지,
들어왔다면 예약과 결제 행이 각각 하나인지 본다.

**셋. HOLD 생성이 채널로 나가는가.** 16주차 A 가 메운 비대칭이다. 6단계의 HOLD
생성 시점에 재고 변경 이벤트가 나가는지 로그로 확인한다. 채널 연결이 없으면 나갈
곳이 없으므로 이벤트 발행까지만 본다.

로그는 `backend.log` 에서 센다. **14주차 Outbox 결함은 밖으로 아무 증상이 없었고
로그를 파일로 받아 세어 보고서야 드러났다** — 5분에 973건 발행, 예약 94개.
