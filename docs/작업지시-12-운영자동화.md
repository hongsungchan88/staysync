## 1. 지금 상태

P4 14주차까지 `origin/main` 에 푸시돼 있다. 최신은 `b280e71` 이다.
백엔드 253건 + 시뮬레이터 37건 + 프론트 75건 통과.

통합 인박스, 메시지 템플릿, 자동 발송 스케줄러가 들어가 있다.

### 착수를 막는 것은 없다

인박스 브라우저 확인은 끝났고, 거기서 나온 결함 넷(확인-05 3절)도 고쳐 `b280e71` 로
푸시했다. 확인-05 4절의 완료 조건 여덟이 다 닫혔다.

**Outbox 백로그는 이미 비워 뒀다.** 결함 A 때문에 그때까지 만들어진 이벤트 107건이
`published_at` 이 빈 채로 남아 있었는데, 9월 7일 22:20 재기동에서 두 주기에 걸쳐 한 번
빠졌다. 관측 기록은 확인-05 7절이다.

**이 순서에는 이유가 있었고, 이번 주가 그 이유다.** 이번 주는 체크아웃 이벤트에 새
소비자를 붙이는 일이다. 백로그가 남은 채로 소비자를 붙였으면 그 한 번의 배수에서
**과거 체크아웃 전부에 청소 태스크가 생겼을 것이다.** 2절 B 의 중복 방지는 같은
이벤트가 두 번 오는 것을 막지, 옛 이벤트가 처음 오는 것을 막지 못한다.
**소비자를 새로 붙일 때마다 같은 질문을 한다.**

### 이번 주에 함께 볼 것

- **D(SSE 끊김이 ERROR 로 올라오던 것)가 아직 실물로 확인되지 않았다.** 재기동
  관측에서는 브라우저를 안 붙여 끊김 자체가 없었다. 완료 조건 15 의 브라우저 확인에서
  캘린더를 열었다 닫고 `backend.log` 에 ERROR 가 안 뜨는지 본다
- **게스트 N+1 이 있다.** 이벤트 하나마다 `guest ... where id in (?)` 을 한 건씩
  읽는다(확인-05 7절 E). 이번 주에 고칠 것은 아니지만, **청소 알림이 같은 경로를
  쓰므로 거기에 같은 모양을 새로 만들지 않는다**

로그는 `2>&1 | tee ../backend.log` 로 받는다. 결함 넷이 다 그 파일에서 나왔다.

### Outbox 소비자의 네 번째 입주자

SSE(9주차), 채널 전파(12주차), 자동 발송(14주차)에 이어 **체크아웃 이벤트가 이번 주다.**

계획서 8.6 이 그린 흐름 그대로다 — 체크아웃이 일어나면 청소 태스크가 생긴다.

### 준비돼 있는 것

- `ops_task` — V1 에 테이블이 있고 엔티티는 없다
- 예약 상태 머신 — 체크아웃 전이가 4주차부터 있다. `outbox_event` 도 남긴다
- `AutoMessageDispatcher` — 14주차의 자동 발송. **알림이 이것을 재사용할지가 5절 2번**
- `Reservation` 의 체크인·체크아웃 시각

## 2. 이번에 만드는 것

### A. 태스크 도메인

`OpsTask` 엔티티와 저장. 계획서 8.6 의 결과 형태가 명세다.

| 항목 | 값 |
|---|---|
| `type` | `CLEANING` |
| `unit_id` | 판매 단위. **계획서 8.6 은 `roomId` 라고 썼지만 2계층 모델에 호실이 없다** |
| `due_from` / `due_to` | 체크아웃 시각 ~ 다음 체크인 시각 |
| `assignee` | 담당자 |
| `status` | `TODO`, `IN_PROGRESS`, `DONE`, `BLOCKED` |

`OwnedResources` 를 거친다. 남의 조직 태스크는 404 다.

### B. 체크아웃 이벤트로 태스크 생성

- 체크아웃 이벤트를 소비해 `CLEANING` 태스크를 만든다
- **기한의 끝은 다음 체크인 시각이다.** 다음 예약이 없으면 열어 둔다.
  같은 판매 단위의 다음 예약을 찾아야 하므로 booking 이 공개한 인터페이스를 쓴다
- **같은 예약으로 태스크를 두 번 만들지 않는다.** Outbox 는 최소 1회 전달이다.
  14주차의 발송 이력과 같은 문제이고 같은 방식으로 푼다.
  **이것은 같은 이벤트가 두 번 오는 것을 막는 장치다.** 옛 이벤트가 처음 오는 것은
  못 막는다. 1절을 볼 것
- **취소된 예약에는 만들지 않는다.** 체크아웃된 예약이 나중에 취소되는 경우가 있다

### C. 청소 상태 연동

계획서 8.6 의 마지막 줄이다 — 태스크가 완료되면 판매 단위 상태가 `CLEAN` 이 된다.

`Unit.housekeeping` 이 이미 있다(V1, 기본값 `CLEAN`). 체크아웃 시 `DIRTY` 가 되고
청소 완료 시 `CLEAN` 으로 돌아온다.

**태스크 완료와 판매 단위 상태 변경은 한 트랜잭션이다.** 하나만 반영되면
"청소 끝났는데 더러움" 또는 그 반대가 남고, 둘 다 화면에서는 정상으로 보인다.

### D. 칸반 보드

`/ops/tasks` 다. 계획서 8.6 이 네 칸을 정했다.

- `TODO` · `IN_PROGRESS` · `DONE` · `BLOCKED`
- 날짜와 담당자로 거른다
- 칸 사이 이동으로 상태를 바꾼다

**8주차의 드래그와 같은 규칙이다.** 낙관적 업데이트를 하되 서버가 진실이고,
거절되면 원위치로 되돌리고 이유를 보여 준다. `dnd-kit` 이 이미 있다.

**키보드로도 옮길 수 있어야 한다.** 8주차에 정한 것이 그대로 적용된다.

### E. 알림

담당자에게 알린다. 5절 2번을 볼 것 — 웹푸시나 알림톡을 만들지 않는다.

- 태스크가 생기면 담당자에게 간다
- 기한이 지난 태스크는 화면에서 눈에 띄게 표시한다

## 3. 이번에 만들지 않는 것

- **웹푸시와 알림톡.** 5절 2번
- **사진 업로드.** 계획서 8.6 이 말하지만 첨부 파일과 같은 이유로 미룬다 —
  저장소, 크기 제한, 만료가 따라온다. 14주차에 같은 판단을 했다
- **모바일 화면.** 계획서 8.6 이 "담당자가 모바일에서"라고 적었지만 반응형으로
  충분하다. 네이티브 앱은 계획서 3.2 의 제외 항목이다
- **담당자 계정과 역할별 인가.** 여전히 3~5단계로 미뤄져 있다.
  담당자는 이름 문자열이면 된다(5절 3번)
- **리포트, 직접예약 위젯, 결제.** 16주차다
- **`CLEANING` 외의 태스크 종류.** 정비·점검은 만들 이유가 아직 없다

## 4. 지켜야 할 제약

- **모듈 경계.** `ops` 가 `booking.domain` 이나 `property.domain` 을 보지 않는다.
  다음 체크인 조회는 booking, 판매 단위 상태는 property 가 공개한 인터페이스로 한다
- **한 트랜잭션.** 태스크 완료와 판매 단위 상태가 함께 성공하거나 함께 실패한다
- **예외로 흐름을 제어하지 않는다.** 3주차·12주차·14주차에 세 번 같은 함정에 빠졌다.
  CLAUDE.md 함정 목록에 있다. **먼저 조회해 분기한다**
- **`@Transactional` 메서드를 같은 클래스에서 부르지 않는다.** CLAUDE.md 에 적혀
  있는데도 14주차에만 두 번 났다 — `sendOnce`, 그리고 결함 A 의
  `OutboxRelay.run()` → `relayPending()`. **스케줄러가 부르는 진입점을 테스트가
  그대로 부르지 않으면 이 부류는 안 잡힌다.** 기존 Outbox 테스트가 전부
  `relayPending()` 을 직접 불러 통과하고 있었다. 이번 주의 체크아웃 소비자도
  스케줄러나 이벤트 리스너가 부르는 그 메서드를 테스트가 부른다
- **`OwnedResources` 를 거친다**
- **15초 사슬을 건드리지 않는다.** 청소 태스크는 그 사슬 밖이다
- **`ddl-auto: validate`, V1 수정 금지**
- 주석과 문서는 한국어, 식별자는 영어, 테스트 이름은 한국어 서술형

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. `{{guestName}}` 구멍 | 먼저 원인을 확인하고, 필드 하나면 이번 주에 메운다 |
| 2. 알림 | 인박스 스레드에 시스템 메시지로 남긴다. 웹푸시·알림톡을 만들지 않는다 |
| 3. 담당자 | 이름 문자열. 계정을 만들지 않는다 |

### 1번 — 먼저 확인할 것

14주차에 `ChannelBookingCommand` 에 게스트 필드가 없어 `{{guestName}}` 을 쓰는
템플릿이 채널 예약에 나가지 못한다는 것이 드러났다. **자동 발송의 절반이 죽는다** —
수기 예약에만 나간다.

**원인을 먼저 본다.** `InboundBooking` 에는 게스트 이름 자리가 있었다(계획서 13.4 가
쓰던 것이고 13주차에 `extractGuestName` 만 지웠다).

- **`InboundBooking` → `ChannelBookingCommand` 경계에서 떨어진 것이면** 필드 하나를
  얹는 일이다. 이번 주에 메운다. iCal 은 어차피 `null` 이고 Mock 은 채울 수 있다
- **처음부터 없던 것이면** 경계 설계를 다시 보는 일이라 이번 주가 아니다.
  그 사실을 적고 16주차나 P6 예비 시간으로 넘긴다

어느 쪽인지 확인한 뒤 판단하고, **판단 근거를 남긴다.**

### 2번의 근거

웹푸시는 서비스 워커와 구독 관리와 키가 따라오고, 알림톡은 사업자 등록과 발신
프로필 심사가 필요하다. **둘 다 이 프로젝트에서 확보할 수 없는 것 위에 있다.**

14주차에 인박스와 메시지 도메인을 만들어 뒀다. **알림을 그 스레드에 시스템 메시지로
남기면 새 경로를 만들지 않고도 담당자가 볼 곳이 생긴다.** 발신자 구분에
`SYSTEM` 이 이미 있다.

계획서 8.6 의 "웹푸시 또는 알림톡"은 실제 서비스를 전제한 문장이다. 학기 프로젝트의
범위에서 무엇이 가능한지를 적고 넘어가는 편이 낫다. **못 만든 것을 만든 것처럼
적지 않는다.**

### 3번의 근거

담당자에게 계정을 주려면 역할별 인가가 필요하고, 그건 ADR 0004 가 3~5단계로 미뤄
둔 것이다. 지금 열면 인증 설계 전체를 다시 본다.

개인 호스트가 청소 담당자 한둘을 이름으로 관리하는 것이 실제 모습이기도 하다.
계정이 필요해지는 시점은 담당자가 직접 로그인해 완료 처리를 할 때이고, 그건
모바일 화면과 함께 오는 일이다.

## 6. 완료 조건

태스크 생성.

1. 체크아웃 이벤트로 `CLEANING` 태스크가 생기는 테스트
2. 기한의 끝이 다음 체크인 시각인 테스트. 다음 예약이 없으면 열려 있다
3. **같은 이벤트가 두 번 전달돼도 태스크가 하나인 테스트.**
   Outbox 는 최소 1회 전달이다
4. 취소된 예약에는 태스크가 생기지 않는 테스트

청소 상태.

5. 체크아웃하면 판매 단위가 `DIRTY` 가 되는 테스트
6. 태스크를 완료하면 `CLEAN` 으로 돌아오는 테스트
7. **태스크 완료가 롤백되면 판매 단위 상태도 되돌아오는 테스트**

칸반.

8. 칸 사이로 옮기면 상태가 바뀌고 서버에 반영되는 테스트
9. 서버가 거절하면 원위치로 돌아오고 이유가 뜨는 테스트
10. 키보드로도 옮길 수 있는지 확인
11. 날짜와 담당자 필터가 동작하는 테스트

알림.

12. 태스크가 생기면 인박스에 시스템 메시지가 남는 테스트
13. 기한이 지난 태스크가 화면에서 구분되는지 확인

`{{guestName}}`.

14. 1번 결정대로 처리하고 **그 판단과 근거를 문서에 남긴다.**
    메웠으면 채널 예약에 `{{guestName}}` 템플릿이 나가는 테스트

전체.

15. 로그인 후 `/ops/tasks` 에서 체크아웃을 만들고 태스크가 뜨는 것,
    칸 사이로 옮기는 것을 **브라우저에서 확인한다**
16. `ModularityTest`, `InventoryConcurrencyTest` 통과
17. `./gradlew test`, `./gradlew build`, `npm run build`, `npm run test` 통과

3번·4번·7번을 빠뜨리지 않는다. 3번은 Outbox 의 성질상 실제로 오고, 4번은
체크아웃된 예약이 나중에 취소되는 경우이며, 7번은 어긋난 채로도 화면이 정상으로 보인다.

**15번을 미루지 않는다.** 이 프로젝트에서 브라우저 확인은 매번 결함을 잡았다 —
7주차 가로 가상 스크롤, 9주차 SSE 폭주, 10주차 응답 필드 누락. 셋 다 자동 테스트가
통과하는 상태였다.
