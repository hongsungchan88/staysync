## 1. 왜 필요한가

확인-12 6.4 에서 Claude Code 가 찾았다. 배포 컨테이너의 JVM 은 UTC 인데 `OpsTaskService.createCleaningFor` 가
체크아웃 시각(11:00)을 `ZoneId.systemDefault()` 로 시각에 붙인다. 그래서 **청소 마감이 20:00 KST** 가 되고, 기한의 끝(다음
체크인 16:00)은 **다음 날 01:00 KST** 가 된다. 개발 PC 는 JVM 이 Asia/Seoul 이라 테스트가 못 잡았다.

배포 환경에는 아직 청소 태스크가 0 건이다. **심사자가 업체 계정으로 체크아웃을 처음 누르는 순간 드러난다** — 1차 심사는
대본 시연이 아니라 직접 써 보는 자리라(인계메모 4절) 누를 가능성이 높다.

같은 원인(서버 시계 = UTC)이 다른 자리에도 있을 수 있다. "오늘"을 서버 기본 시간대로 잡는 곳은 **KST 00:00~09:00 사이에
하루 전 날짜**를 오늘로 본다. 이번에 같이 훑는다.

## 2. 이번에 만드는 것

### A. 착수 전 확인 둘 — 읽기만. 하나라도 걸리면 멈추고 보고한다

결정(5절 1번)의 전제다. 둘 다 통과해야 원시 값 마이그레이션을 미룰 수 있다.

1. **날짜 칸이 밀렸는가.** 배포 DB 에서 예약 몇 건(예: id 60, 메종드서촌 2층 10/10~13)과 그 원장 행의 `LocalDate` 칸을
   psql 로 읽어 `GET /api/...` 응답과 같은지 본다. `TIMESTAMPTZ` 칸 하나(예: 예약 생성 시각)도 화면 표시와 대조한다.
   체크인·체크아웃 **시각**(`LocalTime`) 칸만 +9시간이어야 정상이다
2. **원시 값을 엔티티 밖에서 읽는 곳이 있는가.** 체크인·체크아웃 시각 칸을 네이티브 쿼리·JPQL 비교·뷰·마이그레이션 SQL·
   리포트 집계에서 직접 읽거나 `now()`·`current_time` 과 비교하는 곳. 엔티티를 거치면 쓸 때 +9, 읽을 때 −9 로 짝이 맞아
   문제없다. 엔티티를 거치지 않으면 9시간 틀린 값을 본다

결과는 8절에 적는다. **걸리면 고치지 말고 보고한다** — 그때는 원시 값 마이그레이션을 포함하는 안(B안)으로 다시 정한다.

### B. 청소 마감을 숙소 시간대로

`createCleaningFor` 의 마감과 기한 끝을 **숙소 시간대**(`property.timezone`, 기본 Asia/Seoul)로 만든다. 서버 시계와 무관해야
한다.

### C. 서버 기본 시간대에 기대는 자리를 전부 훑는다

호출자를 다 훑고 원인 자리에서 고친다(인계메모 6절 "절반만 고치고 닫은 결함"). 훑을 것:

- `ZoneId.systemDefault()`, `TimeZone.getDefault()`
- 인자 없는 `LocalDate.now()`·`LocalDateTime.now()`·`LocalTime.now()` (`Clock` 주입이 있으면 그 `Clock` 의 시간대)
- 시간대 없는 `@Scheduled(cron = ...)` — 서버가 UTC 면 KST 기준으로 정한 시각에 안 돈다
- 날짜 기준 자동 발송("퇴실일"·"퇴실 다음 날"), 리포트 기간 경계, "오늘 이후" 조회, HOLD 만료, iCal 날짜 해석, 수량 줄이기의
  "오늘 이후 팔린 날"(작업지시-19), 체크아웃 되돌리기의 "퇴실일 당일까지"(작업지시-20 9절)

자리마다 **고쳤다 / 안전하다(이유)** 를 8절 표에 남긴다. 숙소가 정해지는 자리는 숙소 시간대, 숙소가 없는 자리(전역 스케줄 등)는
Asia/Seoul 을 쓰는 한 곳을 정해 그것을 부른다.

### D. 컨테이너 시간대를 명시로 고정한다

`deploy/compose.yml` 의 `JAVA_TOOL_OPTIONS` 에 `-Duser.timezone=UTC` 를 더하고, 왜 UTC 로 묶어 두는지 주석을 단다 —
**지금 저장된 `LocalTime` 원시 값이 "JVM UTC + `jdbc.time_zone` Asia/Seoul" 조합으로 +9시간 들어가 있어, JVM 시간대가 바뀌면
화면의 체크인·체크아웃 시각이 9시간 어긋난다.** 지금은 이미지 기본값이 우연히 UTC 인 것이고, 이것을 의도된 설정으로 만든다.
`application.yml` 의 `hibernate.jdbc.time_zone` 은 그대로 둔다(같은 이유).

### E. 서버 시간대로 도는 테스트

개발 PC(Asia/Seoul)에서도 **JVM 기본 시간대가 UTC 일 때**를 재현하는 테스트를 남긴다. 확인-12 6.4 의 1회용 테스트를 정식으로
만든 것 — UTC 에서 체크아웃하면 청소 마감 11:00 KST, 기한 끝 16:00 KST. C 에서 고친 자리 중 날짜 경계가 있는 것(KST 새벽에
"오늘")도 하나 넣는다. 기본 시간대를 바꾸는 테스트는 끝나면 반드시 되돌린다 — 안 그러면 뒤 테스트가 다른 시간대로 돈다.

## 8. 진행 상황

### 8.1 착수 전 확인 둘

**둘 다 통과(10-02). 원시 값 마이그레이션은 계획대로 P6.**

**1. 날짜 칸 — 밀리지 않았다.** 배포 DB 를 `BEGIN READ ONLY … ROLLBACK` 안의 SELECT 로만 읽었다. 기준은 사용자가 준 값.

| 대상 | 칸(자료형) | 원시 값 | 기준 | 판정 |
|---|---|---|---|---|
| 예약 60 메종드서촌 2층 | `check_in`·`check_out`(DATE) | 2026-10-10 · 2026-10-13 | 10-10 · 10-13 | 같음 |
| 예약 60 의 박 | `reservation_night.stay_date`(DATE) | 10-10 · 10-11 · 10-12 | 10-10 · 10-11 · 10-12 | 같음 |
| 같은 판매 단위 원장 | `inventory_ledger.stay_date`(DATE) | 10-10~10-12 행 `booked_units` 1 | 박 셋에 맞음 | 같음 |
| 예약 60 생성 시각 | `created_at`(TIMESTAMPTZ) | `2026-09-17 00:41:28+00` = **09:41 KST** | 09:41 KST 무렵 | 같음(9시간 어긋남 없음) |
| 숙소 셋 | `check_in_time`·`check_out_time`(TIME) | 지니하우스·메종드서촌 01:00 · 20:00, 시험 숙소 00:00 · 20:00 | API 16:00 · 11:00(시험 숙소는 기본값 15:00 · 11:00) | **+9시간만** — 예상대로 |

`LocalDate` 는 시간대 변환을 타지 않고, `TIMESTAMPTZ` 는 순간으로 저장돼 맞다. 어긋나는 것은 `LocalTime` 칸뿐이다.

**2. 원시 값을 엔티티 밖에서 읽는 곳 — 없다.** 로컬 저장소 전체(`node_modules`·`build`·`dist`·문서 제외)를 훑었다.

- `check_in_time`·`check_out_time` 이 나오는 SQL 은 `V1__init.sql` 의 칸 정의 하나. 뒤 마이그레이션·뷰·네이티브 쿼리·JPQL 비교에 없다
- 자바에서 이 칸은 `Property` 엔티티의 두 필드뿐이고, 바깥으로는 `UnitCatalogService.stayTimesOf`(엔티티 getter → `StayTimes`)와
  `PropertyDtos`(API 응답)로만 나간다. 둘 다 엔티티를 거친다
- `TIME` 자료형 칸은 이 둘뿐. `current_time`·`localtime`·`::time` 비교 없음
- `tools/`·`docs/scripts/` 의 파이썬 스크립트도 이 칸을 읽지 않는다. 프론트는 API 값만 쓴다

### 8.2 훑기 표

숙소가 없는 자리는 새 `shared.time.ServiceZone`(Asia/Seoul 한 곳 — `SEOUL`·`ID`·`today()`)을 부른다.

| 자리 | 쓰는 것 | 판정 |
|---|---|---|
| `OpsTaskService.createCleaningFor` 마감·기한 끝 | `ZoneId.systemDefault()` | **고쳤다** — 숙소 시간대. `StayTimes` 에 `zone`(`property.timezone`)을 실었다. 이번 결함의 원인 |
| `OpsTaskService.board` 날짜 필터 경계 | `ZoneId.systemDefault()` | **고쳤다** — `ServiceZone.SEOUL`. 여러 숙소에 걸친 필터라 숙소 하나를 고를 수 없다(지금 전부 Asia/Seoul) |
| `ChannelReconcileJob.reconcileOne` 대조 구간 시작 | 인자 없는 `LocalDate.now()` | **고쳤다** — 04:00 KST = 19:00 UTC 전날이라 배포에서 매일 하루 이르게 시작했다(어제 포함, 마지막 날 빠짐) |
| `IcalExportService.export` 발행 구간 시작 | 인자 없는 `LocalDate.now()` | **고쳤다** — KST 00~09시 요청이면 어제부터 발행했다 |
| `ScheduledMessageJob.run`(퇴실일·퇴실 다음 날·체크인 전날 자동 발송) | 인자 없는 `LocalDate.now()` | **고쳤다** — 09:00 KST = 00:00 UTC 같은 날이라 기본 크론에서는 우연히 맞았다. 크론을 09시 전으로 바꾸는 순간 하루 어긋난다 |
| `ChannelBookingWriter`(끝난 예약은 취소 안 함), `UnitCapacityWriter`(수량 줄이기 "오늘 이후", 작업지시-19), `ReservationWriter.undoCheckOut`("퇴실일 당일까지", 작업지시-20 9절) | `LocalDate.now(ZoneId.of("Asia/Seoul"))` | 안전했다 — 이미 Asia/Seoul. 문자열 셋을 `ServiceZone.today()` 로 모았다 |
| `@Scheduled(cron)` 셋 — 재동기화 대조, 리프레시 토큰 청소, 자동 발송 | `zone = "Asia/Seoul"` | 안전했다 — 셋 다 시간대가 있다. `ServiceZone.ID` 로 모았다. 나머지 `@Scheduled` 는 전부 `fixedDelay`(시간대 무관) |
| HOLD 만료(`HoldExpiryJob`, `BookingService` 의 `expiresAt`) | `OffsetDateTime.now()` 와 `timestamptz` 비교 | 안전하다 — 순간끼리 비교. 시간대가 결과를 바꾸지 않는다 |
| 청소 기한 지남(`OpsTask.isOverdue`, `OpsTaskController`), 리프레시 토큰 만료, `sync_job` 의 `now()` | 순간 비교 | 안전하다 — 같은 이유 |
| 리포트 기간 경계(`ReportService`) | 화면이 준 `LocalDate` 와 `DATE` 칸(`stay_date`) | 안전하다 — 서버의 "오늘"을 쓰지 않고, 날짜끼리 비교한다 |
| iCal 날짜 해석(`IcalParser.toLocalDate`) | 문자열의 날짜 여덟 자리 | 안전하다 — 시간대 변환이 없다. `DTEND` 배타 해석 그대로 |
| iCal 발행 `DTSTAMP`(`IcalWriter`) | `OffsetDateTime.now(ZoneOffset.UTC)` | 안전하다 — 규격상 UTC |
| Channex `inserted_at` 해석(`ChannexAdapter`) | `ZoneOffset.UTC` 명시 | 안전하다 — 서버 시간대와 무관 |
| `TimeZone.getDefault()` | — | 없음 |
| 시뮬레이터 `ScenarioRequest` 기본 체크인(오늘 + 7) | 인자 없는 `LocalDate.now()` | 안전하다 — 로컬 Mock OTA 의 시나리오 기본값. 배포되지 않는다 |
| `application.yml` 의 `staysync.timezone: Asia/Seoul` | — | 읽는 코드가 없다(참고만). 이번에 쓰지 않았다 |

**테스트(2절 E).** 둘 다 실제 진입점이고, 옛 코드로 되돌려 돌리면 실패하는 것을 확인했다.
