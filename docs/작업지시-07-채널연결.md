## 2. 이번에 만드는 것

### A. 어댑터 레지스트리

`AdapterType` 으로 `ChannelAdapter` 구현을 찾는 자리다. Spring 이 구현체를 주입하고
타입으로 색인한다.

- 등록되지 않은 타입을 찾으면 `DomainException` 으로 실패한다. 조용히 `null` 을
  돌려주면 호출부가 전부 방어 코드를 갖게 된다
- **프로덕션 코드에 껍데기 구현을 만들지 않는다**(5절 2번). 지금 등록될 구현은 0개다.
  테스트용 가짜 어댑터는 테스트 소스 안에만 둔다
- `capabilities()` 를 조회하는 경로를 함께 만든다. E 의 화면과 12주차 워커가 쓴다

### B. 채널 연결

`ChannelConnection` 엔티티와 저장, 그리고 REST API.

숙소 하나에 채널 연결 여럿이 붙는다. 연결 하나가 어댑터 종류 하나와 자격 증명 한 벌을
갖는다.

**자격 증명을 평문으로 저장하지 않는다.** `PersonalDataCipher` 를 그대로 쓴다
(5절 1번). API 키가 유출되면 그 사람의 채널 계정 전체가 열린다.

- **저장한 자격 증명을 다시 내보내지 않는다.** 조회 응답에는 마스킹된 형태만 담는다
  (`chnx_••••1a2b`). 화면에서 수정할 때는 새 값을 입력하게 하고, 빈 값이면 기존 값을
  유지한다
- `OwnedResources` 를 거친다. 남의 숙소의 채널 연결은 404 다
- **감사 로그를 남긴다.** 연결 생성·수정·삭제는 계정을 건드리는 일이다.
  전후 값에 자격 증명을 넣지 않는다. 어떤 필드가 바뀌었는지만 남긴다.
  ADR 0007 과 5~6주차에서 그은 선이 그대로다

`.env` 의 `CHANNEX_API_KEY` 는 **개발용 기본값**이다. 제품의 모양은 호스트가 화면에서
자기 키를 넣는 것이므로, `.env` 값을 코드가 직접 읽어 쓰지 않는다. 로컬에서 연결을
만들 때 편하게 쓰는 값이다.

### C. 채널 매핑

`ChannelMapping` 엔티티와 저장. 우리 `Unit` 과 채널 쪽 객실 식별자를 잇는다.

채널마다 식별자 모양이 다르다.

| 채널 | 식별자 |
|---|---|
| iCal (에어비앤비) | 리스팅 하나. 내보내기 URL 이 곧 식별자다 |
| Channex | `property_id` → `room_type_id` → `rate_plan_id` 3계층 |
| Mock | 시뮬레이터가 정한다 (11주차) |

**매핑 테이블이 이 차이를 흡수한다.** 도메인은 채널 쪽 계층을 모른다.
문자열 식별자로 다루고 해석은 어댑터가 한다.

- 한 `Unit` 이 채널 여럿에 매핑된다. 그게 이 제품의 존재 이유다
- **같은 연결 안에서 한 `Unit` 이 두 번 매핑되지 않게 막는다.** 중복 매핑은
  같은 재고를 두 번 보내는 결함이 되고, 12주차 워커에서야 증상이 나온다
- 매핑되지 않은 `Unit` 은 그 채널에 나가지 않는다. 화면이 이걸 보여 줘야 한다

### D. iCal 픽스처 저장

조사-02 의 `.ics` 전문을 테스트 리소스로 넣는다.
`src/test/resources/ical/airbnb-unpublished.ics` 정도가 맞다.

13주차 파서가 쓸 것이고, **실제 에어비앤비가 발행한 진짜 샘플**이라 손으로 만든
흉내보다 낫다. 지금 넣어 두지 않으면 조사 문서에만 남는다.

`UID` 의 해시 부분은 그대로 둬도 된다. 계정을 식별하지 않는다.
다만 **iCal 내보내기 URL 은 절대 넣지 않는다.** 그건 비밀이다.

### E. 채널 화면

계획서 8.1 의 경로 중 둘이다. `/channels/:id/logs` 는 12주차 동기화 워커 이후다.

`/channels` — 연결 목록
- 숙소별 연결과 어댑터 종류, 활성 여부
- 연결 추가·수정·삭제
- **`capabilities()` 를 표시한다.** iCal 연결에 "요금 전파 미지원"이 보여야 한다.
  6.1 이 말하는 설계의 요점이 화면에 드러나는 자리다

`/channels/:id/mapping` — 매핑 설정
- 우리 판매 단위 목록과 채널 쪽 식별자 입력
- 매핑되지 않은 단위를 눈에 띄게 표시한다

화면 규칙은 P2 와 같다. React Router 는 **이번에 넣는다** — 화면이 둘에서 넷으로
늘어난다. 7주차에 "화면이 느는 것은 P3 채널 화면"이라고 적어 둔 그 시점이다.

## 3. 이번에 만들지 않는 것

- **어댑터 구현 세 종.** iCal 13주차, Channex 12~13주차, Mock 11주차다.
  레지스트리에 등록될 구현이 이번 주에는 0개다
- **동기화 워커와 `sync_job`.** 12주차다
- **재시도·백오프·실패 큐, ARI 병합 버퍼.** 12주차다
- **충돌 해소 절차와 재동기화 배치.** 13주차다
- **`/channels/:id/logs`.** 보여 줄 로그가 아직 없다
- **iCal 발행 토큰과 `/public/ical/{token}.ics`.** 13주차다
- **역할별 인가.** 여전히 3~5단계다

## 4. 지켜야 할 제약

- **모듈 경계.** `channel` 이 `booking.domain` 이나 `property.domain` 을 보지 않는다.
  판매 단위는 `property.UnitCatalog` 로 받는다. 의존 방향은 channel → property 다
- **자격 증명은 암호화해서 저장하고, 어디로도 평문으로 내보내지 않는다.**
  응답, 로그, 감사 기록, 이벤트 페이로드 전부
- **`OwnedResources` 를 거친다.** 소유가 아니면 404
- **`ddl-auto: validate`, V1 수정 금지.** 컬럼이 모자라면 V3 를 더한다.
  `clean-on-start` 는 꺼져 있다
- **`ChannelAdapter` 인터페이스를 고치지 않는다.** ADR 0003 의 결정이고, 구현체를
  하나도 안 만들어 본 지금 고칠 근거가 없다. 12~13주차에 실제로 부딪히면 그때 연다
- TypeScript `strict`, 주석과 문서는 한국어, 식별자는 영어, 테스트 이름은 한국어 서술형

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. 자격 증명 암호화 | `PersonalDataCipher` 를 그대로 쓴다. 키도 `GUEST_DATA_KEY` 하나로 |
| 2. 레지스트리 구현체 | 프로덕션 코드에 껍데기를 두지 않는다. 테스트용 가짜는 테스트 소스에만 |
| 3. React Router | 이번에 넣는다 |

### 1번의 근거

새 암호화 코드를 쓰지 않는다. `PersonalDataCipher` 가 이미 AES-256-GCM 이고
4주차에 검증됐다. 두 번째 구현을 만들면 검증도 두 벌이 된다.

**키를 나누지 않는 이유.** 게스트 연락처와 채널 자격 증명이 같은 데이터베이스에 있어서,
키를 둘로 나눠도 유출 경로가 갈라지지 않는다. 덤프 하나로 둘 다 나가는 것은 같고,
관리할 환경 변수만 하나 늘어난다. 키를 나누는 것은 저장 위치나 접근 주체가 다를 때다.

검색 해시(`phone_hash` 같은)는 자격 증명에 필요 없다. 자격 증명으로 검색하지 않는다.

### 2번의 근거

5~6주차에 Outbox 소비자 워커 셋을 만들지 않은 것과 같은 판단이다. 등록될 구현이
없는데 껍데기를 만들면 **할 일이 없는 어댑터**가 프로덕션 코드에 남고, 11주차에
진짜 Mock 을 만들 때 그 자리를 두고 헷갈린다.

레지스트리가 비어 있을 때 실패하는 것이 정상 동작이다. 그걸 테스트로 고정한다.

### 3번의 근거

7주차에 "화면이 둘뿐이라 라우터를 넣지 않는다"고 정하면서 "화면이 느는 것은 P3
채널 화면(10주차)"이라고 적었다. 그 시점이다. 로그인·캘린더에 `/channels` 와
`/channels/:id/mapping` 이 더해져 넷이 된다.

## 6. 완료 조건

레지스트리.

1. 등록되지 않은 `AdapterType` 을 찾으면 실패하는 테스트. `null` 이 아니다
2. 테스트용 가짜 어댑터를 등록하면 타입으로 찾아지고 `capabilities()` 가 나오는 테스트

채널 연결.

3. 자격 증명이 데이터베이스에 평문으로 저장되지 않는지 확인하는 테스트.
   행을 직접 읽어 원문 문자열이 나오지 않아야 한다
4. **조회 응답 어디에도 자격 증명 평문이 없는지 확인하는 테스트.**
   응답을 문자열로 훑는다. 5~6주차 9번과 같은 방식이다
5. 자격 증명을 빈 값으로 수정하면 기존 값이 유지되는 테스트
6. 남의 조직 숙소에 연결을 만들거나 조회하면 404 가 나오는 테스트
7. 연결 생성·수정·삭제가 감사 로그에 남고, 전후 값에 자격 증명이 없는 테스트

매핑.

8. 같은 연결 안에서 한 `Unit` 을 두 번 매핑하면 거절되는 테스트
9. 매핑되지 않은 `Unit` 이 목록에서 구분되는지 확인

화면.

10. 로그인 후 `/channels` 로 이동하고, 연결을 만들면 목록에 나타나는 것을 브라우저에서
    확인한다. **자격 증명 입력란이 저장 후 마스킹돼 보이는지도 함께 본다**
11. iCal 종류의 연결에 "요금 전파 미지원" 표시가 뜨는지 확인
12. 라우터가 붙은 뒤에도 새로고침으로 로그인이 복구되는지 확인.
    액세스 토큰은 여전히 메모리에 있다(ADR 0009)

전체.

13. `ModularityTest` 통과. channel → property 방향이 지켜졌는지 여기서 드러난다
14. `./gradlew test`, `npm run build`, `npm run test` 통과

3번·4번·7번을 빠뜨리지 않는다. 자격 증명이 새도 기능은 정상으로 보이고, 드러나는
것은 그 사람의 채널 계정이 열린 뒤다. 이 프로젝트에서 세 번째로 나오는 모양이다.

## 7. 브랜치와 기록

- `feat/channel-connection` — A, B, C, D
- `feat/channel-ui` — E

앞엣것을 먼저 병합한다. 화면이 API 를 필요로 한다.

- **자격 증명 암호화를 ADR 0007 의 결과 절에 이어 적는다.** 새 ADR 을 만들지 않는다.
  같은 결정(`PersonalDataCipher`)의 두 번째 적용이고, 키를 나누지 않은 근거를 함께 남긴다
- React Router 를 넣은 것은 ADR 0009 의 결과 절에 이어 적는다. 7주차에 "P3 에서
  넣는다"고 적어 둔 것을 실행한 것이다
- 끝나면 CLAUDE.md "현재 상태"와 "아직 비어 있는 모듈"을 갱신한다. channel 이 빠진다
- 이 문서에 없는 판단이 필요해지면 임의로 정하지 말고 물어본다
