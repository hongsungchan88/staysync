## 1. 확인한 것

에어비앤비 호스트 계정과 리스팅 하나("개발 테스트용 아파트", 한국)를 만들었다.
리스팅은 **미게시 상태**다. 등록 정보 단계가 남아 있어 게시되지 않았다.

### "비공개 리스팅"이라는 기능은 없다

계획서와 인계메모가 "비공개 리스팅"이라고 적어 온 것은 에어비앤비에 없는 개념이다.
호스트가 쓸 수 있는 것은 **미게시 초안**과 **비활성화**뿐이다. 이 문서에서는
미게시 초안을 기준으로 적는다.

### iCal 양방향이 미게시 상태에서도 열려 있다

달력 → 예약 가능일 → 달력 연결하기 → 다른 웹사이트에 연결하기에 둘 다 있다.

- **1단계 — 내보내기.** 에어비앤비 달력 링크와 복사 버튼. 게시하지 않아도 나온다
- **2단계 — 가져오기.** 다른 사이트의 `.ics` 주소와 달력 이름을 넣는 칸

계획서 6.2 가 필요로 하는 수신·발행 두 방향이 모두 준비돼 있다.

**이 링크는 비밀이다.** 주소를 아는 사람은 누구나 예약 일정을 읽는다. API 키와 같이
취급하고 `.env` 의 `AIRBNB_ICAL_URL` 에 둔다. 저장소에 넣지 않는다.

## 2. 미게시 리스팅의 iCal 은 개별 일정을 담지 않는다

9월 30일 하루를 달력에서 막고 발행물을 받아 봤다. 전문이 이것뿐이다.

```
BEGIN:VCALENDAR
PRODID:-//Airbnb Inc//Hosting Calendar 1.0//EN
CALSCALE:GREGORIAN
VERSION:2.0
BEGIN:VEVENT
DTSTAMP:20260905T024836Z
DTSTART;VALUE=DATE:20260903
DTEND;VALUE=DATE:20270906
SUMMARY:Airbnb (Not available)
UID:7f662ec65913-...@airbnb.com
END:VEVENT
END:VCALENDAR
```

`VEVENT` 가 하나이고 2026-09-03 부터 2027-09-06 까지 **1년치를 통째로** 막고 있다.
미게시 리스팅이라 에어비앤비가 전 기간을 예약 불가로 내보내는 것이고,
직접 막은 9월 30일은 그 덩어리에 삼켜져 구분되지 않는다.

**따라서 미게시 상태의 iCal 로는 개별 예약도 개별 차단도 검증할 수 없다.**

## 3. 파서 명세를 확정해 준다

검증에는 못 쓰지만 **실제 에어비앤비가 발행한 진짜 샘플**이라 계획서 13.4 파서가
지켜야 할 것을 확정해 준다. 이 파일을 파서 테스트 픽스처로 저장소에 넣는다.

| 항목 | 값 | 파서가 지킬 것 |
|---|---|---|
| `DTSTART` / `DTEND` | `;VALUE=DATE` | 시각 없는 날짜형이다. `DATETIME` 을 전제하면 파싱이 깨진다 |
| `DTEND` | `20270906` | **배타적이다.** 9월 5일까지 막힌 것이다. 포함으로 읽으면 매 예약이 하루씩 밀린다 |
| `UID` | `<접두어>-<해시>@airbnb.com` | 멱등성 키로 쓸 수 있다. `(channel_code, channel_booking_id)` 유니크 제약의 입력이다 |
| `SUMMARY` | `Airbnb (Not available)` | 게스트 이름이 없다. 차단인지 예약인지 이 문자열로는 구분되지 않는다 |
| `PRODID` | `-//Airbnb Inc//Hosting Calendar 1.0//EN` | 발행자 판별에 쓸 수 있다 |

**`DTEND` 배타성이 가장 위험하다.** 하루 밀린 예약은 화면에서 정상으로 보이고,
드러나는 것은 재고가 어긋난 뒤다. 이 프로젝트에서 반복된 모양이다.

`SUMMARY` 에 게스트 정보가 없다는 것은 계획서 3.4 가 이미 적은 iCal 의 구조적
한계를 다시 확인해 준다. iCal 수신만으로는 누가 예약했는지 알 수 없다.

## 4. P3 완료 조건을 고쳤다

계획서 12.2 의 P3 완료 조건 셋째가 "실제 에어비앤비 리스팅의 예약이 캘린더에
나타난다"였는데, 미게시 상태로는 성립하지 않는다.

게시하면 성립하지만 **게시된 숙소는 검색에 노출되고 실제 게스트가 예약할 수 있다.**
요금을 높이고 달력을 막아도 위험이 0 이 되지 않으며 실제 결제가 발생할 수 있다.
학기 프로젝트의 테스트용 리스팅에 감당할 위험이 아니다.

**결정 — 미게시를 유지한다.** 에어비앤비는 iCal 파서와 발행 검증에 쓰고,
예약 수신 시나리오는 Channex 스테이징의 부킹닷컴 테스트 숙소와 Mock OTA
시뮬레이터(계획서 6.4, P3 11주차)가 맡는다.

지도교수가 승인한 "iCal·Channex·Mock 조합" 범위 안이다.

## 5. Channex 스테이징 현황

가입과 API 키 발급까지 끝났다. 조사-01 대로 문의나 승인 절차가 없었다.

| 항목 | 상태 |
|---|---|
| API 키 | 발급됨. Properties: All, Allowed IPs: Any IP, 활성 |
| 숙소(Property) | **아직 없음** |
| 채널 목록 | 확인 불가 |

`/channels` 로 가면 `/properties` 로 되돌아온다. **숙소를 먼저 만들어야 채널 연결이
열린다.** 그래서 조사-01 이 전제한 부킹닷컴 공용 테스트 숙소가 실제로 있는지는
아직 확인하지 못했다.

**P3 10주차의 첫 확인 항목이다.** 숙소를 하나 만들고 채널 목록에 부킹닷컴 테스트
숙소가 있는지 본다. 없으면 4절의 결정을 다시 열어야 한다 — 예약 수신 검증이
Mock 하나에만 기대게 되기 때문이다.

## 6. 환경 변수

값은 `staysync/.env` 에 있다. `.gitignore` 가 `.env` 를 막고 있다.

```
CHANNEX_API_KEY
CHANNEX_BASE_URL      https://staging.channex.io
AIRBNB_ICAL_URL
```

`JWT_SECRET`, `GUEST_DATA_KEY` 와 같은 자리다. 없으면 기동이 막히게 한다.
