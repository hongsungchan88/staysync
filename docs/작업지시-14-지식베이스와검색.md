## 4. 지켜야 할 제약

### local 에는 pgvector 가 없다. 이번 주의 가장 큰 제약이다

`application-local.yml` 이 `staysync.vector.type: in-memory` 로, `application-docker.yml`
이 `pgvector` 로 갈라 뒀다. V2 마이그레이션은 docker 프로파일에서만 적용된다 —
`local` 은 `embedding` 이 `REAL[]` 인 채로 남는다. P0 이 그렇게 설계했고 근거가 V1
400행 주석과 V2 머리말에 있다.

**따라서 브라우저 확인(완료 조건 13)은 in-memory 구현만 지나간다.** pgvector 경로는
브라우저에서 한 번도 안 돌아 보고 넘어간다. 이 프로젝트가 되풀이해 만난 자리 —
**"확인했다"가 "다 확인했다"가 아닌 자리** — 이므로 완료 조건 11 을 따로 뒀다.

### 나머지

- **모듈 경계.** `ai` 는 `property`, `booking`, `messaging` 의 테이블을 SQL 로 읽지
  않는다. 숙소 이름 같은 것이 필요하면 그 모듈이 공개한 인터페이스로 받는다
- **자기 테이블에 네이티브 질의를 쓰는 것은 경계 위반이 아니다.** 벡터 거리(`<=>`)와
  `tsquery` 는 JPQL 로 표현되지 않으므로 네이티브가 필요하다. **`@Query(nativeQuery = true)`
  를 `ai` 모듈의 Repository 안에 둔다. `JdbcTemplate` 은 여전히 쓰지 않는다.**
  16주차에 기준을 그렇게 잡은 이유가 살아 있다 — Repository 에 묶인 질의는 어느
  모듈의 것인지가 보이고, `JdbcTemplate` 은 아무 데서나 아무 테이블이나 읽을 수 있어
  경계가 안 보인다. **기준은 그대로다: 프로덕션 코드에 `JdbcTemplate` 을 쓰는 곳이 없다**
- **조직 스코핑.** 문서도 청크도 검색도 숙소로 먼저 거른다. **검색은 특히 그렇다** —
  남의 숙소 청크가 한 건 섞이면 그 답변은 그럴듯하게 틀린다
- **`@Transactional` 메서드를 같은 클래스에서 부르지 않는다.** 14주차에만 두 번 났다.
  **릴레이가 부르는 진입점을 테스트가 그대로 부른다**
- **예외로 흐름을 제어하지 않는다.** 먼저 조회해 분기한다
- **테스트가 실제 OpenAI 를 부르지 않는다.** 가짜 `EmbeddingModel` 이나 WireMock 을
  쓴다. 돈이 들고 값이 매번 달라 회귀 테스트가 되지 않는다
- **픽스처는 서버가 실제로 보내는 형태로 적는다.** 15주차 교훈이다
- **`ddl-auto: validate`, V1 수정 금지**
- 주석과 문서는 한국어, 식별자는 영어, 테스트 이름은 한국어 서술형

## 5. 착수 전에 정한 것

| 항목 | 결정 |
|---|---|
| 1. 임베딩 모델과 차원 | `text-embedding-3-small`, 1536 차원. 바꾸지 않는다 |
| 2. 키워드 축의 한국어 대응 | 접두 매칭 + 얇은 조사 제거. 테스트를 반드시 붙인다 |
| 3. 벡터 축의 구현 | 포트 하나에 구현 둘. Spring AI `VectorStore` 는 쓰지 않는다 |
| 4. 재임베딩 시점 | Outbox 로 뒤따라간다. 저장 트랜잭션 안에서 부르지 않는다 |
| 5. 마스킹 경계 | 이번 주는 마스킹하지 않는다. 대신 경계를 문서에 적는다 |
| 6. 토큰 세기 | 근사한다. 정확한 토크나이저를 넣지 않는다 |

### 1번의 근거

**V2 가 `vector(1536)` 으로 박혀 있다.** `text-embedding-3-small` 이 1536 이고
`3-large` 는 3072 라 컬럼과 안 맞는다. 모델을 바꾸면 마이그레이션이 따라오고 이미
넣은 임베딩을 전부 다시 만들어야 한다.

비용도 같은 쪽을 가리킨다. 계획서 10.1 이 잡은 월 1~3만원 안에서 임베딩은
작은 몫이어야 하고, 18주차의 답변 생성이 큰 몫을 쓴다.

**차원을 한 곳에 상수로 두고 그 값이 V2 와 다르면 기동에서 걸리게 한다.**
안 그러면 모델을 바꾼 다음 넣는 임베딩부터 조용히 틀린다 — 검색이 나빠질 뿐
예외가 나지 않는다.

### 2번의 근거 — 이 결정이 이번 주에서 가장 조용히 틀리기 쉽다

`idx_chunk_fts` 는 `to_tsvector('simple', content)` 다. `simple` 은 **공백과 문장부호로만
자르고 어간 분석을 하지 않는다.** 한국어는 조사가 어절에 붙는다.

```
문서:  "체크인은 15시부터입니다"   → 토큰 [체크인은, 15시부터입니다]
질의:  "체크인 몇 시예요"          → 토큰 [체크인, 몇, 시예요]
```

**한 글자도 안 겹친다.** `plainto_tsquery` 를 그대로 쓰면 키워드 축이 거의 아무것도
못 찾는다.

**그런데 화면에는 아무 증상이 없다.** RRF 가 벡터 축의 결과를 돌려주므로 검색은
멀쩡히 동작하는 것처럼 보이고, **키워드 축이 죽어 있다는 사실은 "정확히 그 낱말"이어야
하는 질의에서만 드러난다.** 이 프로젝트에서 되풀이된 부류 그대로다.

결정은 둘이다.

- **질의 토큰에 접두 매칭을 건다.** `to_tsquery('simple', '체크인:* | 시간:*')` 형태다.
  문서 토큰이 질의 토큰으로 **시작하면** 맞으므로, 조사가 뒤에 붙는 한국어에 맞는
  방향이다. **확장이 필요 없고 local 과 docker 에서 같이 돌며 기존 GIN 인덱스를
  그대로 쓴다**
- **반대 방향을 위해 질의 어절에서 흔한 조사를 뗀다.** 질의가 "체크인은"이고 문서가
  "체크인"이면 접두 매칭이 안 맞는다. 사전이 아니라 목록 하나다 —
  은/는/이/가/을/를/의/에/에서/으로/로/도/만/까지/부터. **얇은 한 겹이고 그렇게 적는다**

한 글자 토큰은 뺀다. `simple` 에 불용어가 없어 "몇", "이" 같은 것이 상위를 채운다.
정렬은 `ts_rank` 다.

**형태소 분석기(mecab, pg_bigm)를 넣지 않는다.** 둘 다 확장이거나 외부 바이너리라
local 의 내장 PostgreSQL 에서 돌지 않는다. 4절의 제약이 그대로 적용된다.

**완료 조건 8 이 이 결정을 지킨다.** 없으면 키워드 축이 죽어도 아무도 모른다.

### 3번의 근거

계획서 9.2 의 구현 스케치는 Spring AI 의 `VectorStore.similaritySearch(...)` 를 쓴다.
**그대로 하지 않는다.** 이유가 셋이다.

1. **local 에서 `PgVectorStore` 를 띄울 수 없다.** pgvector 확장이 없다. 그러면
   어차피 구현이 둘로 갈리고, 그 지점에서 Spring AI 의 추상화가 벌어 주는 것이 없다
2. **`SimpleVectorStore` 는 메모리에 따로 들고 있다.** 청크는 DB 에 있는데 벡터는
   메모리에만 있는 이원 상태가 되고 재기동하면 사라진다. **DB 에 있는 것과 검색이
   보는 것이 다른 상태는 만들지 않는다**
3. **`PgVectorStore` 는 자기 스키마를 관리한다.** `vector_store` 테이블을 따로
   만들어 우리 `knowledge_chunk` 와 이원화되고, Flyway 가 스키마를 든다는 원칙과
   부딪힌다. V1 이 `embedding` 컬럼을 `knowledge_chunk` 안에 둔 것은 P0 의 결정이다

**결정 — 임베딩 생성만 Spring AI `EmbeddingModel` 을 쓰고, 저장과 검색은 우리 것이다.**
`VectorSearchPort` 하나에 구현 둘을 둔다.

| 프로파일 | 구현 |
|---|---|
| docker | `<=>` 코사인 거리로 네이티브 질의. HNSW 인덱스를 탄다 |
| local | `REAL[]` 를 읽어 Java 에서 코사인 유사도. 숙소로 먼저 거른다 |

**둘이 같은 순위를 내야 한다.** 완료 조건 11 이 그것이다.

**계획서 9.2 의 구현 스케치에 이 결정을 한 문단으로 단다.** 그대로 두면 다음 세션이
스케치를 보고 다시 연다. **Cowork 세션이 한다** — 이 지시서를 넘긴 뒤 바로.

### 4번의 근거

임베딩은 외부 API 호출이다. 문서 저장 트랜잭션 안에서 부르면 **OpenAI 가 느린 동안
DB 커넥션을 잡고 있고, 임베딩이 실패하면 문서 저장까지 롤백된다.** 3·12·14주차에서
세 번 만난 트랜잭션 경계 문제와 결이 같다 — 바깥이 롤백될 때 이 쓰기가 남아야 하는가.
**호스트가 쓴 글은 남아야 한다.**

**Outbox 로 낸다.** 이미 있는 장치이고 `OutboxRelay` 가 1초 주기로 돈다. 문서 저장은
커밋되고 인덱싱이 뒤따른다.

대가가 둘이고 둘 다 화면에서 처리한다.

- **저장 직후에는 검색에 안 잡힌다.** 그래서 문서 행에 인덱싱 상태를 둔다(V8) —
  대기 / 완료 / 실패. 화면이 그것을 보여 준다
- **실패를 조용히 삼키지 않는다.** 실패하면 상태가 실패로 남고 화면에 뜬다.
  안 그러면 **그 문서만 검색에서 빠지는데 화면에는 아무 증상이 없다**

**릴레이가 부르는 진입점을 테스트가 그대로 부른다.** 14주차 A 가 그 반대로 하다
났다 — 테스트는 전부 주입받은 프록시를 불러 트랜잭션이 열려 있었고, 스케줄러
경로에만 트랜잭션이 없었다.

### 5번의 근거

계획서 15.2 의 요구는 **"LLM API 가 해외 서비스이므로 마스킹으로 국외이전 자체가
발생하지 않게 한다"** 이다. 대상은 게스트의 개인정보다.

**이번 주에 외부로 나가는 것은 호스트가 직접 쓴 숙소 안내문뿐이다.** 게스트 메시지는
18주차에 처음 나간다. 그러므로 마스킹은 18주차의 일이다.

**다만 경계를 코드 주석과 계획서 15.2 에 적어 둔다.** 적어 두지 않으면 18주차에
"임베딩 쪽은 이미 되고 있다"고 넘어가기 쉽다. 문구는 이것이다 —
**임베딩에 실리는 것은 호스트가 쓴 문서 본문이고, 게스트가 쓴 글은 아직 외부로 나가지
않는다. 나가기 시작하는 지점이 마스킹의 자리다.**

호스트가 안내문에 자기 연락처를 적는 것은 자기 정보이고 국외이전 고지의 대상이 아니다.
**게스트 연락처를 안내문에 적지 않는다**는 것만 화면에 한 줄로 적는다.

### 6번의 근거

계획서 9.2 는 400토큰·80토큰 겹침으로 적었다. **정확한 토크나이저를 넣지 않는다.**

청크 크기는 **일정하기만 하면 되지 정확할 필요가 없다.** 400 이라는 숫자 자체가
경험칙이고, 380 이나 420 이어서 검색이 나빠지지 않는다. 정확한 tiktoken 구현을 넣으면
의존성이 하나 늘고 이 주차가 얻는 것이 적다.

**본체는 문단 경계다.** 문단 가운데를 자르면 한 문장이 두 청크로 갈려 어느 쪽도
답이 되지 못한다. 겹침 80 도 같은 이유로 있다.

`token_count` 는 근사값이고 **그렇게 주석에 적는다.** 아직 측정하지 않은 수치를
성과처럼 적지 않는다는 인계메모 6절 규칙이 여기에도 걸린다 — 근사값을 정확한 값처럼
쓰지 않는다. **한 번 재 보고 얼마나 어긋나는지를 기록에 남긴다**(7절).

## 6. 완료 조건

지식베이스 CRUD.

1. 문서 생성·수정·삭제·조회가 **조직 스코핑을 지키는 테스트.** 남의 숙소 문서에
   닿지 않는다
2. 문서를 지우면 청크도 지워지는 테스트. V1 의 CASCADE 가 실제로 도는지

청킹·임베딩.

3. **문단 경계를 우선해 자르고 겹침이 들어가는 테스트.** 문단 가운데가 잘리지 않는다
4. 문서를 저장하면 인덱싱 이벤트가 나가고 릴레이가 청크와 임베딩을 만드는 테스트.
   **릴레이가 부르는 진입점을 그대로 부른다**
5. 문서를 고치면 **옛 청크가 사라지고 새 청크로 바뀌는** 테스트
6. **임베딩이 실패하면 문서 상태가 실패로 남는 테스트.** 조용히 삼키지 않는다
7. **테스트가 실제 OpenAI 를 부르지 않는다**

검색.

8. **조사가 붙은 문서를 조사 없는 질의로 키워드 축이 찾는 테스트. 그 반대도.**
   5절 2번이 근거다. 이것이 없으면 키워드 축이 죽어도 아무도 모른다
9. **키워드로만 찾을 수 있는 것과 벡터로만 찾을 수 있는 것이 RRF 상위 4건에 둘 다
   들어오는 테스트.** 한 축이 죽으면 여기서 걸린다
10. **다른 숙소의 청크가 결과에 섞이지 않는 테스트**
11. **pgvector 구현과 in-memory 구현이 같은 데이터에 같은 순위를 내는 테스트.**
    Testcontainers 로 pgvector 이미지를 띄운다. 못 띄우면 그 사실과 대신 무엇으로
    확인했는지를 남긴다
12. 청크가 하나도 없을 때 빈 결과를 돌려주고 터지지 않는 테스트

전체.

13. **브라우저에서 문서를 넣고, 인덱싱이 끝나는 것을 보고, 검색 칸에서 질의해 결과와
    점수를 본다.** 이번 주 화면의 존재 이유다
14. `ModularityTest` 통과. **프로덕션 코드에 `JdbcTemplate` 을 쓰는 곳이 없다**
15. `./gradlew test`, `./gradlew build`, `npm run build`, `npm run test` 통과.

**8·11·13 을 빠뜨리지 않는다.** 셋 다 **통과해도 화면에 증상이 없는 자리**를 겨눈다 —
