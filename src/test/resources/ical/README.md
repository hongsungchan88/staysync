# iCal 픽스처

`airbnb-unpublished.ics` 는 **실제 에어비앤비가 발행한 전문**이다. 손으로 만든 흉내가
아니다. 2026-09-05 에 미게시 리스팅의 달력 링크에서 받았다. 조사 경위와 파서 명세는
`docs/조사-02-에어비앤비-ical.md` 에 있다.

13주차 iCal 파서가 지켜야 할 것:

- `DTSTART` / `DTEND` 가 `;VALUE=DATE` 다. 시각이 없다. `DATETIME` 을 전제하면 깨진다.
- **`DTEND` 는 배타적이다.** `20270906` 은 9월 5일까지 막혔다는 뜻이다. 포함으로 읽으면
  모든 예약이 하루씩 밀리고, 화면에서는 정상으로 보인다.
- `UID` 를 멱등성 키로 쓴다. `(channel_code, channel_booking_id)` 유니크 제약의 입력이다.
- `SUMMARY` 에 게스트 정보가 없다. 차단인지 예약인지 이 문자열로는 구분되지 않는다.

미게시 리스팅이라 `VEVENT` 하나가 1년치를 통째로 막고 있다. 개별 예약이나 개별 차단은
이 파일로 검증할 수 없다. 그건 Mock OTA 시뮬레이터(11주차)와 Channex 스테이징의 몫이다.

**내보내기 URL 은 여기에도 저장소 어디에도 넣지 않는다.** 주소를 아는 사람은 누구나
예약 일정을 읽는다. API 키와 같이 취급하고 `.env` 의 `AIRBNB_ICAL_URL` 에 둔다.

## `airbnb-published.ics` — 게시 리스팅 (2026-09-15, 업체 실제 피드 1번)

**업체가 준 게시 리스팅 피드를 그대로 받은 것**이다. 줄 수(139)·접힌 줄(14)·각 줄의
길이·CRLF 가 원문과 같다. 바꾼 것은 값 셋뿐이고 길이는 유지했다 — 저장소에 남의 예약
정보를 두지 않기 위해서다:

- `UID` 의 16진수 → 같은 자릿수의 결정적 치환(같은 원문은 같은 가짜)
- `DESCRIPTION` 의 예약 상세 URL 끝 예약 코드 → 같은 길이의 `X`
- `DESCRIPTION` 의 전화 뒷자리 → `0000`

미게시 피드와 다른 점:

- **예약마다 `VEVENT` 하나.** 15개 중 `SUMMARY:Reserved` 14, `Airbnb (Not available)` 1
- **`DESCRIPTION` 이 붙는다** — 예약 상세 URL 과 게스트 전화 뒷자리. 우리 파서는 읽지
  않지만 **원문을 로그에 찍으면 개인정보가 남는다.** 75옥텟에서 접혀 두 줄이다
- `UID` 는 `<12hex>-<32hex>@airbnb.com`
- `Airbnb (Not available)` 하나가 `DTSTART` 로부터 정확히 365일 뒤 하루다(2027-09-15).
  호스트 차단인지 1년 창의 끝 표식인지는 다음 날 다시 받아 밀리는지로 판정한다

만드는 스크립트는 저장소 밖(세션 스크래치)이다. 주소는 `.env` 의 `AIRBNB_ICAL_URL_1..3`.
